MiClaw🦞 多群聊记忆架构实践

2026-06-03 · 飞书原文 ↗
👍

做这件事，最根本的原因是：

当前个人虾-MiClaw🦞，不支持多Agent能力(相互隔离的workspace)。

因此自己就基于当前架构，调整了一下Memory 架构模式，利用 「飞书群聊间数据通信隔离 与 单Agent的多Session机制」，将1个群聊视为1个Session(1只虾)，打造分身虾，满足我 「1 个群，1 只虾」、「N个群，N只虾」的需求。

对应 Skill 已经上传到公司仓库，大家一键可以安装到自己的爱虾：MiClaw 多群聊记忆架构。

理论上，你可以有无数只虾。

💡

一只龙虾，当多只龙虾用。

一个 Agent，通过 群聊分类 + 记忆路由 + 快捷指令，在不同群里表现为不同的"专家"。

运营群里它是数据播报员，私密群里它是全能管家，吹水群里它是毒舌嘴替。没有多 Agent 编排，没有微服务拆分——纯靠记忆架构做逻辑隔离。

💡

为什么要做这件事？

MiClaw 是一个单 Agent 架构——只有一只龙虾，但我们可以有无数个群，每个群的职责完全不同：有的群只做定时播报，有的群处理日常任务，有的群纯粹吹水。

如果所有群共享同一套记忆和规则，要么规则互相打架，要么上下文被无关信息淹没。多 Agent？成本太高，维护噩梦。

所以只剩一条路：在单 Agent 内部，用架构手段做群间隔离。

设计原则

💡

隔离性

A 群的记忆绝不污染 B 群。每次消息处理只加载一个群的专属文件，上下文干净利落。

💡

按需加载

不预加载、不批量读取。收到哪个群的消息，就只读哪个群的记忆。私聊场景只读全局规则。

💡

自动沉淀

会话结束时自主判断：这次对话产生了什么值得记住的？新规则、新配置、踩坑记录，自动写入对应文件。

消息处理流程

铁律：每次最多加载 1 个群文件，绝不跨群。

收到群消息
  │
  ├─ 1. 读 MEMORY.md → 全局规则 + 路由表
  │
  ├─ 2. 用 chat_id 查路由表
  │     ├─ 命中 → memory_get 只读该群专属文件（最多 1 个）
  │     └─ 未命中 → 全局规则响应 + 触发入群通知流程
  │
  ├─ 3. 检查群分类特殊行为
  │     ├─ observe → 直接 NO_REPLY，不处理
  │     ├─ social → 检查 sender_id 是否在授权名单
  │     └─ risk-mining → 加载 risk-mining-playbook.md
  │
  └─ 4. 群文件中引用规则 → 按需读取

二、群分类体系 & 可扩展性

不同类型的群，加载不同的规则集和记忆文件。分类是一个可扩展注册表，预设五类，用户随时新增。

Source of Truth：多维表格作为唯一可信的多群配置源。

💡

多维表格是唯一的 Source of Truth。 路由表（MEMORY.md）和 gateway config 都是多维表格的下游消费者。数据冲突时，以多维表格为准。

目的有两点：

  1. 多群架构下，龙虾记忆不混乱。
  1. 面向用户，可以速览自己名下的全部Claw群聊和分类。

分类判断流程

收到新群消息时，龙虾怎么判断这个群属于哪个分类？

  • 私密群：群成员1个人1个bot，就自动判定为私密群。

其他类型需要用户自定义分类规则，如：

  • 风控挖掘-私密群：私密群&群名带“风控”。
  • 风控运营-私密群：私密群&群名带“风险运营”

三、钩子触发规则（自定义逻辑Hook）

不是所有规则都需要每次加载。同样，这个规则是按需配置的，按你自己的工作需求定制。

钩子触发规则是一种按需加载机制：规则文件平时不占上下文，只在执行特定操作时被"钩住"触发加载。

机制

在 MEMORY.md 全局规则表中写一条：

| N | 操作 X 前必读约束文件 | 📄 memory/rules/xxx-constraints.md |

Agent 在执行操作 X 时，被这条规则"钩住"，触发读取对应约束文件。

四、快捷指令系统

每个群可配置多个快捷指令，触发词不限于 111。用户可自定义扩展指令。

由于每个私密群的职责不同，有周报管理、会议管理、运营管理等，但日常使用时用户的需求是定的，如：想看一下本周剩余日程会议、想看一下运营情况、想看一下上周周报/本Q的OKR等等。

因此制定了快捷指令系统，你在特定群输入快捷指令后，Claw就会根据 所在群聊+指令内容，触发特定流程输出你想关注的信息。

| chat_id | 群名 | 记忆文件 | 快捷指令 |

群记忆文件中的格式：

## 快捷指令

1. 读取多维表格，筛选状态="跟进中"
2. 表格形式推送

路由表负责快速匹配，记忆文件负责提供执行上下文。路由表是索引，记忆文件是详情。

五、四大工作流

工作流 1：新增分类

触发词：「新增一个群聊分类为 {分类名}」「新建分类 {分类名}」

  1. 创建目录 memory/groups/{分类slug}/
  1. 在 MEMORY.md 群聊分类定义表中新增一行
  1. 在 MEMORY.md 路由表中新增该分类的段落
  1. 创建该分类的示例模板文件
  1. 询问用户：requireMention 默认值、是否配快捷指令、行为模式
  1. 根据用户回答更新分类定义表

工作流 2：新群接入（含入群通知）

触发条件：收到未知 chat_id 的群消息 / 用户在私聊中告知新建了群

内置group-onboard Skill，执行流程。

1. 查群信息：群名、user_count、bot_count
2. 自动判断分类：
   ├─ user_count=1, bot_count=1 → 私密群
   ├─ 私密群 + 群名含"风控" → risk-mining
   └─ 其他 → 展示分类列表让用户选择
3. 私聊通知用户（入群通知）
   └─ 告知：群名、chat_id、推荐分类
4. 用户确认后继续
5. 更新 MEMORY.md 路由表（对应分类段添加一行）
6. 创建群专属记忆文件
7. 更新 Gateway config：
   a. config.get → 获取完整 groups
   b. 追加新群配置（requireMention 按分类默认值）
   c. config.patch 完整 groups
8. 验证：在新群发消息确认响应正常

每一步都是原子操作，漏掉任何一步都会导致后续问题。比如漏了「更新 gateway config」，龙虾在该群里就不会响应消息。

关键约束：

  • config.patch 必须包含完整 groups（不能只写新群，否则覆盖其他群配置）
  • 私密群自动配 requireMention: false，无需向用户确认

工作流 3：配置快捷指令

触发词：「给 {群名} 配置指令」「{群名} 加个指令」

  1. 从 MEMORY.md 路由表找到该群的记忆文件路径
  1. 读取群记忆文件，获取当前快捷指令
  1. 展示配置，按用户指示新增/修改/删除
  1. 同步写入：MEMORY.md 路由表 + 群记忆文件
  1. 确认写入成功

工作流 4：Source of Truth 三方校验

  1. 确定 Source of Truth（多维表格 / MEMORY.md）
  1. 读取三方：Source → MEMORY.md 路由表 → gateway config
  1. 逐条比对差异
  1. 输出报告 + 自动修复建议
  1. 能自动修的直接修，不能的提示用户

修复优先级：Source of Truth → 修 config → 修 MEMORY.md（禁止反向回写 Source）

六、Hub-Spoke 模式：运营群管理

运营群有个特殊需求：龙哥在一个「管理中枢」群里下达指令，龙虾去多个运营群执行操作。

Hub（中枢群）

  • 龙哥的指挥中心
  • 发指令、看汇总、改配置
  • 只有龙哥和龙虾两个成员
  • 例：给所有运营群推一次日报

Spoke（执行群）

  • 各个运营群
  • 接收龙虾的播报和响应
  • 有其他同事在
  • 龙虾在这里只做「本职工作」

注册表示例

Hub 群的记忆文件里维护一张注册表，记录所有 Spoke 群：

## Spoke 群注册表

| 群名 | chat_id | 播报类型 | cron 表达式 | 状态 |
|------|---------|---------|-----------|------|
| VAF 运营群 | oc_aaa | VAF 日报 | 0 10 * * 1-5 | 运行中 |
| 质效数据群 | oc_bbb | 质效周报 | 0 10 * * 1 | 运行中 |
| CR 数据群 | oc_ccc | CR 周报 | 0 14 * * 5 | 暂停 |

龙哥在 Hub 群说「给所有运营群推一次日报」，龙虾遍历注册表，逐个推送。说「暂停 CR 数据群」，龙虾更新状态列。

七、踩过的坑：

以下都是真实翻车记录。每个坑至少浪费了 30 分钟排查时间。

坑 1：config.patch 的群配置覆盖问题

gateway config.patch 写 groups 字段时，是整体覆盖而不是增量更新。如果你只写了新群的配置，所有已有群的配置会被清空。

正确做法： 先读取当前 config，把已有群配置全部带上，再加新群的配置一起写入。

坑 2：飞书不推送「机器人入群」事件

龙虾没法知道自己被拉进了新群。飞书的事件机制不覆盖这个场景。

解决方案： 两条路径兜底——收到未知 chat_id 的消息时自动触发新群接入，或者龙哥私聊告知。

坑 3：私密群的 requireMention 配置

私密群（只有龙哥和龙虾）如果设了 requireMention: true，龙哥每条消息都得 @同事，体验极差。

解决方案： 新群接入流程中，检测到 user_count=1 && bot_count=1 时自动设为 requireMention: false。

坑 4：路由表格式升级时漏改列名

路由表格式变更时，如果新增了列但 MEMORY.md 里的表头没同步更新，龙虾解析路由表时列对不上，功能全部失效。

教训： 路由表格式变更必须同步更新解析逻辑。最好在变更后立刻跑一次数据一致性校验。
