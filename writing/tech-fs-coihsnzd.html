RocketMQ理论 &实践

2025-12-22"飞书工作积累" · 飞书原文 ↗

公司文档：RocketMQ

API Demo平台：cloud.d.公司.net

Rocket MQ管理平台：[内部链接]

💡

RocketMQ提供多种发送方式，同步发送、异步发送、顺序发送、单向发送。

同步和异步方式均需要Broker返回确认信息，单向发送不需要。

与Talos相比，RocketMQ支持：延时消息、POP消费......

理论

基本概念

  1. NameServer：可以理解为是一个注册中心，主要是用来保存 Topic 路由信息，管理 Broker，支持 Broker 的动态注册和发现，保存 Topic 和 Borker 之间的关系。在 NameServer 的集群中，NameServer 与 NameServer 之间是没有任何通信的。
  2. RocketMQ主要由 Producer、Broker、Consumer 三部分组成，其中Producer 负责生产消息，Consumer 负责消费消息，Broker 负责存储消息。
  3. Broker 在实际部署过程中对应一台服务器，每个 Broker 可以存储多个Topic的消息，每个Topic的消息也可以分片存储于不同的 Broker。
  4. Message Queue 用于存储消息的物理地址，每个Topic中的消息地址存储于多个 Message Queue 中。

  1. RocketMQ 支持两种消费模式：集群消费（Clustering）和广播消费（Broadcasting）。

  2. 集群消费：相同Consumer Group的每个Consumer实例平均分摊消息。
  3. 广播消费：相同Consumer Group的每个Consumer实例都接收全量的消息。

  1. RocketMQ 支持两种顺序消费：普通顺序消费、严格顺序消费。

  2. 普通顺序消费：消费者通过同一个消费队列收到的消息是有顺序的，不同消息队列收到的消息则可能是无顺序的。
  3. 严格顺序消费：消费者收到的所有消息均是有顺序的。

  1. key 为消息的一个属性，其主要功能包括：控制台通过 key 来快速定位和查询特定的消息；日志关联: key 可以用于将消息与系统日志关联起来，便于分析和监控；key 可用于业务消息去重处理。

  2. 虽然 key 不要求全局唯一，但在业务上通常需要具有一定的唯一性，以便于查询和追踪。
  3. 长度限制: key 的长度不宜过长，以免影响性能。通常建议在 128 字节以内。
  4. 设置方法: 在发送消息时，可以通过 Message 对象的 setKeys 方法来设置 key。

  1. 同一类Producer的集合，这类Producer发送同一类消息且发送逻辑一致。如果发送的是事务消息且原始生产者在发送之后崩溃，则Broker服务器会联系同一生产者组的其他生产者实例以提交或回滚消息。

  1. 同一类Consumer的集合，这类Consumer通常消费同一类消息且消费逻辑一致。消费者组使得在消息消费方面，实现负载均衡和容错的目标变得非常容易。要注意的是，消费者组的消费者实例必须订阅完全相同的Topic。

高级特性

1.延时消息

💡

延时消息是指消息发送到broker后，不会立即被消费，等待特定时间投递给真正的topic。

  • 每个延迟时间对应一个延迟级别，例如 1s 的 delayLevel 是1，1m 的 delayLevel 是 5

  • 发消息时，设置delayLevel等级即可：msg.setDelayLevel(level)。

  • level有以下三种情况：

  • level == 0，消息为非延迟消息
  • 1<=level<=maxLevel，消息延迟特定时间，例如level==3，延迟10s
  • level > maxLevel，则level== maxLevel，例如level==20，延迟2h

实现原理 ：

💡

原理：“偷梁换柱” -> “定时扫描” -> “还原投递”

先把消息藏在系统内部的一个特殊 Topic 对应的特殊队列里，利用定时器不断检查队头消息是否到期，到期了就改回原来的 Topic 重新发一遍。

  1. 当 Broker 收到一条消息时，会检查消息属性中是否包含 DELAY 属性（即 delayLevel > 0）。 如果包含，Broker 不会直接把消息投递到你指定的 Real Topic（真实Topic），而是做以下修改：

  2. 备份信息：将消息原本的 Real Topic 和 Real QueueId 备份到消息的属性（Properties）中，防止丢失。
  3. 修改Topic：将消息的 Topic 修改为系统内部特定的延迟 Topic，固定名称为SCHEDULE_TOPIC_XXXX。
  4. 选择队列：根据 delayLevel 计算出要投递到哪个队列。
    • 逻辑是：queueId = delayLevel - 1。
    • 例如：level 1（1s）的消息会全部存入 queue 0，level 2（5s）的消息存入 queue 1。
    • 精妙之处：这样设计保证了同一个队列里的消息，延迟时间是固定的。因为是顺序写入（FIFO），如果队列头部的消息没到期，后面的消息肯定也没到期，无需全盘扫描，只需检查队头。

  1. roker 内部有一个核心服务类叫 ScheduleMessageService。

  2. 启动定时器：它会为每个延迟级别（DelayLevel）启动一个对应的定时任务（TimerTask）。
  3. 拉取消息：每个定时任务只负责扫描对应级别的队列（ConsumeQueue）。
  4. 检查时间：
    • 读取队列中的消息索引。
    • 计算目标投递时间：TagsCode（在延时队列中存储的是计划投递的时间戳） vs 当前系统时间。
    • 如果时间没到：停止扫描，过一会再来（Wait）。
    • 如果时间到了：进入下一步。

  1. 当定时任务发现某条消息的“延迟时间”已到：

  2. 读取消息：从 CommitLog 中把完整的消息体读出来。
  3. 还原信息：从消息属性中读取备份的 Real Topic 和 Real QueueId。
  4. 清除延时属性：清除 DELAY 属性（防止再次被当做延时消息处理）。
  5. 重新写入：将恢复后的消息当做一条新消息，重新写入 CommitLog。
  6. 正常消费：此时消息的 Topic 变成了真正的业务 Topic，普通的 Consumer 就能立刻拉取并消费了。
💡

Q1：为什么要设计成“延时级别” 而非“延时时间”？

答：

这是 RocketMQ 早期为了高性能和实现简单做的权衡（Trade-off）：

  • 如果不分级别，支持任意时间延时，Broker 需要对海量消息进行排序（按触发时间排序）。在大数据量下，插入和排序的性能消耗巨大（通常是 O(logN)）。
  • 使用“级别”后，同一个队列延迟时间相同。天然有序，不需要排序。Broker 只需要检测队列头部（第一个）消息是否到期即可。如果是 O(1) 的复杂度，性能极高。
  • 只能使用预设的时间，不够灵活。如果业务需要“延迟 23 分钟”，只能自己组合或者修改 Broker 配置。

值得一提的是，在 RocketMQ 5.0 版本中，引入了 时间轮（Timing Wheel） 机制。 这使得 RocketMQ 终于支持了任意精度的定时消息（不再局限于 Level）。

2.定时消息

💡
  • 延时消息是指需要延时指定时间对消费者可见
  • 定时消息是直接指定对消费者可见的时间

二者均可实现延时能力，延时消息更加简单高效，定时消息更加灵活。

3.消费模式-Pull & Push & Pop

推荐文章：RocketMQ 5.0 POP 消费模式探秘-阿里云开发者社区

💡

RocketMQ 无论是 Push Consumer，还是 Pull Consumer，还是后面要介绍的 POP Consumer，都是客户端拉的方式消费消息。

Push Consumer 只是通过客户端 API 层面的封装让我们感觉是 Broker 推送的。

Pull Consumer - 拉取式消费

Consumer消费的一种类型，consumer通常主动调用拉消息方法从Broker服务器拉消息、主动权由应用控制。一旦获取了批量消息，应用就会启动消费过程。

消费需要不断的从阻塞队列中获取数据，如果没有数据就等待，这个阻塞队列中的数据由"消息拉取线程(pull request thread)"从Broker拉取消息后加入，所以Pull模式下消费需要不断主动从Broker拉取消息。

Push Consumer - 推动式消费

Consumer消费的一种类型，该模式下Broker收到数据后会主动推送给消费端，该消费模式一般实时性较高。

需要注册消息监听器，当有消息到达时会通过回调函数进行消息消费。

从表面上看就像是Broker主动推送给消费者一样，所以叫做推模式，底层依旧是消费者从Broker拉取数据然后触发回调函数进行消息消费，只不过不需要像Pull模式一样不断判断是否有消息到来。

  • 客户端启动的时候会在 Topic，Consumer group 维度发生负载均衡，为每个客户端分配需要处理的 Queue。

  • 负载均衡过程中每个客户端都获取到全部的的 ConsumerID 和所有 Queue 并进行排序，每个客户端使用相同负载均衡算法，例如平均分配的算法，这样每个客户端都会计算出自己需要消费那些 Queue，每当 Consumer 增加或减少就会触发负载均衡，所以我们可以通过 RocketMQ 负载均衡机制实现动态扩容，提升客户端收发消息能力。

  • 不可以。

  • 因为 Queue 数量有限，客户端数量一旦达到 Queue 数量，再扩容新节点无法提升消费能力，因为会有节点分配不到 Queue 而无法消费。即：队列独占问题。

POP Consumer

💡

POP消费支持：

  1. 一个订阅组内的多个客户端同时消费同一个队列。
  1. 消息在不可见时间内（默认为60s）没有被ACK则认为消费失败。
  1. 消费失败后，该消息会重新可见，一段时间后会被再次消费。

通过前面 Push Consumer 的介绍，我们了解到 Push Consumer 的关键痛点：

  • Broker上的每个Queue只能分配到相同 Consumer group下的一台Consumer机器上。

  • 如果遇到客户端机器挂起，处于半死不活的状态，与 Broker 的心跳没有断掉的时候，客户端 Rebalance 依然会分配消费队列到挂起的机器上，并且挂起机器消费速度很慢甚至无法消费的时候，会导致消费堆积。

  • 举例：

    当consumer2挂起时，它所分配到的TopicTest1-q2出现堆积，即便横向扩展新增consumer4，也无法解决。目前处理这种问题，一般可能是找到这台机器重启，或者下线。

    类似还有服务端 Broker 发布时，也会由于客户端多次 Rebalance 导致消费延迟影响等无法避免的问题。

POP Consumer 能够解决上述稳定性问题，并且解除队列占位的限制。

  1. POP Client 从 Broker 的队列中发出 POP 请求消息，Broker 返回消息 message。在消息的系统属性里面有一个比较重要的属性叫做 POP_CK，POP_CK 为一条消息的 handler，通过一个 handler 就可以定位到一条消息。当消息消费成功之后，POP client 发送 ackMessage 并传递 handler 向 broker 确认消息消费成功。

  2. 对于消息的重试，当 POP 出一条消息之后，这条消息就会进入一个不可见的时间，在这段时间就不会再被 POP 出来。如果没有在这段不可见时间通过 ackMessage 确认消息消费成功，那么过了不可见时间之后，这条消息就会再一次的可见。

  3. 另外，对于消息的重试，我们的重试策略是一个梯度的延迟时间，重试的间隔时间是一个逐步递增的。所以，还有一个 changeInvisibleTime 可以修改消息的不可见时间。

  4. 从图上可以看见，本来消息会在中间这个时间点再一次的可见的，但是我们在可见之前提前使用 changeInvisibleTime延长了不可见时间，让这条消息的可见时间推迟了。

  5. 当用户业务代码返回 reconsumeLater 或者抛异常的时候，我们就可以通过 changeInvisibleTime 按照重试次数来修改下一次的可见时间了。另外如果消费 RT 超过了 30 秒（默认值，可以修改），则 Broker 也会把消息放到重试队列。

  1. POP 消费的位点是由 Broker 保存和控制，而且 POP 消费是可以多个 Client 消费同一个队列。

  2. 如下图所示：

  3. 三个客户端并不需要 Rebalance 去分配 Queue，取而代之的是，它们都会使用 POP 请求所有的 Broker 获取消息进行消费。即使 POP Consumer 2 出现 hang，其内部消息也会让 POP Consumer1 和 POP Consumer3 进行消费。这样就解决了 hang 机器可能造成的消费堆积问题。

  1. 从整体流程可见，POP 消费可以避免 Rebalance 带来的消费延时，同时客户端可以消费 Broker 的所有队列，这样就可以避免机器 hang 而导致堆积的问题。
  2. 同时扩展能力提升，POP Consumer 可以消费同一 Topic 下所有 Queue，相比 Push Consumer 解除了每个 Queue 必须 Rebalance 到一台客户端消费的限制，Push Consuner 客户端数量最多只能等于 Queue 的数量。POP Consumer 可以突破这个限制，多个 POP Consumer 可以消费同一个 Queue。

4.并发消费 ⭐️

💡

RocketMQ的并发消费指的是消费者端的并发处理能力，它包括：

  1. 消费者端可以创建多个拉取请求（Pull Request）线程，每个 Pull Request 线程负责从分配给它的队列中拉取消息。

  1. 拉取到的消息会被分发到不同的消费线程中。每个消费线程会顺序处理分配给它的消息，但多个消费线程可以并发执行。

  • 一个 msgs 列表是由某个 Pull Request 线程拉取的数据。
  • 在后续的 consumeMessage 执行中，从消费线程池中获取消费线程(Consume Thread)，执行具体的消费逻辑，而不是由拉取消息的 Pull Request 线程直接处理。这样可以实现消息拉取和消息消费的解耦，提高系统的并发处理能力。
  • consumer = ClientFactory.createNormalConsumer(prope
rties, new MessageListenerConcurrently() {
    // 消费者线程池并发执行消费逻辑
    @Override
    public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ConsumeConcurrentlyContext context) {
        msgs.forEach(msg -> consume(msg.getBody()));
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
});
consumer.subscribe(TOPIC_NAME, "*");

  • msgs 列表包含了从同一个队列中拉取的一批消息。当 Pull Request 线程从队列中拉取消息时，它会收集多条消息并形成一个列表，然后传递给消费逻辑处理。

    在并发消费模式下，consumeMessage 方法的执行可以由不同的线程负责，这些线程是从消费线程池中获取的。

    RocketMQ 消费者端有一个消费线程池（ConsumeThread），用于并发执行 consumeMessage 方法。每个消费线程从消息队列中获取消息列表，然后执行 consumeMessage 方法来处理这些消息。这意味着多个消费线程可以并发地执行 consumeMessage 方法，每个线程处理不同的消息列表。

死信队列

在 RocketMQ 中，死信队列（Dead-Letter Queue，DLQ） 是专门存放 “多次重试消费仍失败” 的消息的特殊队列，核心作用是避免失败消息丢失、支持事后排查与重新处理。

  1. 定义

当一条消息在消费端经历 最大重试次数（默认 16 次，可配置）后仍消费失败（如抛出未捕获异常、消费超时），RocketMQ 会自动将其转移到该消息所属的 “死信队列”，不再继续重试，避免无效重试占用资源。

  1. 核心特性
  • 专属 Topic：死信消息不会混入普通 Topic，而是存放在以 %DLQ% 开头的专属死信 Topic 中（如 %DLQ%risk_engine_consumer_group_dict_change_topic），命名规则为 %DLQ%+消费组名+原Topic名，便于识别来源。
  • 持久化存储：死信队列与普通队列一样持久化到磁盘，不会因 Broker 重启丢失，确保失败消息可追溯。
  • 无自动过期：死信消息不会自动删除，需人工或定时任务处理，避免 “未排查就丢失”（风控场景需保留失败记录用于审计）。
  • 按消费组隔离：同一原 Topic 的消息，若不同消费组消费失败，会进入各自的死信队列（如 “字典变更 Topic” 的消息，风控引擎消费组和规则引擎消费组的死信消息分开存放）。

实践

以"实时风控平台-规则处置"为案例，作以案例分析。

Producer

💡

Q1：final Boolean[] success = {true} 为何不用Boolean 而是用 Boolean[]?

原因：需要在异步回调方法中修改发送状态，而数组允许在方法执行结束后仍然保持对这个状态的修改能力。

详解：

  1. 在Java中，final 关键字修饰的基本数据类型或对象引用是不可变的，这意味着它们的值不能被改变。但是，如果 final 修饰的是一个数组，那么数组的引用是不可变的，但数组的内容是可以修改的。
  1. asyncSend 方法是一个异步操作，它立即返回，不会等待消息发送的最终结果。SendCallback 接口的 onSuccess 和 onException 方法会在消息发送成功或失败时被调用，但这些回调方法的执行是在另一个线程中进行的。因此，直接使用一个局部的 final Boolean 变量是不行的，因为一旦 asyncSend 方法返回，局部变量就会离开作用域，无法在回调方法中被访问。
  1. 数组是在堆上分配的。通过使用数组 final Boolean[] success = {true};，我们可以在 asyncSend 方法的栈帧被销毁后，仍然通过数组来访问和修改 success 的值。

@Component

            log.error("failed to init rule-action producer, msg={}", e.toString(), e);
            new Thread(() -> System.exit(1)).start(); // 强制退出
        }
    }

    public boolean asyncSend(String tag, String data) {
        return asyncSend(tag, data, 0); // 异步消息发送
    }

    public boolean asyncSend(String tag, String data, int delayTimeLevel) {
        Message message = new Message(TOPIC_NAME, tag, "", data.getBytes());
        if (delayTimeLevel > 0) {

        }

        try {

                @Override
                public void onSuccess(SendResult sendResult) {

再来梳理下MQ consumer整个「拉取->消费->确认」的主流程：

假设此时参数如下：

  • PULL_THREAD_NUMS=5；PULL_BATCH_SIZE =50；CONSUME_THREAD_NUM=50；CONSUME_MESSAGE_BATCH_MAX_SIZE=1。

再回顾此次事件「堆积7w+消息，延迟约25min」，因此我们希望在进行调优后，有「瞬发10w+消息，消费延迟1~2min」的能力。

当前规则处置worker的容器配置是(1核4G)，CPU核数太少了，在考虑成本的基础上，先切换成2核4G。

参数配置：

  1. 首先考虑消费者线程数：一般来说，消费线程数不可远超CPU的并行能力，一般设置为 CPU核数*2 或 *3 即可。

如：若将消费线程数设成 50，则远大于 CPU 并行能力，会导致频繁上下文切换、JVM 频繁 GC，最终 吞吐下降、延迟升高。

暂设置为6，是合理范畴。再多的话，上下文切换代价 > 收益。

  1. 对于网络IO型业务(如规则处置)，CPU上下文切换代价可大致忽略，可适当调大线程数量。
  1. 考虑重复消费的情况（考虑MQ的ACK机制），即：当消息消费失败时，MQ是整批消息重试还是仅重试消费失败的消息。

从上述计算方式来看，其实性能主要受限于每秒吞吐量(并行度/单条耗时)，那么在单条耗时一定的情况下，理论来看：「并行度越高->吞吐量越高->总耗时越低」。

但其实在CPU核数一定的情况下，若盲目提高消费线程数，随之JVM线程切换的上下文成本也会更高，即“上下文切换代价 > 收益”，那么此时就需要根据实际业务情况做取舍：

  • 此种业务逻辑耗时较低(几毫秒)，一般均为纯内存计算，此时线程切换较频繁，消费线程数量不易过高，一般约为「CPU核数 * 2」。若消费线程数量过高，容易出现 “ 上下文切换代价 > 收益”的情况。

  • 此种业务逻辑耗时较高(百毫秒-秒)，主要受限于网络IO延时，此时线程切换较稀疏，可适当提高消费线程数量，一般约为「CPU核数 * 5」。
