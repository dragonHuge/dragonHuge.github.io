2025-09-09 高并发场景下HTTP Client配置踩坑

2026-10-14"飞书工作积累" · 飞书原文 ↗
💡

写在前边：

在高并发场景下(QPS>1000)，HTTP CLient连接池配置中，切记要调整以下两配置：

  • MaxConnTotal(全局最大连接数)：默认20
  • MaxConnPerRoute(单路由最大连接数)：默认2

高并发场景下，若未显式调整以上配置，那么MaxConnPerRoute=2 会成为瓶颈，导致大量请求排队等待连接，造成大批超时。

背景

在做TZ真机质量加固中，将HTTP服务所依赖的TZ验签服务，从RPC请求迁移到HTT请求，并将服务部署至Matrix。

在此部署过程中，就出现这种异常现象：

  • 灰度3台机器时，QPS约180，且耗时稳定，平均250ms。
  • 灰度全量10台机器后，QPS约1000，耗时突增，平均耗时达到3s。

问题分析

那么出现此问题后，首先怀疑是TZ验签HTTP服务方扛不住流量，导致验签服务异常，于是联系其扩容。

但扩容后发现问题依旧存在，于是先回滚，又细捋了一下整个接口，最后将问题定位到HTTP Client连接池的配置上：

RequestConfig requestConfig = RequestConfig.custom()
        .setConnectionRequestTimeout(3000) // 连接池等待TTL
        .setConnectTimeout(800) // TCP握手TTL
        .setSocketTimeout(1000) // 数据传输TTL
        .build();
Header ua = new BasicHeader("User-Agent", USER_AGENT);
ArrayList<Header> headers = new ArrayList<>();
headers.add(ua);
return HttpClientBuilder
        .create()
        .setMaxConnTotal(2000) // 全局最大连接数
        .setDefaultRequestConfig(requestConfig)
        .setDefaultHeaders(headers)
        .setMaxConnPerRoute(2000) // 单路由最大连接数，旧代码中没有做此配置。
        .build();

可以看到，在旧代码中，全局最大连接数配置成了2000，但单路由最大数使用的是默认值2，并且在此TZ验签HTTP请求中，核心使用的就是1个接口，路由也是一致的。

那么当大批请求同时到达，就出现了问题：大量请求排队，抢占这2个入口。导致耗时一直居高不下，且当前连接池等待TTL为3s，大量请求在等待3s后，放弃了此次请求。这也是为什么高并发时，平均耗时在3s左右。

后记

这属于历史遗留代码问题，TZ真机HTTP服务中的「BL锁状态检查」，也是一个HTTP请求，因此也存在同样的问题：

  • 耗时高的部分就是QPS突增的时候(QPS约800+)、耗时低的部分就是QPS低的时候(QPS约150+)

这也就解释了为什么时不时会有人来咨询真机服务超时的问题。

2026-10-14：风控平台 脱敏服务 OkHttp「僵尸调用」踩坑——超时预算错配

⚠️

核心结论：上层业务超时 ≠ 底层 HTTP 超时。 每一层都有自己的超时预算，若底层 HTTP client 的超时远大于上层业务预算，上层"超时放弃"后底层调用线程仍会继续阻塞——形成"僵尸调用"，高并发下线程被逐渐占满，服务性能随调用量增长而劣化。

现象

风控侧-接口调用方

接口内部性能监控，P99 始终在 200ms 左右

发现：调用量一涨，性能就会随之降低。

  • 脱敏插件监控耗时 300~800ms，但脱敏服务自报接口 P99 <200ms，两边差异巨大；
  • 更关键的是性能随调用量增长而降低，且旧版插件（V2，无分片逻辑）同样存在——说明问题不在业务逻辑，在共用的 HTTP client 层。

排除过程：MaxConnPerRoute 坑不适用

本文上一节是 Apache HttpClient 的 MaxConnPerRoute=2 坑。我们用的是 OkHttp，逐项对照后排除：

  • OKHttpUtils.getResponse 走的是同步 call.execute()，OkHttp Dispatcher 的 maxRequests/maxRequestsPerHost 只约束异步 enqueue，同步调用不受限（代码里配的 2000/1000 对同步实际无效，但无害）；
  • 同步调用连接不够时直接新建连接，不存在"排队抢连接"的瓶颈。

真因：20s readTimeout 与业务预算错配

继续阻塞在 execute() 上

上层放弃后，cancel(true) 只是尽力而为——OkHttp 对已发出的请求 cancel 不保证立即断开，调用线程最长挂满 20s。高峰期超时越多 → 僵尸占用越久 → 分片线程池/引擎执行线程被拖满 → 吞吐下降 → 更多超时，恶性循环，精确复现"随调用量增长而降低"的曲线。

修复：业务专属 HTTP client，callTimeout 兜底

不动全局工具类（其余 40+ 调用方零影响），给脱敏调用配专属客户端：

private static final OkHttpClient DESENSITIZE_CLIENT = new OkHttpClient.Builder()
        .connectTimeout(500, TimeUnit.MILLISECONDS)   // 内网建连冗余,线上抖动容错
        .writeTimeout(2000, TimeUnit.MILLISECONDS)    // 写间隔超时,非整体传输时长
        .readTimeout(2000, TimeUnit.MILLISECONDS)     // 读间隔超时,与 callTimeout 同档不卡边
        .callTimeout(2000, TimeUnit.MILLISECONDS)     // 整体硬预算,超时真正中断并释放线程
        .connectionPool(new ConnectionPool(64, 5, TimeUnit.MINUTES))
        .build();

参数设计依据：

参数

取值

依据

500ms

内网建连通常毫秒级，留线上抖动冗余；整体仍受 callTimeout 约束

writeTimeout

2000ms

写间隔超时（非整体传输时长），2MB body 持续写出即可

readTimeout

2000ms

读间隔超时，与 callTimeout 同档不卡边

callTimeout

2000ms

DNS+连接+写+读全程硬预算，超时真正中断请求、立即释放线程

ConnectionPool

64 空闲 / 5min

空闲连接保留策略（非并发上限）：峰值并发约 120 连接，64 覆盖大部分复用需求，省建连+绕开 TCP 慢启动

两个关键取舍：

  1. 等待类超时不卡边业务配置（2s 而非贴着 650ms）：插件侧超时是 Nacos 热更项，业务可能放宽到 1.2~1.6s，HTTP 层若卡边会在业务调参后反而先断，需再改代码发版——留足冗余让 HTTP 层永不成为主动瓶颈；
  1. callTimeout 是唯一能"真正中断"的配置：正常路径仍由上层先取消，它只在 cancel 失效、服务端彻底无响应时兜底自断，僵尸窗口从 20s 压到 2s（10 倍改善）。

通用检查清单

💡

任何带超时的调用链，自上而下检查一遍每层的超时预算：上层超时应单调小于下层超时；下层超时的职责是"异常路径最终自断"，而不是"比业务预算大一个数量级"。连接池只管空闲连接复用，不是并发上限——同步调用不受 Dispatcher 限制，真正限制并发的永远是线程池和 callTimeout。
