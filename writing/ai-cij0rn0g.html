用了半年 web-access，这篇微信文补了我三层盲区

2026-04-27 · 飞书原文 ↗
💡

如果你想搞清楚浏览器自动化的完整技术链，强烈推荐：逆向OneByOne 的《一文彻底了解浏览器自动化》。

怎么把这篇和我之前那篇《OpenCode、Claw🦞 联网指南》对上？一字心决：叠。

两周前我写了那篇联网指南，把 WebSearch / web_fetch / Defuddle / Browser CDP 四件套的场景选型讲了一遍。自以为透了。

昨天刷到逆向OneByOne 这篇，愣了一下——不是我讲错了，是我漏了另一层视角。

核心要补的三件事：

  • 盲区 1 — CDP 不是终极兜底，shadow dom 面前 CDP 也会死
  • 盲区 2 — 登录态承接有两条路，接管窗口 vs 克隆 profile，我走的是前者
  • 盲区 3 — browsermcp 是官方路线，但 web-access 在一个意想不到的地方反而更完整

一、先说两篇文章的底牌

说白了，我那篇是横切，他那篇是纵深。两条轴正好垂直。

我那张"能力对比表"里 Browser CDP 是一个格子。他把这个格子展开成了一整条技术链。

二、盲区 1：CDP 不是终极兜底，shadow dom 会让它死

先说我之前的认知。

那篇联网指南的核心主张之一就是——搞不定的场景上 Browser CDP 兜底。微信公众号抓不到？上 CDP。小红书需要登录态？上 CDP。Cloudflare 拦截？上 CDP。

CDP 在我心里就是那个"真实浏览器、所见即所得"的终极方案。

逆向OneByOne 直接给我上了一课——他原话是：「视频号后台里有一部分页面用了 wujie 的 shadow dom 结构，你从视觉上看，那个发表视频按钮明明就在页面上，但很多基于 DOM 的自动化工具就是拿不到。」

问题的核心不是 CDP 够不够强，是 DOM 这条路本身有极限。

wujie 是一个微前端框架，它用 shadow dom 做了组件隔离。嵌套式 shadow dom 会把子组件的 DOM 树装进一个封闭的 shadowRoot——外部选择器不管是 Puppeteer、Playwright 还是 CDP 原生 eval，全都拿不到。你得一层一层 shadowRoot 穿透，遇到某些框架的深度嵌套，穿透链路会断。

这时候才有字节的 Midscene 方案——视觉驱动路线。

Midscene 的定位很清楚——不是替代 DOM，是 DOM 不够用时的补位。跨结构理解强，精确定义弱。复杂页面的兜底层，不是主力。

对我 web-access skill 的启示也很直接：

现在 skill 里 /eval 递归遍历支持穿透 Shadow DOM 和 iframe，一般 shadow dom 够用。但我没实测过 wujie 这种嵌套式。真要接视频号这类场景，必须做 POC 验证——必要时引入视觉兜底层，不能死磕 DOM。

换句话说，我之前"CDP 是兜底"那个说法，要加一条脚注——shadow dom 重灾区例外。

三、盲区 2：登录态承接的两条路线，我走的是"接管"

我那篇里提 Browser CDP 的登录态优势，就一句话带过——直连用户 Chrome，天然登录态。

看了逆向OneByOne 这篇才发现，"连上用户 Chrome"其实分两条路，而且差异不小。

3.1 接管路线 — 我的 web-access 走的这条

通过 CDP Proxy 连上用户日常 Chrome 的 remote-debugging 端口，在同一个 Chrome 进程里开后台 tab 做自动化操作。用户在前台用浏览器，AI 在后台另起 tab 干活。

这条路线：

  • 轻，无需复制 user-data-dir
  • 登录态完全实时，跟用户手动操作共享同一个 cookie jar
  • 共享用户环境，风控识别到可疑行为可能拖累用户主账号
  • 用户和 AI 同时操作时可能互相干扰

3.2 克隆路线 — browser-use 走的这条

逆向OneByOne 原文描述很清楚——「带着 profile 去启动，它会去找系统里安装的 Chrome，读取你本机的用户数据目录和 profile 信息，把对应 profile 复制到一个临时目录里，再拉起一个新的 Chrome 进程来跑自动化。它不是接管你现在桌面上已经打开着的那个 Chrome 窗口，而是拿你的身份数据，克隆出一个自动化专用的 Chrome。」

这条路线：

  • 独立进程，与用户主 Chrome 隔离，风控风险低
  • 自动化专用实例，不干扰用户正常使用
  • 重，要复制 profile 到临时目录
  • cookie 不是实时的，快照级别，强设备指纹站点可能要求重新登录

对 web-access 的启示：

接管路线对"临时抓内容、调研性任务"足够好。但要做矩阵账号发布、高频批量操作这种场景——接管路线会成为风险集中点，所有账号共享一个浏览器环境。这时候 skill 可能需要演化出"克隆模式"作为第二形态。

其实这不是单纯的技术选择，是"AI 和我共用一个身体"和"AI 拿我身份的克隆去办事"两种使用哲学的分野。我之前没想清楚这一层。

四、盲区 3：browsermcp 是官方路线，web-access 反而更完整

逆向OneByOne 提到一个我之前完全没听过的东西——browsermcp。原话是：「官方出的 browsermcp。它可以基于你当前正在使用的浏览器，把页面内容、DOM 结构和可操作能力，更自然地暴露给 AI。」

读到这我心里一惊。

这跟 web-access skill 干的事几乎一模一样——接管当前浏览器，把 DOM 和操作能力暴露给 AI。更戳心的是，这是官方出的。

正常逻辑是：官方路线一出来，自建 skill 的价值就贬值。

但翻完原文我发现微信文这句话救了我——「browsermcp 现在也不是完美的。它的能力还没有强到覆盖所有场景，比如像文件选择这类动作，现在还不行。」

这正好是 web-access 解决的问题。

web-access 有一个 /setFiles 端点：

curl -s -X POST "http://localhost:3456/setFiles?target=ID" \
  -d '{"selector":"input[type=file]","files":["/path/to/file.png"]}'

底层走 CDP 的 Input.setFileInputFiles，直接把本地文件路径写进 <input type=file>，绕过文件对话框。

这是我当初踩过坑才补上的能力——没这个，小红书、抖音后台的图片视频上传全走不通。

结果没想到，在这个点上 web-access 反而比官方 browsermcp 完整。

我想基本是因为以下这两点：

一是自建 skill 的路线选对了——同样是"接管当前浏览器"的思路，web-access 在关键的上传场景上更完整。二是不能躺平——browsermcp 一旦补齐文件上传，自建优势就被追上了；必须盯着官方的迭代节奏。

差异化不能靠工程深度堆出来。官方迟早会追上工程细节。真正的差异点要往使用场景深挖——针对特定平台的封装、针对工作流的 skill 级组合。

五、两条视角叠在一起才是完整地图

先画一张合成图。

我的"Browser CDP"盒子，实际对应他纵深链路的 CDP + cdp-use + 接管路线 这个片段。

两张图叠起来才看得清：

  • CDP 是协议层能力，不是一个产品——具体怎么用 CDP，分化出了 Playwright、browser-use、Midscene、browsermcp 等多条路线
  • 接管 vs 克隆 vs 独立是三种身份承接方式——web-access 和 browsermcp 走接管，browser-use 走克隆，纯 Playwright + Chromium 走独立
  • DOM vs 视觉是两种感知方式——绝大多数路线走 DOM，Midscene 是视觉兜底

六、一个观察，一个元领悟

6.1 一个观察

逆向OneByOne 原文最后那句话戳到我了——「以前很多浏览器能力，是给人点的，是给开发者调试的。现在越来越多的能力，开始直接为 AI 准备。」

其实说白了，CDP 本来是调试协议，现在被 browser-use、browsermcp、web-access 拆出来当 AI 操作接口用。Chrome 扩展本来是给浏览器扩功能，现在在被重新封装成 MCP。

整个浏览器的"接口开放面"正在从"给人"转向 "给 AI"。这是一个比单个工具选型更大的信号。

6.2 一个元领悟

做自建 skill 半年，反思几个问题，最大的感受是——技术栈每一层的定位不清楚，选型就永远在拍脑袋。

我那篇横切视角的《联网指南》不是错的。但横切视角本身是有盲区的——它假设"Browser CDP"是一个原子能力，不去追问它内部分层。直到遇到另一个人站在纵深视角写文章，我才发现自己的"Browser CDP"盒子里至少有 5 层封装、3 条分支。

干中学，学中干。

看别人领域外的文章，本质是借用他人的"纵深视角"补自己的"横切盲区"。

你的工具选对没选对，很多时候不是自己检查一遍就能发现的——得有人站在另一个方向，才能照出你视角的边界在哪里。
