理论

基本概念

💡

Talos 提供多种发送方式，同步发送、异步发送、顺序发送，还支持 Schema 功能特性。

  1. Topic 是生产者发布到消息队列每条信息所属的类别，表示一类消息的集合，每个Topic包含若干条消息，每条消息只能属于一个Topic。

  2. 每个 Topic可以被切分成一个或多个分区，即Partition，用来实现水平扩展。

  1. Partition 即分区，是管理消息的最小单元，是集群横向扩展和一切并行化的基础。

  2. 单个分区中的消息强有序。

【注】：Partition个数的指定，请用户参照如下的标准来设置：每个partition允许最大1MB/s的写，最大2MB/s的读

  1. 消息，业务服务将要发送的内容构造成 Message 对象，然后发送到 Talos 中。

  1. 为消息设置的标志，用于同一主题下区分不同类型的消息。来自同一业务单元的消息，可以根据不同业务目的在同一主题下设置不同标签。标签能够有效地保持代码的清晰度和连贯性，消费者可以根据Tag实现对不同子主题的不同消费逻辑，实现更好的扩展性。

  1. 同一类 Consumer的 集合，这类 Consumer 通常消费同一类消息且消费逻辑一致。一个消费者组下的所有消费实例组成一个消费集群，平摊消费某个 Topic 中的消息。

  1. 对于写入每个Partition的每一条数据，Talos都会为其分配一个Partition内部的唯一ID，称其为offset。

  2. offset是一个int64的整数，用于标识其为当前Partition的消息序列号，从0开始，例如0、1、2…等。

  1. 用于标识当前Parititon内部第一条可读的消息，称其为StartOffset。StartOffset是当前Partition内部ID最小的消息。

  2. 💡

    由于Talos的消息存在过期机制，因此StartOffset不一定是0，也可能是其他的有效数值。

  1. 用于标识当前Partition内部的最后一条可读的消息，称其为EndOffset。EndOffset是当前Partition内部ID最大的消息。

  1. 存储在 Talos 中的消息过期之后会被删除，同时更新StartOffset。用户随时可以修改 Topic 的消息保留时间。Talos保证每一条消息的存活周期都大于等于Retention Time。

架构介绍

服务端

  • nginx：负责转发请求，Nginx 会将客户端的请求优先打到本机的 Server 节点上，若本机Server 不可用，则会将请求转发到其他节点上，从而使客户端对服务端节点异常无感知。
  • Server：负责处理 Talos 读写请求的后端节点。
  • Hdfs：数据节点，Server 节点会将数据写入到 Hdfs 中进行持久化
  • HBase：元数据中心，负责存储集群中各类配信息，比如patition与server的调度信息，Topic元数据、消费位点等
  • zk：用于发现 Server 节点，当有节点上下线时，会通知其它 Server 重新计算分区与server的调度信息。
  • Balance server：用来平衡各 Server 节点的流量负载情况
  • Metric Server：用来统计监控指标

高阶特性

见公司文档：@高阶特性

简单陈述一下一些重要概念：

  1. 消息队列中的事务是指 “业务执行本地任务” 与 “消息发送到消息队列” 的原子性。

  2. 事务消息跟普通消息的区别是，在事务提交前，这个消息对消费者来说是不可见的；基于事务消息，消息队列最终解决的是生产者与消费者在分布式事务场景中的一致性问题。

  3. 见：@事务消息

  1. Talos 为支持订阅多个 Topic 同时消费，引入 Topic Group（Topic 组） 的概念，用来预先定义消费者可以消费的 Topic 范围。用户可以通过 SDK 传入 Topic Group 名称来消费该组下所有 Topic。

  2. 文档见：@Topic 组

  1. 标签过滤功能是指生产者向 Topic 中发送消息时，设置消息标签对消息进行分类，消费者订阅 Topic 时设置标签对消息进行过滤，只有标签与之匹配的消息才会被投递到消费端进行消费。

  2. 消费者订阅 Topic 时若未设置任何标签，无论消息发送时是否有设置标签，Topic 中的所有消息都将被投递到消费端进行消费。

1.producer定义

/**
 * @author your-account
 */
@Slf4j
@Component
public class TalosWebProducer {
    @Autowired
    private 风控平台AppConf 风控平台AppConf;
    private static final String TOPIC_NAME = "infosec_risk_风控平台_web_measure";
    private static TalosProducer asyncProducer;
    @PostConstruct
    private void init() {
        try {
            String accessKey = 风控平台AppConf.getTalosWebAccessKey(); // 从配置中心拿取
            String accessSecret = 风控平台AppConf.getTalosWebAccessSecret();
            String endpoint = 风控平台AppConf.getTalosWebEndpoint();
            Properties pros = new Properties();
            pros.setProperty("galaxy.talos.service.endpoint", endpoint);
            pros.setProperty("galaxy.talos.producer.max.put.message.bytes", "5242880"); //5M
            pros.setProperty("galaxy.talos.producer.max.retry.times", "3"); //最大重试次数
            pros.setProperty("galaxy.talos.producer.put.message.max.failed.times", "3");
            // 200ms or 2000条 or 5M 发送一次
            TalosProducerConfig producerConfig = new TalosProducerConfig(pros);
            Credential credential = new Credential().setSecretKeyId(accessKey)
                    .setSecretKey(accessSecret)
                    .setType(UserType.DEV_XIAOMI);
            asyncProducer = new TalosProducer(
                    producerConfig,
                    credential,
                    TOPIC_NAME,
                    new SimpleTopicAbnormalCallback(),
                    new WebMessageCallback()
            );
        } catch (Exception e) {
            log.error("failed to init 风控平台 web producer, msg={}", e.toString(), e);
            new Thread(() -> System.exit(1)).start(); // 强制退出
        }
    }
    // 异步发送
    public void asyncSend(List<byte[]> datas) throws Exception {
        List<Message> messagesList = new ArrayList<>();
        datas.forEach(data -> {
            messagesList.add(new Message(ByteBuffer.wrap(data)));
        });
        asyncProducer.addUserMessage(messagesList); // 发送
    }
    /**
     * 内部类，处理回调
     */
    private static class WebMessageCallback implements UserMessageCallback {
        @Override
        public void onSuccess(UserMessageResult userMessageResult) {
            log.info("success to put message, size={}", userMessageResult.getMessageList().size());
        }

        // retry when failed
        @Override
        public void onError(UserMessageResult userMessageResult) {
            try {
                for (Message message : userMessageResult.getMessageList()) {
                    log.warn("failed to put message will retry to put it, msg={}", message.getMessage());
                }
                asyncProducer.addUserMessage(userMessageResult.getMessageList());
            } catch (Exception e) {
                log.error("failed to retry put message, msg={}", e.toString(), e);
            }
        }
    }
}

public class TalosConsumerDemo {
    private static final String endPoint = "endpoint";
    private static final String accessKey = "${accessKey}";
    private static final String accessSecret = "${secretKey}";
    private static final String topicName = "testTopic";
    // groupName: 消费者组名称，使用相同groupName的消费者会均摊消费Topic下的消息
    private static final String groupName = "testConsumer";

    public static void main(String[] args) throws TException {
        Properties properties = new Properties();
        properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_SERVICE_ENDPOINT, endPoint);
        TalosConsumerConfig consumerConfig = new TalosConsumerConfig(properties);

        Credential credential = new Credential()
                .setType(UserType.DEV_XIAOMI)
                .setSecretKeyId(accessKey)
                .setSecretKey(accessSecret);

        MessageProcessorFactory factory = () -> new MessageProcessor() {
            @Override
            public void init(TopicAndPartition topicAndPartition, long startMessageOffset) {

            }

            @Override
            public void process(List<MessageAndOffset> messages, MessageCheckpointer messageCheckpointer) {
                System.out.println("Message arrived " + messages);
            }

            @Override
            public void shutdown(MessageCheckpointer messageCheckpointer) {

            }
        };

        // groupName: 消费者组名称，使用相同groupName的消费者会均摊消费Topic下的消息
        // prefix: 客户端id的前缀，用户可不指定或指定具备业务属性含义的名称，避免客户端id重复。
        TalosConsumer consumer = new TalosConsumer(groupName, consumerConfig, credential,
                topicName, factory, "${prefix}", new SimpleTopicAbnormalCallback());
        Runtime.getRuntime().addShutdownHook(new Thread(consumer::shutDown));
    }
}

Talos 是分布式消息队列，一个 Topic 会被分成多个 Partition。当你的消费者程序启动时，Talos 服务端会将这些 Partition 分配给不同的消费者实例。

三个核心函数：

init(TopicAndPartition topicAndPartition, long startMessageOffset)

  • 执行时机：当一个 Partition 被分配给当前消费者实例时（只执行一次）。
  • 程序刚启动：消费者上线，服务端进行负载均衡（Rebalance），分配了一些 Partition 给这个消费者。
  • Rebalance（重平衡）之后：如果有其他消费者上线或下线，Partition 会重新分配。如果你“抢”到了一个新的 Partition，就会为那个 Partition 触发 init。
  • 告诉你：“从现在开始，你负责处理 Partition X”。
  • 告诉你：“请从 Offset startMessageOffset 处开始读取”。
  • 可以在这里初始化一些针对该 Partition 的资源（比如独立的计数器）。

process(List<MessageAndOffset> messages, MessageCheckpointer ...)

  • 执行时机：当从服务端成功拉取到一批消息时（循环执行）。
  • 这是一个死循环逻辑。只要该 Partition 还有未消费的消息，SDK 就会不断从服务端拉取数据，一旦拉到数据（List 不为空），就会调用一次 process。
  • 核心消费逻辑。你需要在这里写消费核心逻辑。
  • 注意：如果不处理完（函数不返回），SDK 不会去拉取下一批数据。
💡

Q1：process函数的耗时控制在多久内合理？这个配置是在哪里控制的？

答：

Talos 的 process 函数耗时没有绝对的“硬性配置限制”（不会因为超时直接抛异常），但强烈建议控制在 30秒 以内，最佳实践是 1秒 以内。

它的隐形限制主要来自以下两个配置（在 TalosClientConfigKeys 中）：

  1. 网络请求超时 (GALAXY_TALOS_CLIENT_TIMEOUT_MILLI_SECS)
  • 默认值：10000ms (10秒)
  • 影响： 在你的代码末尾，调用了 messageCheckpointer.checkpoint()。这是一个网络请求。 如果 process 耗时极长（例如 5 分钟），虽然 SDK 内部的心跳线程还在跑，但等到你终于执行到 checkpoint 时，之前的某些 TCP 连接状态可能已经变了，或者服务端的 Session 可能会遇到一些边缘情况（虽然概率较低）。 更重要的是：如果你的 checkpoint 请求发出去，因为网络慢超过了 10秒，抛出了异常，你的这一批 500 条数据就全部白做了（因为没提交成功，下次还会重发）。
  1. 服务端 Rebalance 超时 (Server Side Config)
  • 默认值：通常 30秒 - 60秒（客户端不可改，由运维配置）
  • 影响： Talos SDK 内部有一个独立的心跳线程（Worker 线程卡死在 process 里通常不会阻塞心跳线程）。 但是，如果你的 Worker 线程一直卡在 process 里不出来，虽然你还在发心跳，但你的消费位点（Offset）一直没动。 完善的监控系统会报警“消费堆积（Lag）”。在某些极端的 Rebalance 策略下，长时间不提交 Offset 可能会被服务端标记为“假死”。

shutdown(MessageCheckpointer messageCheckpointer)

  • 执行时机：当该 Partition 不再由当前消费者负责时（只执行一次）。
  • 程序关闭：你调用了 consumer.shutDown() 或者杀死了进程（触发 ShutdownHook）。
  • Rebalance（重平衡）丢失分区：此时有新的消费者加入（例如你的服务扩容了），Talos 决定把当前这个 Partition 挪给那台新机器处理。为了避免数据冲突，它会先调用你的 shutdown，让你停止处理。
  • 最重要的操作：必须在这里最后调用一次 messageCheckpointer.checkpoint()。因为在 Rebalance 发生时，如果你不提交当前的进度，新接手的机器就会从旧的进度开始消费，导致数据重复。

Consumer核心配置

properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_SERVICE_ENDPOINT, endpoint);
// 数据一致性控制，offset自动提交关闭，由用户自己控制offset提交时间点（一定关闭！！）。
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_CHECKPOINT_AUTO_COMMIT, "false");
// 单次拉取的最多消息条数
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_MAX_FETCH_RECORDS, "500");
// 消息拉取间隔
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_FETCH_INTERVAL, "0");
// 控制 不同分区（Partitions）之间 的并发，而非 同一个分区内部 的并发
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_PRODUCER_THREAD_POOL_SIZE, "32");

GALAXY_TALOS_PRODUCER_THREAD_POOL_SIZE：负责不同分区消息的并发。

Talos核心规则：Partition 独占原则，即：同一个 Partition 的数据，永远只会被同一个线程串行处理。

这个参数主要用于 “单进程多分区” 的场景，即 少量的消费者实例处理大量的分区。

虽然参数名里带有 PRODUCER（生产者），但在 Consumer（消费者）端，它是Talos SDK 底层的 IO 与回调线程池。它决定了你的程序能同时并发拉取多少个分区的网络数据。

例1：32个分区，4个消费者实例。那么此时Talos会平均给1个消费者分配8个分区。

  • 假设有消费者A，该配置为1，那么A对8个分区的消息串行消费。
  • 假设有消费者B，该配置为8，那么B对8个分区的消息并行消费。

Talos vs RocketMQ

Talos（以及 Kafka）确实没有像 RocketMQ 那样原生内置的“自动重试队列”和“死信队列”概念。

这是由两者的架构设计理念差异决定的：

  • RocketMQ / RabbitMQ：是基于 队列（Queue） 的模型。消息是可以被单独 ACK（确认）的。如果你处理失败，Broker 可以把这条消息单独拎出来，扔到重试队列里，过会儿再给你。
  • Offset 是线性的（1, 2, 3...）。
  • 规则：你必须先提交 Offset 1，才能提交 Offset 2。
  • 如果你想“跳过”失败的 Offset 1 去消费 Offset 2，同时又想保留 Offset 1 稍后重试，这在 Talos 的模型里是逻辑悖论。

Consumer配置调优

💡

上线后，去容器查看线程池的使用情况，关注活跃线程数，若线程池常满，说明资源不够用，则需要升容器配置或加容器。

背景：Talos producer 峰值QPS约900、4核8G的机器，业务逻辑平均耗时50ms，且EUR Talos有8个分区。

Q1：在保证CPU负载 <=70%的情况下，Talos consumer、消费线程池配置如何调整？需多少个机器？

// 线程池配置：
WORKER_POOL = new ThreadPoolExecutor(10, 50, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(1000), new ThreadFactory() {
    public Thread newThread(@NotNull Runnable r) {
        return new Thread(r, "风控平台-talos-passport-action-" + System.currentTimeMillis());
    }
}, new ThreadPoolExecutor.CallerRunsPolicy() // 队列满时由主线程执行，防止丢数据 - // TODO 上线后排查：是否线程池常满，导致主线程执行，阻塞流程
);
// consumer配置：
// 数据一致性控制，offset自动提交关闭，由用户自己控制offset提交时间点。
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_CHECKPOINT_AUTO_COMMIT, "false");
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_MAX_FETCH_RECORDS, "1000");
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CONSUMER_FETCH_INTERVAL, "50");
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_CLIENT_TIMEOUT_MILLI_SECS, "10000"); // 默认10s
properties.setProperty(TalosClientConfigKeys.GALAXY_TALOS_PRODUCER_THREAD_POOL_SIZE, "8"); // passport_action最多有32个分区

  1. 总QPS=900，那么「需要并发的线程数 = QPS ✖️ 平均耗时」，因此需要的总线程数=45个(900*0.05s=45)。

  2. 即意味着：整个Talos consumer必须同时有45个线程在并行，才能消费完900 QPS的流量而不积压。

  1. 机器数量： 为了高可用（容灾），生产环境最少需要 2 台 机器。
  2. 单机负载： 若2 台机器分摊 900 QPS，每台承担 450 QPS。
  3. CPU 估算：
    • 业务耗时 50ms。假设其中 CPU 密集运算占 5ms（序列化/逻辑），IO 等待占 45ms（写库/RPC）。
    • 单机 CPU 需求 = 450QPS * 0.005s = 2.25核。
    • 当前配置为 4 核，CPU 使用率约为 2.25 / 4 = 56%。2 台机器 完全满足 CPU <= 70% 的要求。
  1. 单机承担 QPS：450；单机所需线程 = 22.5。
  2. 因此建议配置：
    • CorePoolSize: 25 (覆盖日常流量)。
    • MaxPoolSize: 50 (应对抖动)。

  1. 业务逻辑的平均耗时为50ms，且此时拉取消息的时间间隔为50ms，理想情况下，消费速度=拉取速度，此时无空转也无堆积。

  2. 但若某次耗时增长，消费速度跟不上拉取速度，会将拉取后的消息放入等待队列。那么此时需兜底，保证等待队列的大小能兜住至少两次「拉取消息但无法消费的情况」，因此配置线程池的等待队列大小为 单次拉取消息数*2.5=2500。
