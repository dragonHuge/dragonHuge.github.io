2026-03-24 · 飞书原文 ↗

背景与目标

作为 API 提供方（[公司模型服务]），需要识别来自 OpenClaw 等受信任 Agent 工具的调用，对其适当放宽内容审核策略，同时不影响对普通用户的审核逻辑。

关键风险：方案①依赖 OpenClaw 不主动脱敏。飞书文档《OpenClaw API 请求指纹分析与反检测策略》已详细列出反检测路径，一旦用户启用脱敏插件，指纹检测会失效。方案②③具备主动防伪造能力，更适合作为长期方案。

结论：方案①对反检测策略基本无抵抗力，用户一旦启用 P0 级脱敏操作（改段落标题 + 重命名工具）即完全失效。方案②在对抗恶意伪造时存在 header 可被任意客户端伪填的风险，但对 OpenClaw 这类受信任工具而言已足够——前提是 API Key 不泄露。方案③是唯一能对抗所有反检测手段的方案。

推荐实施路径

短期（立即可用）

启用方案①作为自动识别兜底：在 API Gateway 层对 system prompt 做关键词扫描，命中 ≥2 个 OpenClaw 特征词即切换至宽松审核策略。

核心特征词（按唯一性排序）：

  • <available_skills>（XML 标签，唯一性极高）
  • openclaw.inbound_meta.v1
  • sessions_spawn / sessions_send / memory_search
  • HEARTBEAT_OK / [[reply_to_current]]

中期（2-4 周）

推进方案②：在 OpenClaw 的 TOOLS.md 或 SOUL.md 中统一配置自定义请求头，API Key 管理系统增加 trust_tier: agent_tool 字段，Gateway 中间件按 tier 分发审核策略。方案①作为方案②失效时的降级兜底。

长期（配合 OpenClaw 开发）

落地方案③（RFC 9421）：OpenClaw 侧实现 Ed25519 请求签名，API 方接入 web-bot-auth 验证库，对齐 OpenAI ChatGPT Agent 已有标准，具备行业互操作性。

待确认事项

  1. 内容审核位置：审核逻辑在 API Gateway 层还是模型推理层？决定方案①的接入点和改造范围。
  1. OpenClaw 配置控制权：是否有权限修改 OpenClaw 的 TOOLS.md / SOUL.md？决定方案②的推进速度。
