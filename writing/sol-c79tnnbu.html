背景

字典表（Dictionary Table）是软件开发中用于集中管理固定或半固定数据集合的结构化存储方案，核心作用是将系统中重复出现的 “键 - 值映射关系”从代码中抽离，通过统一的存储和接口进行管理。

其本质是 “键值对的集合”。

字典表的核心价值在于：避免硬编码、支持动态更新、统一维护、降低跨模块耦合。

目标

搭建风控-通用字典表能力，做到通用枚举数据即查、即知、即用。

如：账号风险标签、名单库类型动态配置。

实现方案

核心设计目标：

  1. 高性能：支持毫秒级查询(<=200ms)；
  1. 高可用：避免单点故障，缓存与数据库一致性；
  1. 易维护：提供管理界面，支持增删改查、权限控制(沿用风控平台的权限控制吧)。

元数据结构

MYSQL

字典表（risk_dict_table）

用于管理字典分组（如 “名单库类型”、“IP 信誉等级”），考虑业务隔离与通用性需求。

CREATE TABLE `risk_dict_table` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `dict_code` varchar(50) NOT NULL DEFAULT '' COMMENT '字典类型编码（如risk_tag_list、ip_reputation_level）',
  `dict_name` varchar(100) NOT NULL DEFAULT '' COMMENT '字典类型名称（如“风控名单库类型”“登录行为枚举”）',
  `dict_type` varchar(50) NOT NULL DEFAULT '' COMMENT '使用场景区分（普通型、规则型）', -- 补充字段类型，添加默认值
  `status` tinyint(1) NOT NULL DEFAULT '1' COMMENT '状态（1=启用，0=禁用；禁用后该类型下所有字典项不可用）',
  `description` varchar(500) DEFAULT '' COMMENT '备注',
  `created_by` varchar(100) NOT NULL DEFAULT 'risk' COMMENT '创建人',
  `create_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间', 
  `updated_by` varchar(100) NOT NULL DEFAULT 'risk' COMMENT '更新人',
  `update_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间', -- 时间型默认当前时间
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_dict_table` (`dict_code`) COMMENT '唯一索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='字典类型表';

说明：

  1. 当字典表被禁用：直接将字典表这个大key从redis删掉。
  2. 当字典项被禁用：从对应字典表的大key下删除此字典项(HDEL)

字典项表（risk_dict_item）

用于存储具体键值对（如 “black_list -> 黑名单”），包含风控所需的扩展属性。

注意：其中dict_key、dict_value、item1、item2、item3、item4是平级字段，同属于一个集合。

如：

  1. 字典项1：dict_key="解锁",dict_value="usertype",item1="1",item2="白名单"
  2. 字典项2：dict_key="解锁",dict_value="usertype",item1="3",item2="普通用户"
  1. 字典项1：dict_key="用户ID",dict_value="公司ID"
  2. 字典项2：dict_key="ip",dict_value="IP"
  3. 字典项1：dict_key="email",dict_value="邮箱"
CREATE TABLE `risk_dict_item` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `dict_table_id` bigint NOT NULL DEFAULT 0 COMMENT '关联字典表id（数值型默认0，无法空字符串）',
  `dict_key` varchar(100) NOT NULL DEFAULT '' COMMENT '字典键（如black_list）',
  `dict_value` varchar(200) NOT NULL DEFAULT '' COMMENT '字典值（如黑名单）',
  `item1` varchar(200) NOT NULL DEFAULT '' COMMENT '扩展字段1（如1）',
  `item2` varchar(200) NOT NULL DEFAULT '' COMMENT '扩展字段2（如黑名单）',
  `item3` varchar(200) NOT NULL DEFAULT '' COMMENT '扩展字段3（如黑名单）',
  `item4` varchar(200) NOT NULL DEFAULT '' COMMENT '扩展字段4（如黑名单）',
  `status` tinyint(1) NOT NULL DEFAULT '1' COMMENT '状态（1=启用，0=禁用；禁用后该键值对不参与业务逻辑）',
  `created_by` varchar(100) NOT NULL DEFAULT 'risk' COMMENT '创建人',
  `create_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_by` varchar(100) NOT NULL DEFAULT 'risk' COMMENT '更新人',
  `update_at` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_dict_table_id_key` (`dict_table_id`, `dict_key`) COMMENT '唯一标识单个字典项）',
  KEY `idx_dict_table_id` (`dict_table_id`) COMMENT '快速查询某字典表下所有项'
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci COMMENT = '字典项表（具体键值对存储）';

Redis

有几个字典表，Redis中就会有几个大Key。

  • key(固定前缀)：risk_dict:${risk_dict_table_code}
  • hash：存储单条字典项的多属性。每一个子项键值对，存一个字典项。

    即： "${dict_item_id}":"${将此字典项的全部数据拼接成json}"。并且还存储着字典表的元数据，如：dict_name、status等。

    如下示例：

    // 字典表1-其下有字典项2、3、4
* key：risk_dict:RiskTagListMainerType
* value:
    "{
        "2":"{XXX}",
        "3":"{XXX}",
        "4":"{XXX}"
    }"

value中只需要加Item。

综上设计，那么针对字典表、字典项的操作，应遵守以下逻辑：

    • 字典表下线 -> 修改status，且直接删redis key。
    • 字典项更新 -> 更新hash即可(部分更新)。
  • 查操作 -> 查redis（无论是否查到，直接返回）

重点问题思考

  • 高性能：服务只涉及到redis查询和个别MYSQL查询，耗时有保障。唯一需要考虑的是海外集群耗时，是否需要多机房部署？- 》 使用方自己做缓存。国内外隔离，两套字典表。
