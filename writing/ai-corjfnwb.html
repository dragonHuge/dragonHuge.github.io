多 Agent 架构梳理：五家系统的架构、通信与派系归属

2026-08-13 · 飞书原文 ↗

最近看到大家都在聊Agent架构、Agent编排，那么所谓的Agent架构，究竟是什么？

你理解的Agent架构，是否是披着workflow外衣的伪架构？

业内有哪些优秀的架构方案？

在真实工作中，怎么使用Agent架构来进一步提效？

这篇文章一起来聊一聊，在opencode、claude code、openclaw、hermes、kimi 等主流AI工具的Agent架构，以及在实际工作中，如何选型？如何搭建自己的Agent团队。

💡

作为opencode、claude code、OpenClaw的重度使用用户，这篇文章一起来聊一聊「Agent架构」。

从最简单的subAgent(主流)，到Agent teams，再到深入底层的 Swarm()

结论在前：

  1. 两者均支持主从Agent架构(subAgent)。
  2. Claude code支持额外支持Agent Teams架构(平级agent之间peer通信)
  1. OpenClaw 原生支持subAgent，多Agent能力依赖于GateWay机制 + feishu等IM网络通信软件。
  2. Hermes原生支持subAgent。

二、各家 Agent 架构详解

2.1 Kimi Swarm — 模型级 Swarm（派系 A）

架构模式：异质 Orchestrator + 同质 Frozen Workers

  • Orchestrator：K2.5 模型本体，经 RL 训练的调度器
  • Sub-agents：frozen workers，动态实例化
  • 角色没有预设，完全由模型自主决定
  • 最多 100 并发 / 1500 总步数（实测约 5 个同时跑）

核心创新 — PARL

把"该不该并行"训进了模型权重：

  • r_parallel → 激励开 sub-agent
  • r_finish → 防开了不干活
  • r_perf → 任务成功率

模型因此学会"什么时候不该开 Swarm"

💡

关键限制：能力绑死 K2.5，不可迁移到其他模型。紧耦合编码任务会自动退化为单 Agent。

2.2 Claude Code — 主从 + 可选 Peer（派系 B）

架构模式一 · Subagent（主从）

  • 主 Agent 通过 Agent tool 调起子 Agent
  • 子 Agent 独立 context
  • 单向回流：只有 summary 返回主 Agent
  • 子 Agent 不能再调子 Agent（硬编码防递归）

架构模式二 · Agent Teams（Peer）

  • 显式创建 Team：AgentTeamCreate / AddMember
  • 成员之间用 message 工具互发消息
  • 状态持久化到 JSON
  • 适合方案设计 / Code Review / 相互挑战

独门设计：

特性

说明

isolation: worktree

每个 feature 独立 git worktree，多 Agent 并行开发互不干扰，失败回滚不影响主分支

五层上下文压缩

从实时预算控制到硬砍应急，Level 4 子 Agent 共享主缓存前缀（压缩本身也享 Cache）

Connector Text 签名

密码学签名防注入，模型验证签名被改就拒绝继续（Anthropic 独门黑科技）

2.3 opencode — Claude Code 的开源对照物（派系 B）

不支持Agent Teams架构，仅支持主从Agent机制。

与 Claude Code 的共同点

  • 同属主从架构
  • 主 Agent Prompt + Task tool 决定委派
  • 子 Agent 独立 context 单向回流

关键差异

  • 开源（MIT），provider-agnostic（20+ 模型）
  • client/server 彻底解耦（独立 headless server）
  • Session 是显式树结构（parentID/fork/children）
  • 8 级配置 precedence（含企业 MDM 强制）

Session 树 API（一等公民）：

  • POST /session — 创建（可带 parentID）
  • POST /session/:id/fork — 从任意 message 分叉
  • GET /session/:id/children — 列子会话
  • TUI 快捷键可在父子会话间导航

2.4 Hermes Agent — 主从 + 自进化（派系 C）

主从骨架

  • 通过 delegate_task 工具 spawn 子 Agent
  • 子 Agent 独立 conversation / terminal / toolset
  • leaf vs orchestrator 角色分层：
  • leaf（默认）：不能再 delegate，高风险工具直接剥夺
  • orchestrator：可再 delegate，受 max_spawn_depth=1 约束

自进化四条路径

  1. Skill 自主创建：任务结束后自己把做法固化成 SKILL.md
  1. Memory nudge：周期性把学到的东西写 MEMORY.md / USER.md
  1. 跨 session 召回：SQLite + FTS5 全文索引 + Gemini Flash 摘要。
  1. RL 训练回流：Atropos 环境 + trajectory compressor（独家）
💡

与 B 派的本质区别：B 派的 Skill / Memory 是用户手写的静态资产；C 派把"沉淀"做成 Agent 主动行为。leaf 的权限剥夺不是靠 Prompt 叮嘱，而是在工具白名单层直接剥夺——连工具描述都看不见。

不是一个 Agent 演多角色，是多个独立 persona 住在 IM 里。

核心设计：

peer > parentPeer > guildId+roles > accountId > channel > default，确定性规则，不经过 LLM

补充：SubAgent 触发时机、Agent Teams 触发与 Mailbox 通信

SubAgent 什么时候被触发？

各家触发机制完全不同——"subagent"这个词在不同系统里含义天差地别：

触发方式

谁决定"该不该分"

触发时机

Kimi Swarm

模型权重自主决定

模型本身（RL 训练进去的）

推理过程中自动判断，无显式工具调用，是唯一一个不需要 tool call 就能开 SubAgent 的

Claude Code

主 Agent 调 Agent tool

主 Agent（Prompt 引导）

判断子任务独立性足够高时，显式调用 Agent tool 委派

opencode

主 Agent（Prompt 引导）

关键区分：Kimi Swarm 是唯一"模型自决"的；Claude Code / opencode / Hermes 都是主 Agent 通过显式工具调用触发；OpenClaw 的路由发生在 LLM 之前——消息还没到模型就已经被分配好了。

Agent Teams 怎么触发的？

Agent Teams 不是自动触发的，是主 Agent 通过显式 API 三步创建：

① AgentTeamCreate  → 创建 Team（定义团队名称、目标）
② AddMember × N    → 逐个添加成员（每个成员有独立 instructions + tools）
③ Execute          → 启动团队执行

触发时机：主 Agent 判断当前任务适合多角色协作时（如"需要一个人写方案、另一个人挑刺"），由 Prompt 引导主 Agent 调用 AgentTeamCreate。不是框架自动检测"这个任务该开 Team"，而是模型自主决策。

Agent Teams 通信机制：Mailbox 模式。

Agent Teams 成员间采用 Actor Model 的 Mailbox 通信模式，不是共享黑板：

特征

说明

异步投递

A 往 B 的 mailbox 写完就继续自己的事，不阻塞等 B 回复

独立 inbox

每个成员有自己的 mailbox，只看到发给自己的消息

非广播

A 发给 B 的消息，C 看不到（除非 A 也发一份给 C）

轮转消费

成员按 turn 轮转，轮到谁谁就消费自己 inbox 里的消息

持久化

Team 状态（含 mailbox 历史）持久化到 JSON

为什么选 Mailbox 不选共享黑板？

Mailbox（Agent Teams）

共享黑板（Blackboard）

信息可见性

点对点，只有收件人能看到

全员可见

Context 膨胀

O(n) — 每人只处理自己的消息

O(n²) — 每人要扫描全局

风险

信息可能遗漏（没发给该看的人）

Context 爆炸

Mailbox 的核心优势就是防 context 爆炸。3 个 Agent 用共享黑板，每轮每人都要吃全局消息，context 是 O(n²) 增长；Mailbox 点对点投递只有 O(n)。

💡

注意：Mailbox 模式是 Claude Code Agent Teams 独有的。其他四家（Kimi Swarm / opencode / Hermes / OpenClaw）的 SubAgent 间无 peer 通信能力，所有协作都经过主 Agent 中转。

上下文归属：谁的 context 膨胀了？

一个常见误解：Agent Teams 里三个 Agent 的上下文会塞到用户当前 session 里。不会。 无论主从还是 Teams，用户 session 都只吃最终产出。

各上下文空间的内容：

上下文空间

里面有什么

Agent A 的 context

A 的 system prompt + 收到的 mailbox 消息 + A 自己的工具调用和推理

Agent B 的 context

B 的 system prompt + 收到的 mailbox 消息 + B 自己的工具调用和推理

Agent C 的 context

C 的 system prompt + 收到的 mailbox 消息 + C 自己的工具调用和推理

用户的 session

原有上下文 + Team 最终产出（≠ A+B+C 的全部上下文）

那两种架构的真正开销差异在哪？

不在用户 session 里，而在幕后的 LLM 总调用量：

维度

主从 Subagent

Agent Teams

用户 session 膨胀

  • 1 段 summary
  • 1 段最终产出（差不多）

幕后独立 context 数

2 个（主 + 子）

4 个（用户 + A + B + C）

LLM 总调用

主 Agent N 轮 + 子 Agent M 轮

主 Agent N 轮 + A×轮数 + B×轮数 + C×轮数

总 token 消耗

较低（子 Agent 干完就退出）

3-5 倍（多轮 mailbox 来回）

💡

结论：无论主从还是 Teams，用户 session 都只看到最终产出，不会被子 Agent / Team 成员的完整上下文污染。区别在于"幕后"开了几个独立 context、LLM 总调用量多大。Teams 幕后更重但不污染用户 session——这也是 Mailbox 选点对点而非广播的核心原因。

补充：各家 Agent 定义文件结构详解

不同系统定义 Agent 的方式差异巨大——有的用 JSON，有的用 Markdown frontmatter，有的直接训进模型权重。本节逐家拆解 Agent 定义文件的结构和各字段作用。

Claude Code 的 Agent 定义

Claude Code 有两种定义 Agent 的方式：预定义文件（持久化角色）和运行时调用（临时子 Agent）。

方式一：预定义文件（.claude/agents/*.md）

标准格式：Markdown 文件 + YAML frontmatter + body 作 system prompt。

---
name: code-reviewer        # 必需，调用时的 subagent_type
description: 代码评审专家，检查质量、安全漏洞和最佳实践  # 必需，路由依据
tools: Read, Grep, Glob    # 可选，限制工具权限；不写=继承所有
model: sonnet              # 可选，haiku/sonnet/opus；不写=继承父
---

你是代码评审专家。

## 工作原则
- 安全漏洞是第一优先级
- 宁可多报不漏报
- 给出修复建议而非只指出问题

## 评审维度
- 安全性、性能、可维护性、代码风格

字段

必需

作用

name

✅

唯一标识，主 Agent 用 subagent_type: "<name>" 调起此 Agent

description

✅

调度关键——主 Agent 读这个字段决定要不要路由到此子 Agent，写法直接影响命中率

tools

❌

逗号分隔的工具白名单（如 Read, Grep, Glob）。不写 = 继承主 Agent 全部工具

model

❌

haiku（便宜快）/ sonnet（均衡）/ opus（推理深）

frontmatter 下方

✅

Markdown 正文，作为子 Agent 的 system prompt（角色定位、工作原则、输出风格）

加载优先级（同名时项目级覆盖用户级）：

项目级  .claude/agents/     ← 团队共享，提交 Git
用户级  ~/.claude/agents/   ← 个人偏好，跨项目通用
💡

格式对比：Claude Code 和 opencode 的 Agent 定义文件格式几乎一致——都是 Markdown + YAML frontmatter。区别在于 opencode 多了 mode: primary | subagent、temperature、max_tokens 等扩展字段。实践中可以用 symlink 让同一个 .md 文件同时兼容两边。

方式二：运行时调用（Agent tool JSON 参数）

不预定义文件，直接在调用时传参创建临时子 Agent：

{
  "type": "Agent",
  "name": "temp-analyzer",
  "instructions": "分析这段代码的性能瓶颈...",
  "subagent_type": "specialized",
  "model": "sonnet",
  "tools": ["Read", "Grep", "Glob"],
  "run_in_background": false,
  "isolation": "worktree"
}

运行时调用比预定义文件多了 run_in_background（异步执行）和 isolation: worktree（独立 git worktree 物理隔离）两个能力。适合一次性任务，不需要复用。

Hooks 配置（.claude/settings.json）

Hooks 是 Claude Code 的生命周期拦截器，在工具调用前后插入自定义脚本：

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Write|Edit", "command": "bash ./scripts/check-permissions.sh" }
    ],
    "PostToolUse": [
      { "matcher": "*", "command": "bash ./scripts/auto-lint.sh" }
    ],
    "SubagentStop": [
      { "matcher": "*", "command": "bash ./scripts/collect-summary.sh" }
    ]
  }
}

Hook 类型

触发时机

PreToolUse

工具调用之前拦截。matcher 指定匹配哪些工具（支持正则）

PostToolUse

工具调用之后触发。适合自动 lint、日志记录

SubagentStop

子 Agent 结束时触发。收集 summary、清理资源

Notification

Agent 需要用户注意时触发。桌面通知、声音提醒

💡

Exit code 陷阱：exit 0 = 通过、exit 1 = 非阻塞错误（日志记录但不拦截执行）、exit 2 = 真正的安全拦截（阻止工具执行）。80% 的人把 exit 1 当拦截用，实际上只有 exit 2 才真拦。

配置分层（四级优先级）

Hermes Agent 的 Agent 定义

Hermes 通过 delegate_task 的参数实时定义子 Agent，不需要预先配置文件：

{
  "name": "delegate_task",
  "parameters": {
    "goal": "分析这段代码的性能瓶颈",
    "context": "文件路径: src/core/engine.py，用户反馈响应慢",
    "toolsets": ["read", "grep", "bash"],
    "role": "leaf",
    "acp_command": null
  }
}

✅

否

否

否

Hermes 独特之处：Agent 不是预定义的配置文件，而是运行时动态创建。role: leaf 时，子 Agent 连 delegate_task 工具的描述都看不到——不是 Prompt 里说"你不能再委派"，而是物理上工具不存在。

Hermes 的 Skill 自创建（Agent 自己写的持久化定义）：

~/.hermes/skills/
  ├── code-review/
  │   └── SKILL.md        ← Agent 自己写的技能定义
  ├── perf-analysis/
  │   └── SKILL.md
  └── ...

这些 Skill 是 Hermes Agent 任务结束后自主创建的，相当于"Agent 自己给自己写配置文件"。

各家安全设计的共同点：无论定义方式多不同，所有系统都通过工具白名单控制子 Agent 权限，并且子 Agent 永远拿不到 delegation 工具（Claude Code 硬编码剥夺 Agent tool，opencode 剥夺 Task tool，Hermes leaf 剥夺 delegate_task）。这是多 Agent 递归防御的业界共识。

五、选型一句话

💡
  • 严肃编码 + Anthropic 生态 → Claude Code（worktree 隔离独门）
  • 开源 / 多模型 / 企业管控 → opencode（client/server + 8 级配置）
  • 长期个人助手 / 自生长 → Hermes Agent（skill 自创建 + RL 回流）
  • 多身份多 IM / 主动型 AI → OpenClaw（多 persona + bindings 路由）
  • 百级并行研究 / 数据构建 → Kimi Swarm（PARL 模型级方案）
