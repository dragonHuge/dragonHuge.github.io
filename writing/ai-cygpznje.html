2026-03-05 · 飞书原文 ↗

本文仅是为做分享速拟的脚本文档，详细实践记录见：@AI-Coding提效 风控后台实践(OpenCode+OpenSpec)

关键概念速览

更多概念请看：@AI-Coding学习笔记。

  • OpenCode、Micode、Claude Code、CodeX：TUI(terminal ui)形式的AI交互工具。
  • SDD（Specification-Driven Development，规格驱动开发）：一种项目开发范式，一种理念。
  • Spec-kit、OpenSpec：基于SDD理念的工程实践方法论。

工具类别

包含工具

核心角色

规范驱动工具(SDD)

Spec-kit、OpenSpec

定需求的 “项目经理”

AI 编码工具（TUI）

OpenCode、micode、ClaudeCode

写代码的 “码农”

Rules：给AI的全局规范，定义红线规则、别名有“宪法(SpecKit)、Agents.md(OpenCode)”。

Skill：给AI的工作SOP，本质上是提示词，引入“渐进式披露机制”，减少了token消耗。

接下来，我们需要探讨的是：

如何把 “软件工程开发规范SDD” 与 “Vibe Coding”结合，即：如何用 规范流程的确定性 抹平 VibeCoding 的不确定性？

如何做呢？

为了不重复造轮子，使用业内开源项目，且由于风控后台属于已有项目，因此采用 “OpenCode + OpenSpec”。

原生OpenSpec - 实例先行

OpenSpec作为已基本成熟的开源项目，理论来讲直接可以引入项目并直接使用。那我们直接进入主题，以真实需求为例，一起走一遍开发流程。

风控管理后台作为内部管理平台，属于SpringBoot + Vue 的经典前后端分离项目。

原生OpenSpec开发范式

  1. .opencode文件夹：存储Skill、Command等元信息。
  2. openspec做需求变更管理与追踪。

  1. OpenSpec有两种命令形式：

  2. openspec init：这些命令是交互式的，专为终端使用而设计。-> terminal里用的。
  3. /opsx:new：这是 OpenSpec 斜杠命令，在AI 编码助手的聊天界面中调用。 -> AI聊天界面里用的。

需求开发 GOGOGO！

  1. tab切换到plan agent，使用/opsx-explore做需求拆解，自然语言描述需求即可。这整个过程，AI会挖掘你的需求，确认100%理解你的需求后，会拆分为详细的task(task.md)，逐步执行。

  2. 并且会将这整个的需求变更过程，在OpenSpec/changes/文件夹下，持久化一份本次需求变更记录，保证做到需求的进度追踪、变更追踪。

  1. 任务拆解完成后，/opsx-apply，AI就开始根据tasks.md中的任务，逐步开始执行。

  1. 整体需求开发完成后，/opsx-archive，即可完成需求归档，其会将本次需求变更的全部文件，移动到/archive文件夹下。

  3. config.yaml：
  1. .openspec.yaml：change的元数据文件。OpenSpec CLI 通过读取这个文件来判断该 change 应该走哪套 artifact 流程、需要哪些前置依赖。
    • schema: 这个 change 使用哪个工作流（spec-driven 意味着 proposal → specs → design → tasks 这套流程）
    • created: 创建时间。

    spec-driven 是目前唯一内置的 schema，定义了固定4个 artifact 的线性依赖流程：

    proposal → specs ─┐

    ├─→ tasks ─→ apply

    → design ─┘

  2. proposal.md：Why and What，概括了目标、范围和方案。
  3. design.md：How，说明了具体该怎么做。
  4. tasks.md：任务清单。

从上述过程来看，这不很简单吗，下两个开源组件 + 几条命令，我们的工作就已经完成了呀。

真的是这样吗？反思几个问题：

  1. AI生成的代码，符合部门的代码规范吗？符合已有项目的代码风格吗？
  1. AI这次需求又造了多少重复轮子？造这些重复的轮子，AI又烧了多少Token，费了多少时间？
  1. AI实现的代码真的有达到你的预期吗？你敢直接上线吗？测试的话是人为在测对吗？人为CR AI的代码并且测试，工作量大吗？

想象一下：项目中已有HTTP调用的封装工具类，但AI不知道，擅自引入了开源包，自嗨式完成了功能实现。

再想象一下：当需求迭代到一定时期，项目中有无数重复轮子互相缠绕，理不清、理还乱。

再想象一下：当项目代码到一定的体量，AI想要了解这个项目，需要扫描全部项目代码，而这庞大的数据量一下子撑满了AI的上下文。。。。

还需要树立哪些规范？

原生OpenSpec解决了vibe coding的基本开发规范，但正如上问题，还有两个大问题需要解决：

  1. 如何 让AI遵守项目代码风格、代码规范、不重复造轮子？
  1. 如何 提高AI代码实现的可信度（AI-coding下的开发->测试闭环 如何做）？

Agent知识库搭建 & 全局约束规则 & 开发约束规范

此知识库用于Agent快速了解项目，从而 减少 Token消耗、Context上下文长度、AI耗时。

核心思想就是：Rules 定义红线，Skills 提供详情

# SpringBoot Maven 多模块项目知识库构建专家

本 Skill 专为 SpringBoot Maven 多模块项目设计，深度分析项目结构、模块依赖、实体类、RESTful 接口、技术栈信息，生成完整、标准化的项目知识库文档。

## 适用场景

- ✅ SpringBoot Maven 多模块项目
- ✅ 前后端分离的后端项目
- ✅ 包含管理后台（Admin）的系统
- ✅ 微服务模块化项目
- ✅ 需要完整技术文档的老项目梳理

## 核心能力

| 能力 | 说明                                        |
|------|-------------------------------------------|
| **技术栈分析** | 解析 pom.xml，提取 Java 版本、SpringBoot 版本、核心依赖  |
| **目录结构解析** | 完整扫描项目目录，解释每个文件夹的作用                       |
| **模块依赖分析** | 解析 pom.xml，生成模块依赖关系图                      |
| **实体类梳理** | 深度扫描 Entity/Model/DTO/VO，生成数据结构文档         |
| **API 接口梳理** | 扫描 Controller，生成 JSON 格式的完整接口文档           |
| **交互式确认** | 对不明确的文件夹主动咨询用户，确保你 99% 理解文件夹的作用后，才继续下一步动作 |

## 单一职责

**负责**：
- ✅ 技术栈文档生成（Java 版本、依赖清单、构建工具）
- ✅ 项目目录结构分析与文档化
- ✅ Maven 多模块依赖关系分析
- ✅ 实体类数据结构梳理（Entity, Model, DTO, VO）
- ✅ RESTful API 接口文档生成（JSON 格式）
- ✅ 与用户交互确认不明确的结构

**不负责**：
- ❌ 代码规范文档（由 project-rules-scaffold 负责）
- ❌ 代码修改与重构

### Step 1: 项目结构检测

```bash
# 检测是否为 Maven 多模块项目
[ -f pom.xml ] && grep -q "<modules>" pom.xml && echo "MULTI_MODULE" || echo "SINGLE_MODULE"

# 列出所有模块
mvn -pl . -N ru.technonic:flatten-maven-plugin:0.0.1:resolve-gav || \
grep -oP '(?<=<module>).*?(?=</module>)' pom.xml

# 获取 Java 版本
grep -oP '(?<=<java.version>).*?(?=</java.version>)' pom.xml

# 获取 SpringBoot 版本
grep -oP '(?<=<spring-boot.version>).*?(?=</spring-boot.version>)' pom.xml
```

### Step 2: 目录结构扫描与分析

**⚠️ 这是最核心的步骤，必须仔细执行**

1. 递归扫描项目根目录及所有子模块目录
2. 列出完整的目录树结构
3. 对每个文件夹进行初步用途判断
4. 对无法确定的文件夹进行标记，准备咨询用户

### Step 4: 实体类数据结构梳理

**⚠️ 重点关注管理后台（后台/Admin）模块**

扫描以下路径的实体类：
- `**/entity/*.java`
- `**/domain/*.java`
- `**/model/*.java`
- `**/po/*.java`

**对于每个实体类，提取**：

| 提取项 | 说明 |
|--------|------|
| 类名 | 实体类名称 |
| 包路径 | 完整包路径 |
| 继承关系 | 继承的父类（如 BaseEntity） |
| 字段列表 | 所有字段及其类型、注解 |
| 数据库表名 | @TableName 注解值 |
| 关联关系 | 一对多、多对多等关系 |

**实体类文档模板**：

```markdown

### Step 5: RESTful API 接口梳理

**⚠️ 前后端分离项目必做**

**🔴 重要警示：禁止基于 RESTful 规范假设接口**

> **问题背景**：曾有一次，API 文档基于 RESTful 规范假设生成了 `deleteRule`, `updateRule`, `createRule` 等接口，但实际代码中这些接口并不存在。这导致文档与实际代码严重不符。

> **核心原则**：**必须 100% 基于实际代码生成 API 文档**，禁止基于 RESTful 约定俗成进行推测。

#### 5.1 扫描 Controller 文件

1. **查找所有 Controller**

```bash
# 查找所有 @RestController 注解的类
grep -r "@RestController" --include="*.java" src/

# 或使用 glob 模式
glob("**/controller/*.java")
```

2. **读取每个 Controller 文件**，提取：

| 提取项 | 来源 | 示例 |
|--------|------|------|
| 基础路径 | `@RequestMapping("api/v1/xxx")` | `api/v1/rule` |
| 请求方法 | `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` | `@PostMapping("/save")` |
| 完整路径 | 基础路径 + 方法路径 | `api/v1/rule/saveRule` |
| 请求参数 | `@RequestParam`, `@RequestBody`, `@PathVariable` | `@RequestParam("id") Long id` |
| 方法注释 | Javadoc 或方法上注释 | `更新某规则的状态` |

3. **⚠️ 必须验证**
   - 读取实际 Controller 源码
   - 核对每个接口的 HTTP 方法和路径
   - 确认请求参数名称和类型

#### 5.2 禁止的操作

| ❌ 禁止 | ✅ 正确 |
|---------|---------|
| 假设 `POST /api/rule` = createRule | 必须读取 Controller 源码确认 |
| 假设 `PUT /api/rule/{id}` = updateRule | 必须读取 Controller 源码确认 |
| 假设 `DELETE /api/rule/{id}` = deleteRule | 必须读取 Controller 源码确认 |
| 假设 RESTful 标准路径格式 | 必须以实际代码为准 |

## 7. 常见问题

### Q1: 如何判断模块职责？

**A**: 根据模块名和源码内容综合判断：
- 包含 `controller`/`web` → Web/API 层
- 包含 `service`/`app` → 业务逻辑层
- 包含 `dao`/`repository`/`mapper` → 数据访问层
- 包含 `common`/`util` → 公共基础层
- 包含 `infra`/`infrastructure` → 基础设施层
- 包含 `api`/`thrift`/`grpc` → 接口服务层

### Q2: 实体类太多怎么办？

**A**:
1. 优先扫描**管理后台**相关模块的实体类
2. 核心业务实体优先于边缘实体
3. 可以分批扫描，每次扫描一个模块

### Q3: API 接口如何分类？

**A**:
1. 按业务模块分类（如用户、订单、规则）
2. 按 Controller 类名归类
3. 使用 Swagger/OpenAPI 注解辅助判断

### Q4: API 文档与实际代码不符怎么办？

**🔴 这个问题非常严重，必须重视**

**问题表现**：
- 文档中的接口在代码中不存在
- 路径、方法、参数与实际代码不一致
- 基于 RESTful 规范假设接口，但实际代码未实现

**根本原因**：
- 使用了 Swagger/OpenAPI 扫描但未验证
- 基于 RESTful 约定俗成进行推测
- 未直接读取 Controller 源码

**✅ 正确做法**（必须遵守）：

1. **直接扫描源码**：使用 `glob("**/controller/*.java")` 找到所有 Controller
2. **读取每个 Controller 文件**：提取 `@RequestMapping`, `@GetMapping`, `@PostMapping` 等注解
3. **提取完整路径**：基础路径 + 方法路径，如 `api/v1/rule` + `/saveRule` = `api/v1/rule/saveRule`
4. **提取参数信息**：`@RequestParam("id") Long id` → 参数名 `id`，类型 `Long`
5. **禁止假设**：绝对不能因为 RESTful 规范就假设某个接口存在

**验证示例**：

```java
// ❌ 错误：假设存在 deleteRule 接口
// GET /api/rule → 文档写 "获取规则列表"
// POST /api/rule → 文档写 "创建规则"  
// DELETE /api/rule/{id} → 文档写 "删除规则"

// ✅ 正确：读取实际代码
// @RestController
// @RequestMapping("api/v1/rule")
// public class RuleController {
//     @PutMapping("/updateRuleStatus")  // 实际是 PUT，不是 DELETE
//     @PostMapping("/saveRule")        // 实际路径是 /saveRule
//     @GetMapping("/list")             // 实际是 /list
//     @GetMapping("/getRuleById")      // 实际是 getRuleById，不是 /{id}
//     // ❌ 没有 deleteRule 接口！
// }
```

**教训**：宁可少写接口，也不能写错接口。

### 分层架构

```
controller/ → 处理HTTP请求，参数校验 (@Valid)
     ↓
service/    → 业务逻辑处理，事务管理 (@Transactional)
     ↓
repository/ → 数据访问
     ↓
entity/    → 数据库实体映射
```

### Import 规范

```java
// 1. java/javax 包

```

### 代码规范

- **中文注释**: 所有代码注释必须简体中文
- **事务**: Service层必须加 `@Transactional`
- **参数校验**: Controller方法参数必须使用 `@Valid`
- **日志**: 使用 `@Slf4j`，`log.info()`/`log.error()` 记录业务日志，`log.debug()` 记录调试信息
- **异常**: 禁止吞掉异常，必须记录日志或抛出
- **硬编码**: 禁止硬编码，配置必须外置

### 日志规范

```java
// 正确
log.info("查询参数: name={}, id={}", name, id);
log.error("保存失败: {}", e.getMessage(), e);

// 禁止
log.info("查询参数: " + name);  // 字符串拼接
log.error("错误");             // 无变量
```

## ANTI-PATTERNS (零容忍)

- ❌ Controller直接操作数据库 → 必须通过Service层
- ❌ 重复造轮子 → 工具类必须复用已有代码
- ❌ 硬编码 → 配置必须外置到配置中心
- ❌ 吞掉异常 → 必须记录日志或抛出
- ❌ 循环依赖 → 模块间禁止循环引用
- ❌ 跨层调用 → 必须遵循调用链 controller→service→repository→entity
- ❌ 数据库连接信息硬编码 → 必须通过配置中心

# Guardians 项目 Test-After 单元测试执行规范

本规范定义了 Guardians 项目的 Test-After 单元测试全流程。**所有接口（Service/Controller）新增或修改后，必须按照本规范生成并通过单元测试。**

---

## 1. 适用场景

本规范在以下场景中自动触发：

| 场景 | 触发方式 |
|------|----------|
| OpenSpec apply 执行 `[测试]` 类型 task | config.yaml context 指示加载本规范 |
| 非 OpenSpec 路径直接开发接口 | AGENTS.md 红线规则要求执行测试 |

**触发条件**：任何接口（Service 方法 / Controller 端点）的新增或修改。

---

## 2. 测试文件路径推导

### 2.1 路径镜像规则

源文件 `src/main/` → 测试文件 `src/test/`，类名追加 `Test` 后缀。

```
源文件:
  guardians-web/src/main/java/com/xiaomi/infosec/risk/guardians/web/service/dict/impl/RiskDictItemServiceImpl.java

测试文件:
  guardians-web/src/test/java/com/xiaomi/infosec/risk/guardians/web/service/dict/impl/RiskDictItemServiceImplTest.java
```

### 2.2 模块映射

| 源码模块 | 测试目录 |
|----------|----------|
| `guardians-web/src/main/java/...` | `guardians-web/src/test/java/...` |
| `guardians-app/src/main/java/...` | `guardians-app/src/test/java/...` |
| `guardians-rule-engine/src/main/java/...` | `guardians-rule-engine/src/test/java/...` |
| `guardians-infra/src/main/java/...` | `guardians-infra/src/test/java/...` |
| `guardians-data-assemble/src/main/java/...` | `guardians-data-assemble/src/test/java/...` |
| `guardians-common/src/main/java/...` | `guardians-common/src/test/java/...` |

## 3. 测试策略选择

### 3.1 判断规则

```
被测类是否有 @Autowired / @Resource 注入？
  │
  ├── YES → 依赖 Spring 容器（DB/Redis/RPC）
  │         → 使用 @SpringBootTest
  │
  └── NO  → 纯逻辑类
            → 使用 @ExtendWith(MockitoExtension.class) 或直接 new
```

### 3.2 @SpringBootTest 模板

```java
package com.xiaomi.infosec.risk.guardians.web.service.xxx.impl;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import static org.junit.jupiter.api.Assertions.*;

/**
 * XxxServiceImpl 单元测试
 */
@SpringBootTest
class XxxServiceImplTest {

    @Autowired
    private XxxServiceImpl xxxService;

    /**
     * 测试新增 xxx - 正常路径
     */
    @Test
    void testAddXxx_Success() {
        // 准备测试数据
        // 执行被测方法
        // 断言结果
    }

    /**
     * 测试新增 xxx - 异常路径（参数为空）
     */
    @Test
    void testAddXxx_NullParam_ThrowsException() {
        assertThrows(BusinessException.class, () -> {
            xxxService.addXxx(null);
        });
    }
}
```

### 3.3 Mockito 模板（纯逻辑类）

```java
package com.xiaomi.infosec.risk.guardians.rule.engine.engine.service.operator;

/**
 * Xxx 算子单元测试
 */
class XxxTest {

    private Xxx xxx;

    @BeforeEach
    void setUp() {
        xxx = new Xxx();
    }

    @Test
    void testRun_NormalInput_ReturnsExpected() {
        // 测试逻辑
    }
}
```

## 4. Mock 边界规则

### 4.1 核心原则

| 类别 | Mock 策略 | 原因 |
|------|-----------|------|
| **本次需求改动的逻辑** | **禁止 Mock** | 必须验证真实业务逻辑 |
| 无关但必须的外部依赖 | 允许 Mock | 保证测试可运行 |
| 用户提供的测试数据 | 优先使用 | 最贴近真实场景 |

### 4.2 Mock 示例

```java
// 本次需求：新增 addDictItem 方法
// addDictItem 内部调用了一个无关的 RPC 获取用户信息

@SpringBootTest
class RiskDictItemServiceImplTest {

    @Autowired
    private RiskDictItemServiceImpl dictItemService;

    @MockBean  // Mock 无关外部依赖
    private UserInfoRpcService userInfoRpcService;

    @Test
    void testAddDictItem_Success() {
        // Mock 无关依赖的返回值
        when(userInfoRpcService.getUserInfo(anyLong()))
            .thenReturn(new UserInfo("testUser"));

        // 直接调用本次需求的核心方法（不 Mock）
        Long id = dictItemService.addDictItem(request);

        assertNotNull(id);
    }
}
```

### 4.3 测试数据构造

优先级：
1. **用户提供的测试数据** → 直接使用
2. **基于方法签名自动构造** → 根据参数类型、字段名、约束条件构造合理数据
3. **最小化数据** → 仅构造满足测试所需的最少字段

## 5. 执行流程

### 5.1 完整流程图

```
接口实现完成
     │
     ▼
[步骤 1] 推导测试文件路径
     │
     ▼
[步骤 2] 判断测试策略（@SpringBootTest / Mockito）
     │
     ▼
[步骤 3] 生成/更新测试文件
     │  - 文件不存在 → 创建新文件
     │  - 文件已存在 → 追加测试方法（不覆盖已有）
     │  - 已有同名方法 → 更新该方法内容
     │
     ▼
[步骤 4] 执行测试
     │  mvn test -pl <module> -Dtest=<TestClassName>
     │
     ├── 通过 ──→ 标记 task 完成，继续下一个 task
     │
     ├── 失败（逻辑错误）
     │   │
     │   ▼
     │  [步骤 5] 分析失败原因
     │   │  - 读取测试输出的错误信息
     │   │  - 判断是实现代码 bug 还是测试代码 bug
     │   │
     │   ▼
     │  [步骤 6] 修复代码
     │   │  - 修复实现代码或测试代码
     │   │  - 回到步骤 4 重新执行
     │   │  - 最多循环 3 次
     │   │
     │   └── 3 次仍失败 ──→ [步骤 7] 暂停并报告
     │                      输出：失败详情、分析报告、修复尝试记录
     │                      等待用户决策
     │
     └── 失败（基础设施连接错误）
         │  DB/Redis/RPC 连接超时或拒绝
         │
         ▼
        [步骤 8] 通知用户
         │  "DB/Redis 连接失败，是否切换为 Mockito Mock 策略？"
         │
         ├── 用户选择 Mock ──→ 重新生成测试（Mockito），回到步骤 4
         └── 用户选择跳过 ──→ 标记为"需人工验证"，继续下一个 task
```

### 5.2 测试执行命令

```bash
# 执行单个测试类（推荐，快速反馈）
mvn test -pl <module> -Dtest=<TestClassName>

# 示例
mvn test -pl guardians-web -Dtest=RiskDictItemServiceImplTest

# 执行单个测试方法
mvn test -pl <module> -Dtest=<TestClassName>#<methodName>

# 示例
mvn test -pl guardians-web -Dtest=RiskDictItemServiceImplTest#testAddDictItem_Success
```

### 5.3 失败分析要点

| 错误类型 | 特征 | 处理方式 |
|----------|------|----------|
| 断言失败 | `AssertionError`, `expected:<X> but was:<Y>` | 检查实现逻辑或测试预期值 |
| 空指针 | `NullPointerException` | 检查依赖注入或测试数据构造 |
| 编译错误 | `cannot find symbol`, `incompatible types` | 检查 import 和方法签名 |
| 连接失败 | `ConnectionRefused`, `Timeout`, `Cannot get Jedis` | 基础设施问题，通知用户 |
| Bean 加载失败 | `NoSuchBeanDefinition`, `UnsatisfiedDependency` | 检查 @MockBean 或 Spring 配置 |

## 7. 与 OpenSpec 流程的集成

### 7.1 tasks.md 中的测试 task 格式

```markdown
- [ ] X.N [测试] 生成 XxxServiceImplTest，覆盖 methodName 正常/异常分支
- [ ] X.N+1 [测试] 执行 mvn test -Dtest=XxxServiceImplTest，确认通过
```

### 7.2 apply 执行时的行为

当 apply 流程遇到 `[测试]` 前缀的 task 时：
1. 加载本规范（`/dev-tdd`）
2. 按照第 5 节的完整流程执行
3. 测试通过后勾掉 task，继续

---

**测试是开发完成的最后一道门，通过才算完成。**
┌──────────────────────────────────────────────────────────────┐
│  Layer 1: AGENTS.md（全局意识注入）                           │
│  → 红线规则："每个接口新增/修改，必须有测试，且测试必须通过"     │

├──────────────────────────────────────────────────────────────┤
│  Layer 3: dev-tdd SKILL.md（执行行为定义）                    │

│  → apply 执行到 [测试] task 时，按此规范执行                  │
└──────────────────────────────────────────────────────────────┘

本方案本质上沿用了之前「Rules 定义红线，Skills 提供详情」的思路，再加了一层 config.yaml 的任务生成约束，形成了三层闭环。

  • 走 OpenSpec 开发：三层全部生效（意识 + 生成 + 执行）
  • 非 OpenSpec 直接开发：至少第一层 AGENTS.md 生效（兜底）
