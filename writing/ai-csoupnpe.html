此处仅简述个别 AI相关概念。

核心基石：什么是 Agent（智能体）？

💡

Agent = 大脑 (LLM) + 记忆(Memory) + 手脚 (MCP) + 眼口(VL-多模态) + 工程技能（Skill）

Agent是智能体、是代理、是助理、是 “人”。

AI技术的演进，正是将一个 “嗷嗷待哺的婴儿Agent”，逐步培养成一个 “有记忆、有底线、有能力的成熟Agent” 的过程。

可以说，我们正在见证着“一种生命的诞生和进化”，这种生命，人类暂且称之为 Agent。

Agent进化史：

LM(Language Model - 语言模型)：起源。

-> LLM：模型参数不断变大，突然涌现出“智慧”，就有了大脑，婴儿Agent诞生

-> Memory(短期Context、长期KV、专业RAG)：有了记忆，问答Agent开始泛滥

-> VL多模态(Vision-Language)：有了眼睛、嘴巴，通用Agent蓝图展开，并开始入侵现实世界。

-> MCP：有了手脚，Agent与外部数据源之间连接规则标准化，成本骤降，Agent快速进化。

-> Rules：有了生存规矩，Agent懂得了“遵守规则”。

-> SKILL：有了操作手册(SOP)，Agent“做事更快更专业”。面向人类的操作手册叫SOP，面向Agent的操作手册则称之为 SKILL。

-> 再然后然后，

有人综以上所能，放开ROOT权限、打通便捷操作入口(TG、飞书)、赋予灵魂(SOUL.md)，尝试将“贾维斯”搬到现实世界，打造了一款超级Agent，现在我们将其称之为：

“🦞龙虾(OpenClaw)”

💡

这里还想聊一下AI的“智慧”，先说结论：没有智慧，只有预测，AI智慧 = 庞大的知识库 + 算法预测。

归其本质，基于Transformer架构的生成式大模型，底层能力都是预测。@AI 发展-自顶向下

如：人类输入： 12345，模型预测并返回：6789。

如：人类输入： 窗前明月光，模型预测并返回：疑是地上霜。

那么所谓的“智慧”是怎么来的，其实这都归功于 大数据语料、上下文管理(Context Management)。

先聊一下人们为什么觉得AI有了智慧，我想基本是因为以下这两点：

  1. 人们发现AI上知天文，下知地理。 -> 归功于 “庞大的训练语料库”。
  1. 与AI对话上百轮，人们发现AI能记住聊过的信息，有了“记忆”、有了“温度”？->归功于 “上下文管理”。

第一点容易理解，第二点我觉得有展开聊聊的必要：「上下文管理做了什么，才让人类觉得AI有了记忆、智慧？」

上下文(Context)简单理解：其实就是 1次请求时塞给模型的最终输入。

那么上下文管理( Context Management) 如何理解，举个例子(代入下平时与豆包的问答场景)：

假设：

我问一句1，豆包答11；我再问一句2，豆包答一句22。。。。。。这样一直到第100轮，我问了100次，豆包答了100次。同样的，豆包模型输入/输出了100次。

那每一次豆包模型的输入是什么？

常规直觉来看，豆包模型的输入不就是人类每次的输入信息(Prompt)吗？实则不是。

而是：

  • 第一次输入是「用户问1.」
  • 第二次输入是「用户问1，豆包回答11，用户问2」
  • 第三次输入是「用户问1，豆包回答11，用户问2，豆包回答22，用户问3」

.......

  • 到第100次输入是「用户问1，豆包回答11 ...........用户问9，豆包回答99，用户问100」

这个例子中：

用户单次的输入我们称之为 Prompt，而可以看到每一次给模型的最终输入是 随着对话轮次，不断累加的，累加后的结果我们称之为 Contex(上下文)。

这种 Context 管理方法则称之为 Context Management。

随着对话轮次不断上升（1w次、10w次、1kw次....），Context将会变得十分庞大，这个时候模型无法处理这么庞大的单次输入，达到了 Context(上下文窗口) 的极限。

因此可以看出：

每一轮问答之间，模型是无感知、无记忆的，只是人类通过 Context Management，通过对Context的系统化管理，利用Context这个 “中间件/输入载体”，在 人类输入 和 模型输入 加了一层缓冲区，达到了 “用户层面感知到AI有记忆”的假象，人们才觉得AI有了智慧。

把模型理解为："输入" -> 黑盒逻辑 -> "输出"

DeepSeek V4已支持 1M token 的上下文。

💡

什么？你问我什么是token？-> 速速去看：@AI 发展-自顶向下

可视化理解下Token：可视化Tokenizer工具（需要🪜）

  • 宏观理解：Token是AI语言的最小单位，类比下：中国人语言的最小单位是单个汉字、英语人语言的最小单位是单个字母。
  • 微观理解：Token可能是单个汉字、也可能是1个词组、也可能是1个英语单词、也可能是半个英语单词（unhappiness 可能会被切分为 un + happi + ness 3个 Token）。

模型底层只是一台超大型计算器，它没法直接处理“人类世界的语言”。因此我们需要通过 Tokenizer（分词器） 把各种文字切成一堆 Token，再把 Token 转化成数字向量，AI 才能开始它的“预测”。

基本概念： MCP、Rules、Skills

推荐文章：一文读懂 Skills｜从概念到实操的完整指南

  • Prompt(提示词)：人类的输入。
  • Context(上下文)：模型收到的输入，受模型能力限制有长度限制，如 100k、200k......

  • 接入MCP后，大模型可以通过“提示词匹配”，选择性调用MCP提供的Tools，这些Tool是业务自定义的能力，可读、可写、可听、可说。因此我们说：MCP给AI装上了手和脚。

  • 开发同学 RPC协议。

  • Rules：全局宪法、规范、红线。告诉AI"不能做什么、必须做什么"（比如：不能删库、注释必须用中文）。
  • Skills：面向AI的工程化SOP，流程说明书。
💡

Rules、Skills 本质上都是Prompt(提示词)，都属于“提示词工程”的一部分。

但实现细节不同：

  • Rules通过「粗暴式塞入提示词开头/结尾」(因为 Lost-In-Middle)，达到全局性强约束AI的目的。
  • Skills采用「渐进式披露」机制，在尽可能减少Token消耗、减缓上下文膨胀速度 的目的下，教给AI SOP。

MCP & Skills

有人常问这两怎么理解、区分、有没有案例能快速讲解搞懂，所以在这里给大家快速过一遍，以及跟大家聊聊我对这两个东西的看法。

@MCP开发指南(Java) - 组内

Skill：是提供给大模型的一套标准工作流程(SOP)，用于「指导大模型 将事做得更专业」。

MCP：是一种大家共识的 标准/协议 ，用于 「大模型 与 外部业务」交互。

MCP是怎么来的？

在AI发展早期，各家大模型公司在探索AI应用时，需要给AI装上自己业务的接口，让AI连接、使用业务能力，这就是Function Calling。

多家公司合作时，也是这样的场景，若A公司需要给模型装上B公司的业务能力，需要B公司定制1个Function交给A去Call，反过来也是一样。长期以往，成本就很高了，A有A的Function格式、B有B的Function格式(Json Schema)。。。。。。。。

后来有一家公司(Anthropic)觉得这样成本太高，于是在2024年底推出了协议，尝试将Function格式标准化，这个协议就是 MCP。

开发同学 Function Calling 与 MCP 形象类比为：本地函数 & RPC。

MCP仅是协议，真正干事的是 tools_call(工具调用)，我们常说的 "接了1个MCP"，其实指的是将此MCP server包含的所有tools信息注册到了大模型的上下文中，大模型在感知到用户需要调用此tool时，就会走tools_call。

个人看法： 随着 Context 管理变得越来越昂贵且核心，任何不支持“渐进式披露”的协议都会在生产环境中被淘汰。未来赢家一定是那些能让模型 “只在需要时，才知道该知道的事” 的框架。

MCP是AI发展的过程产物，其在出世初期确实促进了Agent的发展，因为其极大降低 Agent与外部业务的交互成本；

但随着AI快速发展、Context Management 变得越来越核心，「MCP tools全部加载到Context的逻辑」对于当前阶段的Agent来说、与Skill的「渐进式披露机制」相比，太重了。因为即便不使用MCP，其全部tools信息也会加载到模型Context中，这无疑是严重污染Context、进而影响模型能力的(幻觉)。

因此OpenClaw的创造者没有用在🦞中内置MCP能力，仅用TOOLS.md去管理工具调用。

再者说，MCP其实是可以被Skill平替的，或许随着AI发展，会有更好的符合「渐进式披露思想」的MCP Plus出来。

### Step 5: RESTful API 接口梳理

**⚠️ 前后端分离项目必做**

**🔴 重要警示：禁止基于 RESTful 规范假设接口**

> **问题背景**：曾有一次，API 文档基于 RESTful 规范假设生成了 `deleteRule`, `updateRule`, `createRule` 等接口，但实际代码中这些接口并不存在。这导致文档与实际代码严重不符。

> **核心原则**：**必须 100% 基于实际代码生成 API 文档**，禁止基于 RESTful 约定俗成进行推测。

#### 5.1 扫描 Controller 文件

1. **查找所有 Controller**

```bash
# 查找所有 @RestController 注解的类
grep -r "@RestController" --include="*.java" src/

# 或使用 glob 模式
glob("**/controller/*.java")
```

2. **读取每个 Controller 文件**，提取：

| 提取项 | 来源 | 示例 |
|--------|------|------|
| 基础路径 | `@RequestMapping("api/v1/xxx")` | `api/v1/rule` |
| 请求方法 | `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` | `@PostMapping("/save")` |
| 完整路径 | 基础路径 + 方法路径 | `api/v1/rule/saveRule` |
| 请求参数 | `@RequestParam`, `@RequestBody`, `@PathVariable` | `@RequestParam("id") Long id` |
| 方法注释 | Javadoc 或方法上注释 | `更新某规则的状态` |

3. **⚠️ 必须验证**
   - 读取实际 Controller 源码
   - 核对每个接口的 HTTP 方法和路径
   - 确认请求参数名称和类型

#### 5.2 禁止的操作

| ❌ 禁止 | ✅ 正确 |
|---------|---------|
| 假设 `POST /api/rule` = createRule | 必须读取 Controller 源码确认 |
| 假设 `PUT /api/rule/{id}` = updateRule | 必须读取 Controller 源码确认 |
| 假设 `DELETE /api/rule/{id}` = deleteRule | 必须读取 Controller 源码确认 |
| 假设 RESTful 标准路径格式 | 必须以实际代码为准 |

#### 5.3 常见错误对照表

| 错误假设（文档） | 实际情况（代码） |
|-----------------|-----------------|
| `POST /api/user` | `POST /api/v1/user/add` |
| `GET /api/rule/{id}` | `GET /api/v1/rule/getRuleById?id=xxx` |
| `DELETE /api/rule/{id}` | **不存在此接口** |
| `PUT /api/rule/{id}` | `PUT /api/v1/rule/updateRuleStatus` |

**文件路径**: `风控平台-web/src/main/java/com/公司/risk/risk/风控平台/web/controller/RuleController.java`

## 7. 常见问题

### Q1: 如何判断模块职责？

**A**: 根据模块名和源码内容综合判断：
- 包含 `controller`/`web` → Web/API 层
- 包含 `service`/`app` → 业务逻辑层
- 包含 `dao`/`repository`/`mapper` → 数据访问层
- 包含 `common`/`util` → 公共基础层
- 包含 `infra`/`infrastructure` → 基础设施层
- 包含 `api`/`thrift`/`grpc` → 接口服务层

### Q2: 实体类太多怎么办？

**A**:
1. 优先扫描**管理后台**相关模块的实体类
2. 核心业务实体优先于边缘实体
3. 可以分批扫描，每次扫描一个模块

### Q3: API 接口如何分类？

**A**:
1. 按业务模块分类（如用户、订单、规则）
2. 按 Controller 类名归类
3. 使用 Markdown 表格格式组织（参考 `4-api/api-modules.md`）

### Q4: API 文档与实际代码不符怎么办？

**🔴 这个问题非常严重，必须重视**

**问题表现**：
- 文档中的接口在代码中不存在
- 路径、方法、参数与实际代码不一致
- 基于 RESTful 规范假设接口，但实际代码未实现

**根本原因**：
- 使用了 Swagger/OpenAPI 扫描但未验证
- 基于 RESTful 约定俗成进行推测
- 未直接读取 Controller 源码

**✅ 正确做法**（必须遵守）：

1. **直接扫描源码**：使用 `glob("**/controller/*.java")` 找到所有 Controller
2. **读取每个 Controller 文件**：提取 `@RequestMapping`, `@GetMapping`, `@PostMapping` 等注解
3. **提取完整路径**：基础路径 + 方法路径，如 `api/v1/rule` + `/saveRule` = `api/v1/rule/saveRule`
4. **提取参数信息**：`@RequestParam("id") Long id` → 参数名 `id`，类型 `Long`
5. **禁止假设**：绝对不能因为 RESTful 规范就假设某个接口存在

**验证示例**：

```java
// ❌ 错误：假设存在 deleteRule 接口
// GET /api/rule → 文档写 "获取规则列表"
// POST /api/rule → 文档写 "创建规则"  
// DELETE /api/rule/{id} → 文档写 "删除规则"

// ✅ 正确：读取实际代码
// @RestController
// @RequestMapping("api/v1/rule")
// public class RuleController {
//     @PutMapping("/updateRuleStatus")  // 实际是 PUT，不是 DELETE
//     @PostMapping("/saveRule")        // 实际路径是 /saveRule
//     @GetMapping("/list")             // 实际是 /list
//     @GetMapping("/getRuleById")      // 实际是 getRuleById，不是 /{id}
//     // ❌ 没有 deleteRule 接口！
// }
```

**教训**：宁可少写接口，也不能写错接口。

AGENT知识库 简解

业务知识库接入参考：@私域知识接入 v2：让 AI 理解并使用你的业务文档

AGENT知识库的结构与后边方案迭代息息相关，但核心思路是不变的。。

【选看】开发规范-探索：Rules or Skills？

开发规范：是指在每一次需求开发时，AI必须遵守的默认规则，不得跳过。

一个比较重要的卡点问题：OpenSpec的开发范式下，开发规范应该放在哪里：Rules or Skills？

Rules实现 - 拉完了

优点显而易见：

Rules作为全局规则(或在Spec-kit中称为“宪法”)，当用户提问，Agent会自动读取Rules内容，将其注入到 System Prompt，作为前置上下文，再结合用户提问给出回复。

因此在Rules中保存开发约束规范，可以100%保证遵守现有规范。

缺点也随之而来：

当开发约束规范越来越长，Rules的内容越来越多，带来的是：

  1. Token消耗量的上升 （钱哗哗向外流。。。）
  1. 被轻松撑满的Context（想象一下每次对话Rules都要在你开头插入一些有的没的。。。）
  1. “注意力稀释”（Attention Dilution）：当 System Prompt 过长且包含大量细碎规则时，LLM 对每一条规则的遵循度会下降，产生“幻觉”或忽略部分指令（尤其是“中间”的指令，即 Lost-in-the-Middle 现象）。

Skills实现 - 人上人

优点：解决Rules Token消耗、Context消耗的痛点

Skills由于其“渐进式披露”的加载机制，似乎能解决Rules Token消耗、Context消耗的痛点。日常场景当然可以，毕竟这是Skill的使命之一。

缺点：用户使用成本上升、规范遵守确定性模糊

但别忘了我们当前使用的是OpenSpec开发范式。这是什么意思呢？见下示例。

假设我们已有1个开发约束规范dev-checklist Skill，此时若：

  • 若纯粹的vibe-coding开发：直接 /dev-checklist 起手显式调用此Skill，进行需求开发。

  • 并且提高了用户的输入成本，体验大打折扣。

  • 实际从Skill原理来讲，即便明示指定使用此Skill，AI也不一定100%遵守成功。

    Skill命令触发是最稳妥的方案。

最终方案1：Rules 引导遵循 Skills- 夯

既然 Rules 太重，Skills 太弱，我们需要结合两者的优势：“Rules 定义红线，Skills 提供详情” ：

  1. Skill：记录详尽的开发约束规范，可迭代。
  1. Rules：记录项目核心全局约束规则，且 强制要求「进行OpenSpec开发时，读取并严格遵循开发约束规范Skill。」

最终方案2：Skills + OpenSpec指令魔改 - 夯爆了

这是一种更加强劲的约束限制，「最终方案1」是Rules文字约束，不是技术强制，依赖于 AI 自律，而AI 可能选择性忽略，直接开始编码 ❌

Q2：增量需求change开发时，AI遵守Specs/的机制是什么？是怎么遵守这些过去的项目规范的？

答：

AI 不是“自觉”去遵守的，而是被 OpenSpec 机制“强迫”去遵守的。

当你在 changes/ 目录下新建一个需求（比如：/opsx-propose 新增一个微信支付风控策略）时，底层的 AI 会经历以下几个强制性步骤：

  1. RAG 检索唤醒

当你下达指令的一瞬间，Agent 并不是直接开始写代码，而是先启动内部的 RAG（检索增强生成）引擎。它会把你那句“微信支付风控策略”，拿到 specs/ 目录下去做向量检索，把相关的原始规范（比如：现有的风控策略表结构、策略拦截类的继承接口）全部“捞”出来，塞进它的短期记忆（Context）里。

  1. 对齐Specs下的定制契约

在生成当前 Change 的 plan.md（设计方案）时，因为 specs/ 的内容已经被强制注入了上下文，AI 就会知道我们定制的Specs：风控规则.md、工具类.md。

这时候，它的方案就不会天马行空地自己乱写一套新标准，而是严丝合缝地贴合你老项目的规范。这就是为什么在你的实战中，能做到“增量需求开发尽可能复用现有能力”。

再看看底层实现细节：

一、 提案/设计阶段（/opsx-propose 或 /opsx-plan）

当你提出一个新需求，要求系统生成 design.md 和 tasks.md 时，底层执行的 Skill（如 openspec-propose）并不会直接把你的话丢给 LLM。

约束的体现位置：指令查询系统 (openspec instructions 命令)

在 openspec-propose 的底层 Skill 源码中，有这样一段硬逻辑：

获取当前要生成的工件的强约束指令：openspec instructions <artifact-id> --change "<name>" --json

这个底层的 CLI 命令返回的 JSON 包含了针对当前正在生成的文件（比如 design.md）的强制约束参数：

  1. dependencies (前置依赖工件)：如果 OpenSpec 的状态机判断当前正在生成的是设计或任务，它会强制要求读取已有的 Specs 规范作为前置依赖。
  1. context (上下文约束)：这里面就会把你写在 config.yaml 里的项目规范（比如技术栈、语言要求、现有系统架构）作为系统级前置约束（System Constraints）强制塞入 Prompt。

结论：在生成设计和任务前，OpenSpec 工具链通过 CLI 会把项目原有的 specs/ 核心内容和 config.yaml 的约束打包，强行变成 AI “生成动作”的前提条件。如果 AI 生成的设计与这些强注入的上下文冲突，就会被视为幻觉。

二、 落地执行阶段（/opsx-apply）

到了真正要敲代码、改文件的阶段，也就是执行 tasks.md 里的任务时，AI 也是被“带着脚镣跳舞”的。

约束的体现位置：执行上下文组装 (contextFiles)

在 openspec-apply-change 这个 Skill 中，第一步是获取“怎么干活”的指令：

openspec instructions apply --change "<name>" --json

这个命令会返回一个极其重要的字段：contextFiles。

  • 如果是 spec-driven 模式，这个 contextFiles 数组里，会强制包含 proposal, specs, design, tasks 等文件路径。
  • 紧接着，Skill 脚本里有一个硬性的规则锁（Guardrails）：

> "Always read context files before starting" (开始执行任务前，必须永远先读取上下文文件)

这意味着什么？

当 AI 准备开始写代码时，它被工具链强迫必须先去执行 Read 工具，把 contextFiles 里的内容（即规范、设计、任务拆解）完完整整地读一遍，装载到它当下的短期记忆里，然后才被允许执行 Write 或 Edit 工具去修改你的业务代码。

总结：强制约束的技术本质

如果你需要在分享中向大家解释这个“强迫”的过程，可以用这三个词来概括：

  1. 链路阻断 (Pipeline Blocking)：在没有读取 Specs 规范前，OpenSpec 的状态机不允许进入下一个环节。
  1. 动态指令下发 (openspec instructions)：这不是一个静态的 Prompt，而是每前进一步，CLI 引擎都会根据当前状态，把需要遵守的规范像“锦囊”一样强行塞给 AI。
  1. 读前写后锁 (Read-before-Write Lock)：在实际编码（Apply）阶段，底层 Skill 强制规定了“不读 Context（包含 Specs）不准写代码”的死规矩。

这就是“规范驱动”能在工程上真正落地的底层保障！它把规范从“人类口头传达”变成了“机器底层工作流的前置依赖”。

⭐️ 最终方案： 三层机制 强制保障流程闭环

现在业内还有一种非常野蛮的方法，极致的“测试驱动开发”：

首先生成需求的完整测试用例，再让AI执行，error后让AI自行修复，error修复且测试通过后，即视为需求开发完成。

## ANTI-PATTERNS (零容忍)

- ❌ Controller直接操作数据库 → 必须通过Service层
- ❌ 重复造轮子 → 工具类必须复用已有代码
- ❌ 硬编码 → 配置必须外置到配置中心
- ❌ 吞掉异常 → 必须记录日志或抛出
- ❌ 循环依赖 → 模块间禁止循环引用
- ❌ 跨层调用 → 必须遵循调用链 controller→service→repository→entity
- ❌ 数据库连接信息硬编码 → 必须通过配置中心

## 4. Mock 边界规则

### 4.1 核心原则

| 类别 | Mock 策略 | 原因 |
|------|-----------|------|
| **本次需求改动的逻辑** | **禁止 Mock** | 必须验证真实业务逻辑 |
| 无关但必须的外部依赖 | 允许 Mock | 保证测试可运行 |
| 用户提供的测试数据 | 优先使用 | 最贴近真实场景 |

**核心链路定义**：HTTP/RPC/DB/Redis 的调用与查询属于核心链路，**必须真实执行，禁止 Mock**。

**数据 Mock 定义**：仅允许对入口方法的**入参**进行构造与模拟，禁止对核心链路返回值做 Mock。

### 4.2 Mock 示例

```java
// 本次需求：新增 addDictItem 方法
// addDictItem 内部调用了一个无关的 RPC 获取用户信息

@SpringBootTest
class RiskDictItemServiceImplTest {

    @Autowired
    private RiskDictItemServiceImpl dictItemService;

    @MockBean  // Mock 无关外部依赖
    private UserInfoRpcService userInfoRpcService;

    @Test
    void testAddDictItem_Success() {
        // Mock 无关依赖的返回值
        when(userInfoRpcService.getUserInfo(anyLong()))
            .thenReturn(new UserInfo("testUser"));

        // 直接调用本次需求的核心方法（不 Mock）
        Long id = dictItemService.addDictItem(request);

        assertNotNull(id);
    }
}
```

### 4.3 测试数据构造

优先级：
1. **用户提供的测试数据** → 直接使用
2. **基于方法签名自动构造** → 根据参数类型、字段名、约束条件构造合理数据
3. **最小化数据** → 仅构造满足测试所需的最少字段

| Mock 边界 | 核心逻辑不 Mock，无关依赖可 Mock |
| log.debug() 节点 | `[TEST-START]` / `[TEST-INPUT]` / `[TEST-OUTPUT]` / `[TEST-END]` |
| 归档文件 | `openspec/changes/<name>/test-records.md` |

**测试是开发完成的最后一道门，通过才算完成。**
┌──────────────────────────────────────────────────────────────┐
│  Layer 1: AGENTS.md（全局意识注入）                           │
│  → 红线规则："每个接口新增/修改，必须有测试，且测试必须通过"     │
│  → 不管走不走 OpenSpec，AI 每次对话都读到这条规则              │
├──────────────────────────────────────────────────────────────┤
│  Layer 2: openspec/config.yaml（任务生成约束）                │
│  → rules.tasks：含接口改动的任务组，自动包含 [测试] 子任务     │
│  → 结果：tasks.md 里测试变成显式 checkbox，apply 执行时跳不掉  │
├──────────────────────────────────────────────────────────────┤
│  Layer 3: dev-tdd SKILL.md（执行行为定义）                    │
│  → 定义"怎么做"：路径推导、策略选择、Mock 边界、执行循环        │
│  → apply 执行到 [测试] task 时，按此规范执行                  │
└──────────────────────────────────────────────────────────────┘
💡

本方案本质上沿用了之前「Rules 定义红线，Skills 提供详情」的思路，再加了一层 config.yaml 的任务生成约束，形成了三层闭环。

  • 非 OpenSpec 直接开发：至少第一层 AGENTS.md 生效（兜底）

## 注意事项

1. **链接使用相对路径**：`../风控平台` 而非绝对路径，这样整个 My_projects 目录迁移后链接仍然有效

## 🎯 核心技术方案

### 1. MyBatis-Plus 多数据源配置

**挑战**: 需要同时访问两个独立的 MySQL 数据库（风控平台 + captcha）

**方案**:
```java
// 主数据源 - @Primary + @Mapper 自动扫描
@Bean(name = "primaryDataSource")
@Primary
@ConfigurationProperties(prefix = "spring.datasource.primary")
public DataSource primaryDataSource() { ... }

// 从数据源 - @MapperScan 显式扫描
@Configuration
@MapperScan(
    basePackages = "com.example.risk.risk.风控平台.web.mapper.captcha",
    sqlSessionFactoryRef = "captchaSqlSessionFactory"
)
public class CaptchaDataSourceConfig { ... }
```

**关键点**:
- ✅ 主数据源标记 `@Primary`，其他 Mapper 自动关联
- ✅ 从数据源使用 `@MapperScan` 指定包路径和 SqlSessionFactory
- ✅ 每个数据源独立的 TransactionManager

### 2. KeyCenter 自动解密配置

**挑战**: 数据库账号密码使用公司内部 KeyCenter 加密，需要运行时解密

**方案**:
```yaml
spring:
  datasource:
    primary:
      username: ${risk.风控平台.db.username}     # 明文
      password: ${risk.风控平台.db.password}     # 密文
      password@kc-sid: ${kc.sid}                  # 标记自动解密
    
    captcha:
      username: ${captcha.db.username}            # 密文
      username@kc-sid: ${kc.sid}                  # 标记自动解密
      password: ${captcha.db.password}            # 密文
      password@kc-sid: ${kc.sid}                  # 标记自动解密
```

**关键点**:
- ✅ 使用 `<field>@kc-sid: ${kc.sid}` 标记需要解密的字段
- ✅ Spring Boot 启动时自动调用 KeyCenter SDK 解密
- ✅ 无需在代码中手动调用 `KeycenterHelper.decryptNoCompress()`
- ✅ 使用 `@ConfigurationProperties` 自动绑定即可

### 3. JSON 字段存储

// 自定义 TypeHandler
public class JsonTypeHandler extends BaseTypeHandler<Object> {

### 问题 1: MyBatis-Plus 与 MyBatis 版本冲突 ⭐⭐⭐⭐⭐

**现象**:
```
NoClassDefFoundError: MybatisXMLMapperBuilder
NoSuchMethodError: parsePendingMethods
```

**根本原因**:
- MyBatis-Plus 3.5.7 官方依赖 MyBatis 3.5.16

1. **父 POM 锁定版本**（`backend/pom.xml`）:

<dependencyManagement>

            <groupId>org.mybatis</groupId>
            <artifactId>mybatis</artifactId>
            <version>3.5.16</version>
        </dependency>
        <!-- 锁定 MyBatis-Plus 3.5.7 全家桶 -->
        <dependency>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-boot-starter</artifactId>
            <version>3.5.7</version>
        </dependency>
        <!-- 其他 MyBatis-Plus 模块 -->
    </dependencies>
</dependencyManagement>
```

2. **模块 POM 排除冲突依赖**（`风控平台-web/pom.xml`）:

<dependency>

        <exclusion>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-boot-starter</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

### 问题 2: Windows 命令行长度限制 ⭐⭐⭐⭐

**现象**:
```
CreateProcess error=206, 文件名或扩展名太长
```

**根本原因**:
- Maven 执行 `java.exe` 时，classpath 参数超过 Windows 32KB 限制

**解决方案**:

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>

    <configuration>
        <fork>true</fork>
        <useTestClasspath>false</useTestClasspath>
    </configuration>
</plugin>
```

**原理**:
- `fork=true`: 在独立 JVM 进程中运行，使用 manifest 文件传递 classpath
- `useTestClasspath=false`: 避免包含测试类路径

**重要性**: ⭐⭐⭐⭐（Windows 环境必须配置）

## 🎓 开发经验总结

### 最佳实践

1. **依赖版本管理**
   - ✅ 使用父 POM `<dependencyManagement>` 锁定版本
   - ✅ 子模块使用 `<exclusions>` 排除冲突依赖
   - ✅ 重大升级后清理本地 Maven 缓存

2. **多数据源配置**
   - ✅ 主数据源使用 `@Primary` + 自动扫描
   - ✅ 从数据源使用 `@MapperScan` 显式指定
   - ✅ 每个数据源独立的 SqlSessionFactory 和 TransactionManager
   - ✅ 使用 `jdbc-url` 而非 `url`（HikariCP 要求）

3. **接口设计**
   - ✅ 前后端路径规范统一（先设计契约）
   - ✅ 前端使用相对路径 + 全局 baseURL
   - ✅ 后端使用完整路径 `/api/v1/{module}/{resource}`
   - ✅ 响应格式统一：`{code, data, message}`

4. **代码复用**
   - ✅ 搜索知识库寻找相似实现
   - ✅ 复用项目现有工具类（Jacksons, StringUtils）
   - ✅ 禁止引入新依赖或造轮子

5. **文档驱动**
   - ✅ 先设计接口契约（contracts/）
   - ✅ 基于契约生成前后端 OpenSpec changes
   - ✅ 开发过程中遇到的问题记录到知识库

### 反面教训

1. **❌ 直接开发不查询规范**

   - 初期未参考 `login.js` 的路径规范
   - 导致前端 API 路径错误

4. **❌ 未理解 KeyCenter 自动解密机制**

        • AI不晓得你的项目里有多少暗坑：我的项目里需要硬配置1个环境变量，否则会导致 bean init error，导致测试跑不起来。AI不知道这个信息，一顿库库撞南墙。

        "Scaling Law (缩放定律) 根本没撞墙" - 什么是 Scaling Law？

        在机器学习中，Scaling Law 是一种经验规律（由 OpenAI 在 2020 年正式提出），它证明了：只要你无脑地增加三个东西，AI 的智商就会按数学比例稳定提升。

        这三个东西是：

        1. 算力 (Compute) ：给 AI 训练用的 GPU 数量。
        1. 数据量 (Data)：喂给 AI 阅读的书本、网页和代码数量。
        1. 模型参数量 (Parameters)：AI 大脑里的“神经元连接”数量（模型规模）。
