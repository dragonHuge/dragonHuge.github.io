多 Agent 架构调研：五家主流系统横评，四派系归纳

2026-05-11 · 飞书原文 ↗
💡

如果你想搞清楚 多 Agent 架构到底有几种玩法，别先去看哪家声量大——先看底层驱动层在哪。

怎么选多 Agent 系统？一字心决：看驱动层。

这篇稿子起源于一个问题：OpenClaw / Hermes Agent / Claude Code / opencode / Kimi Swarm，2026 年当下最主流的五家，全带 subagent / swarm 字样，读起来像一家人，骨子里根本不是一回事。

本文拆成四层递进：

  • 先说结论：五家系统一张表看清定位
  • 逐家详解：每家的架构大图 + 独门设计 + 代表性代码片段
  • 横切对比：五个维度看分野，归纳出四大派系
  • 工程深挖：八个关键机制逐个讲透，最后落到 SXL 自己体系能抄什么

二、逐家详解

2.1 OpenClaw：不是一个 agent 演多角色，是多个独立 person 住在 IM 里

💡

先纠正一个网上流传的错误信息：OpenClaw 的作者是 Peter Steinberger（@steipete），不是 NVIDIA 合作项目。官网明确合作方是 VirusTotal（skill 安全扫描）。

底层 coding agent 叫 Pi，由 Mario Zechner 写（《Libgdx》游戏引擎作者）。

定位：长驻守护进程（launchd / systemd user service），同时接入 20+ IM 通道——WhatsApp / Telegram / Signal / Slack / Discord / iMessage / Feishu / WeChat / QQ……定位不是 CLI，不是云服务，是本地自托管的长驻 Gateway 守护进程。24/7 在线，装在自己机器上。

架构大图：

核心决策点——bindings 路由：消息从哪个通道来、交给哪个 agent，由 Gateway 的 bindings 以 most-specific-wins 的确定性规则决定：

优先级高 → 低：
peer (具体人) → parentPeer → guildId + roles → guildId/teamId
             → accountId (账号级) → channel fallback → default agent

整个路由层不经过 LLM。确定性规则，可审计。这和 SXL 的"前缀强制路由"气质一致——不信任 LLM 判断，把路由收紧到规则。

独门设计一 · Pi 的极简核心：

Pi 只有 4 个工具——Read / Write / Edit / Bash。明确拒绝 MCP。Armin Ronacher（Flask 作者）在博客里引用 Mario 的原话：

MCP 需要 session 启动时加载，不能热重载。agent 要新能力就让它自己写扩展。

agent 需要新能力时，开一个支线会话写扩展、调试、验证，完成后把"新学的技能"固化，rewind 回主线继续原任务。sessions 是树，不是链——这是 "minimal core + self-extension" 哲学的物理落地。

独门设计二 · Context Engine 14 个生命周期锚点：

OpenClaw 的扩展点是我见过最野心的设计。14 个锚点任你挂钩：

before_model_resolve    before_prompt_build     before_agent_reply
before_tool_call        tool_result_persist     message_sending
agent_end               session_start           session_end
prepareSubagentSpawn    onSubagentEnded         ingest
assemble                afterTurn / compact

系统提示极短，大量行为靠 hooks 塑造。

独门设计三 · 跨 agent 通信强防护：

// ~/.openclaw/openclaw.json (JSON5)
{
  agents: {
    list: [
      { id: "home", workspace: "~/.openclaw/ws-home",
        model: "anthropic/claude-sonnet-4-6" },
      { id: "work", workspace: "~/.openclaw/ws-work",
        model: "anthropic/claude-opus-4-7" },
    ],
  },
  bindings: [
    { agentId: "work",
      match: { channel: "whatsapp",
               peer: { kind: "direct", id: "+86138xxxx" } } },
    { agentId: "home", match: { channel: "whatsapp" } },  // fallback
  ],
  tools: {
    agentToAgent: { enabled: false, allow: ["home", "work"] },
  },
}

注意 agentToAgent.enabled: false——默认关闭跨 agent 通信。开了要显式 allowlist，reply-back 循环 ≤5 回合，对端回 REPLY_SKIP 强终止。这是我见过最保守的 peer 通信设计。

2.2 Hermes Agent：在主从骨架上多了"自己学、自己记、能回流训练"

💡

Hermes Agent ≠ Hermes 模型。Hermes 模型系列（Hermes 2/3/4）是 Nous Research 基于 Llama/Mistral/Qwen 的微调开源模型；Hermes Agent 是一个模型无关的 agent 运行时，默认推荐 Anthropic Opus 4.6，可切到 20+ provider——OpenRouter / Nous Portal / 公司 MiMo / Kimi / MiniMax / z.ai / GLM / NVIDIA NIM / Ollama / vLLM…… Hermes 4 模型只是推荐，不是绑定。

定位：Python + MIT 许可，截至 2026/04 约 11.6 万 stars，15k 测试用例。部署形态不限——$5 VPS / GPU 集群 / Modal / Daytona serverless 都能跑。用户通过 Telegram / Discord / Slack / WhatsApp / Signal / Email / CLI 等 18 种 gateway 接入。"The agent that grows with you"，slogan 里就把"长期搭档"定位写死了。

架构大图——主线 AIAgent + 六大子系统：

"Self-improving" 的四条具体路径：

Hermes 被反复强调的 self-evolving，不是营销词。源码里对应四个机制：

路径 1：Skill 自主创建

任务结束后，agent 自己调 skill_manager_tool 的 create/edit/patch/delete/write_file/remove_file，把"做法"固化成 ~/.hermes/skills/<name>/SKILL.md。文档原话：

"turning successful approaches into reusable procedural knowledge"

路径 2：周期 nudge 写 MEMORY.md / USER.md

系统提示周期性"nudge"模型把学到的东西写下来。两份文件——MEMORY.md（环境/项目约定）和 USER.md（用户偏好），§ 分隔多条目。snapshot 在 session 启动时冻结注入，保证 prompt cache 不失效，mid-session 只落盘不重注入——这是 cache 感知的架构决策。

路径 3：跨 session 召回

SQLite + FTS5 全文索引的 session_search_tool，搜完用 Gemini Flash 做按匹配点居中的摘要（每 session 截断 100k 字符）。不把原始 transcript 灌进主上下文，只把摘要灌进去。

路径 4：RL 训练回流

environments/ 下有 Atropos RL 环境和 trajectory_compressor.py，做 trajectory 生成——为下一代 tool-calling 模型回流训练数据。这是其他四家都没有的闭环。

DELEGATE_TASK_SCHEMA 源码片段（最核心的多 Agent 能力）：

DELEGATE_TASK_SCHEMA = {
  "name": "delegate_task",
  "description": "Spawn subagents in isolated contexts. "
                 "Each gets its own conversation, terminal session, "
                 "and toolset. Only the final summary returns -- "
                 "intermediate tool results never enter your context window.",
  "parameters": {"properties": {
      "goal": {...},
      "context": {...},
      "toolsets": [...],
      "tasks": [...],         # batch parallel
      "role": {"enum": ["leaf", "orchestrator"]},
      "acp_command": {...}    # 可 spawn Claude Code 作为子 agent
  }}
}

注意最后那句：Hermes 的 delegate 可以通过 ACP 协议把 Claude Code 当成自己的子 agent 启动。这个反向包含关系挺有意思——Hermes 是 meta-runtime，能调起其他 agent 框架。

leaf vs orchestrator 的角色分层：

  • leaf（默认）——不能再 delegate，拿不到 clarify/memory/send_message/execute_code 这些高风险工具。连工具描述都看不见。
  • orchestrator——可再 delegate，受 max_spawn_depth 上限（默认 1 层）约束。

这是我最想抄的一个设计。不是靠 Prompt 里叮嘱"你不能再 delegate"，而是在工具白名单层直接剥夺。

2.3 Claude Code：Agent tool + Skill + MCP + Hooks 四件套

定位：Anthropic 官方 CLI，三形态（CLI / IDE 插件 / claude.ai Web），默认 Sonnet 4.6。不是开源的——但官方持续迭代，文档完整，生态系里最成熟。

架构大图：

多 Agent 两套机制：

  • Subagent（主从）：通过 Agent(subagent_type=...) 调起，独立 context，单向回流 summary
  • Agent Teams（peer）：显式 AgentTeamCreate / AddMember / Execute，成员间用 message 工具互发，状态持久化到 JSON

Agent tool 调用示例：

{
  "type": "Agent",
  "name": "novel-master",
  "instructions": "用户要求：创作《XXX》的短故事大纲。\n项目路径：04-项目/私人/番茄小说连载/\n输出要求：生成大纲后写入 a-纲要/ 目录，返回产物路径。",
  "subagent_type": "specialized",
  "model": "sonnet",
  "run_in_background": false,
  "tools": ["Read", "Write", "Grep"]
}

Hooks 配置示例（用对 exit code 才真拦截）：

{
  "hooks": {
    "PreToolUse": [
      {"matcher": "Write|Edit", "command": "check-permissions.sh"}
    ],
    "PostToolUse": [
      {"matcher": "*", "command": "auto-lint.sh"}
    ],
    "SubagentStop": [
      {"matcher": "*", "command": "collect-summary.sh"}
    ]
  }
}

那我问你：上面这个 check-permissions.sh 里写 exit 1 和 exit 2 有什么区别？

答案——exit 1 不阻止执行（非阻塞错误），只有 exit 2 才是真正的安全拦截门。文档里都写了，但 80% 的人用错。

上下文压缩五层（深度独门）：

Level 1 · 实时预算控制    零成本、实时      单结果 > 50k 存磁盘
Level 2 · 微压缩          低成本、延迟     旧工具结果只留摘要
Level 3 · 会话记忆摘要    中成本、预取      滚动摘要 + 最近 2-3 轮
Level 4 · 完整压缩子 Agent 高成本、fork    子 Agent 生成摘要 + 共享主缓存前缀
Level 5 · 响应式硬砍      应急、保命       prompt-too-long 时删 50%

最精巧的是 Level 4 子 Agent 共享主缓存前缀——压缩子 Agent 自己也享 Prompt Cache，压缩本身成本被拉低。

isolation: worktree 编程独门：

claude --worktree feature-x

物理隔离：每个 feature 独立 git worktree，多个 Agent 并行开发互不干扰。worktree 失败回滚，主分支完全无影响——宠物→牲畜 的哲学转变。

2.4 opencode：Claude Code 的开源对照物，把 client/server 和 session 树做成一等公民

定位：sst 团队发起（现主仓库在 anomalyco/opencode），开源、provider-agnostic。官网 opencode.ai。三形态：TUI / desktop app / IDE 插件。核心差异：不绑定任何单一模型提供商，通过 Models.dev provider 列表支持任意 LLM。

最大架构决定——client/server 彻底解耦：

启动方式：

opencode                               # TUI + server 同进程
opencode serve --port 4096             # 独立 headless server
opencode attach http://host:4096       # 另一机器的 TUI 接入已有 server
opencode run "explain closures"        # 一次性 CLI

Server 的 OpenAPI spec 直接暴露在 http://host:port/doc，用 Stainless 生成产出类型安全的 @opencode-ai/sdk。TUI / IDE / Web 都是平等客户端。

session 树 API（一等公民化）：

POST /session                          # 创建（可带 parentID）
POST /session/:id/fork                 # 从任意 message 分叉
GET  /session/:id/children             # 列子会话
POST /session/:id/abort                # 中断
GET  /global/event                     # SSE 实时事件流

和 Claude Code 的关键区别：parentID / fork / children 是数据结构，不是工具调用堆栈。TUI 快捷键 session_child_first / session_child_cycle / session_parent 可在父子会话间导航。

agents/ 目录配置（本地实际用例）：

// 04-项目/私人/番茄小说连载/opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "default_agent": "novel-master",
  "agent": {
    "novel-writer": {
      "description": "章节产出...",
      "mode": "subagent",
      "temperature": 0.7,
      "model": "anthropic/claude-sonnet-4-6"
    },
    "novel-reviewer": {
      "description": "质量审核...",
      "mode": "subagent",
      "temperature": 0.1,
      "permission": { "edit": "deny" }
    },
    "novel-planner": {
      "description": "大纲规划...",
      "mode": "subagent",
      "model": "anthropic/claude-haiku-4-5"
    }
  }
}

这份 opencode.json 是我自己番茄小说项目里实跑的——每个 agent 可独立指定 model，novel-planner 用 Haiku 省钱，novel-writer 用 Sonnet 保质。

配置 8 级 precedence（企业向）：

1. 远程 .well-known/opencode                # 组织级下发
2. global config (~/.config/opencode/)
3. 环境变量
4. project config
5. .opencode/ 目录
6. inline env
7. managed dir                               # 托管目录
8. macOS .mobileconfig (MDM)                 # 企业强制

跨 CLI 兼容：opencode 显式读 CLAUDE.md / .claude/agents/ / ~/.claude/skills/（除非设置 OPENCODE_DISABLE_CLAUDE_CODE=1）。我自己就用 symlink 把 .opencode/agents/*.md 和 .claude/agents/*.md 指向同一份源文件——改一边，两边同步。

2.5 Kimi Swarm：能力训进权重里的模型级 Swarm

💡

Kimi Swarm 是 K2.5 模型能力，不是独立框架。由 Moonshot 自己训练进模型权重里。发布时 Kimi 网页端/App 提供四种模式：K2.5 Instant、K2.5 Thinking、K2.5 Agent、K2.5 Agent Swarm (Beta)。目前 Agent Swarm 仅对高付费层可用，kimi-cli 尚不支持（GitHub issue #746 在讨论）。

架构——异质 orchestrator + 同质 frozen workers：

  • Orchestrator：K2.5 本体，被 RL 训练过的调度器，不是 Prompt 工程
  • Sub-agents：frozen workers，根据任务动态实例化，最多 100 并发 / 1500 总步数
  • 角色没有预设——官方原话 "no predefined roles or hand-crafted workflows"
  • 没有独立 leader election，orchestrator 全程唯一
  • DataCamp 实测观察到"约 5 个 agent 同时跑，其余排队"——声称 100 实际 ~5，基础设施有内部调度限制

核心创新——PARL（Parallel-Agent Reinforcement Learning）：

其他家的多 Agent 是"用户写 Prompt 让模型调用 Agent 工具"。Kimi 是把"该不该并行"这个决策训进了模型权重。

奖励函数：

r_PARL = λ₁·r_parallel + λ₂·r_finish + r_perf

三个分量各司其职：

  • r_parallel —— 激励实例化 sub-agent，防止 serial collapse（坍缩回单 agent）
  • r_finish —— sub-agent 完成率，防止 spurious parallelism（狂开 agent 但不干实事，奖励黑客）
  • r_perf —— 任务整体成功率

Critical Steps 指标：

Critical Steps = ∑(S_main(t) + max_i S_sub,i(t))

评估的是关键路径耗时，不是总 step 数。只有真正缩短关键路径的并行才被奖励——模型因此学会"什么时候不该开 Swarm"。

DataCamp 实测的 Bubble Shooter 案例：模型主动选择单 agent 不开 swarm——因为紧耦合代码加 sub-agent 只增加协调开销。模型自己懂，这是其他框架做不到的。

适用场景：wide research / 数据集构建-标注 / 多源信息抓取 / 办公文档批量生产（"Office Productivity"）。

反模式：紧耦合编码任务。官方明确承认 Swarm 在此场景退化为单 agent。

三、四大派系归纳

前面五家横向看完，归成四派系：

3.1 派系 A：模型驱动型 Swarm

代表：Kimi Swarm

核心特征：多 Agent 能力通过 RL 训练内化进模型权重。orchestrator 和 sub-agent 角色生成、并行决策全部由模型本体承担，框架只提供外壳。

代价：训练贵、权重绑死、能力不可迁移到其他模型。

场景：需要百级并行、动态角色、"该开就开不该开就不开"的 wide research 和数据生产。典型任务：识别 100 个 YouTuber niche → 自主开 100 个 sub-agent 搜索 → 聚合成 300 条 creator 数据。

反模式：紧耦合编码任务。

3.2 派系 B：运行时主从型

代表：Claude Code、opencode

核心特征：框架提供 Agent tool / Task tool，主 agent 通过 Prompt 决定委派，子 agent 独立 context 并单向回流。调度决定权在 Prompt 和框架约束的组合里。

场景：

  • 严肃编码、高可控性、Anthropic 订阅 → Claude Code
  • 开源优先、多模型混用、要远程/可编程接入 → opencode

3.3 派系 C：自进化型

代表：Hermes Agent

核心特征：在运行时主从骨架上，额外挂了三条自进化路径——skill 自创建、memory periodic nudge、RL 训练回流（Atropos 环境 + trajectory compressor）。

代价：skill 自创建有"污染"风险（次优解沉淀下来拉低整体）；RL 训练需 GPU；速率限制在并发时卡住。

场景：长期运行的个人助手、垂直领域持续积累的 agent。

和 B 派的区别：B 派的 Skill / Memory 是用户手写的静态资产；C 派把"沉淀"做成 agent 主动行为。这是进化论级别的差异。

3.4 派系 D：多人格网关型

代表：OpenClaw

核心特征：不是"一个 agent 调多个子 agent"，而是多个独立 persona 各自住在 IM 账号里。Gateway 长驻进程 + 确定性 bindings 路由决定哪个 persona 接谁。每个 agent 独立 workspace / auth / sessions，按人（家人、同事）、按账号、按组织完全隔离。

代价：不是编码工具；MCP 被拒绝，靠 agent 自己写扩展；反爬/封号风险（IM 通道非官方 API 时）。

场景：主动型 agent（cron / heartbeat 不在场也持续工作）、IM 原生协作、多身份隔离、隐私敏感（住自己机器）。

3.5 补充派系：去中心化看板 / Peer Team

不在本次五家主线里，但值得记一下。代表：飞书 Bitable Swarm（用户自建 zero-code 方案）、Claude Code 内置的 Agent Teams 模式。要点：peer 协商适合方案设计 / Code Review / Debug / 相互挑战，不适合流水线执行。

跨系统共识（四条原则）：

  1. 静态内容放前面，动态内容放后面——保证前缀稳定
  1. 子 Agent system prompt 复用父的前缀——cache 命中率决定成本
  1. 压缩动作本身要懂 cache——"等缓存过期再动手"、"压缩子 Agent 共享主缓存"

Claude Code Hook 的坑（我踩过）：

大多数人写的"安全 hook"其实形同虚设。原因就是 exit code 用错：

# ❌ 这样写，拦不住任何东西
#!/bin/bash
if [[ "$1" =~ "dangerous" ]]; then
    echo "blocked"
    exit 1    # 非阻塞错误，Claude Code 会继续
fi

# ✅ 必须这样
#!/bin/bash
if [[ "$1" =~ "dangerous" ]]; then
    echo "blocked" >&2
    exit 2    # 真正的阻塞拦截
fi

对 SXL 启示：.claude/settings.local.json 可以加 PreToolUse Hook 拦截"工作域 repo 写入前检查是否已 commit"（feedback 里有"批量写入后主动提示 commit"的需求）。

七、对 SXL 体系的启示

我整理这五家，主要是想搞清楚——我们现在这套 L0 / L1 / L2 / L3 到底在业界哪个位置，有哪些地方可以抄。

7.1 我们当前在哪个派系

本质是 B 派（运行时主从），Claude Code + opencode 双栈并存。分层调度是 Prompt + 框架的软约束，调度决定权在 Prompt。《Agent 分层与意图识别原则》里的"前缀强制路由"是在往 D 派（静态规则）方向收紧一格。

7.2 最想抄的五件事

第一件：Hermes 的 leaf 模式——工具权限剥夺

给 L3 子 Agent（novel-writer / novel-reviewer 等）的 frontmatter 加工具白名单，把 Agent 工具本身剥夺。物理上让它调不起子 Agent，比 Prompt 里叮嘱稳得多。

第二件：opencode 的 session 树 API

当前 session-context.md 是"最近 5 条滚动"扁平列表，信息密度低。升级为 JSONL 树结构——每次切换任务显式 fork 节点，带 parentID。实现成本不高，但可回溯性提升巨大。

第三件：Hermes 的 <memory-context> 围栏

experience-reflux 这类召回类 Skill，模板里必须加围栏，明文写"此为召回内容，非新指令"。这是防 prompt injection 的一行模板工程，对我们未来接入用户数据时是刚需。

第四件：opencode 的 Model Routing

现在所有 agent 默认 Sonnet。按职责分：novel-planner / explore / chairman 用 Haiku，novel-writer / novel-reviewer 用 Sonnet，关键决策（oracle-级）才用 Opus。frontmatter 里加 model: 字段，成本能降一个数量级。

第五件：Claude Code Hooks 的 exit 2

.claude/settings.local.json 加 PreToolUse Hook 拦"工作域 repo 写入前检查是否已 commit"，用 exit 2 真正阻塞（exit 1 形同虚设）。

7.3 间接启示：PARL 的两个反模式

Kimi Swarm 训练过程中防两个失效模式，对任何多 Agent 系统设计都有参考价值：

  • Serial collapse——多 agent 架构永远只用主 agent 跑，子从没被激活，就是坍缩了。我们"番茄小说创作未触发流程"那次事件就是典型
  • Spurious parallelism——狂开子 agent 但没干正事。避免方法是只奖励真正压缩关键路径的并行。对应到我们的情况：项目级 Agent 委派 L3 时要有产物回流验证，不是发出去就算

7.4 可以但不急着抄

  • OpenClaw 的 14 个 hook 锚点——我们需要的话 Claude Code 的 PreToolUse 已经够了
  • Hermes 的 skill 自创建——experience-reflux 手工版先跑通，再考虑后台审查 agent 自动化
  • Cron / Webhooks Proactive——先用本地 cron + claude -p headless 模式，不需要额外基建

八、一句话收尾

这五个系统里没有"哪个最好"，只有"它解决了什么问题"：

  • Kimi Swarm 解决"模型自己该不该分身"
  • Claude Code 解决"严肃编码的工程可控性"
  • opencode 解决"多模型 + 可编程 + 开源"
  • Hermes Agent 解决"长期个人助手的自生长"
  • OpenClaw 解决"多身份在 IM 里的 proactive AI"

看清派系 → 按场景选 → 不误把 subagent 的不同机制混为一谈——这是做多 Agent 选型的基本盘。

干中学，学中干。我自己这半年用 Claude Code + opencode 双栈并行，每一条坑都是真踩过才知道的。这五家看一圈下来最大的收获不是"哪个最好"，而是——多 Agent 架构是个被严重低估的子领域。大家都在聊 LLM 能力，但真正决定 agent 产品形态的是 orchestration 层的工程化水平。这一层还有很大空间。
