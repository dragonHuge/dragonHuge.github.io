    开发约束规范-探索：Rules or Skills？

    开发约束规范：是指在每一次需求开发时，模型必须默认遵守的规则，不得跳过。

    在构建前端项目的开发约束规范时，就遇到了这个比较重要的卡点问题：OpenSpec的开发范式下，开发约束规范应该放在哪里：Rules or Skills？

    Rules实现 - 拉完了

    优点显而易见：

    Rules作为全局规则(或在Spec-kit中称为“宪法”)，当用户提问，Agent会自动读取Rules内容，将其注入到 System Prompt，作为前置上下文，再结合用户提问给出回复。

    因此在Rules中保存开发约束规范，可以100%保证遵守现有规范。

    缺点也随之而来：

    当开发约束规范越来越长，Rules的内容越来越多，带来的是：

    1. Token消耗量的上升 （钱哗哗向外流。。。）
    1. 被轻松撑满的Context（想象一下每次对话Rules都要在你开头插入一些有的没的。。。）
    1. “注意力稀释”（Attention Dilution）：当 System Prompt 过长且包含大量细碎规则时，LLM 对每一条规则的遵循度会下降，产生“幻觉”或忽略部分指令（尤其是“中间”的指令，即 Lost-in-the-Middle 现象）。

    Skills实现 - 人上人

    优点：解决Rules Token消耗、Context消耗的痛点

    Skills由于其“渐进式披露”的加载机制，似乎能解决Rules Token消耗、Context消耗的痛点。日常场景当然可以，毕竟这是Skill的使命之一。

    缺点：用户使用成本上升、规范遵守确定性模糊

    但别忘了我们当前使用的是OpenSpec开发范式。这是什么意思呢？见下示例。

    假设我们已有1个开发约束规范dev-checklist Skill，此时若：

    • 若纯粹的vibe-coding开发：直接 /dev-checklist 起手显式调用此Skill，进行需求开发。

    • 并且提高了用户的输入成本，体验大打折扣。

    • 实际从Skill原理来讲，即便明示指定使用此Skill，AI也不一定100%遵守成功。

      Skill命令触发是最稳妥的方案。

    最终方案1：Rules 引导遵循 Skills- 夯

    既然 Rules 太重，Skills 太弱，我们需要结合两者的优势：“Rules 定义红线，Skills 提供详情” ：

    1. Skill：记录详尽的开发约束规范，可迭代。
    1. Rules：记录项目核心全局约束规则，且 强制要求「进行OpenSpec开发时，读取并严格遵循开发约束规范Skill。」

**每个接口（Service/Controller）新增或修改，必须有对应测试类和测试方法，且测试必须通过。**

执行流程：
1. 接口实现完成后，按 `/dev-tdd` 规范生成对应测试

### 分层架构

```
controller/ → 处理HTTP请求，参数校验 (@Valid)
     ↓
service/    → 业务逻辑处理，事务管理 (@Transactional)
     ↓
repository/ → 数据访问
     ↓
entity/    → 数据库实体映射
```

### 代码规范

- **中文注释**: 所有代码注释必须简体中文
- **事务**: Service层必须加 `@Transactional`
- **参数校验**: Controller方法参数必须使用 `@Valid`
- **日志**: 使用 `@Slf4j`，`log.info()`/`log.error()` 记录业务日志，`log.debug()` 记录调试信息
- **异常**: 禁止吞掉异常，必须记录日志或抛出
- **硬编码**: 禁止硬编码，配置必须外置

### 日志规范

```java
// 正确
log.info("查询参数: name={}, id={}", name, id);
log.error("保存失败: {}", e.getMessage(), e);

// 禁止
log.info("查询参数: " + name);  // 字符串拼接
log.error("错误");             // 无变量
```

## ANTI-PATTERNS (零容忍)

- ❌ Controller直接操作数据库 → 必须通过Service层
- ❌ 重复造轮子 → 工具类必须复用已有代码
- ❌ 硬编码 → 配置必须外置到配置中心
- ❌ 吞掉异常 → 必须记录日志或抛出
- ❌ 循环依赖 → 模块间禁止循环引用
- ❌ 跨层调用 → 必须遵循调用链 controller→service→repository→entity
- ❌ 数据库连接信息硬编码 → 必须通过配置中心

# 风控平台 项目 Test-After 单元测试执行规范

本规范定义了 风控平台 项目的 Test-After 单元测试全流程。**所有接口（Service/Controller）新增或修改后，必须按照本规范生成并通过单元测试。**

## 1. 适用场景

本规范在以下场景中自动触发：

| 场景 | 触发方式 |
|------|----------|

## 3. 测试策略选择

### 3.1 判断规则

```
被测类是否有 @Autowired / @Resource 注入？
  │
  ├── YES → 依赖 Spring 容器（DB/Redis/RPC）
  │         → 使用 @SpringBootTest
  │
  └── NO  → 纯逻辑类
            → 使用 @ExtendWith(MockitoExtension.class) 或直接 new
```

### 3.2 @SpringBootTest 模板

```java
package com.example.risk.risk.风控平台.web.service.xxx.impl;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import static org.junit.jupiter.api.Assertions.*;

/**
 * XxxServiceImpl 单元测试
 */
@SpringBootTest
class XxxServiceImplTest {

    @Autowired
    private XxxServiceImpl xxxService;

    /**
     * 测试新增 xxx - 正常路径
     */
    @Test
    void testAddXxx_Success() {
        // 准备测试数据
        // 执行被测方法
        // 断言结果
    }

    /**
     * 测试新增 xxx - 异常路径（参数为空）
     */
    @Test
    void testAddXxx_NullParam_ThrowsException() {
        assertThrows(BusinessException.class, () -> {
            xxxService.addXxx(null);
        });
    }
}
```

## 4. Mock 边界规则

### 4.1 核心原则

| 类别 | Mock 策略 | 原因 |
|------|-----------|------|
| **本次需求改动的逻辑** | **禁止 Mock** | 必须验证真实业务逻辑 |
| 无关但必须的外部依赖 | 允许 Mock | 保证测试可运行 |
| 用户提供的测试数据 | 优先使用 | 最贴近真实场景 |

### 4.2 Mock 示例

```java
// 本次需求：新增 addDictItem 方法
// addDictItem 内部调用了一个无关的 RPC 获取用户信息

@SpringBootTest
class RiskDictItemServiceImplTest {

    @Autowired
    private RiskDictItemServiceImpl dictItemService;

    @MockBean  // Mock 无关外部依赖
    private UserInfoRpcService userInfoRpcService;

    @Test
    void testAddDictItem_Success() {
        // Mock 无关依赖的返回值
        when(userInfoRpcService.getUserInfo(anyLong()))
            .thenReturn(new UserInfo("testUser"));

        // 直接调用本次需求的核心方法（不 Mock）
        Long id = dictItemService.addDictItem(request);

        assertNotNull(id);
    }
}
```

### 4.3 测试数据构造

优先级：
1. **用户提供的测试数据** → 直接使用
2. **基于方法签名自动构造** → 根据参数类型、字段名、约束条件构造合理数据
3. **最小化数据** → 仅构造满足测试所需的最少字段

## 5. 执行流程

### 5.1 完整流程图

```
接口实现完成
     │
     ▼
[步骤 1] 推导测试文件路径
     │
     ▼
[步骤 2] 判断测试策略（@SpringBootTest / Mockito）
     │
     ▼
[步骤 3] 生成/更新测试文件
     │  - 文件不存在 → 创建新文件
     │  - 文件已存在 → 追加测试方法（不覆盖已有）
     │  - 已有同名方法 → 更新该方法内容
     │
     ▼
[步骤 4] 执行测试
     │  mvn test -pl <module> -Dtest=<TestClassName>
     │
     ├── 通过 ──→ 标记 task 完成，继续下一个 task
     │
     ├── 失败（逻辑错误）
     │   │
     │   ▼
     │  [步骤 5] 分析失败原因
     │   │  - 读取测试输出的错误信息
     │   │  - 判断是实现代码 bug 还是测试代码 bug
     │   │
     │   ▼
     │  [步骤 6] 修复代码
     │   │  - 修复实现代码或测试代码
     │   │  - 回到步骤 4 重新执行
     │   │  - 最多循环 3 次
     │   │
     │   └── 3 次仍失败 ──→ [步骤 7] 暂停并报告
     │                      输出：失败详情、分析报告、修复尝试记录
     │                      等待用户决策
     │
     └── 失败（基础设施连接错误）
         │  DB/Redis/RPC 连接超时或拒绝
         │
         ▼
        [步骤 8] 通知用户
         │  "DB/Redis 连接失败，是否切换为 Mockito Mock 策略？"
         │
         ├── 用户选择 Mock ──→ 重新生成测试（Mockito），回到步骤 4
         └── 用户选择跳过 ──→ 标记为"需人工验证"，继续下一个 task
```

### 5.2 测试执行命令

```bash
# 执行单个测试类（推荐，快速反馈）
mvn test -pl <module> -Dtest=<TestClassName>

# 示例
mvn test -pl 风控平台-web -Dtest=RiskDictItemServiceImplTest

# 执行单个测试方法
mvn test -pl <module> -Dtest=<TestClassName>#<methodName>

# 示例
mvn test -pl 风控平台-web -Dtest=RiskDictItemServiceImplTest#testAddDictItem_Success
```

### 5.3 失败分析要点

| 错误类型 | 特征 | 处理方式 |
|----------|------|----------|
| 断言失败 | `AssertionError`, `expected:<X> but was:<Y>` | 检查实现逻辑或测试预期值 |
| 空指针 | `NullPointerException` | 检查依赖注入或测试数据构造 |
| 编译错误 | `cannot find symbol`, `incompatible types` | 检查 import 和方法签名 |
| 连接失败 | `ConnectionRefused`, `Timeout`, `Cannot get Jedis` | 基础设施问题，通知用户 |
| Bean 加载失败 | `NoSuchBeanDefinition`, `UnsatisfiedDependency` | 检查 @MockBean 或 Spring 配置 |

    最终方案迭代 V1：

    在真实需求的方案测试中遇到多次失败与反复修正，因此需要对初版方案做细化迭代，形成三层强制保障闭环。

    背景与目标

    • 目标：让“开发→测试→记录”形成强制闭环，保证所有接口改动都被测试且留痕可追溯。
    • 核心原则：以规范驱动 + 模板执行 + 记录归档三层保障，减少人为漏执行与漏记录。

    初版方案回顾

    1. 命令写死在 AGENTS / config / tasks 中，执行者手动替换类名。
    1. 测试记录依赖人工写入 test-records.md。
    1. 未定义模块识别机制，执行命令不具备可扩展性。

    初版方案存在的问题

    • 命令分散：多处硬编码导致信息不一致，容易用错命令或遗漏更新。
    • 流程可执行性弱：测试执行完全依赖记忆，环境参数（JDK8/REGION）容易遗漏。
    • 记录不稳定：test-records 由人工维护，测试过程与结果存在缺失风险。

    最新方案改动细节

    1. 模板化命令：将命令模板拆分为模块文件，存放在 /.opencode/skills/dev-tdd/templates/，如 风控平台-web-test-template.md。
    1. 规范引用模板：AGENTS.md 与 openspec/config.yaml 统一改为引用模板，禁止再写死命令。
    1. 模块识别规则：无法判定模块必须先询问用户，保证执行命令准确。
    1. 环境强约束：执行测试必须使用 JDK8 + -Pdev + REGION=dev。
    1. 记录闭环：每次执行必须同步到 test-records.md，保证所有测试类与方法的过程和结果可追溯。

    改动带来的收益

    • 一致性：单一模板源，避免多处文档重复维护。
    • 可执行性：固定环境参数，降低执行失败率。
    • 可追溯性：完整记录所有测试过程和结果，便于审计与复查。
    • 可扩展性：新增模块只需添加模板文件并登记即可。

    后续注意事项

    • 若新增模块测试需求，需新增 <module>-test-template.md 并同步登记。
    • 若无法识别测试类所属模块，必须先询问用户后再执行。
    • 任何测试执行都必须同步记录到 test-records.md。

## 7. 常见问题

### Q1: 如何判断模块职责？

**A**: 根据模块名和源码内容综合判断：
- 包含 `controller`/`web` → Web/API 层
- 包含 `service`/`app` → 业务逻辑层
- 包含 `dao`/`repository`/`mapper` → 数据访问层
- 包含 `common`/`util` → 公共基础层
- 包含 `infra`/`infrastructure` → 基础设施层
- 包含 `api`/`thrift`/`grpc` → 接口服务层

### Q2: 实体类太多怎么办？

**A**:
1. 优先扫描**管理后台**相关模块的实体类
2. 核心业务实体优先于边缘实体
3. 可以分批扫描，每次扫描一个模块

### Q3: API 接口如何分类？

**A**:
1. 按业务模块分类（如用户、订单、规则）
2. 按 Controller 类名归类
3. 使用 Swagger/OpenAPI 注解辅助判断

```go
package service

    "context"

    userRepo repository.UserRepository

func NewUserService(ur repository.UserRepository) UserService {

func (s *userService) GetByID(ctx context.Context, id string) (*model.User, error) {
    if id == "" {
        return nil, fmt.Errorf("user id cannot be empty")
    }
    
    user, err := s.userRepo.FindByID(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("failed to get user: %w", err)
    }
    
    return user, nil
```

### Repository

```go
package repository

import (
    "context"
    "database/sql"
    "fmt"
    
    "project/internal/model"
)

type userRepository struct {
    db *sql.DB
}

func NewUserRepository(db *sql.DB) UserRepository {
    return &userRepository{db: db}
}

func (r *userRepository) FindByID(ctx context.Context, id string) (*model.User, error) {
    query := "SELECT id, name, email FROM users WHERE id = ?"
    
    user := &model.User{}
    err := r.db.QueryRowContext(ctx, query, id).Scan(&user.ID, &user.Name, &user.Email)
    if err != nil {
        return nil, fmt.Errorf("query failed: %w", err)
    }
    
    return user, nil
}
```

### Step 5: RESTful API 接口梳理

**⚠️ 前后端分离项目必做**

**🔴 重要警示：禁止基于 RESTful 规范假设接口**

> **问题背景**：曾有一次，API 文档基于 RESTful 规范假设生成了 `deleteRule`, `updateRule`, `createRule` 等接口，但实际代码中这些接口并不存在。这导致文档与实际代码严重不符。

> **核心原则**：**必须 100% 基于实际代码生成 API 文档**，禁止基于 RESTful 约定俗成进行推测。

#### 5.1 扫描 Controller 文件

1. **查找所有 Controller**


2. **读取每个 Controller 文件**，提取：

| 提取项 | 来源 | 示例 |

| 请求方法 | `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` | `@PostMapping("/save")` |
| 完整路径 | 基础路径 + 方法路径 | `api/v1/rule/saveRule` |
| 请求参数 | `@RequestParam`, `@RequestBody`, `@PathVariable` | `@RequestParam("id") Long id` |
| 方法注释 | Javadoc 或方法上注释 | `更新某规则的状态` |

3. **⚠️ 必须验证**
   - 读取实际 Controller 源码
   - 核对每个接口的 HTTP 方法和路径
   - 确认请求参数名称和类型

| ❌ 禁止 | ✅ 正确 |

## 7. 常见问题

### Q1: 如何判断模块职责？

**A**: 根据模块名和源码内容综合判断：
- 包含 `controller`/`web` → Web/API 层
- 包含 `service`/`app` → 业务逻辑层
- 包含 `dao`/`repository`/`mapper` → 数据访问层
- 包含 `common`/`util` → 公共基础层
- 包含 `infra`/`infrastructure` → 基础设施层
- 包含 `api`/`thrift`/`grpc` → 接口服务层

### Q2: 实体类太多怎么办？

**A**:
1. 优先扫描**管理后台**相关模块的实体类
2. 核心业务实体优先于边缘实体
3. 可以分批扫描，每次扫描一个模块

### Q3: API 接口如何分类？

**A**:
1. 按业务模块分类（如用户、订单、规则）
2. 按 Controller 类名归类
3. 使用 Swagger/OpenAPI 注解辅助判断

### Q4: API 文档与实际代码不符怎么办？

**🔴 这个问题非常严重，必须重视**

**问题表现**：
- 文档中的接口在代码中不存在
- 路径、方法、参数与实际代码不一致
- 基于 RESTful 规范假设接口，但实际代码未实现

**根本原因**：
- 使用了 Swagger/OpenAPI 扫描但未验证
- 基于 RESTful 约定俗成进行推测
- 未直接读取 Controller 源码

**✅ 正确做法**（必须遵守）：

1. **直接扫描源码**：使用 `glob("**/controller/*.java")` 找到所有 Controller
2. **读取每个 Controller 文件**：提取 `@RequestMapping`, `@GetMapping`, `@PostMapping` 等注解
3. **提取完整路径**：基础路径 + 方法路径，如 `api/v1/rule` + `/saveRule` = `api/v1/rule/saveRule`
4. **提取参数信息**：`@RequestParam("id") Long id` → 参数名 `id`，类型 `Long`
5. **禁止假设**：绝对不能因为 RESTful 规范就假设某个接口存在

**验证示例**：

```java
// ❌ 错误：假设存在 deleteRule 接口
// GET /api/rule → 文档写 "获取规则列表"
// POST /api/rule → 文档写 "创建规则"  
// DELETE /api/rule/{id} → 文档写 "删除规则"

// ✅ 正确：读取实际代码
// @RestController
// @RequestMapping("api/v1/rule")
// public class RuleController {
//     @PutMapping("/updateRuleStatus")  // 实际是 PUT，不是 DELETE
```

      1. Sisyphus (Ultraworker)：主要统筹者。负责任务规划、子 Agent 调度和并行执行，并以高效的并行执行力推动任务完成。他从不半途而废，也从不分心，他一定会完成任务。
      1. Hephaestus (Deep Agent)：复杂架构推理者，使用GPT-5.3 Codex 的推理风格来进行深入的架构工作或复杂的调试，

      1. 按Tab 键进入 Prometheus 模式，或@plan "your task"从 Sisyphus 模式输入。

      1. 立即/start-work Atlas就会开始在你最近一次plan中执行。

      @专业子 Agent，通常被核心Agent调用，也可 @ 手动触发，用于执行特定领域的任务。

      1. @general / @explore(快速代码库搜索器)：探索和理解代码库，进行信息收集。
      1. @Prometheus / @Sisyphus-Junior：规划和轻量编排。
      1. @oracle(架构/调试器)：一位高智商的只读顾问，擅长架构决策和复杂调试。遇到不熟悉的模式、安全问题或多系统权衡时，请咨询 Oracle。
      1. @librarian(图书管理员)：文档管理、知识库检索。
      1. @multimodal-looker：多模态（图片 / 视频）分析。
      1. @Metis (Plan Consultant)：查漏补缺，在计划最终定稿之前，找出遗漏之处，优化 Prometheus 的计划。
      1. 100% 文件引用已验证

      Oh-my-opencode

      安装 oh-my-opencode 后，默认可能会替换原生的 plan 和 builder Agent

      如果你希望保留这两个原生 Agent（例如用于执行轻量级任务以节省 Token），可以通过修改配置文件来实现。

      在 ~/.config/opencode/oh-my-opencode.json 文件的第一层级中添加以下配置：

      {
  "sisyphus_agent": {
    "default_builder_enabled": true,
    "replace_plan": false
  }
}
