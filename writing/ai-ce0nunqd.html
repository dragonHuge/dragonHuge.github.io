知识库-微调

长知识库拆分

由于官方提供的部分知识库文档很长(如：@【知识库-1】FSSC-T&E-客服知识库-V0 用户版（黑马）)，在调用官方文档解析接口时，会超时导致异常。因此根据语义，将其拆分为多个小文档，再做解析。

剔除重复英文内容

用中文问答，肯定是用中文知识库，毕竟检索本质上是用向量索引，并且重复的英文语料会导致召回多条重复片段，导致重排模型效率低下。

因此对「知识库-8」中的英文内容删减。

测试集正确率 75%->91.67%。

图片删减

本次比赛是单项选择题的形式，阅览了知识库文档发现，其实很多图片在此场景下不仅没有用，还会给Embedding模型增负，因此逐个去除掉知识库文档中的无用图片。

针对这种RAG知识库，有几个问题帮我分析一下：
1. 其中的向量索引类型怎么配置？哪种向量索引类型最适合？
现有的向量索引类型有：flat
利用蛮力搜索算法进行精确的kNN搜索，支持所有的向量数据类型。
int8_flat
利用蛮力搜索算法并自动进行标量量化，仅支持 float 类型。
int4_flat
利用蛮力搜索算法并自动进行半字节标量量化，仅支持 float 类型。
bbq_flat
利用蛮力搜索算法并自动进行二进制量化，仅支持float类型。
hnsw 
利用HNSW算法进行可扩展的近似kNN搜索，支持所有的向量数据类型。
int8_hnsw 
浮点向量的默认索引类型。利用HNSW算法，并为float类型的的向量数据自动进行标量量化，以实现可扩展的近似 kNN 搜索。可以将内存占用减少 4 倍，会牺牲一些精度。
int4_hnsw 
利用HNSW 算法，并为float类型的向量数据自动进行标量量化，以实现可扩展的近似kNN搜索。可以将内存占用减少 8 倍，会牺牲一些精度。
bbq_hnsw 
利用HNSW算法，并为float类型的 element_type 自动进行二进制量化，以实现可扩展的近似 kNN 搜索。这可以将内存占用减少 32 倍，但会牺牲精度。

2. 向量匹配类型怎么选择？哪种向量匹配类型最适合？
现有的向量匹配类型有：None
不进行向量相似度计算
L2
欧式距离，最直观的度量方式，它关心向量在空间中的绝对距离，适合图像、语音等连续数值特征的检索，但在高维文本向量中常受“距离趋同效应”影响
IP (Inner Product)
通过点积衡量两个向量的方向与长度是否一致，如果向量的模长本身带有强度或权重意义（例如推荐系统 embedding 中的“偏好强度”），IP 能很好地体现这种差异。
COSINE
关注向量之间的夹角，完全忽略模长差异，非常适合文本语义 embedding，因为在自然语言中我们更在意“方向”（语义相似度），而不是向量的绝对大小，因此在大多数 RAG 文本检索场景下是默认选择
HAMMING
用于二进制向量，通过统计不同位的数量来衡量差异，常见于局部敏感哈希（LSH）等场景；它速度快，但只能处理二进制特征，不适合连续 embedding
JACCARD
适合集合或稀疏特征数据，它通过交并比来刻画集合相似度，常用于标签集合、关键词集合等离散特征的检索

3. 在进行RAG检索时，搜索类型应该选哪种？
现有的搜索类型有3种：vector表示向量搜索，keyword表示关键词检索，all表示向量检索和关键词检索同时进行。

4.es检索时候选的结果数量应该为多少？

以提高知识库的提问检索精度为准，分析并回答上述问题。
  • 针对用于回答单选题的 RAG 知识库，结合 “提高检索精度” 的核心目标，对四个问题的分析如下：
1. 向量索引类型的选择：优先flat
单选题的核心需求是 “精准匹配问题与对应答案”，错误的检索结果可能直接导致选项判断错误，因此精度优先于速度和内存占用。
flat 索引采用蛮力搜索，能实现精确的 kNN 搜索，确保不会因近似算法（如 hnsw）或量化（int8/int4/bbq）导致相关信息被遗漏。
hnsw 系列（包括 int8_hnsw、int4_hnsw 等）是近似搜索，虽能提升速度和减少内存，但会牺牲精度，可能漏掉与问题高度相关的知识库条目（例如 “发票校验码” 与 “防伪加密字段” 的精准对应）。
量化索引（int8/int4/bbq）通过压缩向量降低内存，但会进一步损失精度，对于单选题这种对 “精确匹配” 要求极高的场景不适用。
因此，flat 是最优选择。
2. 向量匹配类型的选择：优先COSINE
单选题的问题与答案本质是 “文本语义匹配”，核心是判断 “问题的语义方向” 与 “知识库中对应条目的语义方向” 是否一致，而非向量的绝对距离或模长。
COSINE 专注于向量夹角（语义方向），忽略模长差异，最适合文本语义匹配。例如 “公司马克杯容量是多少” 与 “公司马克杯 390ml” 的语义方向高度一致，COSINE 能精准捕捉这种关联。
L2（欧式距离）在高维文本向量中易受 “距离趋同效应” 影响，可能误判语义相似但距离稍远的向量；IP（点积）受模长影响，而文本 embedding 的模长通常无实际意义（不代表 “重要性”）。
HAMMING（二进制向量）和 JACCARD（集合特征）不适合连续文本 embedding，排除。
因此，COSINE 是最优选择。
3. 搜索类型的选择：优先all（向量 + 关键词）
单选题的问题往往包含两类关键信息：语义意图（如 “什么是发票校验码” 的核心是 “定义”）和实体 / 术语（如 “发票校验码”“公司马克杯”“ml”）。
向量搜索（vector）擅长捕捉语义意图，但可能漏掉精确术语（如 “ml” 若在 embedding 中被弱化，可能匹配到 “升” 的相关内容）。
关键词搜索（keyword）擅长捕捉精确术语（如 “公司马克杯”“校验码”），但无法理解语义变体（如 “公司的马克杯容量” 与 “公司马克杯多少 ml” 的同义性）。
两者结合（all）可互补：关键词确保精确术语不丢失，向量确保语义变体被覆盖，最大化召回相关条目的概率。
因此，all 是最优选择。
4. 检索结果数量：建议3-5 条
结果数量需平衡 “覆盖相关信息” 和 “减少噪声”：
太少（如 1-2 条）：可能因检索偏差漏掉唯一正确的知识库条目（例如问题表述稍有变体时，正确条目可能排在第 3 位）。
太多（如 8-10 条）：易引入无关信息（例如 “公司马克杯” 可能混入 “公司其他产品”“其他品牌马克杯” 的条目），干扰后续 LLM 对选项的判断。
3-5 条：既能覆盖大概率相关的条目（单选题的答案通常集中在少数几条紧密相关的知识中），又能控制噪声，是兼顾精度和召回的合理选择。

但在实测之后发现，搜索类型为all时，测试用例会报错；而搜索类型为vector时，会更精准。

feishu文档的分片逻辑拆解

💡

结论：

飞书文档的分片逻辑依赖目录层级：通过解析文档的层级结构（level），建立父子节点关系，最终将 “上层标题 + 当前段落内容” 拼接为一个分片。这样的分片保留了内容所属的目录上下文，避免了孤立段落的信息丢失，更适合后续 RAG 检索时的上下文匹配。

从代码逻辑来看，飞书（feishu）文档的分片确实基于目录层级进行处理，核心是通过构建文档的层级关系（父子节点），将 “标题 + 下属内容” 拼接为最终的分片，保留了目录上下文。

具体流程如下：

  1. 解析飞书文档为带层级的节点列表

首先通过 parseIntoNodeList(data) 将飞书文档解析为 List<ChunkData>（即 nodeList）。这里的 ChunkData 应该包含每个内容块的层级（level）、原始内容（data）、ID 等信息（推测飞书文档的结构化数据中包含目录层级标记，如一级标题、二级标题、正文段落等，对应不同的 level）。

  1. 构建目录层级树（父子关系）
  • 先创建根节点（root，level=0），并用 tree（Map<Integer, ChunkData>）存储不同层级的节点（key 为 level，value 为该层级的节点）。
  • 遍历 nodeList 中的每个节点，根据其 level 找父节点：父层级为 level-1，如果该层级不存在，则逐级递减（father_level -=1），直到找到存在的父层级或根节点（level=0）。
  • 找到父节点后，将当前节点的 ID 加入父节点的 childrenId（子节点 ID 列表），同时设置当前节点的 parentId 为父节点的 ID。这一步的目的是建立完整的目录层级关系（如 “一级标题”→“二级标题”→“正文段落” 的父子关联）。
  1. 过滤无效节点并拼接分片内容
  • 先过滤掉 nodeList 中以 # 开头的节点（推测是标题节点本身，需排除，只保留正文类节点）。
  • 通过 parentId 找到其父节点（上层标题），调用 getDataByParentId 获取父节点的标题内容（title）。
  • 将当前节点的内容（item.getData()）与父节点标题（title）拼接，形成 title + chunk 的组合内容（例如 “1. 发票基础概念 \n 什么是发票校验码？...”）。
  • 最终将拼接后的内容作为分片数据（chunkData.setData(...)），加入 chunkResult。

大模型推荐微调：

1. prompt_text：建议主动配置，而非使用默认值
    单选题的答案具有强确定性（仅需输出选项字母，如 A、C），且依赖文档与选项的精确匹配。默认的 “拼接前 5 个 chunk 和 query” 的模板可能缺乏针对性，容易导致模型输出冗余内容（如解释性文字）或偏离选项范围。推荐配置示例："请严格根据参考文档内容，从题目给出的选项中选择唯一正确答案，仅输出选项字母（如A、B、C），无需额外解释。参考文档：{docList}，问题：{query}"通过明确任务边界（仅输出选项字母）和约束逻辑（严格依据文档），直接引导模型聚焦核心目标，减少无效输出干扰。
2. top_k：建议调小至5-10（默认 20）
top_k控制生成时考虑的候选词数量。单选题的答案是离散的选项（如 A、B、C），无需模型在大量候选词中 “发散思考”，反而需要聚焦高概率的正确选项。
若top_k过大（如默认 20），可能纳入低概率的错误选项，增加误选风险；
调小至 5-10，可让模型仅关注概率最高的少数候选，更精准匹配文档支持的正确选项。
3. top_p：建议设置为0.5-0.7（默认 0.6 可保留）
top_p通过累积概率筛选候选词（如 0.6 表示纳入概率累积达 60% 的词）。对于单选题，需平衡 “覆盖正确选项” 和 “排除噪音”：
若top_p过高（如＞0.8），会纳入更多低概率词，增加随机性；
若过低（如＜0.5），可能因筛选过严排除正确选项；默认 0.6 已处于合理区间，可保留或微调至 0.5（更聚焦高概率候选）。
4. temperature：建议调低至0.1-0.3（默认 0.6 需下调）
temperature控制输出随机性（值越低越保守、确定）。单选题的核心是 “复现文档中的正确选项”，而非 “创造性生成”，因此需最大限度降低随机性：
若temperature过高（如默认 0.6），模型可能因 “随机波动” 偏离文档支持的正确选项；
调低至 0.1-0.3，可让模型严格依赖输入的文档和问题信息，优先选择概率最高的选项，减少 “猜测” 倾向。
5. max_new_tokens：建议调小至5-10（默认 1000 需大幅下调）
max_new_tokens控制生成长度。单选题的答案仅需 1-2 个字符（如 A、C），过长的长度限制会导致模型可能输出无关内容（如解释、重复选项），反而增加错误风险。设置为 5-10 即可满足需求（足够容纳选项字母 + 避免意外冗余），同时提高生成效率。
6. repetition_penalty：建议保留默认1.1或微调至1.0-1.2
repetition_penalty用于抑制重复输出。由于单选题输出内容极短（仅选项字母），重复风险较低，无需大幅调整：
1.1 的默认值可轻微抑制重复（如避免 “AA”“CC” 等无意义输出）；
若出现少量重复，可微调至 1.2；若输出过于僵硬，可降至 1.0。


总结配置核心逻辑
通过明确 prompt 约束输出格式、降低随机性（temperature）、缩小候选范围（top_k/top_p）、限制生成长度（max_new_tokens），让模型聚焦 “文档 - 选项” 的精确匹配，最大限度减少干扰因素，从而提高单选题的回答准确率。

生成模型源码逻辑解析 & 提示词优化

因此提示词构建也是十分重要的一环。

提示词优化核心：在保留 “系统提示 + 文档 + 问题” 核心结构的基础上，通过模块化标题分隔、关键规则重申、日志增强，让模型更易识别各模块功能，同时提升代码可维护性和调试便利性。

示例：

def generate_prompt_text(query, docList):
    """
    生成优化后的单项选择题答题Prompt
    :param query: 用户输入的单项选择题（含选项，格式示例："问题：xxx？A.xx B.xx C.xx D.xx"）
    :param docList: 前置召回的知识库文档列表（需确保内容去重、无冗余，表格内容已按"|"分割）
    :return: 结构化Prompt文本
    """
    # 1. 定义优化后的系统提示（模块化、关键规则加粗，替换原外部SYSTEM_PROMPT，也可设为外部常量）
    OPTIMIZED_SYSTEM_PROMPT = """
# 一、角色与核心任务
角色：企业级单项选择题问答专家
任务：仅依据【参考文档】内容，输出唯一正确选项（仅A/B/C/D字母），不附加任何解释、思考过程或引用来源；每题独立，不受其他题目影响。

# 二、核心约束（必须严格遵守）
1. **答案唯一来源**：仅使用后续【参考文档】内容作答，无文档依据时不做任何推断；
2. **表格解读规则**：文档中表格以"|"为列分隔符，"√"表示"享有/是"，无"√"表示"不享有/否"；
3. **输出格式强制**：仅输出选项字母（如A），任何额外文字（如"答案：B"）均视为无效。

# 三、示例（理解答题逻辑）
示例1：
【参考文档】：企业级问答机器人仅依赖知识文档列表（docList）作答。
【问题】：机器人作答依赖什么？A.用户历史 B.知识文档列表 C.外部网站 D.数据库
【答案】：B

示例2：
【参考文档】：|假期类型|实习生|事假|√|法定节假日|√|
【问题】：实习生可享受哪些假期？A.法定年休假 B.事假、法定节假日 C.婚假 D.产假
【答案】：B
    """
    
    # 2. 处理文档列表：添加模块标题、标注文档数量，明确"唯一依据"属性
    # （若docList为空，需提示模型无法作答，避免无效输出）
    if not docList:
        processed_docs = "【参考文档】：无召回知识库内容，无法作答（仅输出A/B/C/D的无效情况）"
    else:
        # 给每个文档加序号，方便日志追溯；标注"唯一答题依据"强化约束
        doc_items = [f"【文档{idx+1}】：{doc.strip()}" for idx, doc in enumerate(docList)]
        processed_docs = f"# 四、参考文档（唯一答题依据，共{len(docList)}份）\n" + "\n\n".join(doc_items)
    
    # 3. 处理问题：添加"作答要求重申"，避免模型遗忘规则
    processed_query = f"# 五、问题与作答要求\n【问题】：{query.strip()}\n【要求】：1. 仅用【参考文档】内容；2. 仅输出A/B/C/D字母。"
    
    # 4. 拼接最终Prompt（按"指令→依据→任务"逻辑排序，符合模型信息处理习惯）
    prompt = f"{OPTIMIZED_SYSTEM_PROMPT}\n\n{processed_docs}\n\n{processed_query}"
    
    # 5. 增强日志：记录文档数量、Prompt长度，方便调试（如文档过多导致Prompt超长）
    logger.info(f"生成Prompt：召回文档{len(docList)}份，Prompt长度{len(prompt)}字符")
    print(f"生成Prompt内容：\n{prompt}\n")
    
    return prompt
