1.MYSQL自增主键，在删除数据后，主键依然按删除数据的最大主键增长，而不是按已有数据的主键连续增长

  • 场景：每次在数据库删除数据，再插入数据后，其自增主键就会按已删除数据的最大主键自增。而不是已有数据的最大主键自增。
  • 解决方法：每次删除后执行这句就好了：

```SQL ALTER TABLE tablename AUTO_INCREMENT =1 -- 将下次主键自增长启始位置设置为1 ```

  • 原理：

😍 将AUTO_INCREMENT =1表示将下次主键自增长启始位置设置为1，但如果表中已经有比1大的主键了就默认下次自增从已有的最大主键+1开始。

比如表中已经有1,2,3,4这4个id,删掉1这个id后，就算执行AUTO_INCREMENT =1，下一次自增的id也会是5。

2.使用limit查询100w行数据，这样有啥问题？

  • 回表

我们一般对于查询频率比较高的字段会建立索引。索引会提高我们的查询效率。我们上面的语句使用了SELECT * FROM user，但是我们并不是所有的字段都建立了索引。当从索引文件中查询到符合条件的数据后，还需要从数据文件中查询到没有建立索引的字段。那么这个过程称之为回表。

  • 覆盖索引

如果查询的字段正好创建了索引了，比如 SELECT create_time FROM user，我们查询的字段是我们创建的索引，那么这个时候就不需要再去数据文件里面查询，也就不需要回表。这种情况我们称之为覆盖索引。

  • IO

回表操作通常是IO操作，因为需要根据索引查找到数据行后，再根据数据行的主键或唯一索引去聚簇索引中查找具体的数据行。

聚簇索引一般是存储在磁盘上的数据文件，因此在执行回表操作时需要从磁盘读取数据，而磁盘IO是相对较慢的操作。

LIMTI 2000,10 ？

你有木有想过LIMIT 2000,10会不会扫描1-2000行，你之前有没有跟我一样，觉得数据是直接从2000行开始取的，前面的根本没扫描或者不回表。其实这样的写法，一个完整的流程是查询数据，如果不能覆盖索引，那么也是要回表查询数据的。

现在你知道为什么越到后面查询越慢了吧！

问题总结

我们现在知道了LIMIT 遇到后面查询的性能越差，性能差的原因是因为要回表，既然已经找到了问题那么我们只需要减少回表的次数就可以提升查询性能了。

解决方案

既然覆盖索引可以防止数据回表，那么我们可以先查出来主键id（主键索引），然后将查出来的数据作为临时表然后 JOIN 原表就可以了，这样只需要对查询出来的5条结果进行数据回表，大幅减少了IO操作。

3.MYSQL支持哪些存储引擎？默认使用哪个？

  1. MySQL 支持多种存储引擎，你可以通过 SHOW ENGINES 命令来查看 MySQL 支持的所有存储引擎。
  1. MySQL 当前默认的存储引擎是 InnoDB。并且，所有的存储引擎中只有 InnoDB 是事务性存储引擎，也就是说只有 InnoDB 支持事务。

4.MYISAM和InnoDB的区别

MySQL 5.5 之前，MyISAM 引擎是 MySQL 的默认存储引擎，可谓是风光一时。

虽然，MyISAM 的性能还行，各种特性也还不错（比如全文索引、压缩、空间函数等）。但是，MyISAM 不支持事务和行级锁，而且最大的缺陷就是崩溃后无法安全恢复。

MySQL 5.5 版本之后，InnoDB 是 MySQL 的默认存储引擎。

区别：

  1. InnoDB 支持行级别的锁粒度，MyISAM 只支持表级别的锁粒度。

MyISAM 只有表级锁(table-level locking)，而 InnoDB 支持行级锁(row-level locking)和表级锁,默认为行级锁。

  1. MyISAM 不提供事务支持。InnoDB 提供事务支持，实现了 SQL 标准定义了四个隔离级别。
  1. MyISAM 不支持外键，而 InnoDB 支持。
  1. MyISAM 不支持 MVCC，而 InnoDB 支持。

毕竟 MyISAM 连行级锁都不支持，而MVCC其实就是行级锁的一个升级，可以有效减少加锁，提升性能。

  1. 虽然 MyISAM 引擎和 InnoDB 引擎都是使用 B+Tree 作为索引结构，但是两者的实现方式不太一样。

InnoDB 引擎中，其数据文件本身就是索引文件。相比 MyISAM，索引文件和数据文件是分离的，其表数据文件本身就是按 B+Tree 组织的一个索引结构，树的叶节点 data 域保存了完整的数据记录。

  1. MyISAM 不支持数据库异常崩溃后的安全恢复，而 InnoDB 支持。

因为这个恢复依赖于redo log，而MYISAM不支持事务呀。

  1. InnoDB 的性能比 MyISAM 更强大。

5.哪些操作会加表级锁？哪些操作会加行级锁？简单举例说一下

  1. 表级锁包括：表锁、元数据锁、意向锁、AUTO-INC锁。
  • 对于表锁而言，当存储引擎不支持行级锁时，使用表锁。SQL 语句没有匹配到索引时，使用表锁。
  • 对于元数据锁而言，对表做增删改查时，会加上 MDL 读锁。对表结构做变更时，会加上 MDL 写锁。
  • 对于意向锁而言，对表中的行记录加锁时，会用到意向锁。
  1. 而对于行级锁而言，增删改查匹配到索引时，会使用行级锁。那如果匹配不到索引，就会将使用表锁将整张表锁住。

6.MYSQL如何使用乐观锁和悲观锁？

悲观锁与乐观锁是人们定义出来的概念，你可以理解为一种思想，是处理并发资源的常用手段。

悲观锁

对于数据的处理持悲观态度，总认为会发生并发冲突，获取和修改数据时，别人会修改数据。所以在整个数据处理过程中，需要将数据锁定。

悲观锁的实现，通常依靠数据库提供的锁机制实现，比如 mysql 的排他锁，select …. for update 来实现悲观锁。

乐观锁

对数据的处理持乐观态度，乐观的认为数据一般情况下不会发生冲突，只有提交数据更新时，才会对数据是否冲突进行检测。

如果发现冲突了，则返回错误信息给用户，让用户自已决定如何操作。

乐观锁的实现不依靠数据库提供的锁机制，需要我们自已实现，实现方式一般是记录数据版本，

一种是通过版本号，一种是通过时间戳。

给表加一个版本号或时间戳的字段，读取数据时，将版本号一同读出，数据更新时，将版本号加 1。

当我们提交数据更新时，判断当前的版本号与第一次读取出来的版本号是否相等。如果相等，则予以更新，否则认为数据过期，拒绝更新，让用户重新操作。

8.B+树做索引比红黑树好在哪里？

B/B+树与红黑树等相比，最大的优势是：树高更小。

  1. BST：中序遍历有序，左小右大，一般用于构建二分查找树。但是有时会退化为链表，复杂度为O(n)，因此引入AVL。
  1. AVL：严格平衡二叉树，左右节点的高度差(平衡因子)不大于1，但插入、删除时，为了维护树形，旋转效率太低，引入红黑树。
  1. 红黑树：在红黑树中，插入、删除一般不会破坏红黑特性，不需要频繁地调整树的形态，即使需要，也可以在常数级时间内完成。保证了：最长路径 ≤ 最短路径的2倍。但在磁盘中，树还是太高，所需的IO次数还是太多。因此引入B树。
  1. B树：将二叉树改为多路平衡查找树，B树的每个非叶子结点可以有多个子树。树高降低。
  1. B+树：进一步降低树高，且叶结点用双向链表连接成链表，范围查询更高效。

9、行级锁的使用有什么注意事项？

锁全表！！！

InnoDB 的行锁是针对索引字段加的锁，表级锁是针对非索引字段加的锁。

当我们执行 UPDATE、DELETE 语句时，如果 WHERE条件中字段没有命中唯一索引或者索引失效的话，就会导致扫描全表对表中的所有行记录进行加锁。这个在我们日常工作开发中经常会遇到，一定要多多注意！！！

10、当前读和快照读的区别

  1. 快照读（一致性非锁定读）就是单纯的 SELECT 语句，但不包括下面这两类 SELECT 语句：

```SQL SELECT ... FOR UPDATE # 共享锁 可以在 MySQL 5.7 和 MySQL 8.0 中使用 SELECT ... LOCK IN SHARE MODE; # 共享锁 可以在 MySQL 8.0 中使用 SELECT ... FOR SHARE; ```

快照即记录的历史版本，每行记录可能存在多个历史版本（多版本技术）。

快照读的情况下，如果读取的记录正在执行 UPDATE/DELETE 操作，读取操作不会因此去等待记录上 X 锁的释放，而是会去读取行的一个快照。

只有在事务隔离级别 RC(读取已提交) 和 RR（可重读）下，InnoDB 才会使用一致性非锁定读：

  • 在 RC 级别下，对于快照数据，一致性非锁定读总是读取被锁定行的最新一份快照数据。
  • 在 RR 级别下，对于快照数据，一致性非锁定读总是读取本事务开始时的行数据版本。

快照读比较适合对于数据一致性要求不是特别高且追求极致性能的业务场景。

  1. 当前读 （一致性锁定读）就是给行记录加 X 锁或 S 锁。

当前读的一些常见 SQL 语句类型如下：

```SQL # 对读的记录加一个X锁 SELECT...FOR UPDATE # 对读的记录加一个S锁 SELECT...LOCK IN SHARE MODE # 对读的记录加一个S锁 SELECT...FOR SHARE # 对修改的记录加一个X锁 INSERT... UPDATE... DELETE... ```

11.聚集索引和非聚集索引的区别？非聚集索引一定回表查询吗？

  1. 聚簇索引（Clustered Index）即索引结构和数据一起存放的索引，并不是一种单独的索引类型。InnoDB 中的主键索引就属于聚簇索引。

优点：

  • 查询速度非常快：聚簇索引的查询速度非常的快，因为整个 B+树本身就是一颗多叉平衡树，叶子节点也都是有序的，定位到索引的节点，就相当于定位到了数据。相比于非聚簇索引， 聚簇索引少了一次读取数据的 IO 操作。
  • 对排序查找和范围查找优化：聚簇索引对于主键的排序查找和范围查找速度非常快。

缺点：

  • 依赖于有序的数据：因为 B+树是多路平衡树，如果索引的数据不是有序的，那么就需要在插入时排序，如果数据是整型还好，否则类似于字符串或 UUID 这种又长又难比较的数据，插入或查找的速度肯定比较慢。
  • 更新代价大：如果对索引列的数据被修改时，那么对应的索引也将会被修改，而且聚簇索引的叶子节点还存放着数据，修改代价肯定是较大的，所以对于主键索引来说，主键一般都是不可被修改的。
  1. 非聚簇索引(Non-Clustered Index)即索引结构和数据分开存放的索引，并不是一种单独的索引类型。二级索引(辅助索引)就属于非聚簇索引。MySQL 的 MyISAM 引擎，不管主键还是非主键，使用的都是非聚簇索引。

非聚簇索引的叶子节点并不一定存放数据的指针，因为二级索引的叶子节点就存放的是主键，根据主键再回表查数据。

优点：

  • 更新代价比聚簇索引要小 。非聚簇索引的更新代价就没有聚簇索引那么大了，非聚簇索引的叶子节点是不存放数据的。

缺点：

  • 依赖于有序的数据:跟聚簇索引一样，非聚簇索引也依赖于有序的数据
  • 可能会二次查询(回表):这应该是非聚簇索引最大的缺点了。 当查到索引对应的指针或主键后，可能还需要根据指针或主键再到数据文件或表中查询。
  1. 非聚簇索引一定回表查询吗？

非聚簇索引不一定回表查询。

试想一种情况，用户准备使用 SQL 查询用户名，而用户名字段正好建立了索引。

```SQL SELECT name FROM table WHERE name='guang19'; ```

那么这个索引的 key 本身就是 name，查到对应的 name 直接返回就行了，无需回表查询。

即使是 MYISAM 也是这样，虽然 MYISAM 的主键索引确实需要回表，因为它的主键索引的叶子节点存放的是指针。但是！如果 SQL 查的就是主键呢?

```SQL SELECT id FROM table WHERE id=1; ```

主键索引本身的 key 就是主键，查到返回就行了。这种情况就称之为覆盖索引了。

如果一个索引包含（或者说覆盖）所有需要查询的字段的值，我们就称之为 覆盖索引。

12、Hash索引和B+树索引的优劣分析

MySQL 的 InnoDB 存储引擎不直接支持常规的哈希索引，但是，InnoDB 存储引擎中存在一种特殊的“自适应哈希索引”，自适应哈希索引并不是传统意义上的纯哈希索引，而是结合了 B+Tree 和哈希索引的特点，以便更好地适应实际应用中的数据访问模式和性能需求。

自适应哈希索引的每个哈希桶实际上是一个小型的 B+Tree 结构。这个 B+Tree 结构可以存储多个键值对，而不仅仅是一个键。这有助于减少哈希冲突链的长度，提高了索引的效率。

既然哈希表这么快，为什么 MySQL 没有使用其作为索引的数据结构呢？

主要是因为： Hash 索引不支持顺序和范围查询，只支持等值查询。假如我们要对表中的数据进行排序或者进行范围查询，那 Hash 索引可就不行了。并且，每次 IO 只能取一个。

试想一种情况:

```SQL SELECT * FROM tb1 WHERE id < 500; ```

在这种范围查询中，优势非常大，直接遍历比 500 小的叶子节点就够了。而 Hash 索引是根据 hash 算法来定位的，难不成还要把 1 - 499 的数据，每个都进行一次 hash 计算来定位吗?这就是 Hash 最大的缺点了。

13、char和varchar的区别？

两者的主要区别在于：CHAR 是定长字符串，VARCHAR 是变长字符串。

  1. 存储长度区别：
  • CHAR 在存储时会在右边填充空格以达到指定的长度，检索时会去掉空格；
  • VARCHAR 在存储时需要使用 1 或 2 个额外字节记录字符串的长度，检索时不需要处理。
  1. 适合数据类型：
  • CHAR 更适合存储长度较短或者长度都差不多的字符串，例如 Bcrypt 算法、MD5 算法加密后的密码、身份证号码。
  • VARCHAR 类型适合存储长度不确定或者差异较大的字符串，例如用户昵称、文章标题等。

CHAR(M) 和 VARCHAR(M) 的 M 都代表能够保存的字符数的最大值，无论是字母、数字还是中文，每个都只占用一个字符.

14、VARCHAR(100)和 VARCHAR(10)的区别？

VARCHAR(100)和 VARCHAR(10)都是变长类型，表示能存储最多 100 个字符和 10 个字符。因此，VARCHAR (100) 可以满足更大范围的字符存储需求，有更好的业务拓展性。而 VARCHAR(10)存储超过 10 个字符时，就需要修改表结构才可以。

虽说 VARCHAR(100)和 VARCHAR(10)能存储的字符范围不同，但二者存储相同的字符串，所占用磁盘的存储空间其实是一样的，这也是很多人容易误解的一点。

不过，VARCHAR(100) 会消耗更多的内存。这是因为 VARCHAR 类型在内存中操作时，通常会分配固定大小的内存块来保存值，即使用字符类型中定义的长度。例如在进行排序的时候，VARCHAR(100)是按照 100 这个长度来进行的，也就会消耗更多内存。

15、DECIMAL 和 FLOAT/Double 的区别

DECIMAL 和 FLOAT 的区别是：DECIMAL 是定点数，FLOAT/DOUBLE 是浮点数。DECIMAL 可以存储精确的小数值，FLOAT/DOUBLE 只能存储近似的小数值。

💡 定点数：小数点的位置在计算机的存储是固定的。一个小数的整数部分和小数部分分别转化为二进制的表示。

定点数并不是仅仅只能表示整数，定点数也可以表示小数。 浮点数同样可以表示小数和整数；定点数和浮点数只是计算机表示数据的两种不同方式而已。

DECIMAL 用于存储具有精度要求的小数，例如与货币相关的数据，可以避免浮点数带来的精度损失。

在 Java 中，MySQL 的 DECIMAL 类型对应的是 Java 类 java.math.BigDecimal。

Decimal的底层实现：

BigDecimal保证精度的解决思路其实极其的简单朴素，还是用一句话来解释：

十进制整数在转化成二进制数时不会有精度问题，那么把十进制小数扩大N倍让它在整数的维度上进行计算，并保留相应的精度信息(小数点的位置)。

使用Decimal时需要注意的事项：

  • 1.MySql中的统计函数：sum()、avg()等等，给JAVA应用默认返回的是Double类型！在处理小数的时候可能产生精度问题，此时把预处理的字段数据用cast强转成decimal类型，那么MySql给JAVA应用返回的就是BigDecimal类型。
  • 2.不要使用BigDecimal（double），存在精度损失风险，因为实际存储的值是double数值的二进制表示，可能会有精度损失。
  • 3.使用除法注意事项：使用roundingMode指明结果的保留规则，否则遇到无限循环小数时，会报错。
  • 4.BigDecimal等值比较时，使用CompareTo（），而不是equals（），因为equals会比较精度，而compareTo会忽略精度，那些无实际意义的0会自动忽略。

16、为啥不推荐使用text和blob？

TEXT 类型类似于 CHAR（0-255 字节）和 VARCHAR（0-65,535 字节），但可以存储更长的字符串，即长文本数据，例如博客内容。

BLOB 类型主要用于存储二进制大对象，例如图片、音视频等文件。

在日常开发中，很少使用 TEXT 类型，但偶尔会用到，而 BLOB 类型则基本不常用。如果预期长度范围可以通过 VARCHAR 来满足，建议避免使用 TEXT。

数据库规范通常不推荐使用 BLOB 和 TEXT 类型，这两种类型具有一些缺点和限制，例如：

  • 不能有默认值。
  • 在使用临时表时无法使用内存临时表，只能在磁盘上创建临时表。
  • 检索效率较低。
  • 不能直接创建索引，需要指定前缀长度。
  • 可能会消耗大量的网络和 IO 带宽。
  • 可能导致表上的 DML 操作变慢。

17、如何排查慢SQL？

  1. 开启慢查询日志，记录执行时间超过阈值的SQL语句。
  1. 使用EXPLAIN或其他数据库分析工具分析这些慢查询，查看执行计划，识别是否有全表扫描、索引失效等情况。
  1. 根据分析结果，优化SQL语句，比如添加合适的索引，调整查询条件，或者改写查询逻辑。
  1. 对于复杂查询，可以考虑分解成多个简单查询，减少单次查询负担。

18、数据库连接池是怎么加快数据库访问的？

● 客户端连接池：减少多次创建数据库连接时，频繁出现的TCP三次握手、四次挥手、SSL握手等过程。

○ 客户端连接池免了等待网络握手的时间

● 服务端连接池：减少多次创建数据库连接时，频繁创建和销毁工作线程造成的资源开销。

○ 服务端连接池避免了等待线程创建的时间 ...

1.什么是连接池

数据库连接池负责分配、管理和释放数据库连接，它允许应用程序重复使用一个现有的数据库连接，而不是再重新建立一个。

在程序初始化时，预先创建一定数量的数据库连接，并对其进行集中管理，就构成了数据库连接池，由程序动态地对池中的连接进行申请、使用和释放，既保证了较快的数据库读写速度，又提高了安全可靠性。

2.为何要用连接池/使用连接池的好处

使用数据库连接池好处：

  • 资源重用：避免了频繁的创建、释放连接引起的性能开销，在减少系统消耗的基础上，也增进了系统运行环境的平稳性（减少内存碎片以及数据库临时进程/线程的数量）
  • 更快的系统响应速度：数据库连接池在初始化过程中，往往已创建了若干数据库连接于池中备用，此时连接的初始化工作均已完成，对于业务请求处理而言，直接利用现有可用连接，避免了从数据库连接初始化和释放过程的开销，从而缩减了系统整体响应时间
  • 统一的连接管理，避免连接数据库连接泄漏：在较为完备的数据库连接池实现中，可根据预先的连接占用超时设定，强制收回被占用连接。从而避免了常规数据库连接操作中可能出现的资源泄漏。

3.传统的连接机制与数据库连接池的运行机制区别

  1. 不使用连接池的流程

TCP建立连接的三次握手 MySQL认证的三次握手 真正的SQL执行 MySQL的关闭 TCP的四次握手关闭

  1. 使用连接池：

第一次访问的时候，需要建立连接。 但是之后的访问，均会复用之前创建的连接，直接执行SQL语句。

4.连接池和线程池的区别

  • 连接池：被动分配，用完放回。
  • 线程池：主动干活，有任务到来，线程不断取出任务执行。

19、MYSQL中为什么要用自增主键，有什么好处？

在 MySQL 中使用自增主键有以下几个好处：

  1. 唯一性和简洁性： 自增主键可以确保每行数据在表中都有唯一的标识符。由于它是自增的，所以不需要应用程序来生成唯一标识符，这使得数据库设计更简单，避免了可能出现的重复键的问题。
  1. 快速查找和排序： 自增主键通常基于整数类型，例如 INT 或 BIGINT。由于这些类型的索引是按顺序排列的，因此查询、排序和连接等操作都会更加高效。数据库可以利用这种顺序来更快地查找和访问数据，而无需执行额外的排序操作。
  1. 降低索引碎片： 自增主键的值是连续的，因此插入新数据时，不会造成数据页的分裂和索引碎片的产生。这有助于减少数据库维护所需的资源，并提高插入性能。
  1. 提高性能： 使用自增主键的表在插入新数据时通常比具有复合主键或其他类型的主键更快，因为数据库引擎不需要检查和维护主键的唯一性。这可以提高插入操作的性能。
  1. 减少存储空间： 相比使用复合主键或其他类型的主键，自增主键通常占用更少的存储空间，因为它们只是简单的整数值，而不需要存储多个列的组合。

总的来说，使用自增主键可以简化数据库设计、提高查询和排序性能、减少索引碎片、提高插入性能，并节省存储空间。这些优点使得自增主键成为设计数据库表时常用的一种方式。

21、B+树能存多少数据

3层B+树大概可以存：

  • 主键为bigint：约2000w
  • 主键为int：约4000w

在Innodb存储引擎里面，最小存储单元是页，而一个页的大小默认是16KB。 一个节点的大小就是一页。

在MySQL Innodb存储引擎中的B+树的一个节点大小为“1页”，也就是16k。

也即代表B+树的每个节点可以存16KB数据。

  1. 非叶子节点：存储内容：主键+指针

指针是用来指向下一个“节点”的。

  • 假设主键类型为bigint，占用8Byte，指针可以设置为占用6Byte，总共14Byte。这样就可以算出一个非叶子节点大概可以存放16KByte/14Byte=1170个“主键+指针”的组合。
  • 假设主键类型为int，占用4Byte，指针可以设置为占用6Byte，总共10Byte。这样就可以算出一个非叶子节点大概可以存放16KByte/10Byte≈1600个“主键+指针”的组合。
  1. 叶子节点：存储真实数据

在B+树中，真正的数据是只存储在叶子节点中的。

这里我们假设我们的一行数据大小是1K，那么我们一个叶子节点就可以存16KByte/10Byte=16条（行）数据。

由此，可以推算出公式：

两层总数 = 非叶子节点(根) * 叶子节点。

三层总数 = 非叶子节点(根) 非叶子节点 叶子节点。

  1. 主键为bigint（约2000w）：

2层B+树的话：可以存放1170个*16条=18720条（行）数据。 3层B+树的话：可以存放1170个**1170个*16条=21902400条（行）数据。

  1. 主键为int（约4000w）：

思路：根节点存放于1页中(16KB)，"主键+指针"大小为10B，因此1页可以存放16KB/10B=1600个非叶子结点。此时就属于1600阶B+树。

而一个叶子节点也是一页，"一条数据为1KB"，那么1页可以存放16条数据。

因此有：

  • 2层B+树的话：可以存放1600个16条=25600条（行）数据。
  • *3层B+树的话：可以存放1600个**1600个*16条=40960000条（行）数据。

22、SQL中关键字的执行顺序是？

在 SQL 查询语句中，关键字的执行顺序通常按照以下顺序进行：

  1. FROM： 指定要查询的数据表或者视图。
  1. WHERE： 对数据进行筛选，仅选择满足指定条件的行。
  1. GROUP BY： 将查询结果按照指定的列分组，通常与聚合函数一起使用。
  1. HAVING： 对分组后的数据进行筛选，仅选择满足指定条件的分组。
  1. SELECT： 选择要查询的列，或者进行一些列的运算。
  1. DISTINCT： 对查询结果进行去重，仅保留不同的行。
  1. ORDER BY： 对查询结果进行排序，可以指定一个或多个列，并指定排序方式（升序或降序）。
  1. LIMIT / OFFSET： 对查询结果进行分页，指定返回结果的起始位置和数量。

在实际使用中，有些情况下并不一定按照这个顺序执行，例如子查询、联合查询等复杂情况可能会改变执行顺序。但通常情况下，上述顺序是执行查询语句时的一般规则。

举例：

（8）SELECT（9）DISTINCT <select_list>
（1）FROM <left_table>
（3）<join_type> JOIN <right_table>
（2）ON <join_condition>
（4）WHERE <where_condition>
（5）GROUP BY <grout_by_list>
（6）WITH {CUTE|ROLLUP}
（7）HAVING <having_condition>
（10）ORDER BY <order_by_list>
（11）LIMIT <limit_number>

💡 每步关键字执行的结果都会形成一个虚表，编号大的关键字执行的动作都是在编号小的关键字执行结果所得的虚表上进行（或者说编号大的关键字处理的对象是编号小的关键执行过后得到的虚表），以此类推。

23、Join、Left Join、Inner Join、right Join

JOIN操作用于将两个或多个表的行组合在一起，基于这些表之间的共同列。常见的JOIN类型有LEFT JOIN、RIGHT JOIN和INNER JOIN。

  1. Inner Join（内连接）

内连接是最常用的JOIN类型，它会返回两个表中具有匹配值的行。

如果某个表中的行在另一个表中没有匹配的值，则不会返回该行。

```SQL SELECT column_name(s) FROM table1 INNER JOIN table2 ON table1.column_name = table2.column_name; ```

  1. LEFT JOIN（左连接）

左连接会返回左表中的所有行，即使在右表中没有匹配的值。

如果在右表中没有匹配的值，则会返回NULL。

```SQL SELECT column_name(s) FROM table1 LEFT JOIN table2 ON table1.column_name = table2.column_name; ```

  1. RIGHT JOIN（右连接）

返回右表中的所有行，即使在左表中没有匹配的值。

如果在左表中没有匹配的值，则会返回NULL。

总结：

  • left join: 包含左表的所有行，对应的右表行可能为空。
  • right join: 包含右表的所有行，对应的左表行可能为空。
  • inner join: 只包含左右表都匹配并且不为空的行。

24、数据库大量请求读写时，性能问题主要是什么带来的？

  1. 数据库连接池瓶颈： 大量请求可能导致数据库连接池的资源竞争，当连接池中的连接数不足以满足请求时，会造成连接等待和排队，降低了数据库的响应速度。
  1. 数据库锁竞争： 大量并发的读写请求可能导致数据库中的行级锁、表级锁或者其他类型的锁发生竞争，当多个请求试图同时修改同一行数据或者同一张表时，会导致锁等待和阻塞，降低了数据库的并发处理能力。
  1. 索引性能问题： 大量的读写请求可能导致数据库中的索引出现性能问题，例如频繁的更新操作可能导致索引失效或者产生大量的碎片，影响了查询性能。
  1. SQL语句效率问题： 大量的 SQL 查询和更新操作可能导致数据库服务器的 CPU 和内存资源消耗过高，例如查询语句中的 join 操作或者子查询过于复杂，更新语句中的索引更新过于频繁等，都会影响数据库的性能。
  1. 硬件资源限制： 大量的请求可能超出了数据库服务器的硬件资源限制，例如 CPU、内存、磁盘 IO 等资源的限制，导致数据库服务器的性能达到瓶颈。
  1. 数据库设计问题： 数据库的设计问题也可能影响性能，例如表结构设计不合理、索引设计不恰当、数据库范式设计不合适等，都会影响数据库的性能。

25、数据库调优由几部分构成：

总的来说分为以下三部分：

SQL调优

这是最常用、每一个技术人员都应该掌握基本的SQL调优手段（包括方法、工具、辅助系统等）。这里以MySQL为例，最常见的方式是，由自带的慢查询日志或者开源的慢查询系统定位到具体的出问题的SQL，然后使用explain、profile等工具来逐步调优，最后经过测试达到效果后上线。这方面的细节，可以参考MySQL索引原理及慢查询优化。

架构层面的调优

这一类调优包括读写分离、多从库负载均衡、水平和垂直分库分表等方面，一般需要的改动较大，但是频率没有SQL调优高，而且一般需要DBA来配合参与。那么什么时候需要做这些事情？我们可以通过内部监控报警系统（比如Zabbix），定期跟踪一些指标数据是否达到瓶颈，一旦达到瓶颈或者警戒值，就需要考虑这些事情。通常，DBA也会定期监控这些指标值。

连接池调优

我们的应用为了实现数据库连接的高效获取、对数据库连接的限流等目的，通常会采用连接池类的方案，即每一个应用节点都管理了一个到各个数据库的连接池。随着业务访问量或者数据量的增长，原有的连接池参数可能不能很好地满足需求，这个时候就需要结合当前使用连接池的原理、具体的连接池监控数据和当前的业务量作一个综合的判断，通过反复的几次调试得到最终的调优参数。

26.MYSQL的分库分表

为什么要分表

核心原因：MYSQL的单表性能问题。

详细解释：当MYSQL的单表数据量超过一定大小，基于B+Tree的这种索引结构，高度会增加，而每增加一层高度，整个索引的扫描就会多一次IO，对应的响应时间会增加。

为什么要分库

核心原因：MYSQL容量上写入是很昂贵的资源

详细解释：MYSQL即使做了很多优化，但在存入数据时，依旧存在很多放大(维护索引结构等)，同时主从的架构，从库需要完整地复制写入容量，因此一套主从集群地写入容量，完全依赖于主库的硬件。如果写入超过了硬件的上限，就需要分库。
