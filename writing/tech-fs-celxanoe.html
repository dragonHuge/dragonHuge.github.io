Arthas理论&实践：阿里开源、Java在线诊断工具

2025-12-25"飞书工作积累" · 飞书原文 ↗

官方文档：https://arthas.aliyun.com/doc/

简介

Arthas 是一款线上监控诊断产品，通过全局视角实时查看应用 load、内存、gc、线程的状态信息，并能在不修改应用代码的情况下，对业务问题进行诊断，包括查看方法调用的出入参、异常，监测方法执行耗时，类加载信息等，大大提升线上问题排查效率。

实践1：线程池分析

背景：查看某容器下线程池的活跃线程数、等待队列负载情况，据此判断线程池配置是否合理。

场景实践：场景详情见@Talos理论 & 实践中的「Consumer配置调优」模块。

教程文档：https://arthas.aliyun.com/doc/quick-start.html#_5-%E9%80%9A%E8%BF%87-jad-%E6%9D%A5%E5%8F%8D%E7%BC%96%E8%AF%91-main-class

开始诊断

dashboard：当前系统的实时数据面板，ctrl+c退出。

  1. 如图所示，有两种线程：

  • 这个线程的个数，与talos consumer的GALAXY_TALOS_PRODUCER_THREAD_POOL_SIZE配置有关，其决定了：你的程序能同时并发拉取多少个分区的网络数据。

  • 风控平台-talos-passport-action-XX ：自定义的消费线程池。
  1. 线程状态：
  • RUNNABLE ： 运行中 / 就绪。即：“正在执行” 或者 “等待CPU调度执行”。
  • TIMED_WAITING： 限时等待。即：“线程主动挂起，暂停执行，不消耗CPU”。这有两种情况：1. QPS低，线程池空闲 2.线程挂起等待网络IO。
  1. 且上图中可看到消费线程池，同时运行的线程为34个，但代码中配置核心线程池数为25。因此可以判断：等待队列满，且TIMED_WAITING的线程是在等网络IO。
WORKER_POOL = new ThreadPoolExecutor(25, 50, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(2500), new ThreadFactory() {
    public Thread newThread(@NotNull Runnable r) {
        return new Thread(r, "风控平台-talos-passport-action-" + System.currentTimeMillis());
    }
}, new ThreadPoolExecutor.CallerRunsPolicy()
  1. systemload.average参数：显示的是 过去 1 分钟 的平均负载，用来衡量系统的繁忙程度。

简单理解：

  • CPU 核数 = 收费窗口的数量。（4 核 即有 4 个窗口）
  • System Load = 正在办理 + 正在排队的车辆总数。

判断负载高低，必须结合 CPU 核数 来看。你的机器是 4核：

  • Load < 4：健康。4 个窗口都在干活，偶尔有车来，马上就能办完，几乎不用排队。
  • Load = 4：满载。4 个窗口全部坐满，且没有空闲，但也没有车在排队。
  • Load > 4：过载（排队）。窗口全满，后面还有车排起了长龙。

图中值为126.65，意味着有126个任务在等待处理，但系统却只有4核。但奇怪的是，CPU负载仅有5%。

这说明有可能：当前进程任务属于IO密集型，大量请求卡在等待网络IO上。

但还有一种情况：宿主机负载高，这是容器的一个坑。--- 从后文分析得出结论，这里的高负载正是宿主机的原因，而非线程僵住。

Arthas 读到的 System Load 往往是物理宿主机的负载，而不是你当前容器的。如果这台物理机上别的容器在“挖矿”或跑大数据，你的 Load 也会显示 126，但你的 CPU 使用率很低。

因此，需要进一步分析线程池情况，继续向下探究。

ognl 表达式：万能探针，Arthas最强大的工具。

简介：OGNL 全称是 Object-Graph Navigation Language（对象图导航语言）。它就像是 Java 内存世界的 “GPS 导航” 或 “万能探针”。

在 Arthas 中，OGNL 是最强大的工具，因为它允许你通过一行简单的文本命令，直接钻进正在运行的 JVM 内存里，去读取或修改任意对象的属性、调用任意方法，而不需要你写一行 Java 代码或重启服务。

语法：

在 OGNL 表达式里，为了区分静态（Static）资源和普通资源，它有一套特殊的语法规则。

  1. TalosFingerPrintConsumer.WORKER_POOL // 假设 WORKER_POOL 是静态的
  2. // 第一个 @ 告诉它后面是类名，第二个 @ 告诉它后面是静态变量
@com.公司...TalosFingerPrintConsumer@WORKER_POOL
  1. workerPool.getQueue().size() // Java写法
workerPool.queue.size // OGNL写法，它会自动去调用 getQueue() 和 size()，或者直接访问字段
  1. myMap.get("Register") // java
myMap['Register'] // ognl

关键参数分析：等待队列为空(workQueue)、当前存活线程数(workers)=34、历史已完成任务总数(completedTaskCount)=0、但核心线程数(corePoolSize)=25。

分析参数后，发现2个诡异情况：

  1. 等待队列为空，说明任务未堆积，但此时存活线程数却大于核心线程数(34 > 25)。
  1. 历史已完成的任务总数为0，这说明没有任何已被完成的任务。

而这2个诡异情况，指向了一种可能：进程在被一大波流量冲击后，线程数从25->34，之后所有线程僵死阻塞，导致历史已完成的任务总数为0，且存货线程数始终为34。但从监控日志来看，服务是在正常运行的，因此不可能是这种情况。

以上，单靠查看线程池参数，无法解释上述情况，因此继续深入到某个线程内部，查看其执行情况。

Thread：查看当前线程信息，查看线程的堆栈信息

thread | grep 风控平台-talos // 查看当前所有线程信息（name like '风控平台-talos'）
thread 372 // 查看线程ID：372的堆栈情况。

抽样查看某几个线程的堆栈情况，发现大多如下：

此时核心线程数25，活跃线程数34。

从抽样的线程堆栈信息可知：线程并没有卡死，它只是在摸鱼(空闲等待)。

它正在执行 ThreadPoolExecutor.getTask()，进而调用队列的 poll() 方法。

意思是这个线程是空闲的并未僵死，它在盯着任务队列，等待任务分配，若这9个临时线程连续60s内未被调度，才会自动销毁，此时活跃线程数就会稳定到核心线程数上(25)。

另外一种方法佐证上述结论：对比workers.size 与 activeCount

  • activeCount：正在干活的线程数。其并不是 ThreadPoolExecutor 类中的一个“成员变量”，而是一个“方法”，是实时计算出来的。

上图可知，此时正在干活的线程数为0，而存活的线程数为34。所以这34个线程都在等待。

那么此时就可以回答上边的遗留问题：

💡

Q1：观察10分钟后，workers 依然是 34（或在 25-34 之间波动），而不是稳定降回 25，为什么？

答：

只要有一点点流量，倒计时就会“重置”。keepAliveTime=60s 的意思是：连续 60 秒没有任何活干。

在持续运行的消息队列应用中，只要不是彻底断流，线程池往往很难缩容回 Core 大小，因为总有零星任务在“续命”。

💡

Q2：completedTaskCount 为什么始终是 0？

答：这是一个非常底层的 JDK 实现细节。

  • OGNL 看到的字段：你通过 OGNL @...WORKER_POOL 看到的是 ThreadPoolExecutor 对象里的原始字段 private long completedTaskCount。
  • 更新时机：这个字段不是实时更新的！它只有在 Worker 线程被销毁（退出）的那一刻，才会把这个线程一生干完的任务数累加到全局计数器里。

因此有个推论：

  • 因为那 34 个线程（包括那 9 个临时工）目前都还活着，还没人“离职”。
  • 所以它们干过的活，都记在它们的线程局部变量中，还没上报给由 OGNL 监控的全局变量。
  • 因此你会看到全局 completedTaskCount 一直是 0，直到有一天流量彻底停了 60 秒，那 9 个线程被销毁了，这个数字才会突然跳变。
