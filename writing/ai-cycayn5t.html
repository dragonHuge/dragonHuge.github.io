OpenCode + OMO 多层 Agent 架构与 Fallback 配置实践

2026-04-28 · 飞书原文 ↗

FallBack 链参考文档：@OpenCode 配置与 Oh-My-OpenCode Fallback 。@引用

插个广告：@聊聊AI-Coding、AI提效、AI底层认知 - 研发效能与工程化探索

背景

个人日常用 OpenCode + OMO(Oh-My-OpenAgent) 做 AI 辅助编程，用了一段时间后碰到两个问题：

⚠️

OpenCode 原生 Agent 太少。

自带的 Plan + Builder 两个主 Agent 能处理通用编码任务，但碰到架构设计、代码评审、多模态分析这些场景就不够用了。你得不停地在 prompt 里补角色描述，效率很低。

⚠️

OMO（Oh-My-OpenAgent）插件自带的 Agent 又太重。

OMO 默认把 sisyphus、oracle 这些都配成独立主 Agent，每个都有完整的工具集和系统提示。实际用的时候你需要手动切换 Agent，而且不同项目的需求差异很大，全局统一配置经常不合适。

两者如何权衡呢？

这篇文档讲我怎么把两者拆开重组 —— 全局只保留两个主 Agent，OMO 的所有角色降级为 SubAgent 按需调用，项目目录里再按领域定制专属 Agent。

SubAgent 调用机制详解

💡

核心机制：主 Agent（Plan / Builder）通过 opencode 的 Task tool 委派任务给 SubAgent。

SubAgent 在独立 context 中执行，只有最终 summary 返回主 Agent，中间的工具调用和推理过程不进入主 Agent 的 context window。

调用流程

主 Agent 看到所有已注册 SubAgent 的 description 字段，根据当前任务与 description 的匹配度决定调用哪个 SubAgent。

这就是为什么每个 SubAgent 的 description 要写得精准——它直接影响调度准确率。

SubAgent 之间不能互调

💡

重要限制：10 个 SubAgent 之间不能直接通信。

oracle 不能调 momus，explore 不能调 librarian。所有协作都必须经过主 Agent 中转——这是 opencode 主从架构的固有限制。

如果需要 SubAgent 间协作（如 oracle 做完分析后让 momus 评审），流程是：

  1. 主 Agent 调 oracle → 拿到 summary
  1. 主 Agent 把 summary 作为 context 传给 momus → 拿到评审结果
  1. 主 Agent 综合两份 summary 决定下一步

每一步都经过主 Agent，SubAgent 互相看不到彼此的存在。

这与 Claude Code 的 Agent Teams 模式形成对比——Agent Teams 支持成员间通过 message 工具直接点对点通信，不需要中心 Agent 中转。

但 opencode 目前没有 peer 通信能力。

多 Agent 通信架构：主从 vs Peer vs Mailbox

💡

理解本文架构前的必备知识：opencode 的 SubAgent 属于「主从架构」，而 Claude Code 还支持「Agent Teams（Peer 架构）」。两者的通信机制、触发方式、上下文管理完全不同。本节先讲清这些概念，再看具体配置。

opencode 的触发关键：主 Agent 通过 Task tool 委派时，匹配依据是 SubAgent 的 description 字段——这就是为什么本文每个 SubAgent 的 description 都写得很精准，它直接影响调度准确率。

Agent Teams 的通信机制：Mailbox 模式

Claude Code 的 Agent Teams 采用的是 Actor Model 的 Mailbox 通信模式：

特征

说明

异步投递

A 往 B 的 mailbox 写完就继续自己的事，不阻塞等 B 回复

独立 inbox

每个成员有自己的 mailbox，只看到发给自己的消息

非广播

A 发给 B 的消息，C 看不到（除非 A 也发一份给 C）

轮转消费

成员按 turn 轮转，轮到谁谁就消费自己 inbox 里的消息

持久化

Team 状态（含 mailbox 历史）持久化到 JSON

为什么选 Mailbox 而不是共享黑板？ 核心原因是防 context 爆炸——共享黑板模式下 3 个 Agent 每轮都看全局消息，context 增长是 O(n²)；Mailbox 点对点投递，增长是 O(n)。

💡

本文 opencode 架构没有 Mailbox / Peer 能力。所有 SubAgent 间的"协作"必须经过主 Agent 中转：主 Agent 先调 oracle 拿到分析结论 → 再把结论作为 context 传给 momus 做评审 → 最终汇总。这是主从架构的固有限制，也是主从架构 context 更可控的原因。

结论先行 ⭐️

🔥

三句话概括整套架构：

  1. 全局两个主 Agent 打底 — Plan 拆任务，Builder 干活，所有项目共享.
  1. OMO 角色全部降为 SubAgent — 10 个通用角色挂在全局，各自绑定模型和 Fallback 链，主 Agent 按需调用.
  1. 专家主 Agent，区分项目目录，按需定制 — 最少配置切换主 Agent，追加领域 SubAgent，和全局 SubAgent 池叠加使用.

全局与项目级 SubAgent 叠加机制

进入项目目录后，主 Agent 能看到全局 10 个 + 项目级 N 个 SubAgent 的 description，按 description 匹配度决定调谁。同名 Agent 项目级覆盖全局，不同名的追加叠加。

举例：电商项目定义了 api-architect 和 order-expert，运行时主 Agent 的 SubAgent 池 = 全局 10 个 + 这 2 个 = 12 个可调用角色。

为什么这么设计？

OpenCode 原生不够用

OpenCode 开箱只有 Plan 和 Builder。写代码够了，但你想让它做代码评审（momus）、深度推理（oracle）、图片分析（multimodal-looker）就得自己写 prompt 或手动定义 Agent。每个项目重复一遍这个过程很烦。

OMO 默认太重

OMO 插件提供了 sisyphus、hephaestus、oracle 等十几个预定义 Agent，覆盖面广。

但默认配置下它们都是独立主 Agent，互相之间不会自动协作。你想用 oracle 做推理，得手动切过去；用完再切回来继续编码。

整体架构

整套配置分两层，加载时全局先加载，项目级再覆盖叠加。

全局层

~/.config/opencode/

  • opencode.json — 模型 Provider（8 家）、插件、主 Agent
  • oh-my-openagent.json — SubAgent 池（10 个）、Category（8 类）、Fallback 链
  • MIFY_API_KEY — 密钥文件，统一引用

项目层

./项目目录/

  • opencode.json — 覆盖 default\_agent + 加载指令
  • .opencode/agents/*.md — 领域 Agent 定义
  • AGENTS.md — 项目专属系统指令
💡

加载顺序： 全局 ~/.config/opencode/ 先加载（Provider、插件、OMO SubAgent）→ 项目级 ./opencode.json + .opencode/agents/ 覆盖上去。同名 Agent 被替换，新增 Agent 被追加。最终运行时两层叠加。

第一层：全局配置

两个主 Agent 打底

全局 default_agent 设为 plan。日常只跟两个角色打交道：

角色

职责

Plan

拆解任务、规划步骤

Builder

执行编码、文件操作

SubAgent 池

所有 OMO 角色统一设为 mode: "subagent"，Plan/Builder 按需调用，不用手动切换。

🔥

调整后 10 个 Agent 覆盖了 6 个不同的模型/家族（Opus / Sonnet / GPT-5.4-Pro / GPT-5.4 / Codex / Gemini / MiMo / Kimi），单一厂商故障最多影响 2-3 个角色，不会全挂。

💡

选模型的逻辑：

  • Opus 给需要全局视野和长链路不跑偏的角色（sisyphus、prometheus）
  • GPT-5.4-Pro 给推理天花板场景（oracle）
  • GPT-5.4 给逻辑拆解和分析（metis）
  • Sonnet 给需要严谨理解但不需要最强推理的角色（momus 评审、librarian 研究）
  • Codex 给纯代码生成（hephaestus）
  • Gemini 给多模态（multimodal-looker）
  • MiMo Flash 给低延迟轻量任务（explore）
  • Kimi 给大窗口文档场景（atlas）

SubAgent 详解

sisyphus — 复杂多步任务执行者

主模型 Claude Opus 4-6 | temperature 默认 | Fallback Opus 4.5 → Sonnet 4-6 → Sonnet 4.5 → Kimi → GLM

Executes complex multi-step tasks that require sequential operations with dependencies. Use when a task involves multiple stages that build upon each other, such as refactoring across files, setting up environments, or implementing features with multiple interdependent components.

什么时候用： 多步骤串行执行、步骤间有依赖关系的任务。跨文件重构、搭建开发环境、实现涉及多组件的功能。

hephaestus — 工程构建专家

主模型 Codex-9 | temperature 默认 | Fallback Codex-8 → Codex-7 → Codex-6

Engineering and build system specialist. Expert in build configurations, compilation issues, dependency management, CI/CD pipelines, and tooling setup.

什么时候用： webpack/vite 配置、package.json 依赖冲突、CI/CD 调试、编译失败。Codex 系列专精代码生成。

oracle — 深度推理顾问

主模型 GPT-5.4-Pro | temperature 0.3 | Fallback GPT-5.4 → Codex-9 → Kimi → Grok

Deep reasoning and precise question answering expert. Provides thoughtful analysis of complex technical problems, architectural decisions, and nuanced questions requiring careful consideration.

什么时候用： 架构决策、技术方案权衡、复杂 bug 根因分析。 基于信息做推理和判断，不只是检索。

prometheus — 战略规划架构师

主模型 Claude Opus 4-6 | temperature 0.2 | Fallback Opus 4.5 → Sonnet 4-6 → Sonnet 4.5 → Kimi → Grok

Strategic planner and software architect. Designs high-level architecture, evaluates technical approaches, makes technology selections, and creates implementation roadmaps.

什么时候用： 系统架构设计、技术选型、路线图规划。prometheus 偏规划（输出方案），oracle 偏分析（输出结论）。

metis — 问题分析解决者

主模型 GPT-5.4 | temperature 0.5 | Fallback Codex-9 → Kimi → Sonnet 4-6 → Grok

Intelligent problem solver and analytical thinker. Breaks down complex problems into manageable parts, identifies root causes, proposes solutions, and weighs tradeoffs.

什么时候用： 性能瓶颈分析、复杂 bug 调试、系统行为分析。metis 偏动手拆解，oracle 偏权威判断。

momus — 代码评审员

主模型 Claude Sonnet 4-6 | temperature 0.6 | Fallback Sonnet 4.5 → Kimi → Gemini Pro → Grok

Code reviewer and quality auditor. Reviews code for bugs, security issues, performance problems, maintainability concerns, and adherence to best practices.

什么时候用： 代码合并前的质量检查。 Claude 偏保守，做评审是优点——宁可多报不漏报。

explore — 快速代码搜索

主模型 MiMo v2 Flash | temperature 0.7 | Fallback MiMo Pro → MiniMax → Haiku

Fast read-only codebase explorer. Quickly finds files by patterns, searches for code snippets, identifies function locations, and answers questions about code structure.

什么时候用： 快速找东西：搜文件、定位函数、查结构。只读不写。explore 求快（侦察），librarian 求深（研究）。

librarian — 代码研究员

主模型 Claude Sonnet 4-6 | temperature 0.2 | max_tokens 8192 | Fallback Sonnet 4.5 → Kimi → MiMo Pro → Gemini Flash

Comprehensive codebase researcher and documentation specialist. Performs deep analysis of code structure, patterns, dependencies, and historical context.

什么时候用： 深度代码研究：理解大型代码库结构、追踪数据流、分析依赖、编写技术文档。

multimodal-looker — 多模态视觉分析

主模型 Gemini 3 Pro | temperature 0.4 | Fallback Kimi → Gemini Flash

Visual content analyzer for images, diagrams, screenshots, PDFs, and design mockups. Extracts information from visual materials, describes UI layouts, reads diagrams, and analyzes design specifications.

什么时候用： 看截图、读架构图、分析设计稿、提取 PDF。Gemini 多模态能力最好。

atlas — 文档知识导航

主模型 Kimi K2.5 | temperature 0.3 | Fallback GLM → MiniMax → Grok

Knowledge navigator and technical reference expert. Searches documentation, finds API references, retrieves code examples, and locates relevant information from knowledge bases.

什么时候用： 查框架 API、语言特性、第三方库文档。explore 搜代码库内部，atlas 搜外部知识。Kimi 260K context 窗口大、中文好。

Fallback 链

🔥

每个 Agent 绑 4-6 级 Fallback，模型挂了自动降级，不中断工作。 三条降级规则：

  1. 同厂同系列 — Opus 4-6 → Opus 4.5 → Sonnet 4-6
  1. 跨厂同级 — GPT-5.4-Pro → GPT-5.4 → Codex-9
  1. 兜底低成本 — Kimi K2.5、GLM-5

成本策略： 轻量任务（explore、quick）用 MiMo Flash 省钱，重量任务（oracle、ultrabrain）用旗舰模型保质量。Fallback 链跨越多家厂商，单一厂商故障不影响整体。

Category 与 Agent 的关系

💡

两套路由是正交的：

  • Agent 是角色级路由 — 按角色分配模型（oracle 用 GPT-5.4-Pro，explore 用 MiMo Flash）
  • Category 是任务级路由 — 按任务类型选模型（ultrabrain 场景用 GPT-5.4-Pro，quick 场景用 MiMo Flash）

Category 影响的是主 Agent 自己用什么模型处理当前任务，Agent 影响的是委派给谁执行。两者不冲突，可以叠加生效。

项目级 opencode.json

路径：./项目目录/opencode.json

{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["AGENTS.md"],
  "default_agent": "ecom-main"
}

三行配置。default_agent 覆盖全局，instructions 加载项目指令。

项目级 Agent 定义示例

每个 .md 文件的 frontmatter 声明 mode 和参数，文件名即 Agent 名。mode: primary 是主 Agent，mode: subagent 被主 Agent 按需调用。
