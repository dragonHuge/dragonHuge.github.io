Redis 使用规则

2026-07-09"本地沉淀 · 风控工程知识库"

本文是工程规则（团队约定 + 踩坑结论），不是入门教程： 适合「已经知道要做什么，只想知道怎么做才不出事」的场景。

1. 适用范围

风控服务用 Jedis 4.x 直连 Redis（不走 spring-data-redis，不走 Lettuce）。覆盖：在线服务读写、Flink 窗口算子批写、离线 Spark 直写回灌。

2. 版本 / 依赖

坐标版本备注
redis.clients:jedis4.4.64.x 主线，新项目对齐
com.github.fppt:jedis-mock1.1.4仅 test scope，BVT 进程内 Redis

关键 API：

  • JedisPooled（连接池单例）— 替代旧的 JedisCluster / Jedis 模式
  • Pipeline — 批写
  • Pipeline.syncAndReturnAll() — 拿回每条命令的返回值，做 partial error 检测

3. 标准骨架

3.1 单例工厂

public final class ${jedisFactoryClass} {
    private static volatile JedisPooled INSTANCE;

    public static JedisPooled createJedisPooled(String host, int port, String password) {
        // 走 JedisPooled 而不是 new JedisCluster；
        // 连接池参数走 Duration API（jedis 4.x 风格）
        ConnectionPoolConfig poolCfg = new ConnectionPoolConfig();
        poolCfg.setMaxTotal(${redisMaxTotal});
        poolCfg.setMaxIdle(${redisMaxIdle});
        poolCfg.setMinIdle(${redisMinIdle});
        // ... timeout / blockWhenExhausted / testOnBorrow

        if (password == null || password.isEmpty()) {
            return new JedisPooled(poolCfg, host, port);
        }
        return new JedisPooled(poolCfg, host, port, ${connectTimeoutMs}, password);
    }
}

3.2 Pipeline 批写（高吞吐场景）

try (Pipeline p = jedis.pipelined()) {
    for (WriteOp op : ops) {
        if (op instanceof WriteOp.Hset) {
            p.hset(redisKey, op.field(), op.value());
        } else if (op instanceof WriteOp.Hdel) {
            p.hdel(redisKey, op.field());
        } else if (op instanceof WriteOp.Del) {
            p.del(redisKey);
        }
    }
    List<Object> results = p.syncAndReturnAll();
    throwIfPipelineHasPartialErrors(results);
}

铁律：

  • 用 try-with-resources 包 Pipeline
  • 用 syncAndReturnAll() 拿返回值检查 partial error，而不是无脑 sync()
  • 单批操作数控制在 100~500 之间，过大批量 Redis 响应慢

3.3 重试（固定 backoff，整批重试）

private boolean flushOpsWithRetry(List<WriteOp> ops, String key) {
    JedisException last = null;
    for (int attempt = 1; attempt <= ${maxRedisRetries}; attempt++) {
        try {
            flushOps(ops, key);
            return true;
        } catch (JedisException e) {
            last = e;
            PerfCounter.setMeterCount("${metricPrefix}.redis.pipeline.retry", 1);
            if (attempt < ${maxRedisRetries}) {
                if (!sleepBeforeRetry()) return false;  // 中断信号
            }
        }
    }
    PerfCounter.setMeterCount("${metricPrefix}.redis.pipeline.exhausted", 1);
    log.error("Pipeline flush exhausted, key={}, ops={}, err={}",
        key, ops.size(), last != null ? last.getMessage() : "unknown");
    return false;
}

private static boolean sleepBeforeRetry() {
    try {
        Thread.sleep(${redisRetryBackoffMs});  // 典型 10ms
        return true;
    } catch (InterruptedException ex) {
        Thread.currentThread().interrupt();
        return false;
    }
}

实测：${maxRedisRetries}=3 + ${redisRetryBackoffMs}=10ms 在网络抖动场景下整批重试成功率 > 99%。

3.4 fail-open（读场景）

try {
    DeviceValue v = repo.hget(key, field);
    return toResp(v);
} catch (${ExceptionType} e) {
    if (e.getCode() == 50301) {
        log.warn("query fail-open, key={}", key);
        PerfCounter.setMeterCount("${metricPrefix}.service.query.fail_open", 1);
        return defaultResp();  // 返回默认未命中
    }
    throw e;
}

铁律：

  • fail-open 只用在"读 + 业务允许默认值"场景（如查不到信任度返回未信任）
  • 写操作：不能 fail-open，必须抛错让上层重试或人工介入
  • 强一致读：不能 fail-open

3.5 partial error 检测

static void throwIfPipelineHasPartialErrors(List<Object> results) {
    int errors = 0;
    for (Object r : results) {
        if (r instanceof JedisDataException) {
            errors++;
        }
    }
    if (errors > 0) {
        PerfCounter.setMeterCount("${metricPrefix}.redis.pipeline.partial_error", errors);
        throw new JedisException("Pipeline partial errors: " + errors);
    }
}

partial error 通常是单条命令服务端报错（如 OOM），与整批连接级失败（JedisConnectionException）区分。

4. 配置项

key默认说明

redis.${configPrefix}.key.prefix由使用方提供业务 key 前缀，如 ${redisKeyPrefix}

6. 常见踩坑

6.1 🔴 写操作 fail-open

后果：脏数据 / 业务一致性破坏。 正确：写只重试 + 抛错，绝不 fail-open。

6.2 🔴 pipeline 内单条命令报错导致整批失败

现象：服务端 OOM，部分 hset 成功部分失败，业务以为整批失败重试，导致重复写。 正确：用 syncAndReturnAll() + 显式 partial error 检测（§3.5）。

6.3 🟠 connection pool 配置不当

  • maxTotal 太小：高峰期阻塞
  • maxIdle 远小于 maxTotal：频繁创建销毁连接
  • 没设 testOnBorrow：拿到死连接报错才发现

正确：参考 实测值，maxTotal 32-64，maxIdle 同 maxTotal，开 testOnBorrow。

6.4 🟠 海外 region 没 Redis

某些 region 部署时 Redis Bean 可能为 null（如纯查询服务 + 海外只读模式）。 正确：调用方加 if (jedis != null) 守卫，或在 BeanConfiguration 用条件 Bean。

6.5 🟢 用 Jedis 单实例（非 JedisPooled）

后果：高并发抢锁，吞吐降一个量级。 正确：永远用 JedisPooled。

6.6 🟢 大 key 没监控

后果：单个 hash > 10k field 时 hgetall 卡线程池。 正确：业务侧设计阶段就考虑分桶 / 阈值 + HLEN 提前预警。
