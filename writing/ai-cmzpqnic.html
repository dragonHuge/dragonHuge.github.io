AI-Coding学习笔记

2026-03-18 · 飞书原文 ↗

如果你想知道 AI的前世今生和底层原理，我推荐你首先阅读：@AI 发展-自顶向下 -组内分享

💡

Prompt -》 Agent -》WorkFlow -》 Function Calling -》MCP -》Rules -》Skills。

是对 AI 应用「降本、记忆（Context）、能力边界」三个维度的 不断探索与进步，术语层出不穷，五花八门，但底层逻辑是一样的。

至于 AI-Coding实战的重点，我认为在以下5点：

  1. 开发前定好 “需求、方案明确的项目文档” - SDD，对于复杂需求预研，所有需求有精确的方案，不要给 AI 复杂的开放需求。

  2. 至于Coding框架选择，VAF还是Spec-kit都行（但VAF框架及其复杂，太重）

  1. 学习基础理论知识，可搭建个人Agent，去辅助开发、提示词撰写。可以利用Mify构建通用提效Agent ：“提示词大师Agent”、“SQL生成Agent”

  1. 人力维护，不可避免。

  2. Skills 撰写需遵循「最小职责原则」，项目开发过程 Skills、Flow 维护，需不断人为 check、调优。

  1. 有了优质实例，AI 能力成倍提升。

  1. 小步快跑，及时 Commit： 每当 AI 完成一个可用的小功能，立即 Git Commit。AI 很容易在修改一个 Bug 时引入三个新 Bug，你需要随时能回滚的“后悔药”。

在 AI-Coding 语境下，SDD（Specification-Driven Development，规格驱动开发） 是解决 AI 幻觉和逻辑断层的终极武器。

核心逻辑： AI 最擅长的是“填充内容”，最差的是“保持长程逻辑一致性”。SDD 要求人类先定义 “形状” （不局限于需求方案、类定义、接口参数定义。。。），将业务逻辑限制在一个确定的框架内。

OpenSpec有两种命令形式：

  • openspec init：这些命令是交互式的，专为终端使用而设计。-> terminal里用的。
  • /opsx:new：这是 OpenSpec 斜杠命令，在AI 编码助手的聊天界面中调用。 -> AI聊天界面里用的。

见下图，是openspec的工作目录，红框内是一次需求开发的过程文档。

  1. specs/：记录项目现状。
  2. changes：记录所有增量需求的变更开发记录。每项修改都会生成一个单独的文件夹，其中包含所有相关的文件。开发完成后，本次需求变更会合并到主specs/目录中。
  3. config.yaml：
  1. .openspec.yaml：change的元数据文件。OpenSpec CLI 通过读取这个文件来判断该 change 应该走哪套 artifact 流程、需要哪些前置依赖。
    • schema: 这个 change 使用哪个工作流（spec-driven 意味着 proposal → specs → design → tasks 这套流程）
    • created: 创建时间。

    spec-driven 是目前唯一内置的 schema，定义了固定4个 artifact 的线性依赖流程：

    proposal → specs ─┐

    ├─→ tasks ─→ apply

    → design ─┘

  2. proposal.md：Why and What，概括了目标、范围和方案。
  3. design.md：How，说明了具体该怎么做。
  4. tasks.md：任务清单。
  5. specs/：写清本次change需要新增/修改/删除的需求。
  6. 💡

    Q1：为何1个change中的 specs/ 会有多个子目录，如下图中的dev-tdd-skill 与 test-enforcement?

    答：划分依据是 proposal 中定义的两个 Capability。坦率说，对于这个需求来说，它们关系紧密，合成一个 spec 也完全合理。OpenSpec 的 spec 划分没有硬性标准，核心原则是"一个 spec 对应一个可独立理解的能力"。

    这里拆开是因为 proposal 里列了两个 capability，如果你觉得合并更清晰，可以调整。

OpenCode 通过读取每个 Agent 定义文件（.opencode/agents/*.md）开头的 YAML Front Matter 中的 mode 字段来区分：

  • mode: primary → 可以直接接收用户输入
  • mode: subagent → 只能被其他 Agent 调用

这是一个声明式配置，OpenCode 在启动时扫描所有 Agent 文件，解析 YAML，然后在运行时强制执行访问控制规则。

Q1: 可以有多个 Primary Agent 吗？

A: 理论上可以，但在一个会话中只能激活一个。可以定义多个，但 default_agent 只能指定一个。

用户可以切换

用户：@debug-assistant

OpenCode：✅ 切换成功（因为也是 primary）

Q2: Subagent 可以调用其他 Subagent 吗？

A: 技术上可以，但要看设计。

在你的设计中：

revision-coordinator (subagent)

↓ 可以调用

backend-specialist (subagent)

↓ 可以调用

frontend-specialist (subagent)

这是三级调用：

  1. Primary → revision-coordinator
  1. revision-coordinator → backend-specialist
  1. revision-coordinator → frontend-specialist

OpenCode 支持这种嵌套调用，但需要在 revision-coordinator.md 的 Prompt 中明确说明。

Q3: 如果不设置 mode 会怎样？

A: 默认为 primary。

AI -底层技能原子

相比传统 Copilot 式提示补全，Vibe Coding 更强调“意图-行动-验收”循环。

很多人觉得 “Vibe” 是 “代码风格”“编程感觉”，其实 ——Vibe Coding 的核心是 “代码语境的一致性”：指代码在语法风格、业务逻辑、复用规则上形成的 “隐性共识”，就像团队的 “知识库”，不用刻意沟通就能理解彼此的实现思路。

已知大模型的本质是“概率”，是预测、记忆而非思考。

大模型的“思考”，就是它在生成最终答案之前，自己生成一系列的中间令牌。这些令牌不是直接的答案，而是用来引导模型走向正确答案的“内部独白”或“思考路径”。（把推理组合起来就是“思考”）

主流的几种推理组合方式：

  1. 代表技术： Chain-of-Thought (CoT) / Zero-Shot CoT

  2. 核心机制： 分步思维是最基础也是最有效的推理策略之一。它通过引导模型将一个复杂的任务分解成一系列逻辑连贯、单向线性的推理步骤

  1. 代表技术： CoT-SC (Chain-of-Thought - Self-Consistency)

  2. 核心机制： 自洽性策略是为了解决单个CoT推理路径可能产生的错误或不一致性。

  1. 代表技术： ReWOO / HuggingGPT

  2. 核心机制： 模块化思维是一种更为复杂的推理架构，它将任务视为一个需要多次迭代和协作的“项目”。多次调用自身（例如进行多次反思和改进），或通过接口调用外部工具和模型（如搜索引擎、代码解释器等）。

  1. 代表技术： ToT (Tree of Thoughts) / LMZSP / RAP

  2. 核心机制： 树状推理模仿了人类“深思熟虑”的决策过程，突破了线性推理的限制。在推理的每一步，模型不再只沿着一个方向前进，而是会同时生成多个潜在的中间推理状态或“想法”（即分支）。这些分支随后会被评估其可行性和潜力。LLM会像搜索树一样，探索不同分支的可能性，通过前瞻性评估来选择最有希望的路径继续深入，直到找到最优解。这使得模型在需要进行复杂规划、搜索和多步决策的任务中表现出色。

构建具有角色分工、工具使用能力、记忆与规划能力的智能体集合，而非单纯调用 LLM API

解决 “怎么做” 的问题：通过 Analyst/Architect/Tester 等角色分工，模拟人类开发流程，实现 “需求→代码” 的自动化闭环

Flow（形态层）

标准化、工业化的工作流，让需求从输入到交付像水一样流畅流转，无断点、无偏差

解决 “怎么有序做” 的问题：通过固定流程固化 Vibe 共识，避免因个人习惯导致的代码不一致，提升开发效率和可复用性

CodeX 的 Flow 调度层按该维度设计，确保每个编码任务都遵循 “解析→匹配→生成→校验→交付” 的标准流程

核心关联逻辑：Vibe 是 “灵魂”（定方向），Agentic 是 “手脚”（做执行），Flow 是 “路径”（保一致）。三者缺一不可：无 Vibe 则 Agent 生成的代码 “无共识”，无 Agentic 则 Flow 只是空架子，无 Flow 则 Vibe 无法稳定传递。

  • Template 解决 “模仿的对象”→ 加快学习的速度；

Skills 原理解析

📚 官方解释：https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview

参考文章：一文读懂 Skills｜从概念到实操的完整指南

一个 Skills 通常以一个文件夹的形式存在，里面主要装着三样东西：一份说明书（SKILL.md）、一堆操作脚本（Script）、以及一些参考资料（Reference）。

Skills的架构原理：渐进式加载（按需调用）⭐️

Skill 的设计很巧妙，它运行在一个沙盒环境里，这个环境允许大模型访问文件系统和执行 bash 命令（可以理解为一种电脑操作指令）。在这个环境里，一个个 Skill 就像一个个文件夹。Agent 就像一个熟悉电脑操作的人，通过命令行来读取文件、执行脚本，然后利用结果去完成你交代的任务。这种“按需取用”的架构，让 Skill 成为一个既强大又高效的“工具箱”。

为了平衡效果和效率，Skill 设计了一套聪明的三层分级加载机制：

Level 1：元数据（始终加载）

元数据就像是 Skill 的“名片”，里面有名称（name）和描述（description），是用 YAML 格式来定义的。Claude 在启动的时候，会把所有已经安装的 Skill 的元数据都加载进来，这样它就能知道每个 Skill 有什么用、什么时候该用。因为元数据很轻量，所以你可以安装很多 Skill，不用担心把上下文占满。

Level 2：说明文档（触发时加载）

SKILL.md 文件的正文就是说明文档，里面有工作流程、最佳实践和操作指南。只有用户的请求和 Skills 元数据里的描述相符时，Claude 才会用 bash 指令读取这份文档，把内容加载到上下文里。这种“触发式加载”能保证只有相关的详细指令才会消耗 Token。

Level 3：资源与代码（按需加载）

Skills 还能打包一些更深入的资源，比如更详细的说明文档（FORMS.md）、可执行脚本（.py）或者参考资料（像 API 文档、数据库结构等）。Claude 只有在需要的时候，才会通过 bash 去读取或执行这些文件，而且脚本代码本身不会进入上下文。这样一来，Skills 就能捆绑大量信息，几乎不会增加额外的上下文成本。

Skills vs Rules

💡

Skills 比 Rules 更省 Token（省40%）。

Rules 是让 AI “记住”所有细节（全量文本），而 Skills 是给 AI 一个“索引”（函数定义），让它需要的时候再去“翻书”（执行函数获取 Token）。

“索引”当然比“全书”要小得多。

因此：全局性、配置性约束使用Rules，功能性、数据性约束使用Skills。

从底层原理来看，Rules（规则）和 Skills（技能/工具）最终确实都是作为“文本（Tokens）”输入给大模型的。

之所以普遍认为 Skills 比 Rules 更省 Token，并不是因为它们“本质不同”，而是因为它们的 “加载方式”和“生效机制” 不同。

1. Rules（规则）：全量加载，“背诵全书”

Rules（ System Prompt 或 .cursorrules 文件）是静态上下文。为了让模型遵守这些规则，你必须把规则的全文塞进模型的每一次对话的上下文里。

Token 消耗：高且固定。

2. Skills（技能）：按需加载，“查字典”

动态上下文。你不需要把具体的知识写出来，你只需要告诉模型“你有一个工具可以查文档”。

  • 工作机制：你只告诉模型“目录结构”，不给“正文”。只有当模型觉得需要时，它才会去“调用”这个技能获取具体内容。
  • 第一步（定义阶段）：你只输入 Skill 的定义（Schema）。例如：“我有一个工具叫 read_database_schema”。这可能只占 50 个 Token。
  • 第二步（执行阶段）：只有当模型真的需要查数据库时，它才会调用工具，此时工具返回的具体数据（比如 500 个 Token）才会临时进入上下文。
  • 结果：如果不调用，就只花 50 Token；如果调用，才花更多。

Flow

如果说 Skills（技能） 是 AI 手中的“工具箱”，那么 Flow（流程/工作流） 就是你写好的“操作手册”或“SOP（标准作业程序）”。

它是对 Skills 使用方式的强制性、逻辑性编排。
