synchronized、volatile、ReentrantLock、CountDownLatch、Condition

1.sychronized— 可重入不公平锁

1.什么是sychronized

synchronized 是 Java 中的一个关键字，翻译成中文是同步的意思，主要解决的是多个线程之间访问资源的同步性，可以保证被它修饰的方法或者代码块在任意时刻只能有一个线程执行。

2.怎么使用sychronized关键字

  1. 修饰实例方法：锁当前对象实例。

给当前对象实例加锁，进入同步代码前要获得 当前对象实例的锁 。

```Java synchronized void method() { //业务代码 } ```

  1. 修饰静态方法：锁当前类。

该类的所有实例对象用的是同一把锁。因为：静态方法是属于类而不属于对象的。会作用于类的所有对象实例 ，进入同步代码前要获得 当前 class 的锁。

```Java synchronized static void method() { //业务代码 } ```

  1. 修饰代码块：锁指定对象/类

```Java synchronized(this) { //业务代码 } ```

对括号里指定的对象/类加锁：

  • synchronized(object) 表示进入同步代码库前要获得 给定对象的锁。

一般来说，你会传入一个特定的对象，来确保多个代码块在相同的对象上同步执行。如果多个线程需要同步执行一些代码，但这些代码不属于任何特定的对象，你可以创建一个新的对象，使用它来作为锁对象。

  • synchronized(类.class) 表示进入同步代码前要获得 给定 Class 的锁

在整个类的范围内只有一个线程可以执行同步代码块

总结：

  • synchronized 关键字加到 static 静态方法和 synchronized(class) 代码块上都是是给 Class 类上锁；
  • synchronized 关键字加到实例方法上是给对象实例上锁；
  • 尽量不要使用 synchronized(String a) 因为 JVM 中，字符串常量池具有缓存功能。

3.构造方法可以用sychronized吗？

先说结论：构造方法不能使用 synchronized 关键字修饰。

构造方法本身就属于线程安全的，不存在同步的构造方法一说

构造方法不需要同步化，因为它只可能发生在一个线程里，在构造方法返回值前没有其他线程可以使用该对象。

（一个线程已经在构造方法里面了，另外一个线程也可以调用构造方法，第一个线程里面生成的对象和第二个线程里面生成的对象是不同的对象。）

4.sychronized底层原理了解吗？

synchronized 同步语句块的实现使用的是 monitorenter 和 monitorexit 指令，其中 monitorenter 指令指向同步代码块的开始位置，monitorexit 指令则指明同步代码块的结束位置。

💡 Q1：这两个指令的作用是？

monitorenter 指令和 monitorexit 指令是 Java 虚拟机（JVM）中用于实现同步的指令。

  • monitorenter 指令用于在进入同步代码块之前获取对象的监视器（monitor），即获取对象的锁。当线程执行到 monitorenter 指令时，会尝试获取对象的锁，如果对象的锁没有被其他线程占用，则当前线程获取到锁，并继续执行同步代码块，否则当前线程会被阻塞，直到获取到锁为止。
  • monitorexit 指令用于在退出同步代码块之后释放对象的监视器，即释放对象的锁。当线程执行完同步代码块后，会执行 monitorexit 指令来释放对象的锁，这样其他线程就有机会获取该对象的锁并执行同步代码块。

这两个指令通常会成对出现，确保同步代码块的正确性和线程安全性。在 Java 中，synchronized 关键字就是通过这两个指令来实现同步的。

synchronized 修饰的方法并没有 monitorenter 指令和 monitorexit 指令，取得代之的确实是 ACC_SYNCHRONIZED 标识，该标识指明了该方法是一个同步方法。

  • 当执行 monitorenter 指令时，线程试图获取锁也就是获取 对象监视器 monitor 的持有权。
  • 对象锁的的拥有者线程才可以执行 monitorexit 指令来释放锁。在执行 monitorexit 指令后，将锁计数器设为 0，表明锁被释放，其他线程可以尝试获取锁。

不过两者的本质都是对对象监视器 monitor 的获取。

2.volatile

1.sychronized和volatile的关系

synchronized 关键字和 volatile 关键字是两个互补的存在，而不是对立的存在！

  1. volatile 关键字是线程同步的轻量级实现，所以 volatile性能肯定比synchronized关键字要好 。

但是 volatile 关键字只能用于变量而 synchronized 关键字可以修饰方法以及代码块 。

  1. volatile 关键字能保证数据的可见性，但不能保证数据的原子性。synchronized 关键字两者都能保证。
  • volatile关键字主要用于解决变量在多个线程之间的可见性，而 synchronized 关键字解决的是多个线程之间访问资源的同步性。

2.如何保证变量可见性？

volatile 关键字其实并非是 Java 语言特有的，在 C 语言里也有，它最原始的意义就是禁用 CPU 缓存，也不用寄存器。

如果我们将一个变量使用 volatile 修饰，这就指示编译器，这个变量是共享且不稳定的，每次使用它都到主存中进行读取,不会由于编译器优化造成数据不一致错误。

3.如何禁止指令重排序？

volatile 关键字除了可以保证变量的可见性，还有一个重要的作用就是防止 JVM 的指令重排序。 如果我们将变量声明为 volatile ，在对这个变量进行读写操作的时候，会通过插入特定的 内存屏障 的方式来禁止指令重排序。

在 Java 中，Unsafe 类提供了三个开箱即用的内存屏障相关的方法，屏蔽了操作系统底层的差异：

public native void loadFence();
public native void storeFence();
public native void fullFence();

3.ReentrantLock

注意一点：必须在finally块中释放锁。

1.什么是ReentrantLock？

ReentrantLock 实现了 Lock 接口，是一个可重入且独占式的锁，和 synchronized 关键字类似。

  • 可重入：ReentrantLock锁可以被同一个线程多次获取。

不过，ReentrantLock 更灵活、更强大，增加了轮询、超时、中断、公平锁和非公平锁等高级功能。

ReentrantLock 里面有一个内部类 Sync，Sync 继承 AQS（AbstractQueuedSynchronizer），添加锁和释放锁的大部分操作实际上都是在 Sync 中实现的。

Sync 有公平锁 FairSync 和非公平锁 NonfairSync 两个子类。

ReentrantLock 默认使用非公平锁，也可以通过构造器来显式的指定使用公平锁。

// 传入一个 boolean 值，true 时为公平锁，false 时为非公平锁
public ReentrantLock(boolean fair) {
    sync = fair ? new FairSync() : new NonfairSync();
}

从上面的内容可以看出， ReentrantLock 的底层就是由 AQS 来实现的。关于 AQS 的相关内容推荐阅读 AQS 详解open in new window 这篇文章

2.公平锁和非公平锁的区别

ReentraantLock是通过一个FIFO的等待队列来管理获取该锁所有线程的。

  1. 公平锁(fairSync)：线程依次排队获取锁；

性能较差一些，因为公平锁为了保证时间上的绝对顺序，上下文切换更频繁。

  1. 非公平锁(NonfairSync)：锁被释放之后，后申请的线程可能会先获取到锁，是随机或者按照其他优先级排序的。

性能更好，但可能会导致某些线程永远无法获取到锁

3.sychronized和ReentrantLock的区别

两者均为可重入锁。区别如下：

  1. synchronized 是依赖于 JVM 实现；ReentrantLock 是 JDK 层面实现
  1. synchronized不公平；ReentrantLock两者均可
  1. synchronized不可中断；ReentrantLock可中断

synchronized一旦尝试获取锁就会一直等待直到获取到锁→不可中断。

具体解释： ReentrantLock中的lockInterruptibly()方法使得线程可以在被阻塞时响应中断。

比如一个线程t1通过lockInterruptibly()方法获取到一个可重入锁，并执行一个长时间的任务，另一个线程通过interrupt()方法就可以立刻打断t1线程的执行，来获取t1持有的那个可重入锁。而通过ReentrantLock的lock()方法或者Synchronized持有锁的线程是不会响应其他线程的interrupt()方法的，直到该方法主动释放锁之后才会响应interrupt()方法。

  1. synchronized不可限时，ReentrantLock可以。

超时不能获得锁，就返回false，不会永久等待构成死锁。

使用ReentrantLock.tryLock(long timeout, TimeUnit unit)来实现可限时锁，参数为时间和单位。

  1. 可实现等待/通知模式（锁可以绑定多个条件）:
  • synchronized关键字与wait()和notify()/notifyAll()方法相结合可以实现等待/通知机制。
  • ReentrantLock类当然也可以实现，但是需要借助于Condition接口与newCondition()方法。

4.可中断锁和不可中断锁

可中断锁：获取锁的过程中可以被中断，不需要一直等到获取锁之后 才能进行其他逻辑处理。ReentrantLock 就属于是可中断锁。

不可中断锁：一旦线程申请了锁，就只能等到拿到锁以后才能进行其他的逻辑处理。 synchronized 就属于是不可中断锁

4.CountDownLatch

1.什么是CountDownLatch？

Java 中的一种同步工具，用于控制一个或多个线程等待其他线程完成执行。

它的作用类似于一个计数器，只有计数器的值变为零时，等待的线程才能继续执行。CountDownLatch 的计数器计数的是需要等待的事件数量。

CountDownLatch 允许 count 个线程阻塞在一个地方，直至所有线程的任务都执行完毕。

CountDownLatch 是一次性的，计数器的值只能在构造方法中初始化一次，之后没有任何机制再次对其设置值，当 CountDownLatch 使用完毕后，它不能再次被使用。

2.原理

CountDownLatch 是共享锁的一种实现，它默认构造 AQS 的 state 值为 count。这个我们通过 CountDownLatch 的构造方法即可看出。

CountDownLatch 主要包含两个方法：

  1. await()：调用该方法的线程会阻塞，直到计数器的值减为零。如果计数器的值已经是零，那么该方法会立即返回。
  1. countDown()：每次调用该方法会将计数器的值减一。一般情况下，该方法应该在某个任务完成后被调用，以通知 CountDownLatch 有一个事件已经发生。

3.实战(一般用在哪儿？)

CountDownLatch 的两种典型用法：

  1. 某一线程在开始运行前等待 n 个线程执行完毕 :

将 CountDownLatch 的计数器初始化为 n （new CountDownLatch(n)），每当一个任务线程执行完毕，就将计数器减 1 （countdownlatch.countDown()），当计数器的值变为 0 时，在 CountDownLatch 上 await() 的线程就会被唤醒。

💡 典型应用场景：启动一个服务时，主线程需要等待多个组件加载完毕，之后再继续执行。

  1. 实现多个线程开始执行任务的最大并行性：

注意是并行性，不是并发，强调的是多个线程在某一时刻同时开始执行。

💡 类似于赛跑，将多个线程放到起点，等待发令枪响，然后同时开跑。

做法是：初始化一个共享的 CountDownLatch 对象，将其计数器初始化为 1 （new CountDownLatch(1)），多个线程在开始执行任务前首先 coundownlatch.await()，当主线程调用 countDown() 时，计数器变为 0，多个线程同时被唤醒。

5.Condition

1.什么是Condition？

  1. 是一个Java多线程接口，Condition接口提供了类似Object的监视器方法。
  1. 作用：与Lock配合可以实现等待/通知模式。
  1. 它的作用是对原生的wait()、notify()/notifyAll()方法进行增强。

这种方式相比于传统的 wait()/notify() 方法更加灵活，因为它允许线程等待在不同的条件下，并且可以唤醒一个或多个等待的线程。

这种灵活性使得 Condition 可以更好地用于复杂的线程协作场景，例如生产者-消费者模式、读写锁等。

3.使用注意事项

  1. Condition依赖于Lock对象→Lock.newCondition()

Condition对象是由Lock对象（调用Lock对象的newCondition()方法），获取一个Condition必须通过Lock的newCondition()方法

  1. 与Lock配合实现等待/通知模式

Condition定义了等待(await)/通知(signal)两种类型的方法。

当前线程调用这些方法时，需要提前获取到Condition对象关联的锁。

Condition 接口定义了以下几个重要的方法：

  • await()：使当前线程进入等待状态，并释放当前线程持有的锁。

当其他线程调用 signal() 或 signalAll() 方法时，当前线程会被唤醒，并且重新竞争锁。

  • await(long time, TimeUnit unit)：使当前线程等待指定的时间，如果在指定的时间内没有被唤醒，则会自动唤醒。
  • signal()：唤醒一个等待在 Condition 上的线程。
  • signalAll()：唤醒所有等待在 Condition 上的线程。

Condition 可以与 Lock 接口的实现类（如 ReentrantLock）一起使用，通过 Lock 的 newCondition() 方法创建 Condition 实例。

线程可以在 Condition 上等待特定条件的出现，当条件满足时，其他线程可以通过调用 signal() 或 signalAll() 方法来通知等待线程。

4.常见用法举例

Condition 的常见用法包括：

  1. 生产者-消费者模式：在多线程环境中，生产者线程负责生产数据，消费者线程负责消费数据。可以使用 Condition 来实现生产者等待消费者消费完毕后再生产，消费者等待生产者生产完毕后再消费的机制。
  1. 有界队列：在多线程环境中，使用队列作为共享数据结构，可以使用 Condition 来实现对队列的长度进行限制，当队列满时，生产者线程等待队列不满，当队列为空时，消费者线程等待队列不空。
  1. 线程等待/唤醒：在多线程环境中，可以使用 Condition 来实现线程的等待和唤醒机制。例如，一个线程等待某个条件满足后再继续执行，另一个线程在某个条件满足时唤醒等待的线程。
  1. 读写锁：在读写锁的实现中，通常会使用两个 Condition 分别来管理读线程和写线程。读线程在写锁被占用时等待，写线程在读锁和写锁都被占用时等待。
  1. 定时任务等待/唤醒：在定时任务执行的场景中，可以使用 Condition 来实现线程等待一定时间后再继续执行的机制。当定时任务超时时，可以通过 Condition 的 signal() 方法唤醒等待的线程。

总的来说，Condition 提供了一种灵活的线程协作机制，可以根据具体的需求和场景灵活地实现线程的等待和唤醒，从而更好地控制线程的执行顺序和并发度。
