DeepSeek dsh-superagent 技术方案分析（学习版）

2026-11-01 · Agent应用开发/20261101-DeepSeek-dsh-superagent技术方案分析.md

调研对象：deepseek-ai/dsh-superagent-prototype（GitHub，MIT，2026-10-31 深夜开源，11-01 刷屏） 配套文章：Exploring Super-agent Design: Towards a More Autonomous Agent System（README 中引用的论文题目） 调研方式：通读仓库全部 9 篇官方设计文档（docs/000~008，约 18 万字符）+ 仓库结构 + SETUP/README 调研人：小墨 · 2026-11-01 定位声明：这是研究原型（research prototype），作者自述「非产品、可能有 bug、大量工程由 coding agent 完成」。学习它的思想与架构，不建议直接部署生产。

0. 一句话总结

DeepSeek Harness 团队把「让 Agent 一直在线、主动找活干」当成一个分布式系统问题来解：用计算机系统领域几十年的老思想（事件源、准入控制、授权票据、单写者事务、发件箱、副作用队列）重写了一遍 Agent 的组织方式，核心交付物不是代码，而是一套可抄的架构范式。

1. 它要解决什么问题

1.1 单 Session Agent 的四个缺口

普通 Coding Agent（Claude Code / Hermes / OpenClaw 的默认形态）本质是 单 Session 的 ReAct 循环：收到消息 → 思考 → 调工具 → 回复 → 结束。团队总结它撑不起「超级智能体（Super-agent）」的四个特征：

  1. 连续（Continuous）：Session 结束就断线，没人喊它就彻底沉默，无法长期跟随一个任务（比如一个 PR 的三天评审期）。
  2. 高效（Efficient）：所有事情挤在一个上下文里做，Router 级判断和工程级执行混在一起，长任务互相拖累。
  3. 主动（Proactive）：不能自己发现「该干活了」（CI 挂了、有人评论了、规则允许我自动处理），只能被动等 @。
  4. 持久（Persistent）：进程一重启，内存里的工作状态全丢，恢复靠人重新交代。

1.2 设计哲学：Attention 即成本

全篇文档的第一原理（000-philosophy）：

Take as little human attention as possible, and give as much value as possible. 尽量少占用人的注意力，尽量多交付价值。

由此推出 Agent 的三条行为铁律：

  • 只在被请求、或被书面规则允许时才动手（work nobody asked for needs a rule）。
  • 只在「人必须行动」或「人能用到结果」时才说话（干活时保持安静；消息默认一句话、硬上限 100 词）。
  • 按影响面收尾，不按工作量收尾（本地小改动做到可 review；需要设计决策的立即停下来问一个具体问题）。

对操作者的三条责任：先窄后宽（白名单从小开始、主动工作先只记录不执行）、降噪不解释噪（吵就改短改严 prompt，不要发更多消息解释为什么吵）、为它说的话负责（以你的账号发消息，读它发了什么、错了就改 prompt）。

这套哲学值得整段抄进我们任何 Agent 的 SOUL。

2. 总体架构

2.1 双层角色

                 ┌────────────────────────────┐
 GitHub/飞书 ──▶ │  Source（事件源）            │ ──Trigger──▶ Thread
                 │  游标/轮询/去重/翻译         │
                 └────────────────────────────┘
                                   │
                 ┌─────────────────▼──────────────────┐
                 │ Main Session（Router / orchestrator）│
                 │ 只做：准入判断 Eval · 路由 · 回复      │
                 │ 不做：任何技术决策                    │
                 └───────┬──────────────────┬─────────┘
                    Ticket+Mandate      Channel（回写）
                         │                  ▲
                 ┌───────▼──────────┐       │
                 │ Executor Session │ ──────┘
                 │ (Worker/worker-N)│  报告/PR/回复
                 │ 一票一Session一目录│
                 └──────────────────┘
  • Router（主 Session，orchestrator）：常驻，接事件、维护全局上下文、只做「这件事归谁、要不要开工」的任务级分派。用轻量模型即可（路由不深入技术细节，路由备注限 30 词）。禁止等待：宿主直接拒绝 sleep、>30 秒的 shell、>5 秒的 job 等待——因为阻塞一步就会积压新候选。
  • Worker（执行器 Session，worker-N）：每张 Ticket 一个独立 Session + 独立目录（git worktree 检出），上下文互相隔离，干具体的活。工具集被砍掉「问人、展示 UI、改配置」类工具，无人值守执行。

2.2 一条消息的完整生命周期

Source 产出 Trigger（不可变事件）
  → 归入一个或多个 Thread（会话线）
    → 两条路：
       A. 订阅扇出（Subscription fan-out）：已订阅该 Thread 的活 Ticket 直接收到作为上下文，不走评估
       B. Eval 评估：gate 准入 → assess 研判 → Decision（accept/stop/ignore/unavailable）
          → accept：原子创建 Ticket + Mandate（授权票据）+ 首个 Assignment + 订阅 + 确认回复
             → Assignment 派工给 Worker（pending → running → ended）
                → 结果经 Channel 回写原会话（PR/评论/群回复）

关键设计：Session 不是用户的认知载体。用户看到的是「一个请求 → 一个工单 → 一条结论」，背后 Worker Session 可以换、可以重试、可以重启，全部是系统内部实现细节。

3. 域模型：11 个概念 + 一份「拒绝清单」

官方文档 001 是全文档含金量最高的一篇：它先定义概念，再列出刻意不引入的概念。学习分布式系统设计，这份「反面清单」比正面定义更值钱。

3.1 核心概念（压缩版）

概念一句话关键约束
Source事件流实现（GitHub/飞书），带自己的游标重启不重放；机器人自己的消息直接丢弃
Trigger一条不可变事件，带发送者元数据审计与幂等的最小单位；重复接受只产生一张 Ticket
Thread时序排列的 Trigger 集合同一 Thread 上同时最多跑一个 Eval
CorrelationThread 之间的关联只加上下文，永不路由
ChannelThread 的写侧（回复地址）确认、答复、PR、结案都是「写」
Policy版本化的接单规则 + 各 Source 的白名单/准入表版本变更作废运行中的 Eval；不撤销已发放的 Mandate
Eval对一批 Trigger 的判断（gate 准入 + assess 研判）无状态，只产出 Decision
Mandate授权票据：策略版本+范围+强度+命中规则+发送者身份不可变；只有三个操作能改变它（受理发放 / 人工停止 / 再校验失败吊销）
Ticket一单位「被授权的工作」只有 Eval 能创建；自持状态，不跟随执行器状态
AssignmentTicket 与某个执行器实例的绑定状态独立于 Ticket；只有最终报告能从执行侧终结工单
SubscriptionTicket↔Thread 多对多订阅后续讨论自动到达，不需要再 @ 机器人；不授予任何新权限

3.2 被拒绝的概念（反面教材精选）

拒绝掉的理由
用户/成员实体、跨平台身份映射「一个人」只是 Trigger 的元数据；白名单是 Source 的一部分；跨 Source 认人靠 prompt 文本，不建数据模型
Eval 自己调度延时任务需要等待的条件就做成一个普通 Source，Eval 永不反向依赖 Source
Ticket 状态跟随执行器 SessionTicket 可以被交接/重试/换执行器，所以状态必须自持
「往已有工单追加」这种 Decision追加=订阅扇出，不需要评估
从报告自由文本推断「在等人」分类必须用结构化字段，不允许从自然语言里猜
政策变更就取消运行中的工单取消会留下半成品；改为记录变更并通知受影响工单
每 Thread 只允许一张活 Ticket一个会话线天然可以并行多件事，去重交给研判阶段
锁死失败执行器的全部工具会误伤「人直接进 Session 协作」和恢复后的汇报；只需暂停自动输入

为什么这份清单重要：它演示了「概念预算」思维——每个新需求优先变成已有概念的一个属性或一段 prompt，而不是新增一个概念。我们的名录/任务板演化时同样适用。

4. 授权体系（风控视角精读）

这一章和你的本行同构，可以当成「Agent 版准入风控系统」来读。

4.1 双通道：授权通道 vs 上下文通道

  • 授权通道（Eval）：决定「要不要开工」。只有它能创建工单、发放权限。
  • 上下文通道（Subscription）：决定「工单能看见什么」。订阅线上的所有消息（含机器人和 CI）直达工单，绕过 gate、不授予任何新权限。

一句话：上下文与授权彻底分离。看到 ≠ 被授权；一个 Ticket 永远只在自己的 Mandate 范围内活动。

4.2 Gate：三维准入表

一个消息是否成为「明确请求」，由三格交叉决定：

维度取值
发件人是否在该 Source 白名单在 / 不在
是否直接对 Agent 说话（@机器人 / 私聊）是 / 否
消息落在哪个接收范围（群/私聊/新Issue/PR评论/CI）每个范围一行

三个格子的合法取值（默认值保守）：

  • 白名单内、没 @ → 默认 inferred（可进研判）
  • 白名单外、@了 → 默认 ignore（陌生人 @ 默认不理，可改成 explicit 用于专属支持群）
  • 白名单外、没 @ → 默认 ignore

4.3 强度与接受模式（影子上线机制）

强度：explicit（明确请求）/ inferred（推断候选）/ not admitted（不受理）。名单上的人 @ 了 = explicit；名单上的人在有工单的 Thread 里跟进 = inferred；其他机器人永远只能产生 inferred 候选，不能产生明确请求，也不能停止工单。

接受模式（Policy 的一部分）：

模式效果
off一切推断候选不成立（只有明确请求有效）
observe（默认）推断候选照常研判；正向结果只记录为 "would accept"，不真正接单
auto研判通过的推断候选自动接单

这就是风控的影子模式（shadow mode）：先跑 observe 积累 Decision 记录，人工审过「would accept 都判得对」再切 auto。官方明确要求：从 observe 起步。

4.4 Mandate：授权票据的生命周期

一张 Mandate 记录：策略版本、授权范围、强度、命中的规则、发送者身份、消息进入的路径。它是不可变的（immutable）——范围变大不是修改，是开新工单。

只有三个操作能改变它：

  1. accept 创建（Eval 的一次通过）；
  2. 人工 stop 撤回（群里说 stop 本身也是一条 Trigger，由 Eval 判定；面板 stop 是直接命令）；
  3. 再校验（revalidation）失败吊销。

Revalidation（工单复活前重校验）是精髓：已结束的工单被人的消息唤醒时，按 Mandate 的「出身」逐项复查——白名单成员还在不在？准入格子今天还能给出同样强度吗？机器人还在机器人名单上吗？auto 模式还开着、命中规则还启用吗？任何一条不满足，工单保持结束、等待消息退回 Eval 重新评估。

这就是安全里的「会话票据 TTL + 权限快照校验」：旧授权不因时间流逝自动有效，恢复现场前先对当前策略重算一遍。

4.5 Policy 版本化

规则 + 接受模式 + 各 Source 白名单/准入表 → 哈希成一个 Policy version，写进每张 Mandate。变更时：

  • 运行中的 Eval 作废重排（不能用旧规则判新消息）；
  • 受影响的活工单收到「策略变更」输入（告诉你：命中规则改了/请求人已无权/主动模式已关），不受影响的工单一个通知都不发；
  • 存量 Mandate 不立即吊销，留到复活时再校验。

4.6 与风控系统的同构映射

dsh-superagent风控对应物
Source 游标 + 去重事件摄取 + 幂等键
Gate 准入表准入策略引擎（三维交叉规则）
accept mode off/observe/auto拦截/影子/自动处置三档
Mandate授权票据（含策略版本快照）
Revalidation会话恢复时的权限重校验

停止只有人能下人工兜底优先级高于自动化

5. 执行体系

5.1 Ticket 状态机：互斥且完备

阶段表从上到下首行命中生效，保证每个活工单恰好落一格：

阶段条件
person/delivery投递输入到 Worker 失败（2s 起指数退避重试）
person/answer有未回答的 Attention（结构化提问）
person/review最新报告 = ready（可评审）
person/blocked·failed最新报告 = blocked/failed 且此后无人的消息
working/queued无派工或派工待启动
idle最新报告 = waiting，或本轮派工结束（等下一条触发）
working其余一切

person/* = 没有人参与就推不动；idle = 干完一轮且没有待答问题，等订阅线上的新触发续命。人的消息会立刻把 blocked/failed 释放回工作态——错误永远可以被人叫醒。

5.2 Worker 的资源模型

  • 一票一 Session 一目录：目录由 prepare 命令创建（典型：git worktree 拉独立检出，10 分钟超时），失败记为工单失败。
  • Worker slot 并发控制：并发上限 N，外加 1 个特权槽专门留给人的消息/状态查询——「新任务不能阻止人继续老任务」（wakes 优先于 launches）。
  • 5 秒切后台：前台 shell 超 5 秒自动转后台作业，这样 Worker 在长命令跑着时还能在下一步收到新消息。
  • 30 分钟上限：回合结束后后台作业最多再跑 30 分钟，到点杀掉并报告「等待」；子代理可以继续。交接给人时立刻释放 slot。

5.3 失败与恢复（区分瞬时/永久）

  • 瞬时失败（模型方/网络：408/429/5xx/连接重置）：三次退避重试（launch 重跑、Worker 被告知继续）。
  • 永久失败（prepare 命令失败、其他启动失败）：不自动重试，工单转 failed，等人来（retry 是人的操作）。
  • blocked/failed 期间：CI 和机器人消息只记录不投递、不唤醒；人的消息仍可到达（工具保持可用，人可以直接进 Session 接管）。
  • 重启恢复：运行中的派工以「宿主已重启」终结；新派工带恢复便签（recovery note）：先检查目录、git 历史、GitHub 上的外部动作，再决定要不要重做，最老的 Ticket 先恢复。
  • 先存后做（stored work）：一切对外动作（转发、派工、投递、发消息）先落库再执行，失败按 2s→60s / 5s→300s 指数退避；连续失败 3 次才升格为「系统问题」。

5.4 结束语义

  • ready 报告 = 完成（可带 PR）；dropped = 无事可做（静默结束，不发消息）。
  • 开了 PR 的工单：跟随 PR 而不是报告——PR 关闭/合并才终结工单，结案后订阅保留，人再评论可原票据复活（不重新评估）。
  • 被人工 stop 的工单：保持结束、什么也不再收；要继续必须重新受理。

6. 一致性与可靠性工程（最值得抄底的部分）

  1. 单写者原则：Engine 是 Trigger/Thread/Decision/Ticket/Assignment 的唯一写者；Source 只写自己的游标和 meta；Settings/Prompts/Effects/Outbox 各有唯一写者。所有命令同步 + 单事务，副作用在事务内入队、提交后才执行。
  2. Effects 持久副作用队列：六种 kind（assessment/launch/delivery/relay/notice/reply），kind+key 去重（同 key 重入替换 payload 不改队序），指数退避，连续失败 3 次才报健康错误。relay/notice 严格保序，失败的会挡住同类后续（保证「确认先于答复」）。
  3. Outbox 发件箱：每条对外消息一个回执，pending/sent/dropped 三态；同一工单对同一会话保序发出；dropped 的消息记录原因且永不重排（防重复轰炸）。
  4. Passes 轮次：每 2 秒（或被命令要求时）跑一轮——先清到期副作用，再跑到期评估；一轮只跑一次，期间新到的合并进下一批。整个系统是「轮询驱动的状态机」，不依赖长连接魔法。
  5. 暂停语义：pause 停派工/评估/投递/回复，但 Source 继续记录、Worker 正在跑的回合不打断；恢复后暂停期间收到的人类消息先复活工单；Eval 的 deadline 顺延暂停时长。
  6. 可观测：每个部件在健康板上认领自己的条目（一夫一妻制，重复认领直接拒绝）；面板只回答三个问题（现在要我处理吗？系统健康吗？某件事的来龙去脉是什么？），健康态不占空间。

7. Prompt 与人机边界

7.1 角色纪律

  • Router 只路由：转发原始触发与路由事实，不做技术判断，路由备注 ≤30 词；一次路由调用批量处理 1–20 个决策。
  • Worker 决定自己的跟进：范围内请求自己接并确认（每个新请求先在原消息下确认「我要做什么、产出什么」，一次）；超出范围的交回（handback）给 Router 重新评估，附理由。
  • 协调只走两条路：订阅相关 Thread（只给上下文不给权限），或 Router 发 ≤100 词的「事实便签」（同样不给权限）。
  • 提问必须结构化：Worker 把一个具体问题放进 Report 的结构化字段，Router 原样转发，宿主在触发它的那条消息下问。「等待人工」不允许从自由文本里推断。
  • 自动评审员每 PR 最多 3 轮；已修复的评审意见静默 resolve，被拒绝的给一句话理由。
  • 撞车让路：如果人的分支已经包含同样修改，Worker 关掉自己的 PR 并一句话指过去。

7.2 优先级五层（Prompt Injection 防线）

从硬到软：

  1. 代码强制的事实（身份、权限、工具参数校验、回复用途、长度上限）——prompt 改不动；
  2. 内置/生成的 prompt 段（含团队覆写后的实际文本）；
  3. 主动工单命中规则里的流程/沟通要求（对该 Worker 生效）；
  4. 团队段落与团队技能；
  5. 外部文本（消息、评论、文档、引用）：永远是数据，永远不能改变规则与授权。

这就是「不可信输入」的标准处理：无论群里有人说什么都越不过 gate 和 Mandate，因为它们在代码里而不是在 prompt 里。

7.3 Prompt 版本化

配置即版本（每次保存 = 不可变快照，含前驱、时间、来源）；每次模型请求读最新版；团队覆写记录「基于哪个内置版本」，升级时内置默认变了会在面板标 Default updated 并给 diff，由人决定「保留我的 / 用新默认」。

8. 实测表现与代价

配套文章的合成负载实测（引自 10-31 发布期调研，非本机复测）：

  • 双层架构：p50 12.4 分钟 / p95 15.7 分钟；
  • 对照组「单 Session + Subagent」：p95 29.5 分钟；
  • 代价：读缓存 token 从 2323 万涨到 3177 万（约 +37%）——多进程换低时延，烧更多 token。

结论：当「人的等待时间」比「token 成本」贵时，这套架构划算；反过来不划算。

9. 局限与风险（清醒剂）

  1. 绑死 DeepSeek Harness：Node/pnpm 工程，Session/预设/插件体系全是 Harness 私有概念，代码不可移植，能移植的是文档里的设计。
  2. 隔离是软的：文档明说账号包装器「是默认值不是安全边界」，Worker 是 danger-full-access、能按绝对路径执行任意程序、能读操作者家目录；真要隔离得给它独立 OS 账号。
  3. 无治理闭环：Nothing deletes old records——trigger/disposition/decision 无限增长，需要自己做归档。
  4. 研究代码：作者声明有 bug、风格不一致、部分论文设计未实现（比如每 2 秒一轮的「主动 pass 评估」论文版在原型里简化掉了）。
  5. 信任边界仍是开放问题（官方 Open questions）：Trigger 的哪些字段可信（Source 给的 actor/成员关系）与哪些不可信（正文/引用），文档只给了原则没给完实现。

10.2 三条最值得抄的机制（本次落地 v1）

  1. Mandate 入任务卡：任务板每张任务卡头部强制写「授权依据 / 授权范围 / 强度（explicit/inferred）/ 策略版本 / 失效条件」，替代散在群聊里的口头派单。防越权、防「没人让我干但我顺手干了」。
  2. observe 影子模式：巡检类自动补做先跑 observe——发现问题先生成「建议补做」记录，不直接动手；连续 7 天判断全对再切 auto。对应我们现在「巡检发现问题直接补跑」的激进做法。
  3. 上下文与授权分离：追问/后续消息进原话题群即可直达（订阅直通），但不产生新授权；超出原任务范围必须回主助理重新分派（handback 语义），禁止 Worker 在老工单里顺手接新活。
