H5 活动风控 · 完整技术调研（从零到落地方案）

定位：本篇是 REQ-004 的总文档，面向「后端/业务风控出身、对浏览器与前端技术是小白」的读者，从需求还原讲到核心技术概念，再到行业常见方案与落地路线。 阅读路线：只想知道结论 → 看第七章；要补前端与风控基础 → 按 1→6 顺序读；要上手 → 看第七章路线图 + 第八章名词表。 前两轮专题笔记（更细的技术细节与来源）：2026-10-28-JS虚拟化保护第一轮调研.md（VM 保护原理）、2026-10-28-H5活动风控第二轮调研.md（厂商落地/WebAuthn/攻击面）。

一、需求还原（先把需求讲完全）

1.1 你的原话拆成需求条目

  • 手机端活动已有一套跑通的核心能力：真机能力 = SDK 采集（一重）+ 服务端核算校验（二重），能识别「这个请求是不是从真机发起」，直接打击纯接口调用的黑产。
  • H5 页面活动没有对等能力：接口直接暴露在浏览器网络面板里，黑产抓包后脚本直调即可爆破/批量刷。
  • 你之前听说「H5 可以靠 JS 虚拟化实现类似效果」，但没深入研究过；想借这次调研把这块能力学会（不是只要结论）。
  • 你的工作场景：安全风控、负责业务活动与黑产对抗，日常做手机端，现在要把经验迁移到网页端。
  • 期望产出：通用性评估 + 是否可行 + 可落地的方案建议，一边学一边研究的长期单（已立项 REQ-004）。

1.2 我对需求的完整理解（可直接纠错）

编号我的理解若有偏差的后果
N1真正要解决的是「H5 活动接口裸奔 → 黑产脚本直调刷奖」，虚拟化只是候选手段之一，不是目标本身若把 VM 当目标，会做出投入大、收益错位的方案
N2目标是能力迁移：把手机端「端上采集 + 服务端二重校验」的思路在 Web 侧找到等价实现若只抄手机端，会因 Web 缺硬件锚点而处处落空
N3需要从零讲清核心概念（前端/浏览器/抓包/签名/指纹/VM/WebAuthn），不能只给结论若只给结论，你无法在内部评审里讲清「为什么」

1.3 「好」的验收标准（交付前自查）

  • 一个没做过前端的人，读完能说清「一次 H5 活动请求从浏览器到服务端经历了什么」
  • 每个核心技术（指纹/签名/防重放/人机/VM/指纹保护/决策引擎）都有：是什么 → 怎么工作 → 能挡什么 → 挡不住什么 → 成本
  • 行业常见方案至少 3 类（自研 / 商业 SDK / 边缘动态安全）且有代表厂商与能力差异
  • 黑产视角完整（产业链分工 + 攻击链），与防线一一对应
  • 给出 2–3 个落地方案 + 明确推荐 + 分阶段路线与验收指标
  • 名词表可当速查手册用

二、地基概念（小白视角，从零讲）

2.1 一次 H5 活动请求的完整生命周期

用户点开活动链接
 → 浏览器向你的服务器要 HTML/JS（这一步就是「前端代码被下载到用户机器上」）
 → 浏览器执行 JS：渲染页面、读取浏览器信息、算出各种参数
 → JS 发起接口请求（领奖/抽奖/投票…），请求里带 token、sign、指纹等
 → 你的网关/WAF 收到 → 服务端校验 → 业务逻辑 → 返回结果

最要命的一点：第 1 步就把 JS 交给用户机器了，用户（和黑产）拥有完整源码 + 可以断点调试 + 可以改里面任何一行。所以：

Web 侧的一切「端上计算」都是可被观察、可被复现的。端上做的所有事只能提高成本，不能构成信任。

这就是你手机端「真机能力」和 H5 的根本差别：手机端有不可复制的硬件与系统环境（SE/TEE、系统 API、签发的设备证书），浏览器里的一切攻击者都能自己造。

2.2 抓包 / DevTools：黑产的第一件工具

  • DevTools（F12）→ Network：能看到每一次请求的 URL、Header、Body、耗时——接口「直接暴露」就是指这里。
  • Sources：能看到未压缩的 JS 源码，能打断点、看变量、单步执行。
  • 因此黑产的起点永远是：打开页面 → 看请求 → 找出必填参数 → 看 JS 里这些参数怎么算出来 → 用 Python 复现。

2.3 前端加密到底防谁（最容易误解的概念）

  • 防不住「已经能打开 DevTools 的人」——算法、密钥、逻辑全在他机器上。
  • 防得住的：
    1. 降低「无差别扫描器/脚本小子」的成功率；
    2. 缩短明文在客户端的暴露窗口（密码、敏感字段提交前先处理）；
    3. 防篡改（参数签名：改了金额签名校验就不过）；
    4. 防原样重放（时间戳 + nonce）；
    5. 把攻击者的工作从「读明文」抬到「逆向 + 调试 + 追密钥」的难度级。
  • 一句话：前端保护是时间窗武器，不是保密武器；密钥与最终判决必须在服务端。压缩（minify）≈ 零安全价值，混淆提高成本，VM 提高更多，但没有一种能让代码「不可读」。

2.4 HTTPS 防什么、不防什么

  • 防：链路上的窃听与中间人篡改（传输层加密）。
  • 不防：① 端点自己（你的页面/我的浏览器各自看到明文）；② 合法请求被原样重放；③ 参数在发出之前就被改（脚本直调时签名算对即可）；④ 业务层的越权与批量。
  • 所以 HTTPS ≠ 风控，它只是地基。

2.5 五个必懂小概念（后面反复出现）

  • 哈希（MD5/SHA256）：任意数据 → 固定长度摘要，不可逆，用来「验完整性」和「当指纹」。
  • HMAC：哈希 + 共享密钥，只有持密钥者能算出正确值 → 用来验真与验未篡改（签名）。
  • 对称/非对称加密：对称（AES）快、适合加密内容；非对称（RSA/ECDSA）有公私钥，适合签名与密钥交换。签名保证「来源真实 + 内容没改」，不保证内容保密（要保密得另做加密）。
  • 时间戳 + nonce：时间戳限制「这请求有多老」（窗口），nonce 保证「窗口内只能用一次」。两者必须同时有——只有时间戳，窗口内可无限重放；只有 nonce，可无限期重放。
  • Cookie / Session / Token：浏览器自动带的凭证（Cookie）→ 服务端会话（Session）→ 自包含凭证（Token/JWT）。JWT 有签名只说明 token 内容没被改，管不住承载它的 HTTP 请求体有没有被改——这是高频事故点。

2.6 什么是「二重校验」

  • 一重（端上）：采集 + 加工，产出一个「证据」（deviceToken、签名、行为数据）。
  • 二重（服务端）：核算 + 交叉验证，出判决。
  • 关键纪律：端上永远不判决。Web 端的一重证据天生可伪造，价值全靠服务端把它与「账号历史、网络信誉、行为时序、关联图谱」交叉后才成立。

三、核心技术积木（行业方案的 8 块砖）

M1 设备指纹（Web 端的「设备 ID」）

是什么：采集浏览器环境的上百个特征 → 算出一个相对稳定的 ID，用来「认出是不是同一台设备/同一个环境」。

采集维度（常见分组）：

  • 环境：UA、语言、时区、屏幕分辨率/色深、DPR、CPU 核数/内存、插件、字体列表
  • 渲染：Canvas（让浏览器画同一张图，读回像素比对——OS/显卡/字体渲染/抗锯齿的细微差异产生差异）、WebGL（显卡与驱动信息）、AudioContext、Audio 指纹
  • 网络：出口 IP/ASN、WebRTC 暴露的真实地址、DNS
  • 硬件/系统（移动端 H5）：陀螺仪、电池、触摸能力
  • 行为：鼠标/触摸轨迹、点击与滚动时序、停留时长

怎么把特征变成 ID：

  1. 各维度取值 → 拼接 → 哈希 → 指纹串；
  2. 稳定性问题（同一个用户两次访问是否还是同一个值）：单个特征会变（时区、UA 升级），所以要用多特征加权 + 相似度匹配（而非严格相等）：两串指纹的汉明距离/相似度超过阈值就判「同一设备」；
  3. 熵与唯一性：学术测量显示约 89.4% 的浏览器指纹是唯一的；但单靠一两个特征熵不够，必须组合（Canvas/WebGL/字体/屏幕/时区叠加）；
  4. 碰撞治理：厂商专利级做法——按「机型/OS」分桶统计每个特征的重复率与空值率，超阈就降权或剔除，防止「大批设备算出同一个指纹」（碰撞）或「某特征大面积为空导致指纹失效」。

能挡什么：同设备批量账号、设备多开、脚本环境（navigator.webdriver、自动化框架痕迹、环境不自洽）。 挡不住什么：改机/指纹伪造工具、云手机、真实设备农场——所以指纹只能当弱绑定，必须配统计信号（见 M7）。 自研 vs 商厂：自研可控、免费、但碰撞治理与黑产情报要自己积累；商用（顶象/数美/易盾/腾讯 TDS/阿里云设备风控）自带黑产库与团伙情报，按量付费、数据出域。

M2 接口签名与防重放（H5 最基础的一层）

目标：挡「抓包改参数」与「原样重放」。

标准配方：

sign = HMAC-SHA256(规范化参数串(排序后的业务参数) + timestamp + nonce + deviceId, secret)
  • 服务端：先验 timestamp 在窗口内（如 ±60s）→ 查 Redis 里 nonce 是否首次出现（重复=重放）→ 用同样规则重算 sign 比对 → 再进业务。
  • 密钥纪律：secret 不写死在 JS 里；由服务端登录/进页后动态下发、定期轮换；参与签名的字段必须覆盖所有敏感字段（漏一个就是可篡改缺口）。
  • 边界：这层挡脚本小子与原样重放，挡不住「在真浏览器里跑一遍 JS 把 sign 正确算出来」的脚本——那要靠 M5（提高算 sign 的成本）与 M1/M4（证明是真人真环境）。

M3 会话与调用链（L2，H5 最短的板）

是什么：把「页面访问」和「接口调用」串成一条链。

  • 进页：服务端下发一次性 sessionId / state（可与 CSRF token 合一），JS 带在后续请求里；
  • 服务端：接口必须能在本会话的前序记录里找到依据（浏览过活动页 → 拿过奖池 → 才能领奖），缺前序直接拒；
  • 再叠加频控/限流：同 deviceId/账号/IP 在 60s/1h/活动周期内的次数阈值。

为什么性价比最高：纯接口调用者天然没有前序会话，第一道就被打死；不需要逆向任何东西，1–2 周可上线。

M4 行为与人机识别（无感验证 / 验证码）

演进路线：扭曲文字 OCR 可破 → 点选/滑块（可被脚本/打码平台破）→ 无感验证（不打断用户，靠行为与环境评分）。

工作方式（美团活动 Web 页面实践的形状）：

  1. 风控服务端先下发 Token 给前端；
  2. 前端采集交互行为（点击、滑块轨迹、触摸力度/加速度/抖动、页面路径）并加密上报；
  3. 服务端按「自然人初筛指标 + 生物行为特征」两阶段判断是不是真人（专利级做法：轨迹的速度剖面、加减速、超调、力度、以及与该客户端历史轨迹的吻合度）；
  4. 有异常 → 才升级成显式挑战（更难的轨迹曲线/点选）。

关键认知：成熟的 Bot Management 不是「检测到机器人就弹验证码」，而是：

原始事件 → 按会话/账号/设备/时间窗聚合特征 → 算风险分 → 分级处置
低=放行 / 中=降速、后台挑战 / 高=显式验证 / 极高=阻断+人工复核

验证码只是处置动作之一，不是检测本身；证据充分时直接限速/拦截，不浪费验证码。

能挡：脚本直调、纯轨迹模拟（脚本轨迹是固定的，聚类后「完全一致」即异常）。 挡不住：打码平台（人工）、真人代刷（羊毛党真人参与）。→ 后者只能靠 M1 的关联统计 + M7 的图谱。

M5 JS 保护与虚拟化（把「校验逻辑本身」藏起来）

三档强度（判断一个方案是不是真 VM，看这条界线）：

  1. 压缩 minify：删空白/注释/缩短变量名 → 安全价值约等于零（格式化工具一秒还原）。
  2. 静态混淆：控制流平坦化（状态机）、字符串加密与集中、常量池运行时解码、死代码、属性名混淆、点符号转方括号等 → 可被 deobfuscator 还原，但要花时间。
  3. 字节码虚拟化（真 VM）：为每次构建生成一套自定义 opcode 指令集，把目标函数编译成字节码 + 内嵌解释器；产物里没有原始函数体，普通 deobfuscator 无对象可还原。
  4. （加强档）WASM / C 编译：核心逻辑用 C 写再编译到 WebAssembly，二进制级防护；以及 运行时防线：反调试（devtools 检测、时间差）、完整性校验/防篡改、域名锁定、密钥运行时下发。

必须理解的边界（厂商文档原话级结论）：

  • 混淆只提高成本、不使其不可能；密钥与权威判决必须在服务端；
  • VM 交付的是「产物不暴露原始函数体 + 每个版本呈现一台不同的 VM」，不是永久保密；
  • 已有专做「JS VM devirtualization」的第三方服务，说明 VM 可被系统性还原；
  • AI agent 已把 449KB 级商用 VM 的逆向从「天」压到「小时级」。

怎么用才对：只虚拟化三处——签名计算、指纹采集、挑战回算；每版本轮换 VM；配套密钥不落产物。VM 的收益是「每次轮换让黑产重新计价」，不是「藏住秘密」。

M6 边缘与网络层（JS 全被绕过也还在）

  • WAF / 速率限制：按 IP、路径、令牌的并发与频率配额；Nginx 层就能拦 403。
  • IP/ASN 信誉：机房段、代理池、秒拨 IP、VPN 标签（百度/腾讯/数美都有 IP 画像库，分钟级更新）。
  • TLS 指纹（JA3/JA4）：客户端 TLS 握手特征——脚本（Python/Go HTTP 客户端）与真实浏览器的握手包结构不同，与 JS 完全无关，JS 被绕过依然有效。
  • HTTP 头一致性：Header 顺序、缺失字段、sec-ch-ua/Accept-Language 与 UA 是否自洽。
  • 动态安全（瑞数类）：页面与脚本动态下发、令牌校验，抬高「拿到稳定入口」的成本。

M7 服务端决策引擎（真正的「判决」）

  • 规则引擎：阈值与名单（频次、黑名单、一机多号、同 IP 段聚集），可解释、上线快。
  • 风险评分：多信号加权 → 0–100 分 → 分级处置（放行/降速/挑战/拦截/人工）。
  • 模型：有标签后上分类模型（异常检测、无监督聚类），处理规则覆盖不了的新型作弊。
  • 关联图谱/团伙挖掘：把设备—账号—IP—收货地址—行为连成图，做聚类与社区发现。
    • 工行实践：百亿级反欺诈知识图谱，从设备相似性与关联性挖出上千台设备的团伙；
    • 典型可操作特征：同一毫秒级时间戳批量生成的指纹（如 100 个账号的「设备启动时间」误差 <3 秒 → 同一台模拟器批量造号）、IP 同 C 段/同机房、注册间隔恒定（每 3 秒一个）、轨迹完全一致、MAC OUI 集中。
  • SDK 只采集，不做模式识别：这一点必须写进方案——采集 ≠ 识别，识别在服务端的聚合与聚类。

M8 令牌化与密码学绑定（Kasada 模式，值得抄的思想）

  • VM/SDK 产出的 token 与同一次执行采集的指纹、完整性信号密码学绑定（哈希进签名）；
  • 服务端只验 token，不认浏览器自述——你没跑完那套反插桩检查就构造不出可用 token；
  • 配合「每发布周期整体轮换 bytecode 与 bundle」，针对某快照写的 solver 下版本作废。

四、行业常见方案全景（3 大派系）

派系 1 · 自研前端加固 + 自建风控（技术驱动型）

  • 形状：前端签名/加密 + JS 混淆或 VM + 自研设备指纹 + 服务端规则引擎与评分 + 边缘限流。
  • 代表实践：京东 H5ST（深度绑定浏览器环境 + 时间戳 + 指纹 + 行为的前端参数签名）、美团活动 Web 人机识别（Token 下发 → 行为采集上报 → 服务端校验，且强调「逻辑不被反编译」是三大挑战之一）、vivo/各家大厂的接口加密实践。
  • 优点：数据不出域、可深度贴合业务、边际成本低。
  • 缺点：黑产情报要自己攒、对抗要长期投入、人才贵。

派系 2 · 商业风控 SDK + 决策引擎（买能力型）

  • 形状：接厂商 JS SDK 拿 deviceToken → 业务服务端调风险识别 API → 拿标签/评分 → 自己的策略或厂商引擎处置。
  • 代表厂商与侧重：
    • 阿里云 风险识别-设备风控：App/Web/小程序多端 SDK → deviceToken → 服务端 API → 标签+评分，主打营销防刷。
    • 腾讯云 TDS：H5 SDK + 服务端接口，模拟器/篡改/群控识别 + 账号-设备-IP 关联网络做团伙聚类。
    • 网易易盾：H5 应用加固（防逆向/调试）+ 设备指纹 + 风控引擎三板斧；明确列 H5 的刷量/撞库/薅羊毛三类风险。
    • 数美：设备指纹 + 行为风险（移动速度、机身姿态、IP 流量、设备聚集性）+ 环境风险（代理/调试/高危软件）。
    • 顶象：设备指纹 + 人机模型 + 无感验证 + 决策引擎，策略库/风险情报沉淀型（4380 条策略、118 种风险类型这类量级）。
    • 百度 AFD 业务安全风控：设备风险、网络风险（代理/秒拨/机房 IP）、黑卡账号、行为异常、威胁情报、设备风险画像，主打营销活动防刷。
    • 验证码/无感验证类：阿里云验证码（无痕验证）、腾讯天御、酷安/极验等——归到 M4。
  • 优点：上线快、自带黑产库与团伙情报、含对抗运营。
  • 缺点：按量计费、数据出域、黑盒、对「活动级」预算可能过重。

派系 3 · 边缘动态安全 / Bot Management（流量入口型）

  • 形状：WAF + Bot 管理 + TLS/HTTP 指纹 + IP 信誉 + 动态页面/脚本下发（瑞数为代表；国际上 Cloudflare/Akamai/Kasada 属同一层）。
  • 特点：不依赖 JS 是否被绕过，从连接与流量层做判定；常与派系 1/2 叠加。
  • 优点：覆盖面广、对爬虫与撞库同样有效。
  • 缺点：改不改业务前端都要动接入；对「业务语义作弊」（真人刷奖）帮助有限。

行业共识：三层叠加——边缘层（谁在连）→ 端上层（环境与行为证据）→ 服务端层（交叉判决与处置）。任何单层都不是答案。

五、黑产视角（知己知彼：他们到底怎么打）

5.1 产业链分工（不是一个人在战斗）

  • 卡商/猫池：批量手机号与接码（物联网卡也常被用）。
  • 养号/设备农场：模拟器多开、群控软件（100 控/200 控，市售千元级）、云手机、改机工具。
  • 打码平台：CNN 脚本对普通验证码 90%+ 通过率，难的转人工打码（低价人力）。
  • 协议党：逆向前端签名/加密参数，用脚本直调接口（H5ST 类参数已有成熟逆向教程与工具链）。
  • 变现：券/红包/实物转卖；已出现「提供侵入、非法控制计算机信息系统程序罪」判刑案例（海淀检察院：3 年 6 个月）。

5.2 攻击链 5 步 ↔ 我方防线

攻击步骤黑产动作我方防线（对应 M 模块）
1 侦察打开页面，Network 里看接口与参数接口最小暴露、非必要参数不下发（M2）
2 逆向读 JS 还原 sign/token 生成逻辑混淆/VM/密钥动态下发，抬高每次轮换的成本（M5、M4 的加密上报）
3 复现Python 脚本直调，或在无头浏览器里跑真 JS会话链缺前序即拒（M3）+ 指纹环境不自洽（M1）+ 人机评分（M4）
4 放大群控/多开/代理池批量执行指纹碰撞与聚集统计、IP/ASN 信誉、频控（M1/M6/M7）
5 绕过升级改浏览器引擎插桩、真人代刷、打码图谱团伙挖掘 + 行为时序 + 人工复核（M7），承认单点不可防，靠多因子

5.3 三条必须记住的对抗事实

  1. 没有单点硬证明：Web 上任何单一信号都可被伪造，判决永远来自多因子交叉。
  2. AI 改变了成本曲线：逆向一个商用 VM 从「天」降到「小时」→ 防线重心从「藏得深」移到「每版本轮换重新计价 + 服务端不可构造因子」。
  3. 真人羊毛党是另一类问题：真人 + 真机 + 真 IP 的「合规作弊」只能靠关联图谱与资损模型（一机多号、聚集性、同源资金/地址），不是靠环境检测。

六、WebAuthn / Passkey 能否当 H5 的「真机」（L3）

结论：不能当进门关的硬 L3，只能当高价值动作的补充因子。 分层理由：

  1. attestation 默认被削弱：标准与浏览器厂商都不鼓励 RP 请求 attestation，实际拿到的多是 none——「这是哪台设备/哪颗芯片」的证书链基本拿不到。
  2. synced passkey 绑的是账号不是设备：passkey 通过密码管理器跨设备云同步（Apple/Google/Microsoft 均如此），一个凭据多机可用；学术对比研究结论是「提升可恢复性、削弱设备绑定保证」。
  3. 强证明与体验直接对冲：厂商文档自证——启用 attestation 就无法做跨设备注册/认证（Android 硬件 attestation 同理会退出同步体系）。C 端无登录前置的活动只能选弱的一侧。
  4. 可利用的信号：authenticatorAttachment = cross-platform 表示凭据来自另一台设备（扫码/蓝牙 CDA）→ 可当负向信号；AAGUID 只标认证器型号，signature counter 在 sync 场景下语义退化。
  5. 可用性硬伤：要 RP ID 域名一致、要求用户已有平台认证器——不适合陌生人流量的活动进门关。

正确用法：在登录/领奖等已有身份的动作做二次强因子，并沉淀「凭据 ID ↔ 账号 ↔ 首次设备指纹」的绑定记录，作为图谱的一条边（M7）。

7.2 三个方案（带推荐）

方案 A · 轻量三件套（1–2 周，纯自研）

  • HMAC 签名 + 60s 窗口 + Redis nonce 一次性（防篡改、防重放）
  • 一次性会话链：进页下发 sessionId，接口缺前序即拒（打掉纯脚本直调）
  • 分维度频控（设备/账号/IP·ASN 阈值 + 分级处置）
  • 效果预期：挡住约 80% 的「抓包直调 + 重放」脚本；挡不住群控与高仿真人。

方案 B · A + VM 保护 + 令牌绑定 + 指纹（1–2 月，推荐）

  • 阶段 1 先完整落地 A（见上）
  • 关键三函数做字节码 VM 虚拟化（签名计算 / 指纹采集 / 挑战回算），每版本轮换 opcode，密钥运行时下发
  • 服务端下发挑战 → 端上算 → 产出与本次指纹/完整性信号密码学绑定的 token → 服务端只验 token
  • 自研或商用 deviceToken 二重校验（含碰撞率/聚集性统计）
  • 边缘加 IP/ASN 信誉与限流
  • 效果预期：把「逆一次用半年」变成「每次轮换重新计价」，覆盖到群控与多开；挡不住愿意改浏览器引擎的定向攻击（但那成本已高于活动奖金），也挡不住真人羊毛党 → 交给 C 的图谱。

方案 C · 商业全家桶（快、贵）

  • A 的骨架 + 厂商 SDK（顶象/数美/易盾/腾讯 TDS/阿里云任一）+ 决策引擎 + 无感验证；有预算时补图谱与情报。
  • 何时选：活动量级大、需要现成团伙情报与对抗运营、内部没有前端加固人力。

推荐：按 B 分两阶段推进，A 先当骨架；预算充足或活动量级大时，把 C 的 SDK 作为 M1 的捷径买进来（VM 与会话链仍自研——买不来你业务的语义）。 不推荐：把 VM 当保密手段；把单个指纹当硬证明；把 WebAuthn 当进门关；只做前端签名不做服务端交叉。

7.3 分阶段路线图与验收指标

  • 阶段 0（1 周）· 摸底：把现有活动接口清单列全，逐个标注「是否需要登录、是否有前序、是否裸奔」→ 产出接口暴露面清单。
  • 阶段 1（1–2 周）· 补地基：签名 + 防重放 + 会话链 + 频控。
    • 验收：脚本直调的无前序请求 100% 被拒；重放同一请求第二次必失败；正常用户无感（零误伤投诉）。
  • 阶段 2（2–4 周）· 端上证据：设备指纹 deviceToken + 无感行为评分 + 分级处置（放行/降速/挑战/拦截）。
    • 验收：同设备关联账号数、同 ASN 聚集度可查询；风险分分级可解释；误报率 < 设定阈值（建议先 0.5% 观察）。
  • 阶段 3（1 月）· 抬高逆向成本：三函数 VM 化 + 挑战 token 密钥学绑定 + 每版本轮换机制。
    • 验收：每个发布版本 VM 结构变化可验证；密钥不在产物中出现（静态扫描通过）；绕过需要重新逆向。
  • 阶段 4（持续）· 团伙与情报：图谱聚类（时间戳聚集、IP C 段、轨迹同质）+ 黑名单沉淀 + 商用情报补充。
    • 验收：能给出「疑似团伙」清单及依据边（设备—账号—IP）。

7.4 与 ZCode 五层模型的对应（你熟悉的参照系）

  • L0 端点/挑战动态下发 ↔ 服务端下发挑战与一次性会话（M3）
  • L1 边缘连接指纹 ↔ WAF + IP/ASN + JA3/JA4（M6）
  • L2 调用链归因 ↔ 页面会话 → 接口前序链（M3，H5 最短板）
  • L3 设备锚点 ↔ 设备指纹弱绑定 + 统计信号（M1，Web 无硬件锚点）
  • L4 凭据不落产物 ↔ 密钥运行时下发 + VM 保护（M5）
  • L5 会话连续性/行为时序 ↔ 行为评分与聚合特征（M4/M7）
  • ZCode 有而 H5 要补的：把「校验逻辑本身」藏进 VM，防止黑产读出「查了什么」再精准伪造（M5/M8）。

八、名词速查表

  • 接口（API）：前端向后端要数据/做操作的 URL 调用，参数都在请求里明文可见（HTTPS 加密的是链路）。
  • 抓包：截取并查看网络请求内容；DevTools 的 Network 面板就是图形化抓包。
  • DevTools：浏览器自带开发者工具，可看源码、断点、改代码、重发请求。
  • 前端/后端：前端=跑在用户浏览器里的代码（不可信）；后端=你的服务器（唯一可信判决处）。
  • 哈希（MD5/SHA-256）：数据 → 固定摘要，不可逆，用于完整性校验与指纹生成。
  • HMAC：带密钥的哈希，只有持密钥者能算对，用于签名验真。
  • 签名（sign）：把参数+时间戳+随机数+密钥算出的校验值，服务端重算比对，防篡改。
  • nonce：一次性随机串，服务端记录并在窗口内拒绝重复 → 防原样重放。
  • 时间戳窗口：请求时间与服务端时间差超过阈值即拒 → 限制重放寿命。
  • 重放攻击：把截获的合法请求原样再发一次。
  • 对称/非对称加密：AES 类（一把钥匙，快，加密内容）/ RSA、ECDSA 类（公私钥，签名与密钥交换）。
  • JWT：自包含的令牌，签名只保证 token 内容没改，不保证 HTTP 请求体没改。
  • Cookie/Session/Token：浏览器自动凭证 / 服务端会话 / 自包含凭证。
  • 设备指纹：采集上百个环境特征算出的相对稳定的设备标识。
  • Canvas/WebGL 指纹：让浏览器画同一张图、读回像素比对，因 OS/显卡/字体渲染差异产生差异。
  • 指纹熵：指纹能区分多少设备的「信息量」；熵不足会大量碰撞。
  • 碰撞：不同设备算出同一个指纹 → 需按机型分桶统计重复率/空值率做治理。
  • 相似度匹配：指纹不是严格相等比较，而是汉明距离/加权相似度超阈值判同一设备。
  • deviceToken：SDK 采集后产出的设备凭证，业务服务端拿它调风险识别 API。
  • 二重校验：端上采集出证据 + 服务端核算出判决。
  • risk score / 风险分：多信号加权得到 0–100 分，按分档分级处置。
  • 规则引擎：阈值与名单的可解释判定（频次、黑名单、聚集）。
  • 无感验证：不打断用户的隐式人机验证（行为与环境评分）。
  • CAPTCHA / 验证码：显式人机挑战（文字、点选、滑块）；只是处置动作之一。
  • 行为轨迹：点击/滑动的时序、速度、加速度、抖动、力度——真人有生理噪声，脚本往往过于规整。
  • 生物行为特征：轨迹中的生理一致性特征，用于区分真人与脚本。
  • 打码平台：人工或模型替黑产过验证码的产业环节。
  • 群控：一台电脑控制上百台手机批量操作。
  • 云手机/多开/改机：伪造设备环境的工具，用来批量造号。
  • 协议党：逆向前端签名逻辑、用脚本直接调接口的黑产技术工种。
  • 混淆（obfuscation）：把代码变得难读（字符串加密、控制流平坦化等），只提高成本。
  • 字节码虚拟化（VM 保护）：把函数编译成自定义指令集 + 解释器执行，产物里没有原始函数体。
  • devirtualization：把字节码 VM 还原回可读逻辑的逆向技术，已有商业化服务在做。
  • WASM：浏览器里的二进制模块，核心逻辑用 C 编译后防护级别更高。
  • 反调试/完整性校验：检测 DevTools、检测代码被改，一改就失效或改变行为。
  • JA3/JA4：TLS 握手特征指纹，区分「真实浏览器」与「脚本 HTTP 客户端」，与 JS 无关。
  • IP/ASN 信誉：IP 段的机房/代理/秒拨风险标签。
  • WAF：网络应用防火墙，在入口做过滤、限流与拦截。
  • Bot Management：面向机器流量的管理体系（信号 → 聚合 → 评分 → 分级处置）。
  • 关联图谱：把设备、账号、IP、地址、行为连成图做聚类，用来挖团伙。
  • WebAuthn/Passkey：浏览器标准的公钥认证；passkey 可云同步，故绑账号不绑设备。
  • attestation：认证器出具的「这台设备」的证明；实际默认被削弱成 none。
  • token 密码学绑定：token 与同次执行的指纹/完整性信号哈希绑定，服务端只验 token。
