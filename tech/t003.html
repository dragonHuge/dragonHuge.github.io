LLM Agent 工程原理 — 学习笔记

📅 2026-05-20 · 📄 AI底层原理/LLM-Agent工程原理.md

LLM Agent 工程原理 — 学习笔记

学习来源：Claude Code 源码深度解析（飞书文档）+ 问答 开始日期：2026-04-21 目标：搞懂将 LLM 变成 Agent 的工程原理，能自己设计 Agent 架构

一、提示词工程

1.1 提示词的分类体系

按角色/位置分（API 层面）：

类型位置谁写的特点
System Promptsystem 字段开发者设定身份、规则、能力边界。用户看不到
User Messagemessages[].role=user终端用户用户的具体问题或指令
Assistant Messagemessages[].role=assistant模型生成/开发者预填模型的回复，或开发者预设的回答开头
Tool Resultmessages[].role=tool工具返回工具执行结果，注入回对话供模型参考

按功能/目的分（Prompt Engineering 层面）：

类型做什么举例
身份设定 (Persona)告诉模型"你是谁""你是一个资深 Python 工程师"
行为规则 (Rules)"什么能做什么不能做""不要编造不存在的 API"
任务指令 (Task Instruction)"现在要做什么""分析这段代码的性能瓶颈"
上下文信息 (Context)给模型"背景资料"代码文件内容、环境信息
输出格式 (Output Format)"怎么回答""用 JSON 格式返回"
示例 (Few-shot Examples)"参考答案"输入→输出的范例对

按技巧分（招式层面）：

  • Zero-shot：不给示例直接问
  • Few-shot：给几个示例再问
  • Chain-of-Thought (CoT)：让模型一步步推理
  • ReAct：推理+行动交替（Agent Loop 的核心模式）
  • Self-Consistency：多次生成取共识
  • Tree-of-Thought：分支探索多条推理路径

Claude Code 的映射关系：

  • 12 层 System Prompt = Persona + Rules + Task Instruction + Output Format + Context 的组合
  • Agent Loop = ReAct 模式实现

1.2 Prompt Caching（提示词缓存）原理

为什么缓存能省钱：

调 API 付的钱不只是"模型思考"的钱，还包括"模型读题"的钱。模型处理一次请求分两步：

  1. Prefill（预填充/读题）：把所有输入 token 逐个过 Transformer 全部层，计算每个 token 的 KV Cache（键值缓存）。计算量和输入 token 数成正比
  2. Decode（生成/答题）：基于 KV Cache 逐个生成输出 token

缓存命中 = 跳过 Prefill = GPU 没干活 = 只收存储读取的搬运费（便宜 90%）

技术实现三个关键点：

  1. 前缀匹配是逐 token 精确匹配——多一个空格就失效。所以 Claude Code 把静态内容放前面、动态内容放后面，用分界线隔开保证前缀稳定
  2. 缓存存在服务端，有 TTL——5 分钟不活动过期，频繁请求自动续期。Claude Code 支持 cache_control: { type: 'ephemeral', scope: 'global', ttl: '1h' } 手动控制
  3. KV Cache 是什么——Transformer 每层为每个 token 计算的 Key+Value 向量对。10 万 token 输入的 KV Cache 可达几十 GB

Claude Code 的三个缓存断点位置：

  1. 系统提示词静态部分末尾
  2. 工具描述列表末尾
  3. 对话历史中较早的消息

成本对比：

操作消耗成本
Prefill 计算GPU 算力$3 / 百万 token
缓存读取内存/磁盘 IO$0.3 / 百万 token
首次写入缓存GPU + 存储$3.75 / 百万 token

1.3 提示词优先级系统

核心理解：P0-P4 是互斥选择（选一个当主体），append 是无条件拼接。

最终 System Prompt = 主体提示词（P0-P4 选一个）+ appendSystemPrompt（始终追加）

优先级表：

优先级来源触发场景实际效果
P0（最高）overrideSystemPrompt极少触发，特殊循环模式完全替代默认提示词
P1Coordinator 提示词Agent Teams 协调模式主 Agent 变调度员
P2Agent 提示词Subagent 被创建时基础提示词精简版 + 角色专属指令
P3--system-prompt用户命令行手动传参开发者自定义系统行为
P4默认提示词99% 的情况12 层动态组装的 getSystemPrompt()
始终追加appendSystemPrompt无条件CLAUDE.md、MCP 指令等永远拼在末尾

关键细节：

  • P2 子 Agent 提示词 ≠ 凭空造的全新提示词，而是"基础系统提示词精简版 + 角色专属指令"（比如 Explore Agent 砍掉写入工具指南，追加"只负责收集信息"）
  • appendSystemPrompt 保证 CLAUDE.md 的规则在任何模式下都生效——主 Agent、子 Agent、Coordinator 都受约束
  • 正常使用时几乎永远是 P4 + append

二、Agent Loop（智能体循环）

2.1 核心机制：while(true) 的"思考→行动→观察"

Agent Loop 是 Agent 和 Chatbot 的本质区别。Chatbot 每轮等用户说话；Agent 自己干到完为止。

极简代码模型（src/query.ts → queryLoop()）：

while (true) {
  response = await callClaudeAPI(messages)           // 思考
  toolUses = response.content.filter(t => t.type === 'tool_use')
  if (toolUses.length === 0) break                   // 没有工具调用 → 完成
  toolResults = await executeTools(toolUses)          // 行动
  messages.push(response, toolResults)                // 观察结果追加到历史
}

2.2 关键认知：每一轮都是一次完整的 API 调用

Agent Loop 每轮都把全部历史消息重新发给 API：

第1轮请求：[系统提示词] + [用户问题]
第2轮请求：[系统提示词] + [用户问题] + [AI说要读文件] + [文件内容]
第3轮请求：[系统提示词] + [用户问题] + [AI说要读] + [结果] + [AI说要改] + [结果]
...

直接后果：

  • 消息越来越长，token 消耗越来越大 → 需要五层上下文压缩
  • 系统提示词每轮重复发送 → Prompt Caching 省钱的原因
  • 用户说一句话，Agent 可能自己跑 20 次 API 调用

2.3 两层循环结构

外层循环（conversationLoop）—— 等用户输入
  ↓ 用户说了一句话
  内层循环（queryLoop）—— Agent 自主执行 N 轮
    → API → 工具 → API → 工具 → ... → AI 说完了
  ↓
  回到外层，等用户下一句话

2.4 退出条件

条件API 响应处理
end_turnstop_reason: 'end_turn'，无 tool_use 块正常退出，展示回复
max_tokensstop_reason: 'max_tokens'，输出被截断自动续一轮让 AI 继续
用户中断Ctrl+C强制退出

2.5 工具并发编排（单轮内部）

一次 API 响应可请求多个工具，执行引擎按规则判断：

  • 多个 Read/Grep → 并发执行（Promise.allSettled）
  • Read + Edit → 串行（先读完再改）
  • Edit + Edit → 串行（防冲突）

2.6 完整数据流

用户输入
  → 组装消息（getSystemPrompt 12层 + 历史 + 用户消息）
  → 发送 API（带 Prompt Cache 标记）
  → 收到响应
    ├── 有 tool_use → 权限检查 → 执行工具（可能并发）→ 结果追加 → 回到"发送 API"
    └── 无 tool_use → 展示回复 → 回到外层等用户

每轮附加检查：token 用量（触发压缩？）、stop_reason（max_tokens 则自动续轮）

2.7 工具调用结果如何注入回提示词

核心机制：工具结果通过 tool_result 块伪装成 user 消息注入回对话历史，下一轮 API 请求随全部历史一起发给模型。

消息结构——严格的 user/assistant 交替：

{ role: "assistant", content: [
  { type: "text", text: "让我看看文件" },
  { type: "tool_use", id: "call_001", name: "Read", input: { path: "main.py" } }
]},
{ role: "user", content: [
  { type: "tool_result", tool_use_id: "call_001", content: "def main():\n    x = 1/0" }
]}

三个关键点：

  1. tool_result 伪装成 user 消息——Claude API 要求 user/assistant 严格交替，工具结果塞在 role: "user" 里通过 type: "tool_result" 区分
  2. tool_use_id 配对——AI 请求时生成 id，结果返回时带 tool_use_id，一一对应不搞混
  3. 多个工具结果打包在同一条 user 消息——保持交替不被打破

注入前的处理（不是原样塞进去）：

  • 大小控制：超预算的结果截断（保留头尾 + "...省略..."），完整内容存磁盘
  • 错误处理：执行失败时注入 is_error: true + 错误信息，AI 看到后调整策略
  • 特殊类型：图片返回 base64 图片块，Bash 返回分 stdout/stderr

Connector Text（连接文本）：Anthropic 独有机制，在工具调用之间插入带密码学签名的文本。作用：防蒸馏、防篡改。Claude 模型会验证签名，发现被改就拒绝继续。

三、多 Agent 协作

3.1 为什么需要多 Agent

单 Agent 三个硬伤：上下文窗口共享易撑满、串行执行慢、角色冲突（探索者 vs 执行者提示词打架）。

3.2 模式一：Subagent（子智能体）—— 临时工

  • 主 Agent fork 出子 Agent → 子 Agent 独立跑 Agent Loop → 返回结果 → 销毁
  • 上下文完全独立，不占主 Agent 空间
  • 单向通信：主 Agent 下达任务 → 子 Agent 返回结果
  • 不能嵌套：子 Agent 不能再创建子 Agent（防递归爆炸）

6 种内置类型：

类型角色权限用途
Explore侦察兵只读调查代码结构、搜索信息
General全能工几乎全部通用子任务
Code Review审核员只读+Diff审查代码变更
Pre-commit门卫只读+Bash(受限)提交前检查
Verification质检员只读+Bash验证修改是否生效
Orchestrator调度员可创建子Agent复杂任务中间层编排

3.3 模式二：Agent Teams（智能体团队）—— 正式团队

  • 创建持久化团队，多个 Agent 各自独立 Agent Loop 真正并行执行
  • 双向通信：成员间通过 message 工具互发消息（A→B："接口格式改了" B→A："新格式？"）
  • 状态持久化到磁盘（JSON），意外中断可恢复

3.4 Coordinator 模式—— Agent Teams 的高级形态

  • Coordinator（总指挥）：完整权限，负责拆分任务、分配、汇总、解决冲突
  • Worker（工人）：受限权限，执行具体任务
  • Coordinator 的提示词："你是总指挥，不要自己干活，分配给团队成员"

3.5 Subagent vs Agent Teams 对比

维度SubagentAgent Teams
通信单向（下达→返回）双向（互发消息）
并行主等子完成真正并行
持久性完成即销毁持续存在
适用临时一次性子任务大型复杂项目长期协作

3.6 业内多 Agent 协作模式全景

模式代表核心思路
主从调度Claude Code Coordinator、AutoGen中心调度分配给 Worker
子AgentClaude Code Subagent、OpenCode call_omo_agent临时 fork 子任务
流水线LangChain SequentialChainA→B→C 线性传递
去中心化OpenAI Swarm无中心，发布-认领
辩论/对抗ChatDev、MetaGPT多角色讨论收敛最优方案
层级嵌套CrewAI树状 Agent 结构

Claude Code 选主从+子Agent，因为编程场景需要确定性和可控性。

四、记忆与知识系统

LLM 本身无状态，上下文窗口只解决单次会话内的记忆。记忆系统让 Agent 拥有跨会话、跨项目、跨团队的持久化记忆。

4.1 CLAUDE.md 加载器 —— 人写的静态知识

  • 四级层次：全局（~/.claude/）→ 用户 → 项目（项目根/CLAUDE.md）→ 私有（项目根/.claude/CLAUDE.md，不提交 Git）
  • 每次 API 请求前作为 appendSystemPrompt 注入
  • 支持 @include 引用其他文件，加载器自动展开
  • 对应 OpenCode：AGENTS.md 是等价物，多级层次 = 根目录 → 04-项目/ → 番茄小说连载/

4.2 自动记忆提取 —— AI 自己记笔记（跨会话持久化）

  • 每轮对话结束后，后台 fork 只读 agent 分析对话，提取值得长期记住的信息
  • 写入 ~/.claude/memory/ 目录（Markdown 文件，人类可读可编辑）
  • 内容类型：用户偏好、项目发现、错误经验
  • 增量追加，不覆盖旧记忆
  • 下次对话时加载进系统提示词

4.3 AutoDream（记忆整理）—— AI 给自己"做梦"

  • 后台周期性（或手动 /dream）整理记忆文件
  • 合并重复、解决冲突（保留最新）、删除过时、提升高频
  • 类比人类睡眠时整理记忆：巩固重要的，丢弃无用的

4.4 会话记忆（Session Memory）—— 单次会话便签

  • 当前会话中自动维护 Markdown 便签，记录任务进度和关键信息
  • 和上下文压缩第3层联动：压缩时用便签作为"会议纪要"替代完整对话历史
  • 关掉会话就没了（区别于自动记忆提取的跨会话持久化）

4.5 团队记忆同步 —— 团队共享大脑

  • 本地记忆同步到 Anthropic 服务端，团队共享
  • 上传前自动扫描敏感信息（API key、密码）并脱敏
  • 一人发现的项目知识，所有人都能用

4.6 五层总览

持久程度 ↑
  │  团队记忆同步 ── 跨人、跨设备、服务端存储
  │  AutoDream ── 跨会话、定期整理清理
  │  自动记忆提取 ── 跨会话、增量写入
  │  CLAUDE.md ── 跨会话、人工维护、长期稳定
  │  会话记忆 ── 仅当前会话、自动、会话结束丢弃
  └──────────────────────────→ 自动化程度 ↑
维度Session Memory自动记忆提取AutoDreamCLAUDE.md

五、自定义 Agent

5.1 定义方式

在 .claude/agents/ 下放 .md 文件，支持 YAML frontmatter 配置：

---
name: my-reviewer
tools: [Read, Grep, Glob]    # 工具白名单（代码级硬约束）
model: sonnet                 # 独立指定模型
maxTurns: 10                  # 最大循环次数
background: true              # 后台运行
isolation: worktree           # git worktree 隔离
skills: [review-standards]    # 预加载技能
hooks: ...                    # Agent 特定钩子
permissionMode: ...           # 权限模式
---
你是一个代码审查专家...（提示词正文）

5.2 调用方式

对话中 @agent-name 调用 → fork 出 Subagent → 按 frontmatter 配置限制工具和行为 → 返回结果。

5.3 和内置 Subagent 的对比

维度内置 Subagent自定义 Agent
提示词代码硬编码用户写的 .md 文件
工具权限按类型预设frontmatter tools 白名单（硬约束）
模型跟主 Agent 一致可独立指定
Skill 预加载不支持支持 skills 字段

5.4 OpenCode 对应

  • .claude/agents/reviewer.md ↔ .opencode/agents/novel-reviewer.md
  • @reviewer 调用 ↔ @novel-reviewer 调用
  • 两边能力已非常接近（工具限制、模型指定、Skill 加载都支持）

六、Subagent vs Agent Teams 的 Agent 定义方式对比

6.1 Subagent —— 运行时临时创建

不需要提前定义。AI 在运行中决定"我需要帮手"时直接创建：

  • 内置类型：选 type: "explore" 等，权限和提示词代码预设
  • 自定义 Agent：引用 .claude/agents/xxx.md 文件名

6.2 Agent Teams —— 事先规划，分步构建

显式三步走：

  1. AgentTeamCreate 创建团队
  2. AgentTeamAddMember 逐个添加成员（name + role + instructions + tools 白名单）
  3. AgentTeamExecute 启动执行

6.3 核心对比

维度SubagentAgent Teams 成员
定义时机运行时临时事先规划分步构建
提示词来源内置预设 / .md 文件AddMember 的 instructions 参数
工具权限内置硬编码 / 自定义默认全部显式白名单（代码级硬约束）
身份定义只有类型name + role + instructions 完整身份
持久化不持久，完成即销毁团队结构存磁盘，可恢复

最关键的区别是工具权限：Subagent 自定义 Agent 只能靠提示词软约束（"你不能写"），Agent Teams 成员是显式白名单硬约束（没给 Edit 就真的调不了）。

类比：Subagent = 叫外卖骑手（来了就干，干完就走）；Agent Teams = 组建项目组（定组织架构、分工、权限，长期协作）。

七、Claude Code vs OpenCode 自定义 Agent 差异

7.1 Claude Code 自定义 Agent = 只是自定义提示词

.claude/agents/xxx.md 只能定义提示词。工具权限无法限制（默认全部），模型不能独立指定。

7.2 OpenCode 自定义 Agent = 完整角色配置

通过 opencode.json 注册 + .opencode/agents/xxx.md 定义：

  • ✅ 提示词（.md 内容）
  • ✅ 可指定不同模型
  • ✅ 可设为 default agent（进入目录自动激活）
  • ✅ 提示词中声明调用哪些 Skill
  • ✅ @agent-name 互相调用

7.3 最大差异：Agent + Skill 分离

Claude CodeOpenCode
知识组织所有知识揉进提示词Agent 定义"谁来做"，Skill 定义"怎么做"
切换能力需要写多个 Agent 文件同一 Agent 按需加载不同 Skill
示例xiuxian-writer.md + dushi-writer.mdnovel-writer + skill("xiuxian-writing") / skill("dushi-writing")

Skill 是独立的可复用知识包，Agent 按需加载，避免提示词爆炸。

7.4 内置泛用型子 Agent 对比

OpenCodeClaude Code 对应独有？
explore≈ Explore Subagent
oracle≈ General Subagent
hephaestus≈ General Subagent
momus≈ Code Review
librarian无✅ 外部文档检索
metis无✅ 策略规划

八、Skill 机制：渐进式加载（Anthropic 原生概念）

8.1 Skill 是 Anthropic 提出的原生概念

Skill 不是社区补丁，也不是 OpenCode 发明。Anthropic 官方推荐的模式：

  • 在 .claude/ 下组织可复用指令集
  • CLAUDE.md 声明"什么场景加载什么 Skill"
  • AI 根据任务上下文自主决定 Read 哪些 Skill 文件

核心理念：渐进式加载——用到才读，读了就够。

8.2 Claude Code 中的三个相关概念

概念本质触发方式
Custom Slash Commands用户快捷指令用户手动 /命令
Skill（渐进式加载）可复用知识包AI 自主判断 + Read 加载
CLAUDE.md 路由Skill 的发现机制AI 读 CLAUDE.md → 知道有哪些 Skill → 需要时 Read

Slash Commands 只是 Skill 的一种（最弱的）触发方式。真正的 Skill 是 CLAUDE.md 声明 + AI 自主 Read。

8.3 Anthropic 原生 Skill 加载链路

CLAUDE.md 声明："代码审查参考 .claude/skills/review.md"
  → AI 收到审查任务
  → 看 CLAUDE.md 发现有 review.md
  → Read 工具读取 → 按方法论执行

8.4 差异在"工程化程度"，不在"有没有"

维度Claude Code（原生 Skill）OpenCode Skill
加载机制AI 用 Read 读文件（消耗一轮工具调用）skill() 内置函数注入（零成本）
发现机制CLAUDE.md 文字描述，AI 自己判断框架注册，自动匹配触发条件
嵌套AI 读完再自己 Read 下一个（串行慢）框架处理嵌套引用
标准化无固定格式SKILL.md 规范（触发条件/流程/反馈日志）
附带资源.md 里写路径让 AI 自己读Skill 目录打包模板、示例，框架关联

一句话：概念是 Anthropic 提出的，OpenCode（通过 Superpowers 标准化）把它工程化了——从"AI 自己 Read 文件"升级为"框架原生 skill() 调用"。

8.5 演进链条

Anthropic 提出渐进式加载理念
  → Superpowers 社区框架标准化（统一注册/触发/加载格式）
  → OpenCode 集成 Superpowers → 我们现在用的 skill() 系统

九、上下文压缩五层具体实现

9.1 第1层：工具结果预算控制（实时·零成本）

每次工具返回结果时实时检查，三道防线：

  • 单个结果 > 50,000 字符 → 存磁盘，上下文只留预览 &lt;persisted-output&gt;
  • 单个结果 > 100,000 tokens → 硬截断
  • 单消息所有结果合计 > 200,000 字符 → 超出存磁盘

AI 需要详情时用 Read 读磁盘。纯本地操作，零 API 成本。

9.2 第2层：微压缩（延迟·低成本）

两种触发：

  • 时间触发：对话间隔 > 60 分钟 → 裁剪旧工具结果只留摘要。故意等缓存过期（TTL 5分钟），清理免费
  • cache_edits：利用 API 服务端缓存编辑能力，完全不影响缓存

和第1层区别：第1层是"结果太大就存磁盘"（实时），第2层是"旧结果不再需要就缩短"（延迟）。

9.3 第3层：会话记忆压缩（中成本·用摘要替代历史）

后台预取对话滚动摘要 → 压缩时用摘要替代完整历史 → 最近 2-3 轮保持完整不压。AI 仍知道之前做了什么，但丢失细节。

9.4 第4层：完整压缩（高成本·额外 API 调用）

Token 用量超 ~80% 上下文窗口时触发：

  1. fork 压缩子 Agent（共享主对话缓存前缀省钱）
  2. 子 Agent 生成结构化摘要（对话概要、已完成工作时间线、待完成、关键发现、用户偏好）
  3. 摘要替代整段对话历史，保留最近 1-2 轮

9.5 第5层：响应式压缩（应急·硬砍 50%）

API 返回 prompt-too-long 错误时兜底。直接删除中间 50% 消息，保留开头（系统提示词）和结尾（最近几轮）。粗暴但保命。

9.6 五层联动

成本↓  侵入性↓
第1层 实时预算    零成本 · 信息不丢
第2层 微压缩      低成本 · 裁旧结果
第3层 会话记忆    中成本 · 摘要替代
第4层 完整压缩    高成本 · AI总结
第5层 响应式      最高 · 硬砍保命

十、权限与安全系统

10.1 三级权限判定

级别含义典型工具
Allow直接执行Read/Grep/Glob（只读）
Ask弹窗询问用户Write/Edit/Bash（写/执行）
Deny完全禁止rm -rf /、访问 ~/.ssh/

判定流程：规则匹配（settings.json）→ LLM 分类器快速判断风险 → 用户确认（Ask 级别）。

10.2 沙盒隔离

平台技术限制
macOSSeatbelt（sandbox-exec）只能访问项目目录+临时目录，不能写系统目录/访问 ~/.ssh/
LinuxLandlock限制文件系统+网络

10.3 Bash 命令静态分析

用 tree-sitter 解析 Shell 命令 AST，检测危险模式：

  • curl | bash（下载并执行）→ Deny
  • rm -rf 带危险路径 → Deny
  • 重定向到系统文件 → Deny
  • 环境变量注入 → Deny

十一、Token 计量与成本控制

11.1 Token 估算：charCount / 3.25 × 1.1

不调 tokenizer（太慢），用字符数估算 + 10% 安全余量。判断"要不要压缩"够用，精确计数由 API 服务端做。

11.2 六维度定价模型

维度含义Sonnet 价格
输入 Token常规输入$3/百万
输出 Token模型生成$15/百万
缓存写入首次建缓存$3.75/百万
缓存读取命中缓存$0.3/百万
Web 搜索服务端搜索按次
Fast 模式快速推理不同价格

11.3 架构层面省钱策略

  • Prompt Cache 静态/动态分层 → 输入成本 -90%
  • 工具结果预算 → 避免无谓输入消耗
  • 微压缩等缓存过期后执行 → 避免缓存失效+重建双重开销
  • 完整压缩子 Agent 共享缓存前缀 → 压缩本身也省钱
  • Explore Agent 不加载 CLAUDE.md → 省 5-15K token/轮

十二、上下文压缩与缓存的协同设计

12.1 核心矛盾

压缩想砍消息（减 token） vs 缓存想保持前缀不变（保持命中）。粗暴砍消息会导致缓存全失效，下轮全价重算，砍了反而更贵。

12.2 每层如何处理矛盾

层级策略对缓存影响
第1层API 前本地操作无关
第2层（时间）等缓存过期后才动手零浪费
第2层（cache_edits）服务端直接编辑完全不影响
第3层替换历史消息重建缓存（值得，空间换来远超成本）
第4层子Agent共享主缓存前缀尽量复用
第5层硬砍全部失效（保命优先）

12.3 设计原则

能不破坏缓存就不破坏（1、2层）
  → 在缓存过期后再动手（2层时间触发）
    → 让压缩本身也享受缓存（4层）
      → 命快没了就放弃缓存（5层）

一句话：不是"满了就压缩"，是成本感知的五层防御。

十三、两种执行路径与流式输出

13.1 交互式 REPL vs Headless/SDK

路径入口场景
交互式 REPLREPL.tsx → handlePromptSubmit → query()终端对话，实时看打字效果
Headless/SDKQueryEngine.submitMessage() → query()claude -p "修bug" 一行命令跑完，适合 CI/CD/脚本

两条路径调同一个 query()（Agent Loop），区别只在入口和交互。Claude Code 内核是一个可编程的 Agent 引擎，可嵌入任何自动化流程。

13.2 流式输出

query() 是 async function*（异步生成器），API 响应一个 token 一个 token 流到终端。终端里"一个字一个字打出来"是真的在流式接收，不是假的打字机效果。

13.3 queryLoop 五种状态转换

转换原因含义
next_turn工具执行完，继续下一轮（最常见）
reactive_compact_retry对话太长，压缩后重试
max_output_tokens_escalate输出被截断，升级限制重试
max_output_tokens_recovery仍被截断，分多次续写
token_budget_continuation还有预算，继续

输出被截断时 Claude Code 自动升级限制或分多次续写，用户无感。

十五、MCP（模型上下文协议）

15.1 MCP 是什么

Model Context Protocol —— Anthropic 提出的开放标准，让 Agent 连接外部工具和数据源。类比：USB 接口，工具遵循 MCP 协议就能插到 Agent 上直接用。

15.2 Claude Code 中的双重角色

角色路径做什么
MCP 客户端src/services/mcp/（20+文件）连接外部 MCP 服务器，通过 stdio/SSE/HTTP 发现加载第三方工具
MCP 服务端src/entrypoints/mcp.ts把 Claude Code 自身暴露为 MCP 服务器
OAuth 认证src/services/mcp/auth.ts远程 MCP 服务器的 OAuth 2.0 认证

15.3 内置工具 vs MCP 工具

内置工具（42个）：Read/Write/Edit/Bash...  ← 编译时确定
MCP 工具（N个）：飞书/数据库/Slack...     ← 运行时动态发现

我们用的飞书 CLI 就是 MCP 场景——通过 MCP 协议连接飞书，获得文档读写能力。

15.4 MCP 的价值

  • 可扩展：Agent 能力不限于内置工具，任何人写 MCP 服务器就能提供新工具
  • 标准化：Claude Code / OpenCode / Cursor 等都支持，一次开发处处用
  • 安全隔离：MCP 工具有独立权限管理
