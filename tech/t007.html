Q1 · JWT 的全称和含义？它和我说的「参数签名 sign」是一回事吗？

提问（2026-10-28）：JWT 的全称是啥、什么含义？我的理解是不是——把业务参数按 key 拼成串，加时间戳、nonce、密钥算出 sign，最终产物就叫 JWT 签名？另外为什么说 JWT「管不住承载它的 HTTP 请求体有没有被改」？我理解的是：Web 端用参数实时生成 token、服务端按同样规则生成一对比，对不上就说明请求体参数被改了。验证≠加密这步我理解了：请求体参数我们没做加密、是裸的，所以不算加密。

答复：

  1. JWT = JSON Web Token（RFC 7519 标准）。三段 Base64URL 用点连接：header.payload.signature——头部（算法）、载荷（claims：用户 ID、过期时间、权限等）、签名。
  2. 你的理解对应的是另一个东西：接口参数签名（API sign）——参数排序拼串 + 时间戳 + nonce + 密钥 → HMAC → sign 字段。它确实能发现「请求体参数被改了」，这部分你的理解完全正确。
  3. 两者的差别不是算法，而是「签名覆盖了哪些字段」：
    • API sign：把整条请求的业务参数都算进去 → 改任何一个字段，重算就对不上。
    • JWT：只把 token 自己的三段内容算进去 → 改的是请求体里的业务参数，那些字段根本不在签名范围内，JWT 验签照样通过。
  4. 类比：JWT 像入场手环（只验手环真伪与有效期，不管你进去之后干了什么）；API sign 像对整张订单盖章（改一个字，章就不对）。
  5. 所以那句「管不住 HTTP 请求体」的准确含义：攻击者拿一个有效的 JWT + 被篡改的 body 发请求，服务端只验手环 → 通过，body 里的金额/数量照单全收。要防 body 被改，必须把 body 字段纳入签名范围——那就是 API sign 的职责，不是 JWT 的。
  6. 补充机理差异：API sign 是「服务端按同样规则重算一遍比对」；JWT 验签是「验这个签名对这三段内容是否有效」（对称密钥算 HMAC，或非对称用公钥验私钥签的名）——都不保密，只保证真实性与完整性，这就是「验证 ≠ 加密」：加密要的是对方读不懂（机密性），验证要的是对方改不了、且来源可确认。
  7. 实战建议：JWT 管「你是谁、有没有过期、有没有权限」；业务参数的完整性另用 API sign（含时间戳 + nonce）管；两者叠加，一个都不省。

Q2 · JWT 到底管什么？谁生成的？会不会被伪造？它算安全概念吗？

提问（2026-10-28）：JWT 只验手环真伪和有效期，那不是很容易被伪装？生成逻辑是服务端下发还是客户端生成？客户端生成不就随便伪造了？就算是服务端下发、由另一个接口下发，我每次先请求那个下发接口拿到 JWT 再去打业务接口，不也拿到了？所以 JWT 其实不是安全概念，而是权限管理/业务有效性的术语？要校验业务参数完整性，就得用带时间戳和防重放的 API sign——我这么理解对吗？

答复：

  1. 谁生成：永远是服务端（或授权服务器）签发，客户端只是携带。对称（HMAC）场景密钥只在服务端，非对称场景私钥只在服务端、公钥验签——客户端从头到尾没有签出合法签名的能力。
  2. 客户端能改的是内容，不是签名：JWT 的 payload 只是 Base64URL（不是加密，明文可读），黑产可以把它改成 uid=别人、exp=10 年后，但一改签名就对不上 → 服务端直接拒。所以「客户端生成就随便伪造」不成立，前提是密钥不泄露 + 验签严格。
  3. 「先调下发接口拿 JWT」是对的，那就是正常流程（登录/换取 token）。风险不在 JWT，而在换取接口本身有没有门槛：换取接口要求密码/登录态/refresh token/验证码/设备指纹。若下发接口裸奔 = 无门槛发手环，那是设计缺陷，不是 JWT 的锅。
  4. JWT 真正防不住的是「凭据被盗用」：用偷来的账号登录拿到合法 JWT、refresh token 泄露、钓鱼——手环是真的，只是戴错了人。这类要靠短时效 + 刷新、jti 黑名单可撤销、会话与设备绑定（把 deviceId 写进 claims 或服务端会话）、异地/异设备检测来补；再配合风控的指纹与行为评分。
  5. 对「JWT 不是安全概念」的修正：JWT 是令牌格式标准，属于认证与授权（Authentication / Authorization）范畴，是安全体系的一部分；但它的安全承诺只有两条——真实性（这手环是我签的）与完整性（这三段没被改）。它不提供机密性（payload 谁都能读，别放敏感数据），不提供业务参数完整性（body 不在签名范围）。
  6. 你的最终结论是对的：业务参数完整性 + 防篡改 + 防重放 = API sign（HMAC + 时间戳 + nonce）；JWT 负责「你是谁/过没过期/有没有权限」。实战里三层各管一段：JWT 认人 · API sign 认这条请求 · 风控信号认环境与行为，缺一层就留一个口子。
  7. 给安全同学的补充：JWT 的经典攻击是实现层而不是格式层——alg=none 跳验签、RS256→HS256 用公钥当 HMAC 密钥的算法混淆、弱 secret 爆破、kid 注入、只验签不校 exp/iss/aud。这些是落地时要逐条堵的。

Q3 · 行业内常见的 JWT 生成算法和参数？用哪几个字段、什么算法？

提问（2026-10-28）：先了解 JWT。它负责校验授权（这个 token 是不是当前账号下发的）、对应账号、过期时间、权限这类证明没被篡改，偏安全领域的认证与授权维度。那行业里常见的 JWT 生成算法和参数是什么？一般用哪几个字段、什么加密算法去生成这个 JWT token？

答复：

1. 结构与字段

三段：base64url(header) . base64url(payload) . base64url(signature)

header（头部）

  • alg：签名算法（必须服务端白名单校验，不能信任 header 自报）
  • typ：固定 "JWT"
  • kid（可选）：密钥 ID，用于密钥轮换时多把密钥共存

payload（载荷 = claims，声明）

  • 标准注册声明：sub（主体/用户标识）、iss（签发者）、aud（受众/接收方）、exp（过期时间戳）、iat（签发时间）、nbf（生效时间）、jti（唯一 ID，用于黑名单撤销与防重放）
  • 业务私有声明：user_id / uid、scope 或 role+permissions、tenant_id、device_id、login_type
  • 禁忌：payload 是 Base64URL 明文可读，不是加密——绝不放手机号/身份证/余额等敏感数据；要保密得用 JWE（整段加密）或只放 ID、详情查库

signature（签名）：对 header.payload 这个拼串计算，密钥/私钥只在服务端。

2. 常见算法（行业实际在用的就这几类）

  • 对称：HS256 / HS384 / HS512（HMAC-SHA 家族）——一把 secret，签与验同一把。适合单体或互信的服务间；secret 一泄露，谁都能签。
  • 非对称：RS256 / RS384 / RS512（RSA，密钥 ≥2048 位）——私钥签、公钥验。网关/微服务只持公钥即可验签，密钥不扩散，这是多服务与开放平台的主流。
  • 非对称：ES256 / ES384 / ES512（ECDSA 椭圆曲线，如 P-256）——签名更短、验签更快，移动端与高并发场景偏好。
  • PS256（RSA-PSS，更安全的填充方式，部分合规场景要求）；EdDSA/Ed25519 较新，按技术栈支持度选。
  • 绝对禁止：alg=none（跳过验签）；以及 RS256→HS256 算法混淆（攻击者拿你的 RSA 公钥当 HMAC 的 secret 自己签一个）——验签端必须用服务端配置的算法白名单，不信 header。

行业默认取舍：单体内网 → HS256；网关/多端/对外 → RS256 或 ES256。JWT 的 HS256 与我们的 API sign 本质是同一族 HMAC，差别只在「签名覆盖了哪些字段」（见 Q1）。

3. 生成与校验的标准流程

生成（服务端）：

  1. 组装 header、payload（JSON）→ 各自 Base64URL 编码 → 用 . 拼成 header.payload
  2. 对拼串签名：HS256 用 secret 做 HMAC-SHA256；RS256/ES256 用私钥做非对称签名
  3. 输出 xxx.yyy.zzz，下发方式：Authorization: Bearer &lt;token&gt; 或 HttpOnly Cookie

校验（服务端）：

  1. 按服务端配置的算法白名单选算法（不信 header.alg）→ 验签
  2. 再校验 exp / nbf / iss / aud（只验签不校时效 = 白验）
  3. 需要撤销时查 jti 黑名单或版本号；要绑设备再核对 device_id 与当前会话

4. 落地参数建议

  • exp 短：访问令牌 15 分钟 ~ 2 小时；配 refresh token（7~30 天，独立存储、可撤销）
  • RSA ≥2048 位 / 优先 ES256；密钥轮换用 kid 指向当前密钥，新旧并存过渡
  • 每次签发写 iat+jti；登出、改密、异地登录时把 jti 打进黑名单
  • payload 只放「够用的最小声明」，敏感信息查库取

Q4 · Base64URL / Header / Payload / Signature 到底是什么？给个 JWT 包装实例

提问（2026-10-28）：你说 JWT 主要装 uid、过期时间和权限，那为什么又有 Base64URL Header、Base64URL Payload、Signature 这些东西？这些分别是什么？举个场景例子，JWT 到底怎么「包装」出来？

答复：

1. 先分清「内容」和「包装」

  • 你要的 uid / 过期时间 / 权限，就是 payload 里那个 JSON 的字段——JWT 本质上是「一段 JSON + 一个防伪章」。
  • Base64URL 不是加密，是编码：把任意字节/JSON 变成只含 A-Z a-z 0-9 - _ 的单行字符串（去掉 = 填充），好处是能安全放进 URL、Header、Cookie 里不出现 + / = 这些麻烦字符。谁拿到都能原样解回来（实测：payload 编码后 decode 直接得到原 JSON）。
  • 所以三段是：说明书（header）+ 内容（payload）+ 印章（signature），用 . 连成一个字符串。

2. 三段各装什么

段内容（JSON）作用能否被客户端伪造
header{"alg":"HS256","typ":"JWT"}（可带 kid）告诉验签方「用什么算法验」能改，但改了印章就对不上；验签方必须用服务端白名单，不信它自报
payload{"sub":"10086","iss":"activity-h5","aud":"draw-api","iat":...,"exp":...,"scope":"activity:draw","jti":"..."}声明「谁、多久、什么权限、谁签的」能改（Base64 明文），但改了印章就对不上
signatureHMAC-SHA256(header.payload, 密钥) 的 Base64URL唯一防伪的部分不能——密钥/私钥只在服务端

3. 完整实例：H5 抽奖活动登录后发 token（HS256）

  • Step 1 写 header JSON：{"alg":"HS256","typ":"JWT"}
  • Step 2 编码：Base64URL → eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9（所有 JWT 开头都是 eyJ，因为那是 { 的 Base64 特征——以后看到 eyJ 就知道这是个 JWT）
  • Step 3 写 payload JSON（业务要的都在这）：

{"sub":"10086","iss":"activity-h5","aud":"draw-api","iat":1793205907,"exp":1793207707,"scope":"activity:draw","jti":"a1b2c3d4"} 编码后得到第二段（同样以 eyJ 开头，decode 就是上面这段 JSON，明文可读）

  • Step 4 拼串：第一段.第二段（注意：签名只对这两段算，第三段还没生成）
  • Step 5 签名：HMAC-SHA256("第一段.第二段", 服务端密钥) → 得到 32 字节 → Base64URL → 43 个字符的第三段（实测 43 位、无 =）
  • Step 6 产出：eyJhbGci...VCJ9.eyJzdWI...QifQ.9BvNMHuTfW46Ij9K1Ill-LowQxhi_21IpZitL7030FM ——这就是发给前端的 JWT
  • Step 7 客户端携带：`Authorization: *** 或 HttpOnly Cookie
  • Step 8 服务端校验：拆成三段 → 按白名单算法用密钥重算第三段并比对（先验印章）→ 再看 exp 是否过期、iss/aud 是否匹配 → 全过才认「uid=10086 的人，在 00:45:07–01:15:07 之间持有 activity:draw 权限」

篡改演示（实测）：把 payload 里的 sub 改成 99999，第三段原样不动 → 服务端按新串重算签名 ≠ 原签名 → 验签失败拒收。这就是「证明没被篡改」的全部机理——不是因为内容被藏起来了，而是改内容会让印章对不上。

验证方法（可自己动手）：随便找一个登录后的 JWT，把第二段贴进 base64url 解码工具，能直接读出所有 claims——这就是「JWT 不保密」的直观证明；所以敏感数据绝不进 payload。

Q5 · 防伪章是密钥吗？JWT 的 header/payload 是不是 HTTP header 和请求体？密钥与公私钥各在哪用？

提问（2026-10-28）：JWT 本质 = 一段 JSON + 一个防伪章，那防伪章就是 JWT 加密的密钥、也就是 Base64URL signature 对吧？JSON 就是 header 和 payload：header 是不是指 HTTP 请求的 header（一般不变）？payload 是不是指 HTTP 请求体里的参数？header 里拿什么参数、payload 里拿什么参数去生成 JWT，是由业务技术方案决定的对吧？生成流程是不是——向服务端请求下发，服务端拿到 header 和业务请求的 payload，分别 Base64 编码，再加密钥签名？密钥分对称/非对称两种都可以；非对称是不是下发（网关 GWP）时用公钥、验证时用公钥，私钥在下发时用？

答复：

1. 三个概念必须先拆开（你这里混了三组）

  • 防伪章 ≠ 密钥：signature 是用密钥算出来的结果（43 字符的那串），密钥是算章的工具，永远留在服务端、从不写进 token。类比：章是印出来的那个印子，密钥是刻章的那块石头。
  • JWT 的 header ≠ HTTP 请求的 header：JWT header 是 token 内部第一段 JSON（alg/typ/kid，告诉验签方怎么验）；HTTP header 是外层运输用的（`Authorization: ***）——一个在信封里，一个在信封上，两层东西。
  • JWT 的 payload ≠ HTTP 请求体参数：JWT payload 是令牌自己的声明（谁、多久、什么权限、谁签的）；HTTP body 里是这次业务操作的参数（itemId、数量、金额）。签名只覆盖 JWT 自己这两段，不覆盖业务 body——这就是 Q1 说的「管不住请求体」的根源。

2. header 和 payload 分别填什么

  • header：基本固定，不用自己设计。alg（算法）、typ（固定 JWT）、kid（可选，密钥轮换标识）——这是 JWT 标准（RFC 7519/7515）规定好的。
  • payload：标准声明 + 业务自定义声明。标准：sub/iss/aud/exp/iat/nbf/jti；业务：user_id、scope/role、tenant_id、device_id 等。
  • 「由业务技术方案决定」——这句对，但只对 payload 成立：你要不要放 device_id、scope 怎么分、exp 给多久，是你的方案定；header 按标准走即可。

3. 生成流程纠正（关键）

  • 不是「拿到业务请求的 payload 再编码」。正确顺序是：
    1. 用户先认证成功（登录/换取 token 接口）→
    2. 服务端自己组装 claims：从会话或库里取 user_id、权限，取当前时间算 iat，加 iat+有效期 算 exp，生成 jti →
    3. header+payload 各自 Base64URL → 拼串 → 用密钥签名 → 下发。
  • 也就是说：JWT 是认证成功后的产物，业务请求体是之后每次请求才带的东西，签发时根本用不到它。

4. 对称/非对称与公私钥的用法

  • 两种都行（HS256 / RS256、ES256）。
  • 非对称：签发用私钥，验签用公钥——你这句方向对，但下发那一步用的是私钥不是公钥（原话里「下发用公钥、验证用公钥」两句撞了）。网关/微服务只持公钥即可验签，密钥不扩散。
  • 对称（HS256）：签与验都是同一把 secret——所有验签方都得持有 secret，泄露即谁都能签，所以只适合互信的内网单体。
  • 「GWP」按网关 gateway 理解：网关是验签方（拿公钥），不是签发方（签发在认证服务，持私钥）。

Q6 · JWT 是什么「协议」？token 封装在请求哪里？给个最小项目全流程 + MiMo Desktop 是否真用了 JWT

提问（2026-10-28）：有点迷糊，举个例子：要拿 JWT 的话请求封装在哪里？需要固定的请求参数格式吗？JWT 具体是什么协议？就用一个业务活动用 JWT 做认证授权的最小化项目，讲清从拿到 token 开始、参与活动的整个流程和接口参数细节；另外看一下 MiMo Desktop 是不是用了这个能力。

答复：

1. JWT 不是「网络协议」，是令牌格式标准

  • JWT 属于 JOSE 家族（RFC 7515 JWS 签名 / 7516 JWE 加密 / 7517 JWK 密钥 / 7519 JWT）：它规定的是一个字符串长什么样、怎么签、怎么验，不规定走哪个端口、什么报文格式。
  • 它不占用任何「请求参数」：不需要在 body 里加 jwt=xxx 字段。标准承载方式是 HTTP 头：`Authorization: *** —— token 是「搭车」过去的。
  • 所以「固定的请求参数格式」问题的答案是：没有。只有两处是标准固定的——① token 内部 header 的 alg/typ；② 传输用的 `Authorization: *** 头。其余（payload 放哪些 claim、业务 body 长什么样）都是你的技术方案定。

2. 最小项目：H5 抽奖活动，用 JWT 做认证授权（4 个接口）

① 登录/换 token — POST /api/auth/login

响应 200: {"accessToken":"<JWT>","refreshToken":"<JWT或不透明串>","tokenType":"Bearer","expiresIn":1800}

服务端此时做的就是 Q4 的流程：验密码 → 组 claims（sub/iss/aud/iat/exp/scope/jti）→ 签名 → 下发。业务请求体在这一步还不存在。

② 参与活动 — POST /api/activity/draw（真正带 token 的请求）

请求头:  Content-Type: application/json
        Authorization: *** 每个业务请求都要带，这就是「封装在哪」的答案
        X-Request-Id: 8f3a...            ← 调用链追踪（可选）
请求体:  {"itemId":2026,"count":1}        ← 业务参数，不在 JWT 签名范围内

服务端四步：

  1. 取 Authorization 的 token → 拆三段（不是 3 段直接 401）
  2. 按服务端白名单算法验签（不信 header 自报 alg）
  3. 校 exp（过期 401）、iss/aud 匹配、必要时查 jti 黑名单（已登出/被撤销 401）

Q7 · JWT 是不是纯概念、生成与算法都由业务自己定、没有协议强制限制？

提问（2026-10-28）：那我理解了——JWT 只是令牌格式标准，规定认证授权的令牌应该长什么样；怎么生成、更偏向概念；有 JWT 就说明有这个授权机制，机制怎么用完全由业务端决定。包括 token 怎么生成、二次校验时用对称还是非对称，都是业务自己定的吧？甚至用什么参数生成 JWT 也是业务自己定，没有强制协议限制——可以这么理解吗？

答复：约九成对，但要分清「业务可定」与「标准已锁死」两张清单。

业务可定（你说对的部分）

  • 上层认证授权机制怎么设计：谁能拿 token（登录/换取条件）、有效期给多久、刷新与撤销策略、scope 怎么切、放在 Authorization 头还是 Cookie。
  • payload 放哪些 claim：标准声明可选用哪些、自定义放 user_id/device_id/tenant_id 还是不放，完全是你的技术方案。
  • 算法档位选对称还是非对称：单体内网 HS256、多服务/对外 RS256 或 ES256，这是架构决策。
  • JWT 只是载体：它本身不「等于」你有完整的授权机制——机制在业务层（校验 scope、权限、风控），JWT 只提供「这枚令牌是真的、没被改、还在有效期内」这三条事实。

标准锁死的部分（协议强制，不是业务自由）

  1. 结构：必须三段 header.payload.signature、用 . 分隔、每段 Base64URL（无 = 填充）；签名必须基于前两段拼串计算——自创结构就不是 JWT 了。
  2. 算法标识：alg 只能取 JOSE/IANA 注册的值（HS256、RS256、ES256、PS256、EdDSA…），不能自造一个 alg:"my-algo" 让别人去实现。
  3. 标准 claim 的语义：一旦你用了 exp/iat/nbf，就必须是 NumericDate（Unix 秒级时间戳）；iss/aud 的类型也有规定——否则任何标准库/网关解析都会错。
  4. 签名覆盖范围：JWS 的签名必须覆盖 header.payload 拼串，不允许「只签 payload 不签 header」这种私改（header 被改 alg 就出事）。
  5. 签名里不能包含密钥本身，且验证方必须按服务端配置的算法白名单选算法，不能信 header 自报的 alg——这不是协议条款，但属于不遵守就一定被打的安全硬约束（alg=none、RS256→HS256 混淆都是经典漏洞）。

一句话总结

协议管「形状与验法」（结构、alg 注册表、标准 claim 语义、签名覆盖），业务管「内容与策略」（放什么 claim、哪把钥匙、什么时候发、谁能用、怎么撤）。 你理解成「概念 + 业务自定」时，只要把上面 5 条锁死项记住就不偏了。

  • 所以「请求里的 header 和 payload」这个说法要改口：请求有 header 和 body；token 有 header 和 payload——两层各说各的，只是名字撞了（这正是 Q5 那个混淆点，再确认一次）。

Q9 · 我的复述对吗？（三段结构、第一段固定、必须有 exp、第三段是「加密」）

提问（2026-10-28）：JWT 整体是一个 Base64 字符串，分三段、点分隔。第一段是固定的，JSON 里放算法和 type；第二段必须有过期时间，另外业务可加参数；第三段是印章——把前两段加起来、用传入的算法做对称或非对称的加密，再整体 Base64 就生成 JWT 了。是这个逻辑吗？

答复：大方向对，四处要修正。

✅ 你说对的

  1. 整体是一个字符串，三段、点分隔、每段都是 Base64URL（不含 + / =）。
  2. 第一段确实是 JSON，装「用什么算法验（alg）+ 什么类型（typ）」。
  3. 第二段装业务参数（自定义 claim），第三段是由前两段算出来的印章，密钥不进去。

🔧 要修正的

  1. 第一段不是「固定值」，是「字段固定、值可变」：永远是 JSON、alg 必有（typ 常见但可省），但 alg 取决于你选的算法（HS256 / RS256 / ES256…），还会带 kid（密钥 ID）等。换算法第一段就变。
  2. 第二段没有「必须有 exp」这回事：exp 是可选的标准 claim（协议不强制）。但安全上必须给——无状态令牌没有 exp 就永不过期，只能靠黑名单兜底；所以实践里 exp 是必配项，这是工程要求不是协议要求。
  3. 第三段是「签名」不是「加密」：RS256/ES256/HS256 做的都是数字签名（对前两段拼串算出一个固定长度的章），不是把 payload 加密——payload 始终是 Base64 明文，谁都能读。签名只保证「改了就对不上」，不保证「看不见」。
  4. 不是「整体再 Base64 一次」：是签名得到的二进制结果自己做 Base64URL → 成为第三段。JWT = 三段各自编码后用 . 拼接；若把整串再编码一次，就没人认得了。

一句话修正版

JWT = 三段 Base64URL 用点拼的字符串：第一段（字段固定、alg 值随算法变）+ 第二段（业务 claims，exp 强烈建议但协议不强制）+ 第三段（前两段拼串经密钥算出的数字签名，只验不藏）。

Q10 · HS256 这些是什么？它们不是加密算法吗？给一个完整 JWT 看

提问（2026-10-28）：HS256 这些都是什么东西？它不是做加密的算法是吗？给我展示一个完整的 JWT token 我看一下。

答复：

1. HS256 / RS256 / ES256 是「算法标识符」（JOSE/IANA 注册的 alg 值），命名可拆解

  • HS256 = HMAC + SHA-256 → 对称的消息认证码（一把 secret，签与验同一把），输出固定 32 字节
  • HS384 / HS512 = HMAC + SHA-384 / SHA-512（同族，摘要更长）
  • RS256 = RSASSA-PKCS1-v1_5（RSA 签名方案）+ SHA-256 → 非对称，私钥签、公钥验
  • PS256 = RSASSA-PSS（RSA 的更安全填充）+ SHA-256，合规场景常用
  • ES256 = ECDSA + P-256 曲线 + SHA-256 → 非对称，签名更短、验签更快
  • EdDSA = Edwards-curve（Ed25519）签名
  • 记法：字母 = 算法族（HMAC / RSA / ECDSA / EdDSA），数字 = 摘要位数（256 = SHA-256）

2. 它们是「签名/MAC」算法，不是加密算法（你的直觉对）

  • 签名（HS/RS/PS/ES/EdDSA 全系）：输入任意长消息 → 输出固定长度的章（HS256=32 字节）→ 不可还原原文，用途=完整性+来源可信。
  • 加密：可逆，解密能还原明文，用途=保密。
  • JOSE 里加密是另一套标识，放在 JWE 的 enc 字段：如 A256GCM、RSA-OAEP-256——alg 管签，enc 管密，两套不混用。所以「JWT 用 HS256 加密」是错的说法，应说「用 HS256 签名」。

Q11 · 验签时 JWT 具体是怎么验的？

提问（2026-10-28）：那验签的时候，JWT 是怎么验的？

答复：

标准验签五步（顺序不能乱）

  1. 拆：按 . 切成 3 段；不是 3 段 → 直接 401（不进任何解析）。
  2. 读 header、但不信它：Base64URL 解码第 1 段拿 alg → 立刻与服务端配置的算法白名单比对：不在白名单、等于 none、或与预期不符 → 拒。这一步是所有 JWT 漏洞的震中：协议允许客户端「自报」算法，实现若照单全收就出事。
  3. 验章（用服务端本地的密钥材料，与 token 内容无关）：
    • 对称 HS*：HMAC-SHA256(第1段+"."+第2段, 服务端 secret) 重算 → 与第 3 段常量时间比较（hmac.compare_digest，逐字节比较会有时序侧信道）。
    • 非对称 RS/PS/ES*/EdDSA：用公钥对「拼串 + 第 3 段」做验签运算 → 通过/失败二值。不需要 secret，也永远不碰私钥（私钥只在签发方）。
  4. 验过才解 payload：签名可信了，第 2 段的 claims 才能采信（先验后用；验签前读 claims 只能用来排查日志，不能据此做任何决策）。
  5. 校验 claims：exp（过期，常留 30~60s 时钟偏移容忍）→ nbf/iat（未生效/未来时间异常）→ iss/aud 是否匹配本服务 → 需要可撤销时查 jti 黑名单或会话状态 → 全过才进业务。

伪代码（对称）

parts = token.split(".")
if len(parts) != 3: return 401
header = b64url_decode(parts[0])
if header.alg not in ALLOWED:            # 白名单，服务端配置，不看 token 自报
    return 401                            # 挡 alg=none / RS256→HS256 混淆
expected = HMAC_SHA256(parts[0]+"."+parts[1], SERVER_SECRET)
if not constant_time_equal(expected, parts[2]): return 401   # 第 3 段不对=改过
claims = b64url_decode(parts[1])
if now > claims.exp + 60: return 401
if claims.iss != "h5-activity" or "draw-api" not in claims.aud: return 401
if claims.jti in blacklist: return 401
return ok(claims.sub, claims.scope)

非对称版本只改第 3 步：verify(RSA_PUBLIC_KEY, parts[0]+"."+parts[1], parts[2])，其余全同。

三个必须记住的坑

  1. alg=none：攻击者把 header 改成 {"alg":"none"}、第 3 段清空 → 实现若「照 header 执行」就直接放行。防御=白名单不含 none。
  2. RS256→HS256 混淆：服务端本该用 RSA 公钥验签，但按 header 里的 alg=HS256 走 HMAC → 攻击者拿你公开的公钥当 secret 自己签一个 → 通过。防御=算法按服务端配置固定，不信 header。
  3. 只验签不校时效：签名合法但可能是三年前的 → 一样要查 exp/iat/iss/aud；且验签顺序先于任何 claims 判断。

密钥材料怎么分

  • 对称：所有验签方都得有同一把 secret（泄露=谁都能签，故只用于互信内网）。
  • 非对称：验签方只持公钥，私钥只在签发的认证服务里——这就是多服务/网关场景选 RS256/ES256 的原因。
  • 轮换：header 带 kid，验签方按 kid 选当前密钥，新旧并存过渡；轮换仍需配合算法白名单。
