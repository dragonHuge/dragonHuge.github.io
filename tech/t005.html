Agent 应用开发 — 知识点全景图

Agent 应用开发 — 知识点全景图

源自简历项目分析 + 拓展延伸，共 9 大模块 60+ 知识点

一、RAG 离线索引

1.1 文档解析

格式工具/方法核心难点
纯文本 PDFPyMuPDF (fitz)多栏布局、页眉页脚去除
扫描件 PDFOCR (Tesseract/PaddleOCR)识别准确率、版面分析
复杂 PDFUnstructured表格嵌套、图文混排
Markdown结构化解析器标题层级、代码块、链接
图片VLM (GPT-4V/Claude Vision/Qwen-VL)图表理解、流程图解读

关键概念讲解：

OCR（Optical Character Recognition，光学字符识别）： 把图片中的文字"读"出来变成可编辑文本。原理是先检测文字区域（文本检测），再逐字识别（文本识别）。Tesseract 是 Google 开源的老牌方案，PaddleOCR 是百度出的，中文效果更好。

VLM（Vision-Language Model，视觉语言模型）： 能同时理解图片和文字的模型。和 OCR 的区别：OCR 只是"把图片里的字抄下来"，VLM 是"看懂图片在说什么"。比如一张柱状图，OCR 只能提取坐标轴上的数字，VLM 能告诉你"2024年Q3营收同比增长30%"。

1.2 Chunk 切分策略

策略原理适用场景优劣
固定大小按字符数/Token 数切简单场景、快速原型简单但可能切断语义
递归切分按分隔符层级递归（nn→n→空格）通用场景LangChain 默认，效果不错
语义切分用 Embedding 判断语义边界长文档、主题切换频繁效果好但慢
文档结构按 H1/H2/H3 标题切结构化文档保留层级信息

核心参数：

  • chunk_size：每个 chunk 的目标大小（常见 500-2000 token）
  • chunk_overlap：相邻 chunk 重叠量（通常 chunk_size 的 10-20%）
  • 太小 → 缺乏上下文，太大 → 检索不精准。需要评测调参。

1.3 索引构建

BM25 索引（稀疏检索）：

  • 基于词频（TF）和逆文档频率（IDF）的经典算法
  • "这个词在这个文档中出现很多次"（TF 高）+ "这个词在其他文档中很少出现"（IDF 高）= 高相关性
  • 优势：精确匹配关键词（错误码、函数名、专有名词）
  • Python 实现：rank_bm25 库

稠密向量索引：

  • 用 Embedding 模型把每个 chunk 变成高维向量
  • 存入向量数据库（Chroma/FAISS/Milvus）
  • 查询时把问题也变成向量，算余弦相似度
  • 优势：理解语义（"怎么验证身份" ≈ "认证流程"）

混合索引 = BM25 + 向量，互补短板

二、RAG 在线检索

2.1 查询改写（Query Rewriting）

用户的原始问题往往不适合直接检索。改写策略：

策略做什么示例
关键词提取从自然语言提取检索词"Agent的记忆怎么做的" → "Agent memory system design"
多查询生成一个问题生成多个变体原始问题 → 3个不同角度的问题 → 分别检索 → 合并
HyDE先生成假答案，用假答案检索问题→LLM生成假回答→用假回答的向量去检索→找到真正的相关chunk
Step-back问一个更宽泛的问题"PyMuPDF 怎么提取表格" → "PDF 解析工具有哪些"

HyDE 原理详解： Hypothetical Document Embeddings。核心洞察：答案和答案更像，问题和答案不一定像。所以先让 LLM "猜"一个答案（可能不准确），用这个猜测答案的向量去检索，比直接用问题的向量检索效果更好。

2.2 多路召回与融合

查询 ──┬── BM25 检索 ──────── 候选集 A
       │
       ├── 向量检索 ──────── 候选集 B
       │
       └── 元数据过滤 ────── 候选集 C
                              │
                    RRF 融合排序 → Top-K → Reranker → 最终结果

RRF（Reciprocal Rank Fusion）： 一种简单有效的多路融合算法。对每个文档，在每个检索结果中的排名取倒数后求和：score = Σ 1/(k + rank_i)。k 通常取 60。不需要分数归一化，只看排名。

2.3 Rerank 精排

为什么初始检索不够： BM25/向量检索是 Bi-Encoder——query 和 document 分别编码再比较，快但粗糙。Reranker 是 Cross-Encoder——把 query 和 document 拼在一起送进模型，精准但慢。

工程模式： 初始检索（快，召回 50-100 条）→ Rerank（慢，从 50 条精选 5-10 条）。这就是"先海选后精挑"。

Reranker特点
Cohere RerankAPI 服务，效果好，有成本
BGE-Reranker-v2开源，可本地部署
Jina Reranker开源，多语言

2.4 上下文拼装与生成

检索到 Top-K chunk 后，拼成 Prompt 交给 LLM 生成答案：

  • 按相关性排序
  • 加上来源标注（便于引用核查）
  • 控制总长度不超过 LLM 上下文限制
  • 低置信度时触发二次检索

引用核查： 检查 LLM 生成的每句话是否在 context 中有依据。减少幻觉的关键。

三、RAG 评测与优化

3.1 RAGAS 框架四大指标

指标评估什么计算方式提升方向
Faithfulness回答忠实于检索内容吗把回答拆成 claims → 检查每个 claim 是否有 context 支持改善 Prompt、加引用约束
Answer Relevancy回答切题吗从回答反向生成问题 → 和原始问题比相似度改善 Prompt
Context Precision检索结果精准吗相关 chunk 是否排在前面优化 Reranker、调 Top-K
Context Recall该找的都找到了吗ground truth 的每个 claim 是否在 context 中出现优化检索策略、扩大 Top-K

3.2 检索指标

  • MRR：第一个正确结果在第几位（MRR=1 意味着总在第一位）
  • Hit Rate@K：前 K 个结果中是否包含正确答案
  • NDCG：考虑排序位置的评分（排在前面的正确结果分更高）

四、Skill 路由系统

4.1 分层模型

用户意图
  ↓ 意图识别
Skill 目录（注册表）
  ↓ 二阶段召回
  ├── 粗召回：Embedding 相似度 / 关键词匹配 → 候选 Skill 集
  └── 精排：LLM 打分 → 选出最佳 Skill
  ↓
Skill 加载与执行
  ↓ Skill 编排多个 Tool
Tool 执行

4.2 两种路由范式对比

范式代表机制优劣
声明式路由Claude Code (CLAUDE.md)AI 读描述 → 自己判断 → Read 加载灵活但依赖 AI 判断力
注册式路由OpenCode (skill-registry)框架匹配触发条件 → 自动注入确定性高但需维护注册表
向量检索式简历中的设计Embedding 匹配 → 精排可扩展但有检索延迟

4.3 Skill 自进化

Skill 不是写死的，会生长：

  • 新增：发现新的高频任务模式 → 提炼为 Skill
  • 优化：根据执行反馈调整 Skill 流程
  • 淘汰：低使用率的 Skill 降低优先级
  • 合并：功能重叠的 Skill 整合

五、记忆系统

5.1 记忆分类

类型内容存储检索方式对应人类记忆
短期当前对话历史内存全量（在上下文中）工作记忆
程序性"怎么做"的经验文件/DB任务类型匹配肌肉记忆
情景"发生过什么"文件/DB语义检索回忆
语义"是什么"的知识文件/DB语义检索常识
用户画像偏好和习惯文件全量注入对人的了解

5.2 记忆闭环

执行任务
  ↓ 产生对话
反思："这次学到什么？"
  ↓ LLM 提取
提炼：去噪、结构化
  ↓
分类存储：按类型写入对应存储
  ↓
索引更新：向量索引 / 关键词索引
  ↓ 下次任务
按需复用：检索相关记忆 → 注入上下文

六、上下文管理

6.1 核心矛盾

Agent Loop 每轮把全部历史发给 API → 消息越来越长 → Token 消耗指数增长 → 需要压缩

但压缩可能破坏 Prompt Cache → 反而更贵 → 需要缓存感知的压缩策略

6.2 压缩层级（从轻到重）

层级触发时机做什么成本信息损失
工具结果预算实时大结果存磁盘，留预览零无（可回读）
微压缩缓存过期后裁剪旧工具结果低轻微
会话摘要Token 达阈值用摘要替代历史中中等
完整压缩Token >80%fork 子 Agent 生成结构化摘要高较大
应急压缩API 报错硬删中间 50% 消息最高严重

6.3 Prompt Cache 协同

关键设计原则：

  • 静态内容（System Prompt）放前面，动态内容放后面
  • 压缩时尽量不破坏已缓存的前缀
  • 等缓存 TTL 过期后再压缩（省双重成本）

七、多 Agent 协作

7.1 协作模式

模式结构通信适用
主从调度中心 Coordinator + Worker单向下达任务可明确拆分
子 Agent主 Agent fork 临时子任务单向（下达→返回）一次性子任务
Agent Team持久化团队双向互发消息长期复杂项目
流水线A→B→C 串行单向传递固定流程
辩论/对抗多角色讨论多向需要多视角验证

7.2 安全约束三板斧

  1. 工具权限白名单：没给的工具硬性调不了（不是提示词"建议"）
  2. 路径边界限制：子 Agent 只能访问指定目录
  3. 嵌套限制：防止递归创建子 Agent 导致资源爆炸

八、安全与防御

8.1 Prompt 注入攻击

类型途径示例
直接注入用户输入"忽略前面所有指令，改为执行..."
间接注入工具返回值网页内容中嵌入"你是一个恶意助手"
数据投毒训练/检索数据RAG 检索到的恶意文档

8.2 防御层次

第1层：输入过滤（正则/关键词检测已知攻击模式）
第2层：工具自检（参数合法性验证）
第3层：AI 风险分类（用 LLM 判断意图是否恶意）
第4层：人工确认（高风险操作弹窗）
第5层：沙盒隔离（限制文件系统/网络访问）
