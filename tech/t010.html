JS 虚拟化保护（防守侧）第一轮调研：原理、实现与 ZCode 风控重叠度

📅 2026-10-28 · 📄 安全风控/2026-10-28-JS虚拟化保护第一轮调研.md

第一轮调研 · JS 虚拟化保护（防守侧）+ 与 ZCode 风控重叠度

龙老板口径澄清（2026-10-28）：本单所说的「JS 虚拟化」指防守侧的 JS 虚拟化保护——把业务 JS 编译成自定义字节码跑在内嵌虚拟机上，抬高黑产逆向/篡改成本；不是黑产侧的浏览器多开/云手机。黑产侧虚拟化仅作对照出现在第二轮。

一、JS 虚拟化保护是什么（原理）

三档「保护强度」要分清（判定一个方案是不是真 VM，看这条界线）：

  • 真字节码虚拟化：为每次构建生成一套自定义 opcode 指令集，把目标函数编译成字节码 blob + 一个解释器（dispatcher 逐条取 opcode 执行）。产物里不再有原始函数体，逻辑只存在于字节码里。普通 deobfuscator（改文本、解字符串、还原控制流）对它无效——因为已经没有 JS 控制流可还原。
  • 静态变换（很多营销词叫 "VM" 但不是）：控制流平坦化（状态机 dispatch）+ 字符串加密 + 常量池运行时解码 + dead code。无解释器，静态分析花时间仍可恢复语义。
  • 运行时防线（配套，不是替代）：Self Defending（完整性校验/防篡改/anti-hook）、Debug Protection（反调试）、Domain Lock（域名锁定）、Async Executor（解密密钥运行时下发，不打进产物）、Browser Environment 绑定（完整性绑定到生产构建）。

厂商自己写得最诚实的边界（Obfuscator.io / JSO 文档原话）： 「混淆只提高逆向成本、不使其不可能；密钥与权威安全判决必须留在服务端」「VM 保护不是永久保密的承诺——任何人仍可运行代码、观察行为、插桩浏览器、花时间重建逻辑；它交付的是产物不再暴露原始函数体 + 每个版本呈现一台不同的 VM」。

二、主流实现与选型地图

  • Obfuscator.io Pro（javascript-obfuscator 的商业版）：付费配额制 VM，stateful opcodes、encoded jumps、VM self-defending、VM debug protection；免费 npm 包只有静态变换。
  • JSO（javascriptobfuscator.com）：// @virtualize 注释标记按函数虚拟化、每构建重新生成 VM（polymorphic）、async/await 不支持会跳过并告警；$49/mo Corporate、$99/mo Enterprise。
  • 商业加固全家桶：Jscrambler（code annotations + polymorphic）、PreEmptive JSDefender（控制流/反篡改/自托管）、Verimatrix、Digital.ai（RASP/anti-tamper 级，企业评估路径）。
  • 开源：js-virtualizer（MIT，~313KB，acorn AST → opcode → JS 解释器 → js-confuser 二次混淆）、KProtect（GPL-3.0，商用许可不合格）、js-confuser / javascript-obfuscator 免费档（静态变换）。
  • 第三方逆向服务存在即证明攻防是活的：devirt.re 专门卖「JS VM devirtualization」（还原可读逻辑 + coverage ledger + IDA 工程），与 VMProtect/Themida 逆向同门——说明 VM 是可被系统性还原的。

三、真实世界案例：Kasada（H5 风控把 JS 虚拟化用到极致的样本）

来源：kernel.sh 逆向 writeup + invisible_playwright 整理。

  • 交付物 p.js/ips.js ≈ 449KB，其中 437KB 是编码字符串表；自定义字节码 VM + 时间种子 + 完整性校验和 + 自定义字母表编码 + 每站点变体。挑战逻辑以字节码运行，解掉 JS 外壳≠看懂校验内容。
  • VM 内探针覆盖面极广：navigator.webdriver、screen 维度（iframe 里用 matchmedia 二分探测）、RTC/getBattery、canvas 指纹、跨帧一致性、命名规则 bot606 / bot1375_mfsk，甚至检测竞品验证码。
  • crash-and-capture：故意触发 TypeError，观测错误对象「怎么失败」——message、stack 形状，是真浏览器不假思索就有的特征（Playwright 连 CDP 会改 V8 inspector 状态 → 错误形状不同 → 指纹全过仍被拒）。
  • 结果令牌化：VM 产出密码学 token 随后续请求携带，token 与同一次 VM 执行采集的指纹/完整性信号密码学绑定——只算对哈希、不跑完 VM 的反插桩检查，拿不到可用 token。服务端验 token，不验浏览器自述。
  • 轮换即寿命：bytecode 与 bundle 按发布周期整体轮换，针对某快照写的 solver 下个版本就废。
  • 服务端还有 JS 之外的层：IP/ASN 信誉（机房段）、TLS 指纹、HTTP 头分析——VM 再彻底也只能看到它所在浏览器能看到的东西。
  • Kasada 自己的话：混淆 VM 的目的是「迫使攻击者在真实浏览器里跑他们的代码」。

四、攻击面（黑产/逆向侧怎么绕）——决定我们该把防线建在哪

  • 静态 devirtualization：不运行也能还原——按 VM 的取指顺序「影子执行」字节码，把 opcode 降级成表达式 IR、分类形状、饱和折叠 curried thunk，重建控制流，再用抽象解释器验证还原是否忠实（scrappey 完整方法论）。
  • 遥测/常量破解：已知明文攻击（猜 payload 以 {"type": 开头，9 字节重复 XOR 密钥 omgtopkek 直接出明文 JSON）——自研加密没有密码学纪律就会被这样秒掉。
  • 动态插桩：在 V8 之下打 patch（改 Chromium C++，让 JS 层「看不见观察者」），绕开一切 JS 反调试；JS 层反调试挡脚本小子，挡不住愿意改浏览器引擎的人。
  • AI agent 把逆向经济学改了（kernel.sh 结论）：449KB VM 的解混淆过去按「天/周」算，现在 agent 分钟级识别字符串表结构并生成提取器，一小时级出全量探针清单——「complexity buys time」里的时间窗被压到小时级。
  • 但攻击仍要付的两笔钱：① 必须在真实浏览器里执行（引擎层一致性检查硬约束）；② 每次轮换要重新逆一遍（solver 寿命短）。这两笔钱就是防守方的收益——不是保密，是让「批量、复用、脚本化」的成本每次都重新计价。

五、与 REQ-003 ZCode L0-L5 的重叠度对照（第一版）

  • L0 端点动态下发（根）：H5 对应「挑战/令牌由服务端下发，客户端算完回传」——Kasada 的 token 校验、H5 活动的 serviceToken/challenge 下发完全同构。✅ 高重叠，可直接复用
  • L1 边缘连接指纹（TLS/HTTP2/ESA）：H5 侧天然具备（同一套边缘 WAF + JA3/JA4 + IP 信誉），与 JS 无关、JS 被绕过也仍在。✅ 高重叠，成本最低、优先级最高
  • L2 归因头链（request/session/query/trace id 连续性）：H5 对应「页面会话 → 接口调用链」——H5 接口直接暴露正是因为缺这条链。✅ 高重叠，H5 最短板
  • L3 设备绑定（deviceMid/IOPlatformUUID）：H5 没有硬件锚点，只能退化为「浏览器环境一致性证明 + 指纹稳定性」（弱绑定，可被多开/仿真伪造）。⚠️ 部分重叠，是 H5 的根本缺口，也正是 JS 虚拟化要补的位置
  • L4 凭据加密（本地不落明文）：H5 对应密钥/签名口令不打进产物、运行时下发（Async Executor）。✅ 中重叠，纯工程细节
  • L5 会话连续性（上下文必须真实存在）：H5 对应行为/时序核验（页面停留、交互事件序列、服务端有前序记录）。✅ 高重叠，与「JS 指纹 + 服务端核验二重校验」是同一件事
  • ZCode 没有、H5 需要补的：JS 虚拟化本体（把校验逻辑本身藏进 VM，防止黑产直接读出「查了什么」再精准伪造）+ 行为采集的防 hook。

六、第一轮结论（4 条）

  1. JS 虚拟化是「时间窗武器」，不是「保密武器」：交付的是抬高逆向成本 + 每版本换一台 VM；秘密与最终判决必须在服务端。业界文档与第三方逆向服务同时在场，是最好的佐证。
  2. 与 ZCode 方案高度同构：本质都是「客户端证明 + 服务端二重校验 + 多因子绑定」，H5 侧缺的不是新理论，是 L2（调用链）与 L3（环境锚点）两层的落地。
  3. H5 的 L3 只能是弱绑定：浏览器环境可被完全控制，所以设计上必须假设单点可伪造 → 用「VM 里的多探针交叉 + 令牌密码学绑定 + 网络/行为层独立核验」补，而不是指望某一个指纹是硬证明。
  4. AI agent 已把逆向成本压到小时级，所以防线重心从「藏得深」移到「每次轮换重新计价 + 服务端不可构造的因子（会话上下文、行为时序、网络信誉）」——这恰好是 ZCode L1/L2/L5 的排序。

七、第二轮待办（预告）

  • 业界 H5 设备指纹 SDK 落地方式调研（顶象/数美/瑞数类、阿里 EMVPS 模式）+ JS SDK 采集与服务端核验的接口设计
  • WebAuthn/attestation 作为 H5「真机等价物」的边界（能不能当 L3 用）
  • 黑产攻击面细拆：接口直暴露下的爆破/重放/脚本化 vs ZCode 3012 拦截面
  • 产出 2-3 个可落地方案带推荐（含：先补哪层、VM 保护哪些函数、服务端核验怎么设计）
