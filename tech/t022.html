架构师（JiaGouX）

我们都是架构师！ 架构未来，你来不来？

周一早上，一个用户打开公司的工作台。旧密码提示错误，他按页面指引完成了重置：邮件确认过了，短信验证码也收到了。可回到登录页，页面还是进不去。

他在客服窗口里写：“密码已经改了，还是登录不上。”

分诊 Agent 先问他用的是企业账号还是个人账号，又让他确认登录入口。两轮之后，窗口提示“已为你转接技术支持”。技术支持接过来，问页面有没有错误码，请他再登录一次。

用户切回浏览器。验证码能收到，密码也能提交，页面却弹出 403。等他回到客服窗口，已经过去七八分钟。

他没有重讲前因后果，只补了一句：“还是不行，403。”

如果是真人客服，技术支持大多能顺着上文继续排查。可系统一旦把这句话当成新一轮，又交给默认的分诊 Agent，接下来很可能还是那几个问题：什么账号、从哪里登录、页面提示了什么。

第一轮确实转接成功了。断掉的是下一轮：系统忘了这段会话已经由技术支持接手。

时点用户看到的系统需要留下的
第一次求助分诊 Agent 询问情况会话身份、已确认的信息
转给技术支持技术支持开始回复当前负责人、交接原因
用户再次发消息“还是不行，403”把消息交回技术支持所需的状态

转接工具返回成功，页面也显示“已转接”，只能说明这一轮走到了新 Agent。等下一条消息进来，系统还能不能找到刚才的接手者，是另一件事。

前面三篇里，Workflow 把路径写进代码，Supervisor 由中央 Agent 派工，Hierarchical 再把控制拆到不同层级。到了 Swarm/Handoff，固定主管可以退到后面，但“现在该谁回复”仍然要有答案。

谁接下一句

Handoff 容易和“请专家帮一次忙”混在一起。两者都可能表现成一次工具调用，责任却不同。

主 Agent 只是请专家查一次退款规则，专家把结果交回来，主 Agent 整理后回复。后面的对话，仍由主 Agent 负责。

如果用户已经进入退款处理，后面还要补订单、核验资格和确认方式，关系就不一样了：分诊 Agent 把会话交给退款 Agent，下一条消息也该回到退款 Agent 手里。

请专家帮一次，还是把会话交出去

图：架构师（ID：JiaGouX）｜左边是一次委派，右边才是后续责任的转移。

OpenAI Agents SDK 把这两种关系分别叫作 agents as tools 和 Handoff。落到使用体验上，差别很直接：专家回来汇报一次，还是从现在起接住用户的后续消息。

本地 aicode 源码里也能看到，Handoff 并不总指同一件事。pi 的 /handoff 会从当前分支整理上下文，生成一份可编辑的提示词，再建立新会话。Claude Code 的 AgentTool 则是在子 Agent 做完后，把控制权交回主 Agent；auto 权限模式下，还会判断这次回交是否需要阻断。

一个换了会话，一个回到协调者，都不等于“专业 Agent 接管了后续对话”。这两个例子也让我不太敢只看 Handoff 这个名字。我更关心的是：下一条用户消息，默认会送给谁？

把责任留下

一次 run 里，Handoff 可以把 active agent 换成新 Agent，后半段由它继续处理。但 run 一结束，下一条消息会重新进入应用。系统得认出这段会话，也得知道刚才的当前负责人是谁。

这一轮换了 Agent，不等于下一轮还找得到它。

不同框架把“负责人”放在不同位置。OpenAI 的结果里会保留最后活跃的 Agent，供后续继续；LangChain 会更新 active_agent，跨轮保存还要依靠 checkpointer；Microsoft Agent Framework 用 checkpoint、稳定的参与者 ID 和上下文同步来恢复交接现场。

责任怎样跨过两次请求

图：架构师（ID：JiaGouX）｜上一轮写下负责人，下一轮先恢复 owner 和上下文，再把消息送回接手者。

名词不一样，边界差不多：这是哪段会话，现在轮到谁，接手时应该从哪份上下文继续。如果这些信息只出现在模型当时看到的提示里，一次压缩或重启，就可能把“轮到谁”一起抹掉。

场景常见做法
普通咨询会话 ID、当前负责人、上下文引用
涉及资金、权限或 SLA再记录交接已发起、已接受、已生效或失败
人工接管记录接管人、时间、原因和恢复入口

状态不必一开始就做得很重。普通咨询能找回负责人，往往已经够用；失败代价高时，再把交接阶段和责任变化记细。状态记到多细，可以跟着失败代价一起长。

这也接上了今年几篇 JGX 文章一直在追的那条线：一轮结束以后，哪些状态还能继续，哪些事实仍然可信。Handoff 只是把问题落到了更具体的一刻——换人之后，这段对话能不能接着走。

带走什么

找回负责人以后，接手者还得知道刚才发生过什么。

全部历史原样带过去最省事，却可能混进内部工具返回、无关分支和不该越过权限边界的数据。只留一句“用户登录失败”又太薄，403、已经试过的操作和用户刚做的选择都会丢掉。

我更倾向于把交接分成两层：先给接手者一份短说明，写清转交原因、已确认事实和当前进度；原始对话与工具结果继续留在记录里，遇到疑点再回看。

一份能接着处理的 Handoff 交接

图：架构师（ID：JiaGouX）｜接手者先读当前上下文和交接说明；原始记录保留下来，工具权限按新身份重新校验。

这和上一篇 Hierarchical 里“摘要与证据分开”有点像。区别在于，分层架构向上汇总的是一份阶段结果，Handoff 交出去的是一段还没聊完的对话。接手者除了知道结论，还要知道用户已经试过什么，免得让人从头再来。

上下文也不等于权限。技术支持 Agent 看到了订单号，不代表它就能退款；退款 Agent 接过会话，也不会因此跳过金额、账户和人工确认。交接内容可以延续，工具和数据权限仍要按新身份检查。

主管退场之后

把 Handoff 放进 Swarm，直觉上像一群 Agent 自己接力：当前 Agent 觉得谁更合适，就把对话交给谁，不必每次回到中央主管。

这里我会把架构思路和旧框架分开看。OpenAI 的 Swarm 仓库是实验、教学项目，仓库说明建议生产场景迁移到 Agents SDK。它也写得很清楚：run() 返回消息、当前 Agent 和上下文，但不会替应用保存两次调用之间的状态。

固定主管退场后，允许谁转给谁、目标 Agent 超时后由谁继续，这些问题仍然存在。系统可以先约定哪些 Agent 能互相转交；会话记住当前负责人；遇到超时或绕圈，也留一条退路。责任换过几次，事后还能查清楚。

这些工作未必需要再交给一个会聊天的“总管 Agent”。Swarm 改变的是谁在对话中做决定，路由、状态和失败处理仍要有落点。

站在用户这边，背后用了几个 Agent 并不重要。他更在意刚说过的信息还在不在，上一位确认过的事还算不算数，转接失败以后有没有人继续处理。

四种架构

把四篇放在一起看，差别主要落在两件事上：下一步由谁决定，状态在哪里续上。

架构下一步由谁决定谁负责回复或交付跨过一轮后留什么
Workflow预先定义的代码流程流程指定的出口节点、检查点、重放位置
Supervisor中央 Agent中央 Agent派工理由、结果、停止条件
Hierarchical当前层级的控制节点当前层级的负责人跨层约束、证据、升级关系
Swarm/Handoff当前 Agent 选择接手者，运行时完成切换当前接手的 Agent当前负责人、交接说明、路由记录

实际系统经常把几种方式放在一起。稳定环节用 Workflow，分诊由 Supervisor 处理；进入专业对话后，再 Handoff 给对应 Agent。任务变大时，中间还可能多一层 Hierarchical。

几种架构可以混用，责任却不能含糊。原 Agent 以为自己已经结束，接手者没拿到状态，下一轮入口又从头分诊，对用户来说，就是一群互相不认识的客服。

写完这篇，我对 Handoff 的理解变窄了一些。它未必比其他多 Agent 架构更先进，只是把一段没聊完的对话交给另一个 Agent 继续负责。

等用户七八分钟后回来，只说一句“还是不行，403”，系统还能让技术支持接着查，而不是请他再讲一遍。对我来说，做到这一步，Handoff 才算跨过了下一轮。
