2026-10-28 · 安全风控/2026-10-28-H5活动风控第二轮调研.md

第二轮调研 · 业界 H5 风控落地方式 + WebAuthn 边界 + 黑产攻击面 + 落地方案

承接第一轮（2026-10-28-JS虚拟化保护第一轮调研.md）：第一轮定了「JS 虚拟化是时间窗武器」「与 ZCode L0-L5 高度同构、H5 缺 L2/L3」两条基调。本轮把「业界怎么落地」「Web 能不能当真机」「黑产到底怎么打」「我们怎么分档落」四个问题补齐。

一、业界 H5 设备指纹 / JS SDK 的落地方式

1.1 通用形态：三段式「SDK 采集 → deviceToken → 服务端二重校验」

厂商（阿里云设备风控、腾讯云 TDS、数美、网易易盾、顶象）在 Web/H5 端的接入模式高度一致：

  1. 页面引入 JS SDK，初始化后 SDK 在端上采集并算出一个 deviceToken / 设备指纹 ID；
  2. 业务前端把 deviceToken 带进活动接口；
  3. 业务服务端拿 deviceToken 调厂商「风险识别 API」，换回风险标签 + 评分；
  4. 业务按标签/评分执行策略（放行 / 挑战 / 拒绝）。

关键点：判决在服务端——端上只负责「采集 + 算 token」，不负责「判定」。这与 ZCode 的 L3/L4（端侧证明、服务端核算）和手机端真机能力的「一重采集 / 二重校验」是同一个形状。

1.2 采集维度（决定指纹稳定性与抗多开能力）

  • 环境类：UserAgent、语言、时区、屏幕分辨率/色深、设备像素比、CPU 核数/内存、触屏能力、Canvas/WebGL/AudioContext 指纹、字体枚举、插件列表、Media devices。
  • 行为类：鼠标/触摸轨迹、滚动与点击时序、页面停留、陀螺仪（移动端 H5）——数美把「移动速度、机身姿态、使用习惯、IP 流量、设备聚集性」单列为行为风险识别维度。
  • 环境风险类：代理/VPN/机房 IP、调试状态（navigator.webdriver、DevTools 端口特征）、自动化框架痕迹、改机工具/多开/Root 痕迹（Web 端主要看浏览器环境一致性）。
  • 网络类：IP/ASN 信誉、WebRTC 暴露的真实出口、DNS 特征。

厂商侧再做碰撞治理：专利与厂商文档都写明——按型号/OS 分桶统计每个特征的重复率与空值率，超阈值就标记为异常特征并动态调整权重（防「同一指纹被批量刷成一样」的碰撞，也防某特征大面积为空导致指纹失效）。

1.3 服务端核验的接口设计（自研版的骨架）

  • 端：SDK 采集 N 维特征 → 加密/编码上送 → 返回 deviceToken（含过期时间）。
  • 业务接口：deviceId + token + timestamp + nonce + sign + 业务参数。
  • 风控服务：验 token 有效性 → 查该 deviceId 的历史（注册时间、关联账号数、IP 集中度、命中记录）→ 出标签。
  • 策略引擎：deviceId 关联账号数 &gt; 阈值、同 ASN 段设备密度、token 过期/复用、指纹维度缺失（如 canvas 为空） → 拦截或下发挑战。

为什么必须是「二重」：端上特征可被伪造，单靠端自述没有意义；真正有效的是服务端把 token 与行为/账号/网络历史做交叉——即第一轮结论 3 的「多因子交叉而非单点硬证明」。

1.4 厂商/方案地图（选型参考）

  • 阿里云 风险识别-设备风控：App/Web/小程序 SDK → deviceToken → 服务端风险识别 API → 标签+评分，场景即「营销防刷」。
  • 腾讯云 TDS 设备安全：H5 SDK + 服务端接口，主打模拟器/篡改/群控识别，再用「账号-设备-IP」关联网络做团伙聚类。
  • 网易易盾：H5 应用加固（防逆向/调试/破解）+ 设备指纹 + 风控引擎三板斧，明确列了 H5 场景的刷量、撞库、薅羊毛三类风险。
  • 数美：设备指纹 + 行为风险（姿态/聚集性）+ 环境风险（代理/调试/高危软件）。
  • 顶象：无感验证 = 设备指纹 + 人机模型 + 决策引擎 + 13 种验证方式；策略库/风险情报沉淀型打法。
  • 前/后端签名参数（自研、无厂商）：京东 H5ST 是典型样本——深度绑定浏览器环境 + 时间戳 + 设备指纹 + 行为特征的前端参数签名，属于「防接口未授权调用」的自研路线；逆向社区已有完整 H5ST 逆向实战文（环境补全 → 接口调用），再次印证「签名只能抬成本」。
  • 边缘/动态安全（瑞数类）：页面动态下发 + 脚本令牌，属于「JS 被绕过也还在」的边缘层，对应 ZCode L1。

二、WebAuthn / attestation 能不能当 H5 的「真机」（L3）

结论先给：不能当硬 L3，只能当一个高权重的弱因子，且必须容忍「用户没有/不同步」的降级路径。

分层看边界（安全风控视角，按「证明强度 → 可用性」排）：

  1. attestation 天然被弱化：W3C/MDN 明确「relying parties 不被鼓励请求 attestation」——RP 收到的多是 none（自证明），拿不到「这是哪台设备/哪颗芯片」的证书链。企业与隐私（浏览器厂商）都在压制硬件证明的可得性。
  2. synced passkey 抹掉了设备唯一性：passkey 通过密码管理器跨设备云同步（Apple/Google/Microsoft 均是），一个凭据能在手机 + 笔记本 + 另一台手机上用——它绑定的是「账号」，不是「设备」。学术侧已有 device-bound vs synced 的对比研究，结论是 synced 提升可恢复性、削弱设备绑定保证。
  3. cross-device flow 会直接暴露「不是本机」：authenticatorAttachment 返回 cross-platform 即表示凭据来自另一台设备（扫码/蓝牙 CDA 流程）。这条可以当负向信号（本次认证来自跨设备），但不能当「设备可信」的正向证明。
  4. 厂商文档自证「开了 attestation 就废掉跨设备」：微软 Entra passkey 文档写明——启用 attestation 时无法做跨-device 注册/认证；Android 硬件 attestation 同样让凭据退出同步体系。也就是说强证明和用户体验直接对冲，活动场景（C 端、低意愿、无登录前置）基本只能选弱的一侧。
  5. AAGUID/counter 只够做「类型与克隆」信号：AAGUID 标认证器型号（不是单台设备），signature counter 用于检测克隆认证器，但在 sync/多设备下计数语义本就退化。
  6. 可用性硬伤：H5 活动常是「无账号、陌生人流量」，WebAuthn 要求 RP ID 域名一致、要求用户已有平台认证器，覆盖率与转化成本都不适合做「进门关」。

可用姿势：把 WebAuthn 放进登录/领奖等已有身份的高价值动作做二次强因子 + 复用「凭据 ID ↔ 账号 ↔ 首次设备指纹」绑定记录；把它当作 L3 的补充证据，主锚点仍交给设备指纹 + 会话/行为/网络因子。

3.2 与 ZCode 3012 拦截面的逐层对照

  • L0 端点/挑战动态下发 ↔ H5 挑战/令牌服务端下发：黑产必须先跑一次「发挑战-回算」，脚本不能直接打终接口 → 对应 H5 的 deviceToken/challenge 流程。
  • L1 边缘连接指纹（TLS/JA3/JA4 + IP/ASN） ↔ H5 边缘 WAF + 机房 IP 信誉：黑产用代理池仍暴露 ASN 与 TLS 指纹 → 成本最低、JS 全绕过仍在的一层。
  • L2 调用链归因（request/session/trace 连续性） ↔ 「页面会话 → 接口」链：黑产纯接口调用必然缺前序页面访问与会话上下文 → 这是 H5 目前最短板、也最容易见效的一层。
  • L3 设备锚点 ↔ 设备指纹（弱绑定）：黑产用群控/多开伪造 → 只能靠碰撞率、聚集性、维度缺失等统计信号。
  • L4 凭据不落产物 ↔ 签名密钥/采集逻辑不打进静态产物、运行时下发：黑产逆向成本从「一次」变成「每次轮换重新计价」。
  • L5 会话连续性/行为时序 ↔ 页面停留、交互序列、服务端有前序记录：挡「模拟点击」和「脚本直调」的最后一道。

一句话：黑产在 H5 侧最省力的路径是「抓包 → 逆签名 → 脚本直调 → 群控放大」，恰好每一环都有对应拦截层；ZCode 3012 之所以拦得住，是因为它把这五层同时开了，而多数 H5 活动只开了「签名」一层（且签名密钥在产物里）。

四、落地方案（3 案带推荐）

方案 A · 轻量三件套（约 1–2 周，纯自研，无厂商）

  1. 防重放签名：HMAC(timestamp + nonce + 规范化参数串)，服务端窗口 60s + Redis 存 nonce 一次性；时间戳必须与 nonce 配合（只用时间戳，窗口内可无限重放）。
  2. 会话链（L2）：页面首跳下发一次性 sessionId，接口必须携带且服务端有前序记录，缺链直接拒——纯接口调用者第一道就死。
  3. 频控 + 关联规则（L5 雏形）：同 deviceId/账号/IP·ASN 的次数与扇出阈值，超限挑战或拒绝。
  • 收益：挡住 80% 的「抓包直调 + 重放」脚本；成本极低。
  • 短板：挡不住群控与高仿真人；签名算法仍在产物里，可被逆。

方案 B · A + JS VM 保护 + 令牌绑定（约 1–2 月，推荐）

在 A 的基础上：

  1. 关键函数虚拟化：只虚拟化「签名计算 + 指纹采集 + 挑战回算」三处（真字节码 VM，非控制流平坦化），每版本轮换 opcode；密钥不落产物、运行时下发。
  2. 令牌密码学绑定（Kasada 式）：VM 产出的 token 与同次执行的指纹/完整性信号绑定，服务端验 token 而非浏览器自述。
  3. 设备指纹 deviceToken 二重校验：自研（采集 → token → 服务端查历史/聚集性）或接厂商 API。
  4. 边缘层：IP/ASN 信誉 + 可选 TLS 指纹（对应 ZCode L1）。
  • 收益：把「逆一次用半年」变成「每次轮换重新计价」，且服务端判决不可构造；覆盖到群控与多开。
  • 短板：需要持续投入（每版换 VM、规则运营）；无法 100% 挡住愿意改浏览器引擎的定向攻击——但那类攻击成本已高于活动奖金。

方案 C · 商业全家桶（快、贵）

A 的骨架 + 厂商 SDK（顶象/数美/易盾/腾讯云 TDS 任一）出 deviceToken 与风险标签 + 决策引擎 + 无感验证；WebAuthn 在领奖环节作强因子。

  • 收益：上线快、有情报与策略库、含对抗运营。
  • 短板：按量计费、数据出域、黑盒依赖；对「活动级」预算可能过重。

推荐

按 B 路线分两阶段走，先落 A 当骨架：

  • 阶段 1（必做，1–2 周）：A 的三件套——签名防重放 + 会话链 + 频控。这一层性价比最高，直接对上 H5「接口直暴露」的核心痛点，且与后续所有方案不冲突。
  • 阶段 2（推荐，1–2 月）：补 B 的第 4–7 项——VM 只保护三个关键函数、令牌密码学绑定、deviceToken 二重校验、边缘 IP/ASN。这是本单「JS 虚拟化该用在哪」的落点：VM 不是拿来藏业务逻辑的，是拿来藏「校验逻辑本身」并让每次轮换重新计价的。
  • 不建议：把 VM 当保密手段（第一轮结论 1）、把单个指纹当硬证明（结论 3）、把 WebAuthn 当进门关（第二节）。
  • 何时选 C：若活动量级大、已有厂商预算，或需要现成的团伙情报与对抗运营。

五、第二轮结论（4 条）

  1. 业界 H5 落地与手机端真机能力同构：三段式「SDK 采集 → deviceToken → 服务端风险 API → 策略」，判决永远在服务端；差别只是 Web 端没有硬件锚点，只能靠特征稳定性 + 碰撞/聚集统计。
  2. WebAuthn 当不了 H5 的硬 L3：attestation 默认被削弱、synced passkey 绑账号不绑设备、强证明又会废掉跨设备体验——只能做高价值动作的补充因子。
  3. H5 最短的两块板是 L2 与 L1/L5：会话链缺失是纯接口调用的直接成因，边缘 IP/ASN 与行为时序是最便宜且 JS 被绕过仍在的防线；L3 用指纹做弱绑定 + 统计信号。
  4. 推荐分两阶段：先 A（防重放 + 会话链 + 频控，1–2 周见效），再 B（VM 保护三个关键函数 + 令牌绑定 + deviceToken + 边缘层）；VM 的定位是「时间窗武器」而非「保密武器」，与第一轮结论一致。
