23:55 · 单Agent思维链惯性与Agent Team挑战者架构

  • 原文：今天有个想法。最近在做 agent的智能巡检逻辑，基于 OpenClaw agent 做风控活动事件的风险巡检，总体流程已跑通，正在调优。调优后发现一个现象：agent 的思维有惯性。当我发给它业务反馈的风险 case，需求其实是让 agent 判断这个 case 到底是不是风险——是风险就深挖风险行为特征和作恶证据链，不是就说明原因。但由于主线链路是风险巡检，agent 会先入为主地认为业务反馈的这批用户已被确认是黑产，后续所有探查都建立在这个前提上，整个思维模式就走偏了：从「分辨是否是风险用户」变成「挖掘这批已确认用户的风险行为」，即便没有明显风险聚集，它也会把弱特征当作实锤证据来答复。本质问题就是思维惯性/上下文偏差。因此需要引入多 agent 架构里的挑战者模式：走两条路——一条默认有风险去挖风险，一条默认正常用户去分析正常轨迹；各自得出结论后由挑战者互相挑战、审核汇总，最后产出最终结果。最大收获：agent team 架构存在的核心本质，是突破单 agent 思维链的局限与惯性。
  • 总结：风控巡检 Agent 先入为主致思维走偏，需引入双路并行+挑战者的 agent team 架构突破单 agent 思维链惯性

14:31 · 反代风险差异本质：studio 与 harness 的接口协议不同

  • 原文：昨天深扒了一下反代，一下子清晰了为啥 studio 这类产品和 desktop 或 mimo-claw 这类产品，反代风险不一样。本质原因：底层服务端接口有本质不同。studio 只是对话工具，不需要 loop，暴露的调模型接口仅是一个接口，参数是用户 query，返回是 answer。desktop、mimo-claw 这类 harness 必须支持 agent loop，涉及多轮工具调用 tool call，底层调模型接口必须兼容 OpenAI 协议，返回格式要带 tool call 等，才能支持 loop。把 studio 反代接口接到自己的虾上，发现没法 loop，只能一次调用（类问答机器人），于是专门搞了个虾做问答，把 studio 的问答能力搬过去。deepseek 等 chat 都是这个逻辑。模型返回不兼容 OpenAI 协议是主因：支持 loop 的话，模型返回本轮回答之外还需返回下一步工具调用决策，studio 返回值没有；agent loop 输入时也要按固定格式告知底层模型本次用户输入和需调用的工具，但 studio 反代接口只有一个 query 参数，loop 输入即使有本次调用信息也会被整段塞进 query，工具调用失效，loop 不起来。studio 主要就是把 mimo-api 接口封装成一个普通接口。loop 停止条件：1.模型输出中无工具调用指令 2.兜底（防无限循环）。
  • 总结：studio 与 harness 反代风险差异的本质是接口协议不同——studio 只有单次 query-answer 接口不兼容 OpenAI 协议故无法支持 agent loop，harness 需带 tool call 的多轮 loop
