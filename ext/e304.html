摘要速览

  • 背景：Guardians 风控 MCP 从只读（@GetMapping + @RequestParam）扩展到写接口（@PostMapping/@PutMapping/@DeleteMapping + @RequestBody DTO），让 LLM 能改风控配置但不能触发"放量到生产"
  • 5 大设计决策：显式 @McpTool 白名单暴露、扩展现有 Provider 而非新建 Controller、同时支持 RequestParam 和 RequestBody、工具名 snake_case + 动词前缀、复用 Service 事务边界（Provider 只做协议适配）
  • 坑 1：DTO 字段名 ≠ JSON 字段名 —— @JsonProperty 注解未被 schema 生成器尊重，导致 LLM 按错名传参
  • 坑 2：MCP 客户端把数组/对象当 JSON 字符串传 —— 需要 preprocessListFields() 预处理，用 getGenericType() 解泛型
  • 坑 3：mapJavaTypeToJsonType 类型覆盖不全 —— List/Set/Array 被 fallthrough 成 "string"，连锁引发坑 2
  • 坑 4-8：写接口爆炸暴露红线（必须白名单）、反射调用绕过 Spring MVC 校验链、审计日志失败路径丢失、snake_case 工具名只 warn 不阻断、工具 description 三段式（用途+参数+返回）决定 LLM 调用质量
  • 附录 A（部署级）：Streamable HTTP 多副本下握手 404 —— 根因是"应用层有状态 session + 基础设施层无粘性路由"的经典错配，notifications/initialized 路由到没有 session 的兄弟 Pod；修复为切换 STREAMABLE_STATELESS 模式
  • 附录 B（协议级）：MCP spec 2025-06-18 structuredContent 字段缺失导致 Claude Code 拿 {} —— 根因是 server 升级了 protocolVersion 声明但 ToolResult builder 没有双写新字段，新客户端优先读空的 structuredContent 不回退 content

一、背景：从读到写，一步之遥但雷区翻倍

读 MCP 已经跑通：

McpSpringToolProvider 扫 @RestController 里被 @McpTool 标注的方法，桥接成 Solon FunctionTool。

但只支持 @GetMapping + @RequestParam，写接口（@PostMapping/@PutMapping/@DeleteMapping + @RequestBody DTO）会被直接跳过。

业务方需要：通过 MCP 创建/更新/启停/删除 风控配置（规则、规则组、事件、字段、风险码、名单库、字典 …），但严格不暴露 规则上线 / 规则发布 / 上线审批 这类有副作用的接口。

一句话总结：让 LLM 能改风控配置，但改不了"放量到生产"这一步。

二、整体技术方案：在 Provider 层做协议适配

1. 桥接拓扑

LLM/Cursor/Claude ──MCP JSON-RPC──▶ Solon MCP Server
                                       │
                                       ▼
                               McpSpringToolProvider  ◀── 反射桥接层（本次扩展）
                                       │
                                       ▼
                               Spring @RestController（既有业务接口，0 改动业务逻辑）
                                       │
                                       ▼
                               Service / Mapper / Holo / Redis（既有事务边界）

2. 核心设计决策（5 条，都直接对应踩坑点）

#决策否决方案否决原因
----
1显式 @McpTool 白名单暴露自动暴露所有 POST/PUT/DELETE写接口风险高，自动暴露 = 内部接口裸奔
2扩展现有 Provider，不新建 MCP 专用 Controller新建一套 MCP 专用工具类复制业务调用 → 长期与后台行为分叉
3同时支持 @RequestParam 和 @RequestBody强制把请求体序列化成字符串类型校验弱、调用体验差、复杂 DTO 无法表达
4工具名 snake_case + 动词前缀（create_/update_/delete_/enable_/disable_）复用 HTTP 路径路径名可读性差、不符合 MCP 工具命名约定
5复用 Service 事务/校验边界，Provider 只做协议适配在 Provider 补业务校验协议层变业务层 → 违反分层

三、核心技术点（带源码定位）

1. 双注解扫描（@RestController + @McpTool）

  • applicationContext.getBeansWithAnnotation(RestController.class) 拿到所有 Controller bean
  • 遍历 clazz.getDeclaredMethods()，只注册同时具备 @McpTool和任一 Spring 映射注解的方法
  • 关键文件：McpSpringToolProvider.java:51-69

2. 映射注解集合白名单

private static final Class<?>[] MAPPING_ANNOTATIONS = {
    GetMapping.class, PostMapping.class, PutMapping.class, DeleteMapping.class, RequestMapping.class
};

注意：@RequestMapping 也包含进来了 —— 因为类级 @RequestMapping 上仍可声明 method 级别的方法注解组合，老代码风格里有些写法走的是这个。

3. JSON Schema 自动生成（核心：DTO 字段展平）

  • @RequestParam → 直接转 schema property
  • @RequestBody DTO → 反射 DTO getDeclaredFields() 把字段展平到顶层 properties

为什么展平？MCP 工具调用的入参是扁平 Map&lt;String, Object&gt;，没有嵌套对象的"标准做法"。展平之后 LLM 的 tool 调用形态最自然。

4. 参数解析（双向转换）

  • 简单类型：convertType() 走字符串 → 目标类型转换
  • 请求体：MAPPER.convertValue(args, dtoClass) 把扁平 map 拼装成 DTO

5. Result&lt;T&gt; 统一解包

// Result.code == 0 返回 data，否则结构化错误
unwrapResult(result) → success: 业务数据 / fail: {code, message}

读写一致，LLM 调用方不用关心业务返回壳。

6. 审计日志：独立 logger + 结构化 JSON

private static final Logger AUDIT_LOG = LoggerFactory.getLogger("MCP_AUDIT");
// 字段：tool, caller, elapsedMs, success, error
  • 单独 logger 名 MCP_AUDIT，logback 里可单独输出文件，便于审计链路
  • 失败路径也走 finally 风格的 logAudit(success=false) —— 不能因为业务异常就丢审计

7. 鉴权传递（ThreadLocal 模式）

  • /mcp/* 路径走独立 Bearer Token Filter（既有）
  • 通过 McpCallerHolder ThreadLocal 把 caller 透传给 invoke 阶段
  • 注意：反射调用 Controller 是同步的，ThreadLocal 安全；如果未来切到异步要单独处理

四、生产级踩坑点（这一节是重点，看 commit 时间线就懂了）

主提交 13:12 落地 → 14:50 修复 → 15:48 又修复。三个小时连续两次 hotfix —— 每一次都是真实环境跑起来才发现的。

坑 1：DTO 字段名 ≠ JSON 字段名（commit 7446300）

症状：DTO 用了 @JsonProperty("dict_table_id") 把驼峰 dictTableId 映射成下划线，但 schema 生成时直接用了 field.getName() —— 结果 schema 里写的是 dictTableId，LLM 按 schema 传，反序列化时却找不到字段。

修复：

JsonProperty jp = field.getAnnotation(JsonProperty.class);
String fieldName = (jp != null && !jp.value().isEmpty()) ? jp.value() : field.getName();

经验：

  • 反射读字段名时永远要尊重 Jackson 注解
  • 风控后台老 DTO 大量用 snake_case，这个坑必踩
  • 类似的还有 @JsonAlias、@JsonNaming，本次只覆盖了 @JsonProperty，但 Guardians 项目里够用

坑 2：MCP 客户端把数组/对象当成 JSON 字符串传（commit 5201c29）

症状：DTO 字段是 List&lt;Long&gt; factors，但很多 MCP 客户端（包括 Claude/Cursor）会把它序列化成字符串"[1,2,3]" 塞进 JSON 顶层，因为它们对 schema 中嵌套类型的支持不一致。Jackson convertValue(map, dtoClass) 直接抛 Cannot deserialize value of type List from String。

修复：在 convertValue 之前加 preprocessListFields() —— 遍历 DTO 字段，遇到 List/Set/Map 类型且传入值是 "[" 或 "{" 开头的 String，先 MAPPER.readValue 解析成对象再放回。

boolean isList = List.class.isAssignableFrom(fieldClass) || Set.class.isAssignableFrom(fieldClass);
boolean isMap = Map.class.isAssignableFrom(fieldClass);
if (isList && !strValue.startsWith("[")) continue;
if (isMap && !strValue.startsWith("{")) continue;
Object parsed = MAPPER.readValue(strValue, javaType);  // javaType 来自 field.getGenericType()

经验：

  • LLM 工具调用的入参是"扁平化、字符串友好"形态，永远要假设嵌套结构会以字符串形式到达
  • 必须用 field.getGenericType() + MAPPER.getTypeFactory().constructType(...) 才能正确解出 List&lt;Long&gt; 这种带泛型的类型，光 field.getType() 拿到的是裸 List

坑 3：mapJavaTypeToJsonType 类型覆盖不全（同 commit 5201c29）

第一版只处理了 Integer/Long/Double/Float/Boolean/String，集合类全部 fallthrough 成 "string" —— 直接导致 LLM 看到 schema 把数组传成字符串（也就是坑 2 的诱因之一）。

修复：补 Short/Byte，补 List/Set/Array → "array"，补 Map → "object"。

经验：JSON Schema 生成器要把 Java 类型空间完整覆盖，schema 错一个字段，LLM 就会按错的形态传，踩坑成本是连锁的。

坑 4：写接口爆炸暴露的红线

设计阶段最重要的否决案：不要"扫到 POST 就自动暴露"。否则风控后台一堆内部接口（如 /import-from-excel、/sync-from-x）会瞬间出现在 MCP 工具列表里。

落地约束（tasks.md 2.1 / 2.7）：

  • 显式标注 @McpTool 才暴露
  • 手工 review 一遍规则上线/发布/审批接口，确认没标注
  • code review 时把 @McpTool 当成"对外暴露权限"来审

RuleController.java:42-47 里 update_rule_status 被注释掉了 —— 就是这个原则的实物：状态变更影响线上规则启停，先不开放。

坑 5：反射调用绕过 Spring MVC 全套机制

写接口反射调用时没有走 Spring MVC 的：

  • HandlerMethodArgumentResolver（参数解析器链）
  • @Valid / JSR-303 校验
  • HandlerInterceptor（拦截器链）
  • @ControllerAdvice 全局异常处理

所以 design.md 明确：业务校验必须在 Service 保证，Controller 上的 @Valid 在 MCP 调用路径下不生效。

经验：反射桥接是协议层，要么 Provider 自己补一遍，要么把校验下沉到 Service。本次选了后者 —— 简单、和 HTTP 调用路径行为一致。

坑 6：审计日志的失败路径

最容易写错的写法：

// ❌ 错误：抛异常时审计日志丢了
Object r = method.invoke(...);
logAudit(success=true);
return r;

正确写法在 McpSpringToolProvider.java:211-229：

try {
    Object result = method.invoke(bean, methodArgs);
    logAudit(toolName, caller, elapsed, true, null);
    return MAPPER.writeValueAsString(unwrapResult(result));
} catch (Exception e) {
    logAudit(toolName, caller, elapsed, false, e.getMessage());
    throw e;  // 必须 rethrow，否则 MCP 客户端拿不到错误
}

McpAuditLogTest.testAuditLog_WriteFail_ThrowsAndLogsError 专门覆盖这条分支。

坑 7：snake_case 工具名只 warn 不阻断

if (!SNAKE_CASE.matcher(toolName).matches()) {
    log.warn("[MCP] 工具名不符合 snake_case 规范: {}", toolName);
}

不抛异常 —— 因为做强校验意味着违规会启动失败。但 warn 也意味着没人盯启动日志就会漏。建议：CI 里加 grep [MCP] 工具名不符合 的扫描，或者直接 fail-fast。

坑 8：工具描述（description）是 LLM 调用质量的关键

看 RuleController.java:56-60 的 save_rule 描述：

包含规则名称、逻辑表达式(logic)、因子列表(factors)、绑定规则组ID等字段。

每条 description 都包含三段（tasks.md 3.2 校验项）：

  1. 用途（创建/更新/删除什么）

这是真正影响 LLM 工具调用准确率的地方 —— 字段名 LLM 能猜，但业务语义不写它就猜错（比如"id 存在表示更新"这种行业 convention）。

六、给学习者的总结清单

如果你正在做生产级 MCP 开发，按下面这个清单 self-check：

A. 协议适配层

  • schema 生成器是否覆盖了 Java 类型空间（含 List/Set/Map/Array/Short/Byte）
  • DTO 字段名是否尊重 @JsonProperty / @JsonAlias
  • 是否处理了 List/Map 字段以 JSON 字符串到达的情况（核弹级常见）
  • 泛型类型解析是否用了 getGenericType 而非 getType

B. 安全边界

  • 暴露策略是 白名单（标注） 还是黑名单（路径过滤）—— 必须白名单
  • 写接口是否有人工 review 流程
  • 是否有"绝对不暴露"清单（上线、发布、审批、删库等）
  • 鉴权是否走独立 Filter（不是 controller 层）

C. 可观测性

  • 审计日志是否独立 logger，便于切文件
  • 失败路径（抛异常）是否仍记录审计
  • 字段是否结构化 JSON，包含 tool/caller/elapsed/success/error
  • caller 透传机制（ThreadLocal）是否在异常路径清理（McpCallerHolder.remove()）

D. 业务一致性

  • 反射调用是否绕过 Spring MVC（一定会绕过），校验是否下沉到 Service
  • 是否复用既有 Controller→Service 路径，不直连 Mapper
  • Result&lt;T&gt; 等统一返回壳是否在 Provider 解包

E. 工具描述质量

  • description 是否包含 用途 + 关键参数 + 返回要点
  • 工具名是否 snake_case + 动词前缀（create_/update_/delete_/list_/get_/enable_/disable_）
  • 业务 convention（如"id 存在表示更新"）是否在 description 里说明

F. 测试覆盖

  • 注册：标注 → 注册 / 未标注 → 不注册
  • 参数：@RequestParam 简单类型 / @RequestBody DTO 转换
  • schema：DTO 字段是否完整出现
  • 兼容性：扩展写接口后读接口行为不变
  • 审计：成功路径 / 异常路径 都覆盖

附录 A：部署级踩坑 —— Streamable HTTP 多副本下的握手 404

这是代码层之外的另一类生产级坑：代码全对，curl 也能 200，但 MCP 客户端就是连不上。原因藏在"应用层有状态 + 基础设施层无粘性"的错配里。

1. 现象（Symptom）

guardians-mcp: https://guardians.pt.xiaomi.com/mcp/guardians/mcp (HTTP) - ✗ Failed to connect

但是直接 curl 打 initialize 是 200，业务 token、网络、URL 都正常 —— 看起来"通了一半"。

2. 诊断证据

按 MCP Streamable HTTP spec 完整跑一遍三步握手：

#请求结果x-proxy-node（MonKing 网关返回的后端节点 ID）
----
1initialize200 ✓，下发 Mcp-Session-Id: c53a446b...F9E7E168E1157F1D
2notifications/initialized（带上面的 sessionId）404 ✗ Session not found: c53a446b...F96A40989A462E15
3tools/list（带 sessionId）200 ✓（但跑到了又一个节点）F96A40989A462E15

关键观察：每次请求的 x-proxy-node 都不一样。

3. 根因（Root Cause）

3.1 MCP Streamable HTTP 的两种工作模式

MCP 在 2025-03-26 spec 之后用 Streamable HTTP 替代了老的 SSE transport，服务端实现可以选两种模式：

  • STREAMABLE（有状态）：服务端给每个客户端分配 Mcp-Session-Id，session 状态（initialize 协商结果、订阅、长任务、SSE 流）保存在该实例的内存里。后续所有请求必须回到同一个进程才能找到 session。
  • STREAMABLE_STATELESS（无状态）：服务端不保存 session，每个请求都是独立、自包含的；客户端发的 Mcp-Session-Id 头被忽略或仅作为 trace。

3.2 出问题时的部署形态

guardians-mcp 服务端跑的是 有状态 模式，但前面挂的 MonKing 网关 + 多副本部署：

        Client (Claude Code)
                |
                v
      MonKing/3.14 网关（无 sticky session）
         /        |        \
    Pod A      Pod B      Pod C
   session=     (空)        (空)
   c53a446b

握手流程：

  1. initialize → 网关随机路由到 Pod A，A 创建 session 存到自己内存里，把 Mcp-Session-Id 返给客户端。
  2. 客户端按 spec 立刻发 notifications/initialized，带上同一个 sessionId → 网关又随机路由到 Pod B，B 内存里没有这个 session → 404 Session not found。
  3. Claude Code 的 MCP 客户端把这一步的 404 当成致命握手失败 → 整个 MCP server 标记为 Failed to connect。

为什么 tools/list 反而能跑？因为该 endpoint 的实现没强校验 session 存在，走的是无状态分支 —— 所以 curl 看着部分能用，迷惑性很强。

3.3 一句话定性

"应用层有状态 + 基础设施层无粘性" 的经典错配。Session 是 in-process 的，但负载均衡按请求级别打散了流量，导致除第一个请求外的所有 follow-up 都路由到没有 session 的兄弟实例。

4. 修复（Fix）

切换到 STREAMABLE_STATELESS 模式。

4.1 为什么这样能修

无状态模式下，服务端根本不再依赖 sessionId 找上下文：

  • 每个 JSON-RPC 请求都自带完整入参
  • initialize 和后续 call 之间没有内存级关联
  • 任何 pod 都能独立处理任何请求 → 网关怎么打散都不影响正确性

notifications/initialized 在无状态模式下要么直接 200/204，要么被忽略，不会再因为"找不到 session"而 404，握手就能跑完。

4.2 修复链路对比

层级修复前修复后
---
MCP 客户端按 spec 发 sessionId一样（无影响）
网关无 sticky无 sticky（没改）
服务端有状态，session 在 pod 内存无状态，不存 session
多副本一致性❌ 失败✅ 通过

注意网关侧没动 —— 修的是应用层，把"对基础设施的隐式假设（粘性路由）"消除了。这是更稳的修法。

5. 取舍（Trade-offs）

切到 STREAMABLE_STATELESS 不是没代价：

能力有状态模式无状态模式
---
tools/list、tools/call 等纯 RPC✓✓
服务器主动推送（notifications/* from server）✓（通过持久 SSE 流）✗ 或受限
resources/subscribe 订阅资源变更✓✗
长任务的进度回调✓✗
LLM sampling 反向请求✓✗
需要跨调用记忆的工具状态✓必须落外部存储（Redis/DB）

幸运的是 guardians-mcp 暴露的是一批纯 CRUD 风格的工具（list_* / get_* / save_* / query_*），全部是请求-响应一次完事，没有用到订阅/推送，所以无状态化对功能 0 影响。

6. 长期建议

如果以后要恢复有状态能力（比如做 resource subscription），有几个选项：

  1. 网关做 sticky：MonKing 按 Mcp-Session-Id header 做 consistent-hash 路由 —— 改基础设施，对应用透明，但跨节点重启时 session 会失效。
  2. session 状态外置：把 session 元数据（initialize 协商结果、订阅列表）写 Redis，pod 变成无状态，请求随便路由都能恢复 session —— 这是公认更稳的工业级做法。
  3. 混合模式：纯 RPC 工具走 stateless 端点，需要订阅/推送的工具走带 sticky 的 stateful 端点。

短期 stateless 是最优解，长期如果有订阅需求，推荐方案 2。

7. 上线 checklist 沉淀

服务端从单实例升级到多副本时，一定要复测 MCP handshake 第二步 notifications/initialized —— 这是最容易"过 curl 测试但过不了真实客户端"的检测点。

具体怎么测：

  • 不要只测 initialize + tools/list：很多人这两步都能 200 就以为通了，但客户端真正的握手包含 notifications/initialized，curl 默认不发
  • 必须用真实 MCP 客户端测（Claude Code / Cursor / mcp-inspector），或脚本严格按 spec 三步顺序发
  • 观察响应头里的后端节点 ID（公司网关一般有 x-proxy-node 之类）—— 如果三个请求落在不同节点 + 服务端是有状态模式 = 一定挂
  • 发布时灰度一台 pod 单独跑，先验证客户端连得上，再扩副本 —— 避免"单实例时跑得好好的，扩到 3 副本就连不上"
  • 健康检查别只查 /health：要把 notifications/initialized 这一步也纳入冒烟测试
  • 如选 stateless 模式，CI 加一条 case：模拟客户端把 Mcp-Session-Id 换成乱写的字符串，期待服务端依旧 200（验证不依赖 session）

→ server 已经声称支持 2025-06-18 spec，但实际只填了一半字段。

3. 根因（Root Cause）

3.1 MCP spec 2025-06-18 关于 ToolResult 的关键变化

老 spec（2024-11-05）的 CallToolResult：

{ content: ContentBlock[], isError?: boolean }

LLM 友好但机器不友好——结果都塞在 content[0].text 里需要 client 二次 JSON.parse。

新 spec（2025-06-18）补了 structuredContent：

{
  content: ContentBlock[],          // 给人 / LLM 看的文本表示（保留）
  structuredContent?: object,       // 新增，机器直接消费的结构化数据
  isError?: boolean
}

spec 推荐 server 两边都填：content[0].text = JSON.stringify(data)，structuredContent = data。

3.2 部分新客户端的偏好读取

Claude Code、某些 Cursor 版本、新版 mcp-inspector 等，优先读 structuredContent：

  • 如果非空 → 直接当返回值用
  • 如果是空 {} → 不再回退读 content，直接给上层返回 {}

老客户端（mcp-inspector v1、早期 Cursor）只读 content[0].text，所以在新坑出现前完全感知不到。

3.3 guardians-mcp server 这一侧

按本文第三节第 5 条提到的 unwrapResult 流程：

// McpSpringToolProvider.java:211-229（推测）
Object data = unwrapResult(result);
return MAPPER.writeValueAsString(data);  // 只写成字符串

framework 把这个字符串塞进 content[0].text，但没有同时填 structuredContent。spec 2025-06-18 兼容性失败。

3.4 一句话定性

"升级了 protocolVersion 但没升级 ToolResult builder" 的经典错配。声称我会说新版英语，但实际只填了老语法字段——curl 看不出，新客户端一开口就懵。跟附录 A "应用层有状态 + 基础设施层无粘性"是同一类错配，都是"我说我是 X，但行为还是 Y"。

4. 修复（Fix）

4.1 server 端双写（最优方案）

McpSpringToolProvider.invoke() 改：

try {
    Object result = method.invoke(bean, methodArgs);
    Object data = unwrapResult(result);                     // 业务数据（List/Map/POJO）
    String json = MAPPER.writeValueAsString(data);          // 字符串表示
    logAudit(toolName, caller, elapsed, true, null);

    return CallToolResult.builder()
        .addContent(TextContent.of(json))                    // 老字段：兼容老客户端
        .structuredContent(data)                             // 新字段：spec 2025-06-18+
        .build();
} catch (Exception e) {
    logAudit(toolName, caller, elapsed, false, e.getMessage());
    throw e;
}

注意点（按本文坑 6 那条精神）：

  • failure 路径同样要符合新 spec：抛错走 isError = true + 双写 error message
  • structuredContent 必须是 object 不是 array — spec 2025-06-18 限定 root 必须是 object/dict。如果业务数据是 list（[{...}, {...}]），要包一层：structuredContent: { items: [...] }
  • 关于 root-must-be-object 这点 spec 有明文，list_events / list_rules 这种返回是数组的工具，包 wrapper 比直接塞 list 更稳

4.2 同步 outputSchema（spec 2025-06-18 配套字段）

spec 同步引入了 Tool.outputSchema：声明 structuredContent 的 JSON schema。让客户端能 typed 解析。

// 注册工具时同时声明输入 + 输出 schema
@McpTool(
    description = "...",
    outputSchema = "{type:'object',properties:{items:{type:'array',items:{...}}}}"
)

没有 outputSchema 客户端只能拿 raw object。短期不做也能跑，长期 LLM 调用质量更好。

4.3 测试层加一条 case（按本文第六节 F 的 self-check 风格）

@Test
void invoke_listEvents_StructuredContentNonEmpty() {
    CallToolResult r = provider.invoke("list_events", Map.of(), caller);

    // 老字段必须有
    assertNotNull(r.getContent());
    assertFalse(r.getContent().isEmpty());

    // 🔥 新字段必须有，spec 2025-06-18 兼容性回归
    assertNotNull(r.getStructuredContent());
    assertNotEquals(Map.of(), r.getStructuredContent());

    // 两边内容一致性
    String contentText = ((TextContent)r.getContent().get(0)).getText();
    Object expected = MAPPER.readValue(contentText, Object.class);
    assertEquals(expected, r.getStructuredContent());
}

5. 取舍（Trade-offs）

升级到双写不是没代价：

维度单写 content（现状）双写 content + structuredContent
---
老客户端兼容（mcp-inspector v1 / 早期 Cursor）✓✓
新客户端兼容（Claude Code 当前版本）✗（拿 {}）✓
网络包体积小翻倍（数据冗余）
schema 定义工作量0每个工具加 outputSchema
spec 合规度半合规全合规

体积翻倍这一点对 list_event_fields（12KB）这类大返回有 latency 影响，但对 LLM 调用频率（每秒最多几次）完全可接受。

6. 上线 checklist 沉淀

每次升级 protocolVersion 声明值，必须同步审计 ToolResult / Tool / Notification 等所有 spec 类型的字段变化 —— 这是最容易"声称支持但实际半合规"的检测点。

具体怎么做：

  • 不要只跟着 framework 升 spec 版本号：framework（Solon MCP / Spring AI MCP）默认 builder 行为可能滞后于最新 spec，盲升 version 号不等于真合规
  • 必须用真实 MCP 客户端测各代版本：至少覆盖 Claude Code（最新）+ 早期 Cursor（最老）+ mcp-inspector（参考实现）三种，验证字段读取行为
  • CI 加"字段对照"回归 case：spec 升级时把新增/变更字段全部加 assertion，避免 ToolResult builder 只填一半
  • server 端 ToolResult 构造逐字段对照 spec，不依赖 framework 的"看起来对"
  • 监控 structuredContent 为空的工具调用比例：如果 > 0 且 server 声称 protocolVersion ≥ 2025-06-18，就是合规漏洞信号
  • 观察用户反馈："server 显示 connected 但工具调用拿不到数据"是这类坑的高敏信号词，应触发立即排查

7. 把这个坑映射回前面的 self-check

第六节"给学习者的总结清单"补一类 H. 协议版本兼容：

  • server 在 initialize 响应里声称的 protocolVersion 是哪个？（2024-11-05 / 2025-03-26 / 2025-06-18 / 更新）
  • 是否每次 spec 升级都同步审计了 ToolResult / Tool / Notification 等类型的字段变化？
  • 真用过 Claude Code / 最新 Cursor / 最新 mcp-inspector 三个不同客户端测过同一批工具？（仅一种客户端测试 = 协议版本兼容性盲区）
  • CI 里是否覆盖了 "structuredContent 必须非空 + 与 content 数据一致" 的回归 case？
  • server 端 ToolResult builder 是不是逐字段对照 spec 而不是依赖 framework 默认行为？（Solon MCP / Spring AI MCP 等 framework 的默认 builder 行为可能滞后于最新 spec）

8. 一句话回答

"为啥 server 一切 OK + curl 一切 OK + Python SDK 一切 OK，唯独 Claude Code 调用拿到 {}？"

因为 spec 2025-06-18 把"机器可读的结构化数据"从 content[0].text 抽到了独立的 structuredContent 字段，server 升级了 protocolVersion 声明但没升级 ToolResult 构造，新版 client 看到空 structuredContent 不再回退读 content —— spec 字段错配。

发现链路：2026-05-19 用 guardians-mcp 跑黑产挖掘 demo 时主对话拿 {} → 用 Python SDK 直连验证 server 真返回 ✅ → 抓 ToolResult 字段层定位到 structuredContent 空 → 复盘成文。
