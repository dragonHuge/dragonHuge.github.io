《AI时代的架构设计100讲》 第7讲：无锁缓存

AI时代，架构设计变了吗？架构师的职责变了吗？准备新起一个AI时代的架构设计系列，初定100讲，每周更新2-3讲，这是第7讲。

前两讲，聊了AI缓存的操作模式（Cache Aside）和AI补偿（binlog二次淘汰）。这一讲，聊缓存的另一个问题：超高并发下，缓存自身的访问性能——以及，无锁缓存这种带权衡的代码，怎么让AI写对。老规矩，先搞清楚方案本身，再说spec的事。

什么样的业务场景，有这类架构需求呢？

  1. 超高吞吐量，每秒要处理海量请求；
  2. 写多读少，大部分请求是修改数据，少部分请求是读取数据。

举个栗子，快狗打车的司机信息读写：

  1. 司机地理位置随时变化，可能每几秒就要修改一次；
  2. 用户打车时查看司机位置，查询频率相对较低。

这里用到两个接口：

大量修改司机信息：

void SetDriverInfo(long driver_id, DriverInfo info)；

相对少量查询司机信息：

DriverInfo GetDriverInfo(long driver_id)。

这一类业务，底层实现往往是一个Map内存缓存：

  1. 查询key定长，例如司机ID；
  2. 返回value也定长，例如司机实体序列化后的二进制串。

也就是类似这样的一个kv缓存结构：

Map<driver_id, DriverInfo>。

对这个kv缓存并发访问，有什么注意事项？

这个kv内存缓存是一个临界资源。临界资源的并发访问，要注意加读写锁，实施互斥。

加锁写入的伪代码：

void SetDriverInfo(long driver_id, DriverInfo info){
WriteLock(m_lock);
Map<driver_id> = info;
UnWriteLock(m_lock);
}

画外音：假设info已经序列化。

加锁读取的伪代码：

DriverInfo GetDriverInfo(long driver_id){
DriverInfo t;
ReadLock(m_lock);
t = Map<driver_id>;
UnReadLock(m_lock);
return t;
}

吞吐量很高时，会有什么问题？

假设快狗打车有100w司机同时在线，每个司机每5秒更新一次经纬度，那么每秒就有20w次写并发。

假设日订单1000w个，平均每秒大概300个下单，对应到查询，大概是每秒1000级别的并发读。

在这样的吞吐量下（每秒20w写、1k读），锁m_lock会成为潜在瓶颈，导致Map访问效率极低。

如何降低锁冲突？

锁冲突之所以严重，是因为整个Map共用一把锁，粒度太粗。

画外音：可以认为是一个数据库的"库级别锁"。

可以水平拆分，把1个Map切分成N个Map：

void SetDriverInfo(long driver_id, DriverInfo info){
i = driver_id % N; // 水平拆分成N份，N个Map，N个锁
WriteLock(m_lock[i]); // 锁第i把锁
Map[i]<driver_id> = info; // 操作第i个Map
UnWriteLock(m_lock[i]); // 解锁第i把锁
}

画外音：类似于数据库的分库，一个库锁变多个库锁。

如此优化，能否提高性能？

  1. 一个Map变成N个Map，每个Map的并发量变成1/N；
  2. 同时，每个Map的数据量也变成1/N。

理论上，锁冲突会呈平方级降低，性能提升。

锁粒度，还能再细吗？

能。一个元素一把锁。

画外音：相当于从"库级别锁"，优化为"行级别锁"。

不妨设driver_id是递增生成的，并且假设内存足够大。此时可以把Map优化成Array，锁粒度细化到最细——每个司机信息一把锁：

void SetDriverInfo(long driver_id, DriverInfo info){
index = driver_id;
WriteLock(m_lock[index]); // 超级大内存，一条记录一个锁，锁行锁
Array[index] = info; // driver_id就是Array下标
UnWriteLock(m_lock[index]); // 解锁行锁
}

这个方案锁冲突降到最低，但锁资源大增。数据量非常大时，内存往往装不下。

画外音：数据量比较小的时候，可以一个元素一把锁。典型的是连接池，每个连接一把锁，表示连接是否可用。

还有没有办法，进一步降低锁冲突？

写多读少的业务，还有一种方案：无锁缓存，把锁冲突降到零。

无锁缓存，可能存在什么问题？

缓存不加锁，读写吞吐量可以达到极限。但是，多线程对缓存中同一块定长数据并发写时，可能出现不一致的脏数据。这个方案为了提高性能，牺牲了一致性。

读取时获取到错误的数据，是不能接受的。

画外音：作为缓存，允许cache miss，却不允许读脏数据。

脏数据，是如何产生的？

不加锁，多线程并发写时，可能出现这种情况：

  1. 线程1对缓存操作，对key想写入value1；
  2. 线程2对缓存操作，对key想写入value2；
  3. 不加锁，两个线程对同一个定长区域并发写，可能各写成功一半——最终结果既不是value1也不是value2，而是一个乱七八糟、不符合预期的value-unexpected。

脏数据问题，怎么解决？

本质上，这是一个数据完整性问题。并发写入的分别是value1和value2，读出的是value-unexpected。数据被篡改了，本质是数据完整性问题。

通常，如何保证数据完整性？

例如：运维如何保证，从中控机分发到上线机的二进制没有被篡改？md5。

又例如：即时通讯中，如何保证接收方收到的消息，就是发送方发出的消息？发送方除了发送消息本身，还要发送消息的签名；接收方收到后校验签名，确保消息完整、未被篡改。

"签名"，是常见的保证数据完整性的方案。

加入签名之后，读写流程要如何升级？

加上签名之后，缓存不但写入定长value本身，还要写入定长签名（例如16bit CRC校验）：

  1. 线程1对key想写入value1，写入签名v1-sign；
  2. 线程2对key想写入value2，写入签名v2-sign；
  3. 不加锁并发写，可能各写成功一半，结果仍是value-unexpected——但签名，一定是v1-sign或v2-sign中的一个；
  4. 读取时，不但取出value，还要像消息接收方一样校验签名。签名不一致，缓存返回NULL，即cache miss。

画外音：16bit/32bit的写，可以保证原子性。

当然，对应到司机地理位置，除了内存缓存，还需要timer对缓存数据定期落盘、写入数据库。cache miss时，从数据库读取。

那么问题来了，到了AI时代，这套无锁+签名的方案，spec该怎么写？

先说结论：思路没变，执行者变了。

没变的部分：签名是无锁方案的前提——省掉签名，就会读到脏数据。这不是性能优化空间，是正确性底线。这个判断，和是不是AI写代码，没有关系。

** **

变了的部分：并发与权衡的实现细节，我们不再逐行写了。我们干的活，是把设计约束写成spec，让AI按spec去实现。前两讲聊过spec的四件事，不重复论证，今天直接给一份能用的。

** **

一份无锁缓存的spec，至少写清四件事：

  1. 模式声明；
  2. 红线约束；
  3. 异常与降级；
  4. 验收标准；

spec示例（md格式），可以直接复制：

# 无锁缓存实现spec ## 模式声明 无锁缓存+签名完整性校验。 1. 写：写入定长value + 定长签名16bit CRC； 2. 读：取出value和签名，校验通过返回value. 不一致返回NULL（cache miss，正常语义，不是错误）。 ## 红线约束 1. 禁止省略签名校验流程； 2. 签名必须定长，位宽16bit CRC，保证原子写； 3. 校验不一致只返回NULL，禁止抛异常。 ## 异常与降级 1. cache miss时，回源数据库读取； 2. 后台timer定期将缓存数据落盘到数据库； 3. 签名不一致率纳入监控，突增时告警。 ## 验收标准 1. 并发写压测下，读到的要么是某个完整写入值，要么是NULL； 2. 写多读少场景（20w写/1k读）吞吐达标； 3. 签名不一致有计数日志，可查询、可统计。

这四件事写清楚，AI输出的无锁缓存代码，大概率是靠谱的。

总结

业务场景：超高并发、写多读少、定长value。提升吞吐量的思路：

  1. 水平拆分降低锁冲突：单库变多库；
  2. Map转Array最小化锁冲突：库锁变行锁；
  3. 无锁最大化并发：行锁变无锁——完整性与性能的折衷；
  4. 签名保证数据完整性：写时写签名，读时校验签名；
  5. AI时代，方案写成spec：红线防AI把签名"优化"掉。

知其然，知其所以然。

思路比结论更重要。
