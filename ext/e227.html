来源：飞书 归档日期：2026-05-19 抓取状态：成功 原文字符：1884｜配图：0 张

摘要速览

  • MCP 是什么：一个协议，为大型语言模型（LLMs）应用提供标准化接口，使其能连接和交互外部数据源与工具
  • 三种通讯模式：STDIO（本地进程级通信，绝对安全）、SSE（单向流式 HTTP，已弃用）、Streamable HTTP（双向流式，官方推荐，云原生友好）
  • SSE 被弃用的原因：SSE 长连接下 Server 无法感知数据丢失，网络波动时数据直接丢且无法恢复；Streamable HTTP 用"块级序列号 + 客户端重连续传（resume_seq）"机制解决
  • Java 开发最小栈：JDK >= 17 + Spring Boot >= 3.2 + Spring AI（spring-ai-mcp-server-spring-boot-starter）
  • 核心注解 @Tool：将 Java 方法标记为可被 LLM 调用的工具函数，description 是模型判断何时触发调用的关键
  • 完整调用链路 5 步：Java 方法注册为 JSON Schema → 客户端获取工具清单 → LLM 语义匹配 description 决策调用 → 客户端通过 JSON-RPC 执行 Java 方法 → 结果回传融入对话
  • STDIO 模式必须关 web：web-application-type: none，否则 Tomcat 默认占端口导致启动失败
  • Agent 不是万能的：本质是概率游戏，最优策略是 Agent 与工程结合使用、扬长避短，方向不对及时更换

Server 配置

  1. Pom:

```XML <parent> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-parent</artifactId> <version>3.4.3</version> </parent> <dependencies> <dependency> <groupId>org.springframework.ai</groupId> <artifactId>spring-ai-mcp-server-spring-boot-starter</artifactId> <version>${1.0.0-M6}</version> </dependency> </dependencies> ```

  1. application.yml

```TypeScript spring: main: web-application-type: none # 必须关 web banner-mode: off ai: mcp: server: stdio: true # 本地调试用，因此开启stdio模式。 name: mcp-server version: 0.0.1 ```

为何必须关闭web模式呢？ 答：因为 Spring Boot 默认会启动内嵌 Web 容器（Tomcat/Netty），即使你没有任何 Controller，也会： 1. 申请端口（默认 8080 或配置值）。 2. 占用系统端口资源 → 如果端口被占或配置为 0，直接抛 PortInUseException/IllegalArgumentException，导致整个 Spring 上下文启动失败。 把 web-application-type: none 就是告诉框架："别给我起 Web 容器，我只做纯 CLI（STDIO MCP Server）。" 因此 必须关 web，否则若 端口冲突 → 启动失败。

核心注解 @Tool

作用：将普通 Java 方法标记成「可被 AI 大模型调用的工具函数」，让大模型在对话里自动识别并执行它。

通俗理解："给 @Tool 写一句口语化描述(description)，模型就能根据提示里的同义词自动触发 MCP 调用。"

示例：

@Component
public class MoodTool {
@Tool(
    name        = "moodImprove",               // 工具名（默认方法名）
    description = "根据人物心情，返回安慰语" )     // 关键！模型用这句话决定何时触发public 
    public String moodImprove(String mood) {
        return "不要再"+ mood + "啦！小龙祝你一路暴富！事业长虹！永远年轻！";
    }
}

将Tool注册到MCP Server

把带有 @Tool 注解的类"注册"到 MCP Server，让大模型真正能够发现并调用这些工具方法。

@Configuration
public class McpConfig {
    @Bean
    public ToolCallbackProvider tools(WeatherTool tool) {
        return MethodToolCallbackProvider.builder()
                .toolObjects(tool)
                .build();
    }
}

在客户端使用MCP Tool

在Cherry Studio等客户端使用MCP时，需要进行两方面的配置。

  1. 客户端环境配置，详情参考官网：https://docs.cherry-ai.com/advanced-basic/mcp/config
  2. MCP server配置，参考如下。
{ // 服务配置
  "mcpServers": {
    "mcp-sxl-server": {
      "command": "/opt/homebrew/opt/openjdk@17/bin/java",
      "args": [
        "-Dspring.ai.mcp.server.stdio=true",
        "-Dspring.main.web-application-type=none",
        "-Dlogging.pattern.console=",
        "-jar",
        "~/IdeaProjects/sxl-mcp/mcp-server/target/mcp-server-1.0-SNAPSHOT.jar"
      ],
      "env": {
        "PATH": "/opt/homebrew/opt/openjdk@17/bin"
      }
    }
  }
}

要点解释：
1.command：定义启动服务的可执行文件路径，这里指定的是 Java 可执行文件的位置：表示使用本地安装的 OpenJDK 17 版本来运行后续的 Java 程序（.jar文件）。
2.env：定义启动服务时的环境变量，这里只配置了PATH：确保启动服务时，系统能在指定路径下找到 Java 相关的可执行文件（与command中的 Java 路径呼应，避免因环境变量问题导致找不到 Java 命令）。

三、原理拓展

大模型如何识别 并 使用MCP Tool？

一句话总结： 大模型自己并不会直接"识别" Java 方法，而是靠 MCP 运行时，把 "1个Tool" 包装成一条 "工具清单"。 当用户提问触发条件时，客户端先让大模型"看见"这条工具，再由客户端反向调用你的 Java 方法，把结果回传给模型。

角色承担任务
--
Java 方法提供业务逻辑
Spring AI + MCP Server把方法转成JSON Schema、反序列化参数、执行方法。
大模型只负责"判断何时调用"以及"把结果融入自然语言"。
客户端负责连接、转发、回传

以本文代码为例，将完整链路拆开研究：

  1. MCP Server启动后：ToolCallbackProvider 会把所有带 @Tool 的方法转成 JSON Schema 并 注册到 MCP Server：

```JSON { // MCP在"tools"阶段返回的工具清单 "tools": [{ "name": "moodImprove", "description": "根据人物心情，返回安慰语", "inputSchema": { "type": "object", "properties": { "mood": { "type": "string" } }, "required": ["mood"] } }] } ```

  1. 客户端拿到所有Tool Schema：将MCP注册到Cherry Studio、Claude Desktop等客户端之后，这些客户端会拿到MCP Server中所有Tool的 JSON schema。
  2. 大模型决定是否调用MCP Tool。此时当大模型看到有用户情绪词 "沮丧"，并且 与moodImprove Tool中"根据人物心情，返回安慰语"的description匹配成功。于是大模型决定调用moodImprove Tool，最后返回一个 工具调用指令：

```JSON { "type": "tool_call", "name": "moodImprove", "arguments": { "mood": "沮丧" } } ```

  1. 客户端反向调用Java 方法客户端收到工具调用指令后，通过 STDIO/SSE 向 MCP Server 发请求，JSON-RPC 2.0 规范的请求：Spring AI 的 McpToolCallback 把 {"mood":"沮丧"} 反序列化成 String mood 参数，真正执行Java方法：

```JSON { "method": "tools/call", "params": { "name": "moodImprove", "arguments": { "mood": "沮丧" } } } ```

```Java moodImprove("沮丧") → return "不要再沮丧啦！小龙祝你一路暴富！..." ```

  1. 结果回传，大模型继续对话

```JSON { "params": { "mood": "糟糕" }, "response": { "content": [ { "type": "text", "text": ""不要再糟糕啦！小龙祝你一路暴富！事业长虹！永远年轻！"" } ], "isError": false } } ```

什么是MCP？ 答：一个协议，旨在为大型语言模型（LLMs）应用提供一个标准化的接口，使其能够连接和交互外部数据源和工具。

一、MCP 三种通讯模式

请跳转：AI 发展-自顶向下的MCP模块，这里不再做MCP的详细介绍。

MCP目前有以下三种通讯模式。

通讯模式特点通俗理解
---
STDIO (Standard Input/Output)标准输入输出，进程级通信，本地运行。适合开发者。Mcp Client和Mcp Server部署在同一台机器上，通过标准输入输出通信的方式就是STDIO模式。因为在本地运行，是绝对安全的；
SSE (Server-Sent Events)单向流式 HTTP传输，浏览器/远端都能连，适合生产发布。服务端通过SSE主动推送数据，客户端通过HTTP POST发送请求。部署在不同机器，通过Http请求通信，就是SSE模式和StreamableHttp模式。若暴露连接方式，可能会有安全问题。
Streamable Http ⭐️双向流式 HTTP传输，官方最新推荐，云原生友好。部署在不同机器，通过Http请求通信就是SSE模式和StreamableHttp模式。（同上）
Studio 模式可视化客户端。官方文档里并没有叫 Studio 模式 的术语，社区一般把 Cherry Studio等带 GUI 的客户端统称为 "Studio 模式"，与之对应的是 纯命令行/代码级 的 STDIO 模式。

2025.03.26,Anthropic在MCP规范中正式弃用SSE传输，全面转向StreamableHttp。为什么？ 答： SSE的原理是MCP Client与MCP Server通过HTTP建立SSE长链接，之后MCP Server就可以不断向Client发送数据，而不需要每次都进行三次握手，而MCP Client可以主动关闭SSE长链接。 问题就在于：SSE传输的MCP Server无法感知到数据的丢失。整个通讯过程都需要依赖SSE长链接，一旦出现网络异常波动（短暂中断），那么MCP Server向MCP Client发送的数据就会丢失，并且MCP Server无法感知到丢失的发生。 而StreamableHttp 模式中，MCP Server可以感知到数据丢失，连接恢复时可以持续地将没有发送给MCP Client的数据再次发送，保证长链接的高可用性。

那么在Streamable Http中，是如何感知到数据丢失的？ 答： 在 StreamableHttp中，数据丢失通过 "块级序列号 + 客户端重连续传" 机制来感知与修复，核心流程如下： 1. 服务端打标：每条数据块下发前由 MCP Server 生成 全局递增序列号 seq 或 时间戳 ts，随块一起发给客户端。 2. 客户端记录：客户端维护 last_ack_seq（或 last_ack_ts），表示已成功接收到的最新块。 3. 断线重连续传：当连接因网络异常断开时，客户端重新发起 GET /stream?resume_seq={last_ack_seq}，服务器根据 resume_seq 跳过已发块，只发送 未确认数据。 4. 零感知恢复：客户端收到 不连续 seq 即可立即判定"丢失"，并触发重连续传；整个过程对业务代码透明。 一句话总结："StreamableHttp 用序列号标记块，断线后 resume_seq 续传，客户端靠 seq 不连续 感知并自动补全数据。"
