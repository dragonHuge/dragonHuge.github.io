摘要 知识库答不准，很多人第一反应是换模型、换嵌入，却忽略了最前面那一步：PDF 被解析成了乱码和串行的表格，后面怎么调都是垃圾进垃圾出。IBM 开源的 Docling（约 66.6K star）用一条可插拔的解析流水线加一套结构化文档格式来解决这件事。这篇讲清它的机制、上手路径，以及一个容易踩的许可证陷阱。

你有没有遇到过这种情况：知识库明明灌了几百份文档，问它一个表格里的数字，它一本正经地答错。

然后你开始怀疑模型不行，换了个更大的；再怀疑向量库不行，又换了一个。折腾一圈，效果还是那样。

问题很可能在最前面那一步——文档解析。错乱的表格、串行的公式、颠倒的阅读顺序、双语混排的乱码，一旦在解析阶段变成"文字垃圾"，后面所有优化都无事无补。

这就是 Docling 要解决的事。它由 IBM Research Zurich 发起，现在由 Linux 基金会托管（LF AI & Data，并已捐赠给 Agentic AI Foundation），MIT 协议。截至 2026 年 9 月，这个仓库约 66.6K star、最新版本 v2.128.0（2026 年 9 月 16 日发布）。从 2025 年 8 月首次公开发布到现在，它已经发了 100 多个版本。

负责这个项目技术方向的 Peter Staar 是 IBM Research Zurich 的首席研究科学家，也是 Linux 基金会 Docling 技术指导委员会主席。他说过一句挺实在的话："这能有多难？嗯，可以非常难。"

多格式输入 → Docling 统一解析 → 结构化输出，可直接接进 GenAI 应用

它怎么做的：一条可插拔的四段流水线

Docling 和"OCR 取字"的工具在路子上完全不同。它把解析拆成四个阶段：

版面检测 → 区块分类 → 阅读顺序 → 内容识别

关键在"可插拔"这三个字：每个阶段可以单独换引擎、可以只跑其中几段、也可以用不同模型处理同一阶段——纯规则引擎能跑，VLM（视觉语言模型）也能跑。

还有两个工程上的取舍值得注意：

• 数字版 PDF 直接读文本层，不走 OCR。又快又准，省下的算力留给真正需要的地方。扫描件才启用 OCR。

• 表格结构交给 IBM 自研的 TableFormer。这是它相对强的一项，金融类表格尤其吃得住。

按技术报告里的说法，版面分析模型是个基于 RT-DETR 改进的目标检测模型，表格结构模型则是 TableFormer。流水线把页面按 72 dpi 渲染后再做识别——这个分辨率低到单颗 CPU 就能跑到亚秒级延迟，这也是它敢说自己"CPU 友好"的底气。

架构：可插拔的 Pipeline → DoclingDocument → 多种导出与切块器

真正的差异化：输出的不是 Markdown

这一点是 Docling 和其他解析工具最本质的分界。

多数工具输出的是一段 Markdown 字符串。Docling 输出的是一个对象——DoclingDocument，每个元素都带类型（标题 / 段落 / 表格 / 图 / 公式 / 图注）、页码、坐标框（bbox）和章节路径。

文档被解析成的层级结构（一）

文档被解析成的层级结构（二）

这个差别在落地时会立刻显现出来：

有坐标，才能做溯源

用户问"这个数字哪来的"，你可以直接高亮原文那一块，而不是让模型自己编一个出处。

有层级，才能正确切块

它自带的 HybridChunker 会保护表格不被切断、按章节分割、保留标题路径元数据。这一点比想象中重要——很多 RAG 效果差，不是解析精度不够，而是按固定 token 数盲目切块，把一张表劈成两半、把标题和正文割裂。

有专门格式，才能对接专业场景

除了 Markdown、HTML、无损 JSON，它还能导出 DocLang、DocTags，以及 USPTO 专利、JATS 学术文章、XBRL 财务报告这几种行业 XML 规范。

元素级的置信度评分

它真正想做的，是把"文档解析"变成一件标准化的事：解析结果可交换、可组合、可复用到别的系统里，而不是一堆只有人能看的文本。

格式覆盖面比你想的宽

输入格式这一项，Docling 铺得挺开：

PDF、DOCX、PPTX、XLSX、HTML、EPUB、Apple Pages、LaTeX、纯文本、Markdown 超集，Office 三件套的开放格式（ODT / ODS / ODP），邮件（EML / MSG），图片（PNG / TIFF / JPEG），扫描件，以及 XBRL 财务报告。

还有一个容易被忽略的：音视频。WAV、MP3 能转，MP4、AVI、MOV、MKV、WebM 也能转——自动语音识别转写加关键帧提取。在开源解析工具里，原生支持视频输入的并不多。

输出侧，除了上面提到的那些格式，还有 WebVTT 字幕格式。另外它能把柱状图、饼图、折线图转成表格或代码，并附一段描述。

图片区域的标注与描述

工程与合规：小团队最该看的一节

先说跑得动吗。它可以纯 CPU 跑，笔记本就能用，Apple Silicon 有 MLX 加速。真要上量，官方给了 NVIDIA RTX 的 GPU 加速路径，宣称最高 6 倍于纯 CPU；再往上可以用 Ray Data 加 KubeRay 扩到 10 到 100 个 Kubernetes 节点。它还和 Red Hat 一起出了 OpenShift Operator，明确瞄准银行这类场景。

再说那几个配套件。Granite-Docling-258M 是个只有 2.58 亿参数的视觉语言模型，Apache 2.0 协议，能一次成图地把整页转出来；官方 MCP Server 让 Agent 直接调用解析能力；还有个 docling-serve 可以当 API 服务跑。生态里有 8 个仓库，集成侧原生支持 LangChain、LlamaIndex、Crew AI、Haystack。

Docling 的生态组成

最后是那个容易踩的坑——许可证。很多人选型只看精度，最后栽在协议上。这三个常被一起比的开源方案，协议差别很大：

项目许可证商用门槛
DoclingMIT无门槛，可直接用在商业产品里
MarkerGPL-3.0 + RAIL-M营收或融资超 200 万美元，禁止免费商用
MinerU基础宽松 + 额外约束无硬性收入门槛，但需法务过一遍

⚠️ 注意 库是 MIT、模型是 Apache 2.0，这是 Docling 对企业最实际的一条优势——零合规风险。反过来，如果你的团队规模不小又用了 Marker，这就是实打实的法律风险。

上手：两行命令

BASH

pip install docling

Python 调用只要三行：

PYTHON

from docling.document_converter import DocumentConverter

converter = DocumentConverter()

result = converter.convert("你的文件.pdf")

print(result.document.export_to_markdown())

想直接用 VLM 一次成图，加个参数就行：

BASH

docling --pipeline vlm --vlm-model granite_docling 你的文件.pdf

注意版本要求：Python 3.10 起，2.70.0 版本之后已经放弃 3.9。

但有几件事得说清楚

· 它不是精度冠军

在第三方的 OmniDocBench 基准测试里，Docling 的表现并不好看——英文和中文的编辑距离都排在被测工具的末尾（英文 0.589、中文 0.909），中文场景问题尤其明显。另一份第三方实测给出的数字是多栏还原 86.5%、公式 89.1%、表格 91.8%，复杂公式容易失真，中文表格偏弱。

要说明的是：这些数字来自第三方评测，测试口径和版本各不相同，不能当成官方结论。但方向是一致的——纯论精度，它打不过专攻中文和公式的方案。

那为什么还要选它？因为它的价值不在"谁更准"，而在结构标准化、可溯源、CPU 友好和零合规风险。这是两种不同的取舍。

· 官方没有发布过与商业方案的正面基准

到目前为止，Docling 没有公开与 Mistral OCR、GPT-4o Vision 或 Google Document AI 的正面对比数据。这个空白，是它下一步要过的可信度考试。

· 上手和调校有门槛

流水线可插拔的另一面，是出问题时你得知道该换哪一段、看哪个日志。不少第三方评测都提到，它的开箱体验不如那种"一条命令出结果"的工具顺滑。开放的 issue 数也在 900 上下——对一个这个体量的项目算正常，但意味着你要有跟进的预期。

· 它的强项要配对场景

复杂公式、中文表格密集的学术文档，有更合适的选择；而如果你的场景是企业知识库、多格式混杂、要过合规审查、可能还要跑在纯 CPU 上，它的定位就非常合适。

写在最后

回到开头那个问题：知识库答不准，是不是模型的锅？

多数时候不是。解析层是整条链路的地基——地基上是文字垃圾，楼上装修得再豪华也没用。

Docling 选了一条不太一样但很有意思的路：不去争"谁解析得更准"这个第一，而是把解析结果做成一种可交换、可溯源、可复用的标准结构，再用纯 MIT 帮企业绕开许可证风险。

它的官方说法是"简化文档处理流程"。看完这一圈我的理解是：它想解决的不是"把文件转成文字"，而是"让解析这件事变得能被信任、能被复用"。这两件事，难度不在一个量级。
