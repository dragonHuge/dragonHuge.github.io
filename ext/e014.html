我经常需要在多个 Coding Agent 之间切换，例如 DeepSeek Harness 在一个项目里补功能，Codex 在另一个项目里查问题。

如果想看看它们干到哪了，得先找到对应的会话；代码改完了，再打开文件检查差异，确认能运行，最后再处理 Git 提交。

如果你同时使用几个编程 Agent，这些操作可能分散在终端、编辑器和不同的桌面应用里。任务一多，找会话、查进度、检查改动也会占掉不少注意力。

周末调研了一个能够完美解决这些问题的开源项目 T3 Code 。它直接把这些操作放进了同一个工作台。它可以接入 Claude Code、Codex、DeepSeek Harness 等编程 Agent，提供项目和会话管理、代码差异查看、Git 提交与 PR 操作，也有 Web 和手机端入口。

T3 Code 是什么？

T3 Code 是一个采用 MIT 协议的开源 AI 编程工作台，也就是编程 Agent 的统一控制界面。

T3 Code 的 GitHub 仓库首页

你可以把已经在用的 Claude Code、Codex 等编程 Agent 接进来，在 T3 Code 中发出需求、查看回复和管理任务。读取项目、修改代码、执行命令，仍然由接入的 Agent 完成。

官方内置 Provider 已覆盖 Codex、Claude Code、Cursor、OpenCode 等常见 CLI。除此之外，还可以通过本地 ACP 把本机已安装、已完成认证的 Agent 接进来。文中后文出现的 Kimi Code、DeepSeek Harness 以及 OpenCode (ACP) 属于后者，需要在运行 T3 Code 的那台机器上自行配置，不能当成每个安装包都自带的默认选项。

日常使用时，先接一个自己熟悉的 Agent 就够了。

需要注意，T3 Code 本身开源免费，接入后使用的模型、订阅额度或 API 费用，仍然属于相应的模型服务。已有订阅能否使用，要看对应 Agent 的认证方式和服务条件。

它提供桌面应用、Web 应用和手机应用。Agent 在运行 T3 Code 服务的那台机器上工作，其他设备可以连接过去操作。项目文件、Agent 的安装和登录信息，也需要在实际执行任务的机器上准备好。

T3 Code 解决了什么问题？

用 AI 改一个功能，通常不会在它回复“完成了”时结束。

你还得确认它改了哪些文件，有没有顺手改掉不相关的逻辑，测试是否真的执行过。如果发现遗漏，就带着具体代码继续追问。确认没问题后，才轮到提交和创建 PR。

T3 Code 把会话和这些代码操作放在一起：任务保留在工作台里，改动可以打开 diff 查看，提交和 PR 也有对应入口。对于经常切换项目和 Agent 的人，这提供了一种集中处理开发任务的方式。

T3 Code 有什么亮点？

一个工作台里，使用不同的编程 Agent

T3 Code 的 Provider 设置用来管理接入的 Agent。内置 Provider 按官方文档启用即可；本机另有 CLI 时，可以在同一页面添加 ACP 实例并指定可执行文件路径。启用或接入成功后，就可以在任务中选择使用的 Agent 和模型。

下图是本机 Settings → Providers 列表的一部分：Kimi Code、DeepSeek Harness 和 OpenCode 通过本地 ACP 接入，状态显示为 Available。这是作者本机的配置示例，不是官方默认清单。Available 只说明接入探测可用，实际能否完成任务，还要发出请求验证。

本机三个 ACP Provider 的接入状态

例如，给一个书签管理页补搜索功能，可以选择 Codex；另一个项目需要补测试，也可以选择 Claude Code。具体交给谁，按自己的账号和使用习惯决定。

已经安装并登录过 CLI 的用户，可以按官方配置方式接入。若程序找不到 CLI，还可以在 Provider 设置里指定可执行文件路径。远程连接时，这些配置属于远程机器，本机登录过并不代表远程也已经登录。

Provider 设置还会提示已知的版本兼容问题。如果某个 CLI 版本与当前 T3 Code 发行版存在已知冲突，可以先查看这里推荐的版本，避免只更新其中一个工具后无法正常连接。

AI 改了哪些代码，可以直接打开看

比起支持多少个 Agent，我更关注它怎样帮助开发者检查结果。

T3 Code 提供 Diff 面板。按照官方文档，一轮任务的改动视图会展示这一轮自己的修改；如果期间发生了拉取、合并或变基，单纯由 Git 带进来的改动会被排除。要检查相对基础分支的全部差异，则应该使用分支对比。

这两种范围对应不同的问题：一个是“它刚刚改了什么”，另一个是“这个分支准备交付哪些改动”。审查整个功能时，只看最后一轮回复旁边的修改还不够。

下面是本次书签任务的实际 Diff 面板，范围选择为 Latest turn，展开的是 index.html。这次从空目录开始创建页面，所以图中展示的是新增代码。

书签任务的 Latest turn 代码差异

桌面端和 Web 端也支持在 Diff 面板里选择 Commits，按本地提交逐个查看差异。项目积累了多次修改以后，可以沿着提交检查，不必只面对一份越来越长的总 diff。

拿书签页举例。本文试用时项目目录起初为空，需求可以写成：

在当前目录用原生 HTML、CSS、JavaScript 制作本地书签管理页面，不安装依赖。内置 8 条示例书签，至少 3 个分类；支持按标题搜索（忽略大小写）和分类筛选，两种条件可同时生效；没有匹配结果时显示提示；提供清空筛选按钮恢复全部列表；附上 README 说明打开方式。

这个例子里，验收时就有明确的检查对象：页面能否直接打开、搜索和分类有没有同时生效、空结果有没有提示、是否添加了额外依赖，以及修改有没有跑到无关文件里。

Diff 能帮助定位代码，页面行为仍然需要实际运行才能确认。找到问题后，再把相关文件和具体现象交给 Agent 继续修改。代码检查与功能验收都完成，才适合进入提交环节。

检查完改动，接着提交代码和创建 PR

T3 Code 在会话里提供 Git 操作，可以提交、推送并创建 Pull Request。提交信息、PR 标题和描述，也可以根据代码变化生成。

按照官方说明，PR 描述还会参考会话中的工作内容，包括执行过的检查。你可以在 Settings → Source control 中选择生成说明的模型和写作方式；其中的 Repository conventions 会参考项目指令和近期提交标题。

这适合接在前面的检查过程后面：确认修改范围，检查生成的提交说明，再决定是否推送、创建 PR。自动生成的文字仍然需要看一遍，尤其是测试结论，不能把“建议运行”写成“已经通过”。

GitHub 接入需要配置认证。T3 Code 支持在设置里保存 Token，也可以使用相应的环境变量或已登录的 GitHub CLI。Git 推送本身还依赖仓库远程地址使用的认证方式，因此能读取 GitHub 信息，不代表 SSH 或 HTTPS 推送一定已经配置好。具体设置可以查看官方源码管理文档[1]。

离开电脑，也能从手机连接任务

T3 Code 提供 iOS 和 Android 应用，手机可以连接另一台机器上的 T3 Code 服务。

官方提供的 T3 Connect 用来把运行环境连接到自己的其他设备，不需要自行配置路由器端口转发。在主机启用 T3 Connect 后，其他设备登录同一账号，再选择对应环境即可。也可以通过局域网或私有网络，用配对链接连接。

如果任务放在一台持续运行的电脑上，这种方式就适合用手机查看和处理任务。手机负责连接和操作，Agent 仍在原来的机器上执行，项目文件也留在那里。

运行任务的主机必须保持运行并且网络可达。 合上笔记本导致休眠后，不能指望手机替它继续执行。远程访问的配置和连接条件，可以查看官方远程访问文档[2]。

T3 Code 怎么使用？

先准备一个用于尝试的项目目录，以及一个已经安装、完成认证的编程 Agent。以本机已有 Claude Code 或 Codex 为例，先确认对应工具能正常工作，再接入 T3 Code，出现问题时也更容易区分是账号、Agent 还是工作台的配置问题。

官方 README 也列出了各 Provider 的安装和认证前置条件，使用前至少准备好其中一个。

官方 README 中的 Provider 安装与认证提示

桌面应用可以从官方下载页面[3]获取。macOS 用户如果已经安装 Homebrew，也可以按官方提供的方式安装：

brew install --cask t3-code

这条命令会安装 T3 Code 桌面应用。启动后，在 Settings → Providers 中启用准备使用的 Provider，确认安装和认证状态。程序找不到已安装的 CLI 时，检查它的路径，必要时填写 Binary path。

这次在 macOS 上使用 T3 Code (Beta) 0.1.6，分别给 Codex、Kimi Code、DeepSeek Harness 和 OpenCode 发了一条最小请求：只回复“连接成功”，不读取文件、不调用工具。四个会话都收到了预期回复。其中 Codex 使用内置接入，另外三个通过本地 ACP 接入。下图是 DeepSeek Harness 的回复；这一步只确认文本请求能跑通。

DeepSeek Harness 在 T3 Code 中完成连接测试

首次尝试还要看一下会话的权限模式。当前权限文档[4]写明，初始默认值为 Full access，允许命令和文件修改不经逐次确认。想先观察执行过程，可以选择 Supervised，由它针对命令和文件修改请求批准；具体执行方式也受 Provider 的权限机制影响。

本次 Kimi 会话选择的就是 Supervised。执行检查命令时出现了审批请求，但文件创建阶段没有观察到逐文件确认弹窗，不能把它理解为所有 Provider 都会以同样方式拦截每次操作。

Kimi 会话的 Supervised 权限模式

随后打开测试项目，创建任务，发出一个修改范围明确的需求。这次新建了一个空目录，选择 Kimi Code 的 K3.1 Pro 和 Supervised 模式，让它用原生 HTML、CSS、JavaScript 制作书签页：内置 8 条书签，支持标题搜索、分类筛选、空结果提示和清空筛选，并附上 README，不安装依赖、不创建 Git 提交。

Kimi 最后生成了四个文件，并在回复里列出实际执行的检查和未检查的内容。T3 中也能看到命令审批和文件变更入口。截图中的“Worked for 9m 13s”包含等待审批的过程，不能当作模型独立完成任务的耗时。

Kimi 完成书签页面任务并列出新增文件

生成后的页面如下。随后通过本机临时 HTTP 服务打开页面，逐项操作确认：8 条书签正常显示，标题搜索忽略大小写，搜索和分类能组合使用，无结果时出现提示，清空后恢复全部书签。自动化浏览器不允许访问 file://，所以“直接双击 HTML 打开”和断网重开没有在本轮验证。

第一次使用到这里就够了。确认本地任务可以正常执行，再按需要接入 GitHub 或配置手机连接，不必一次把所有功能都配齐。

总结

如果你已经在使用 Claude Code、Codex、DeepSeek Harness 等 Coding Agent，想把几个项目的任务和代码检查集中处理，T3 Code 值得留意一下。它的功能设计覆盖了发任务、查改动和提交代码这些日常动作，比较适合拿一个现有小项目试用。

试的时候，重点看自己最常做的那几个操作：能否找到任务、看清修改、继续追问，以及顺利提交。如果现有工具已经把这些事情处理得很好，也可以继续沿用。是否留下 T3 Code，取决于它能否让你的实际工作更顺手。
