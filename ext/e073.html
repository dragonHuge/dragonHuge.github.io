上一篇讲了 容器回收——占着的实例谁该放、何时放、放了数据怎么办。该放的放掉，池子干净了，回到「秒级能聊」，还剩一笔时间账要算。

今天钻进连接层：进入页面时已经打了预热，用户转头就发首句，这两条路径怎么合到一起？合不上的时候为什么必须走冷启，而不是把人卡住？

先看一次真实的值班现场。某天有用户反馈「聊天越来越慢」。查监控，进入页面时预热接口一片 202，成功率 99%，看起来毫无问题；可用户第一次发消息，还是老老实实等了一次冷启动。两边的日志都在说「成功」，就是合不上。折腾半天才发现：预热的接口图省事只带了 Agent 标识和用户，漏了来源标识——钥匙少了一环，锁当然打不开。预热不是没做，是做在另一把钥匙上。

先花一分钟对齐几个词

词说人话是什么意思
槽位连接池里预先准备好、可以被领走的一条可用连接
预热 blank（新会话）给还没建会话的用户领的空连接
预热 resume（续聊）带真实会话键、要接回上一轮历史的连接
匹配键决定这一轮能不能领到同一条连接的那组字段：代理身份 + 用户 + 来源 +（续聊）会话键，此外还有启动来源、原始 Agent 标识、增量开关等；预热与正式开聊必须完全一致
合流首聊到达时预热还在跑，服务端短等一下再领；不是让用户等
冷启没等到现成连接，现起一条，慢但一定可用
supersede（踢旧）同一会话来了新请求，把上一轮踢掉并停干净
启动规格容器与工作区来源的组合；规格变了，旧预热的连接就不能再注册进池

（CLI、SSE、202、stdin、fail-closed 这类通用名词就不解释了。）

01 | 预热做了，首句还是冷的

把预热想成出门前提前叫的网约车：

叫车预热里对应什么
提前叫车进入页面时异步发起预热
车已经在楼下等你预热就绪，首句直接领走（合流）
车还在路上预热进行中，服务端短等一下
司机没来，你重新打一辆冷启：慢，但一定可用
车牌号 + 手机号后四位匹配键——少一位就上不去车
你又叫了一辆，得取消前一辆supersede 踢旧
司机不能为了接单率假装你已上车禁止空消息占坑

这个类比把本篇三个最反直觉的判断一次讲清：

  • 车没来，你还是能出门。 叫车只是提速，不是出门的前提——叫不到车你会换别的办法，不会因此不出门。对应「预热失败必须落冷启，而不是禁用输入框」。
  • 车牌号和手机号少一位，车停在面前你也上不去。 对应匹配键：预热和开聊只要有一项不一致，那条连接就永远领不到，两边的日志还都写着「成功」。
  • 重新叫车之前，得先把前一辆取消掉。 否则两辆车都往你这开，资源白烧。对应同一会话来了新请求必须踢旧，且要把底层进程停干净。

连接层的事故很少长得像「接口 500」。它们长得像「明明预热了，体感还是冷的」。至少回放三种。

事故 A：匹配键少一环，永远领不到那条连接。

症状：进入页面时预热返回 202，首句却再走一次冷启动；两侧日志都写着成功，就是合不上。误判路径通常是怪预热实现「假成功」，或者再打一遍预热碰运气。真相是钥匙不全——代理身份、真实用户、来源标识、续聊时的会话键，任一项与正式开聊不一致，服务端就找不到对应的槽位。

事故 B：把预热当成开聊的前提，失败就禁用输入框。

症状：预热 5xx、业务主动跳过、容量满了跳过昂贵准备——前端一律把输入框灰掉。误判路径是「保证体验，必须等预热好才能聊」。真相是用户表达的是「我想现在说话」，不是「请等你的加速任务成功」。提速手段失败的正确落点是冷启，不是不能聊。这件事做反了，等于提速一抖，主产品跟着停摆。

事故 C：同会话连点两次，两轮抢同一条 stdin。

症状：第二次提问发出后，第一次显示「已停」，旧命令行进程却还在烧；或者两条流交错，会话状态错乱。误判路径是只取消上层逻辑任务，以为前端 abort 就够了。真相是同一匹配键上的新请求必须踢掉旧那一轮，并且把底层进程停干净——只取消上层、下层进程还活着，是同一类失控：主停了，子还在烧。

预热合流要回答的就一件事：提速手段怎么与主路径合流，冲突时又怎么干净地让路。合不上就冷启，抢会话就踢旧并停干净。

三种事故可以叠在同一次值班里：键错了看着像「预热假成功」，这件事做错看着像「前端 bug」，停不干净看着像「成本突刺」。不分层看，你会同时去拧三个无关的旋钮。

回放时固定一个顺序：先对匹配键，再看预热有没有被做成开聊的前提，最后查旧一轮有没有真的终止。顺序反了，日志会把你带进三条死胡同。键对了才谈合流，合流通了才谈停干净。

02 | 五类做法横评：偷什么，拒什么

各家做「快点开始聊」的姿势不同。横评五类，比的是「谁等谁」和「失败之后怎么办」。

做法谁等谁强项短板
前端死等预热再开聊用户等预热实现简单预热失败就等于不能聊
只缓存模型 / 暖推理不管命令行进程SaaS 轻问答够用带工具链的 Agent 场景不够
服务端连接池 + 合流首聊可先发提速手段可丢，主路径不堵竞态与匹配键复杂
每次冷启无预热稳、逻辑直秒级账单每轮都付
预热写空 prompt 进真会话「占坑」保活看起来槽位永远热污染真实会话，应禁止

我们偷三样：从「服务端连接池 + 合流」偷「首聊可以立刻发，合流是服务端的责任」；从「每次冷启」偷「失败兜底路径必须完整，预热不是正确性的前提」；从本机常驻的体验偷「打开就能打字」这个产品目标——实现上用异步预热逼近，而不是阻塞界面。

我们拒四样：拒「前端死等预热」，那是把提速手段做成开聊的前提；拒「空 prompt 占坑」，正确性大于预热成功率的化妆；拒把「只暖模型不暖命令行进程」当成使用态主方案，工具链 Agent 的冷启账单主要花在连接上；拒「只取消逻辑任务不杀进程」，停就要停干净。

结论是异步预热 + 服务端合流 + 失败冷启：提速手段可以丢，主路径不能堵。

偷拒清单收束成四条产品原则：打开就能打字；合不上就冷启；停就要停干净；绝不拿真实会话当预热的化妆台。

03 | blank 与 resume 分槽，合流与踢旧互不干扰

新会话与续聊要的连接不一样——一个还没有会话键，一个必须接回同一条会话历史。所以槽位分成两套：blank（无会话键）给新会话领空连接，resume（带会话键）给续聊接回历史。

预热容量有限，昂贵的准备不该无限排队。所以槽位满时可以跳过预热，聊天仍走冷启，而不是把用户堵在预热队列里——提速手段反而变成最长的阻塞，是最讽刺的翻车方式。

合流与踢旧是两个互不干扰的问题：一个解决「有没有现成连接」，一个解决「同一条连接上会不会双开」。

概念含义
blank不带会话键：给新会话领的空连接
resume带真实会话键：给续聊领的连接
容量有限槽位满时跳过昂贵准备；不打断正在跑的
合流首聊到达时若匹配预热仍在跑，服务端短等领取；失败 / 取消则冷启
提速手段跳过或失败，仍允许立刻聊

匹配键必须与正式开聊逐字一致。它不止四项——除了代理身份、用户、来源、（续聊时的）会话键，还包括启动来源、原始 Agent 标识、是否开启增量这些；真正领取时还要求工作区、工具、密钥、系统提示、容器形态这一整组配置完全相等。回到网约车：车牌号和手机号后四位，叫车时报的和上车时报的必须完全一致——少一位、或者一边用了简称，车停在面前你也上不去，而司机端的记录里还写着「已到达」。

不这么分会怎样？只有一种槽，续聊会接到空白连接，或者新会话误接别人的历史；预热无限排队，提速手段变成最长的阻塞；合流与踢旧搅在一起，排障时根本分不清是「没预热上」还是「双开了」。

预热解决「有没有现成连接」；踢旧解决「同一条连接上会不会双开」。

页面侧的最小正确用法，也可以当成设计推论的一部分：进入页面时发一次就不管了（fire-and-forget）；失败只告警；续聊时把真实会话键同时传给预热和开聊；来源字面量两边必须一致。少做任一条，后面的合流代码写得再漂亮也合不上。

04 | 实现：四种状态都允许立刻聊

先讲不变量。预热是提速手段，无论返回的是已接受（含「跳过昂贵准备」的变体）、正在预热还是已就绪，前端都该能输入。业务侧还有一个「跳过」状态，但它只在部分宿主类型里出现，池侧不产出。轮询预热状态当开门条件，等于把「必须先预热才能聊」从后门又塞回来。

用户完全可能在预热返回之前就发出首句，所以合流必须发生在服务端：匹配得上就短等领取，匹配不上就冷启。前端多轮询一次，只是把「必须先预热才能聊」偷偷加回来而已。

状态（示意）含义可否立刻聊
accepted接受后台预热（或跳过昂贵准备）是
already_warming同会话的续聊连接已在建是
ready同会话已有健康连接是
skipped业务上跳过（仅部分宿主类型产出，池侧不返回）是
// 示意 · TypeScript
// 保证：预热与开聊可并发；匹配得上就等合流，否则冷启
type MatchKey = {
  agentId: string;
  userId: string;
  source: string;
  sessionId?: string;
};

async function openChat(msg: string, key: MatchKey) {
  const warming = findWarmup(key);
  const runtime = warming
    ? await waitOrCold(warming)   // 失败 / 取消 / 超时 → 冷启
    : await coldStart(key);
  return runtime.query(msg);
}

async function waitOrCold(warming: WarmupHandle) {
  try {
    return await warming.waitReady();
  } catch {
    return coldStart(warming.key);
  }
}
# 示意 · Python
# 保证：同一 key 来了新请求，先取消旧一轮，再终止旧进程，避免双开
async def acquire_turn(key: str, new_task) -> None:
    old = turns.get(key)
    if old:
        await old.cancel()
        await terminate_cli(old)   # 停干净，不只是取消逻辑任务
    turns[key] = new_task

边界与并发，逐条明确：

  • 同一组四元组只保留一个续聊槽；重复预热刷新使用次序即可，不必再建。
  • 新会话抢空连接槽：有空闲立刻领，否则等匹配的预热任务。
  • 三槽级容量全忙：后台预热直接跳过，不排队；聊天走冷启。
  • 页面侧：中断上一次预热、发一次就不管、异常只告警。

05 | 实现：规格冲突与四条禁止

晚到的错误规格连接一旦注册进池，会话快照就会错乱。所以遇到启动规格冲突，做法是作废旧预热、禁止晚到的错误连接注册，本轮聊天用自己的规格冷启。注意这条只覆盖续聊：只有带着真实会话键的续聊才会去扫描冲突、把旧那一轮置为「已被替代」并取消；新会话没有这条路径，不兼容的空闲连接由后台补充连接池时直接淘汰。

「预热成功率」好看不等于用户安全。所以预热撞上已有健康连接时直接跳过，绝不用「发一条空消息」去污染真实会话。

四条禁止项：

  1. 用空 prompt「占坑」保活真实会话。
  1. 规格已经变了（例如工作区来源变了）还让旧的预热尝试晚到注册。
  1. 只取消协程 / Promise，不终止底层命令行进程。
  1. 把密钥轮换误判成规格变化而疯狂冷启——轮换本身不该算规格变化。但这里有个真实边界：领取时要求的那组配置里包含 Agent 密钥，密钥轮换会改变这组配置，于是轮换之前备好的空闲连接会被判成不兼容而淘汰。这不是 bug，是必须提前知道的代价。
// 示意 · TypeScript
// 保证：规格冲突时旧预热作废，聊天用自身规格冷启，不吃晚到的脏连接
type LaunchSpec = { workspaceSource: string; agentId: string };

function onSpecConflict(oldAttempt: Attempt, chatSpec: LaunchSpec) {
  oldAttempt.invalidate();
  oldAttempt.cancel();
  // 禁止：oldAttempt.runtime 晚到后再 register()
  return coldStart(chatSpec);
}
# 示意 · Python
# 保证：已有健康连接时跳过预热，绝不写空消息污染会话
async def maybe_prewarm(key: str, has_healthy: bool) -> str:
    if has_healthy:
        return "skipped"          # 正确性优先于「预热成功率」
    if pool_full():
        return "accepted_skip_expensive"
    await start_warmup(key)
    return "accepted"

偶发丢掉「差一点就好了」的预热，好过一次脏注册。这是取舍，不是失误。

再补一条面向用户的表达原则：用户侧可以说「正在连接」，不要说「预热失败，暂时不能聊」。前者承认提速手段有时未命中，后者把提速手段做成了门禁——叫不到车你会换别的办法走，不会因为没叫到车就不出门。

06 | 完整生命周期：进入页面时立刻开聊

串一次最常见的快乐路径，外加几条分叉。每步都带决策点。

  1. 打开对话页 → 异步发起 blank 预热（无会话键）→ Agent 前置网关确认容器 → 申请 blank 槽 → 返回 202。决策点：失败只告警，输入框照开。
  1. 200 毫秒后发出「你好」 → 开聊发现 blank 还没好 → 服务端等合流 → 领取 → 查询。决策点：谁等谁？用户不等，服务端短等预热。
  1. 预热因容量满被跳过：聊天走冷启，照样出字。决策点：提速手段无效，主路径不能堵。
  1. 连点第二次：同一匹配键踢掉第一次，旧流标记被替代，旧进程终止。决策点：可以失败的是旧那一轮，不是让两轮都半死不活。
  1. 续聊：带上真实会话键再预热并开聊，命中续聊槽或者冷续聊。决策点：会话键字面量必须与上一轮一致。
  1. 规格冲突：旧的预热尝试作废，禁止晚到注册，本轮冷启。决策点：正确性优先于预热命中率。

如果当初把预热做成开聊的前提，第 3 步会变成「输入框灰掉」；如果没有踢旧机制，第 4 步会变成两个进程抢同一条会话。

合流竞态口诀，可以贴白板：

  • 预热未完、首聊已到 → 等合流，不拒聊。
  • 预热跳过 / 失败 / 取消 → 冷启，不重试到死。
  • 同一匹配键来了新请求 → 踢旧并停干净，不并行双开。
  • 规格冲突 → 作废旧尝试，不让晚到的脏连接注册。

一次「进入页面时立刻开聊」，成功时用户无感，失败时用户仍能聊。无感与可聊，比预热命中率好看更重要。

07 | 这套设计的代价与选型

五维横评：首句可立即发、失败仍可聊、会话安全、实现复杂度、推荐度。

维度前端死等服务端合流每次冷启空消息占坑合流 + 冷启兜底（我们）
首句可立即发否是是是（有毒）是
失败仍可聊难是是是是
会话安全中强强弱强
实现复杂度低高低低高但可控
推荐否是兜底禁止是

什么时候选谁：

  • 原型验证：每次冷启最省事，先别上合流。
  • 只要网页轻问答：前端死等有时能混过去，但别把这个习惯带到带工具链的 Agent 上。
  • 云上 Agent 要干得稳：服务端合流 + 冷启兜底；空消息占坑直接禁止。
  • 已有健康连接：跳过预热，别为了指标再去「暖一次」。

最后提醒一句：矩阵里「实现复杂度高」本身不是缺点。复杂度应该花在服务端的竞态与停干净上，不应该花在前端死等和空消息化妆上。

08 | 四个坑

坑 1：匹配键少传来源或会话键

诱因：预热接口图省事；续聊时只在开聊带会话键，预热忘了带；两边来源字面量不一致。 错解药：再打一次预热「补救」——钥匙还是错的，永远合不上。 正解药：预热与开聊共用同一个键生成函数；对不齐就冷启，同时去修键。回到网约车：再叫一次车没用，因为你报的车牌号本身就是错的——得先把号码改对。

坑 2：预热失败就锁界面

产品要求「暖好再聊」，于是把 202 以外的响应都当致命错误处理，失败后自动重试预热直到成功。结果预热服务一抖，全站用户都不能输入。正确的做法是只在日志里告警、输入框照开、服务端走冷启兜底——提速手段的问题不该由用户的输入框来承担。

坑 3：取消逻辑任务不杀进程

诱因：框架里取消 Future / Task 很方便，以为上层停了下层自然就停了。 错解药：只标记为「已替代」，不终止命令行进程——旧进程继续烧资源，甚至继续往会话里写。 正解药：踢旧路径同步终止底层进程，停干净之后再接纳新的一轮。

坑 4：用空消息「占坑」

想让预热成功率好看一点，或者误以为「先发一句空的」能保活连接，于是往真实会话里写空消息。后果是污染会话历史：审计记录和用户在界面上看到的内容都变脏，而且这种脏数据极难清理。正确做法是直接禁止；已有健康连接就跳过，需要连接就正规预热或者冷启。

总结

预热只是提速手段，不是开聊的前提；失败必须落到冷启。

合流是服务端的责任，前端别死等。

匹配键错了等于没预热。

同一会话来了新请求，要踢掉旧一轮并停干净。

正确性优先于把预热成功率刷好看。

blank / resume 分槽，合流与踢旧互不干扰。

预热可以丢，会话不能脏，进程不能半死不活。三句话够用，其余都是实现细节。

预热是提速手段，可以丢；会话不能脏，进程必须停干净。
