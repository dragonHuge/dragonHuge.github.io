摘要速览

  • 解决的问题：审核运营日常重复操作（查机审/人审日志、排查审核效果、核验配置）无法被 AI Agent 自动编排，需要标准化 AI 友好接口
  • 核心架构决策：MCP 嵌入现有控制台（而非独立服务或脚本封装），核心判断是"AI 只是控制台的另一类用户"，复用全部 Service/DAO 层，人机始终对齐，每次 bugfix/新增接口 AI 自动受益
  • JDK 8 困境解法：官方 MCP SDK 和 Spring AI 都要 JDK 17+，ali-langengine-mcp-jdk8 是天坑（只有 interface 声明），最终选用 Solon solon-ai-mcp 3.10.4-M1（JDK 8 兼容），通过 SolonServletFilter 嵌入 Spring Boot Tomcat 不占额外端口
  • 传输协议选型：选 Streamable HTTP（MCP 2025-03-26 spec），单 POST 端点，短操作直接返回 JSON、长操作升级 SSE 流，无长连接，适合负载均衡；In-process 部署模式复用 Spring Boot Tomcat 线程池
  • 鉴权机制：McpAuthFilter(Order=0) → Bearer token 校验（Nacos 热刷新，无需重启）→ 跳过 SSO → Solon 兜底二次校验，审计日志记录 mcp:&lt;caller&gt; 可追溯每次 AI 调用
  • 工具注册：@McpTool 注解 + McpSpringToolProvider 自动扫描 @RestController 生成 JSON Schema，结合 @ApiModelProperty/@ApiParam 三层注解生成完整描述，已注册 15 个审核工具
  • 新增工具只需三步：在 Controller 方法加 @McpTool 注解 → 确认 DTO 字段 @ApiModelProperty 描述完整 → 重启验证
  • 适配其他项目：5 个通用文件可直接复制（McpAuthFilter/McpServerConfig/McpSpringToolProvider/McpTool/mcpserver.yml），替换 ConsoleContext/DynamicConfig/WebResponse 即可

一、背景与价值

内容审核中台处理海量多媒体内容，接入腾讯云、数美、易盾、图普等多家供应商。审核运营日常需要频繁登录控制台查询机审/人审日志、排查审核效果、核验配置——这些操作高度重复、耗时，且无法被 AI Agent 自动编排，亟需提效。

痛点AI 友好性基建 方案效果
--
审核运营查数据需登录 Console 手动操作AI 助手直接调用工具，自然语言驱动查询
数据分析需反复切换页面、手动筛选多工具组合调用，一次对话完成复合查询
接口能力无法被 AI Agent 编排标准 AI落地 协议，兼容所有 AI客户端

为什么不用脚本/Skills/CLI，不另起炉灶？

<callout emoji="🔔"> 核心思路：人能查的，AI 也能查，用同一套服务，不造两套。 </callout>

方案代表形态备注
---
脚本/Skills / CLI 封装写一批 Shell/Python 脚本调 REST API，塞进 Claude Code skills每个工具单独维护、无统一协议；接口变更需同步脚本；工具数一多，维护成本线性膨胀
独立 AI 专用控制台 <br/>(或MCP专用server）另搭一套服务专门给 AI 调用两套服务各自演化，容易出不一致的问题；人用控制台的演进无法自动惠及 AI
MCP嵌入现有控制台（选用）在 console 服务内新增 /mcp/** 端点复用全部 Service/DAO 层；鉴权、审计、监控共用；部署单元不增加；人机始终对齐

<callout emoji="🔔"> 核心判断： AI 只是控制台的另一类用户，需要的数据和权限与运营人员高度重合，差别仅在接口形式（自然语言 vs Web UI）。 把 MCP 嵌进现有服务，意味着每次 bugfix、每次新增接口，AI 自动受益，不引入第二套维护债。 *MCP**（Model Context Protocol）是 Anthropic 制定的开放协议，让 AI 模型能够以标准方式调用外部工具。接入后，Claude Desktop、Claude Code、Cursor 等客户端可以直接查询审核数据，无需任何 UI 操作。* </callout>

3.1 为什么不用官方 MCP SDK / Spring AI？

3.2 Solon 内嵌模式

Solon 通过 SolonServletFilter 嵌入 Spring Boot 的 Tomcat，不需要独立端口，不影响现有 Spring 能力。

Spring Boot Tomcat (8085)
  └─ SolonServletFilter → /mcp/*
       └─ Solon 内嵌容器
            └─ McpServerEndpointProvider → /mcp/audition/mcp

关键配置（mcpserver.yml）：

solon.app:
  name: middle-audition-mcp
  enableHttp: false   # 禁用 Solon 自带 HTTP，复用 Spring Boot 的 Tomcat
solon.logging.logger:
  "root":
    level: WARN

3.3 MCP 传输协议选型

MCP 协议在传输层提供 5 种选择，选型取决于部署方式、客户端生态和通信模型。

传输方式协议基础通信模型跨网络多客户端
-----
stdio进程管道stdin/stdout 全双工❌❌
HTTP + SSE（2024-11-05）HTTP 1.1 + SSEGET 建连 + POST 发消息✅✅
Streamable HTTP（2025-03-26）HTTP 1.1单 POST，响应可升级 SSE 流✅✅
WebSocketRFC 6455全双工长连接✅✅
In-process 嵌入式JVM 内方法调用无网络 IO❌❌

① stdio（本地子进程）

客户端直接 fork 本地进程，通过 stdin/stdout 收发 JSON-RPC 消息。Claude Code 大多数官方工具（filesystem、github、brave-search 等）均使用此方式。

{
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
    }
  }
}

优点：无需部署网络服务，进程隔离，安全沙箱易实现。缺点：无法跨网络，不支持多客户端同时接入。

审核场景：用「薄代理」模式低成本接入

无需开发 Client（Claude Desktop / Claude Code 已内置），只需写一个薄代理 Server，把 stdin JSON-RPC 转发给已有的 console REST API：

Claude Desktop（MCP Client，内置，无需开发）
     │  fork 子进程 + stdin/stdout 管道
     ▼
stdio MCP Server（薄代理，只需开发这一层+ 业务知识注入）
     │  HTTP 调用已有 REST 接口
     ▼
middle-audition-console REST API（零改动）

客户端配置只需在本地 .mcp.json 添加一段，服务端零改动：

{
  "mcpServers": {
    "audition-stdio": {
      "type": "stdio",
      "command": "python3",
      "args": ["/path/to/audition_mcp_proxy.py"]
    }
  }
}
维度stdio 薄代理当前嵌入式 Streamable HTTP
---
开发成本~150 行 Python，0.5 天 + 业务接口知识灌入 xx天~600 行 Java，已完成
多客户端同时接入❌ 每人本地起一个进程，需要维护代理✅ 共用一个服务
集中鉴权 & 审计❌ 无✅ Nacos key + MCP_AUDIT
适合场景个人本地试验、快速验证团队共享、生产级

结论：stdio 薄代理适合「个人本地快速验证」或「没有条件嵌入 MCP 的老项目」。生产环境走嵌入式 Streamable HTTP 方案。

② HTTP + SSE（MCP 2024-11-05，已弃用）两个端点分工合作：

  • GET /mcp/audition/sse — 建立 SSE 长连接，服务端通过此通道推送响应
  • POST /mcp/audition/sse/message — 客户端发送 JSON-RPC 请求
{
  "mcpServers": {
    "audition-console": {
      "type": "sse",
      "url": "http://<host>:8085/mcp/audition/sse",
      "headers": { "Authorization": "Bearer mcp_key_xxxxx" }
    }
  }
}

客户端兼容性：Claude Desktop、Claude Code（type: "sse"）、Cursor 均支持。~~本项目曾选用此方案~~，已迁移至 Streamable HTTP。

③ Streamable HTTP（MCP 2025-03-26，本项目选用）单 POST 端点，根据操作时长动态选择响应方式：短操作直接返回 JSON，长操作升级为 SSE 流式响应。

{
  "mcpServers": {
    "audition-console": {
      "type": "http",
      "url": "http://<host>:8085/mcp/audition/mcp",
      "headers": { "Authorization": "Bearer mcp_key_xxxxx" }
    }
  }
}

⚠️ 注意：Streamable HTTP 不接受客户端的 GET 建连请求。若客户端用 type: "sse" 连接 Streamable HTTP 服务端，GET 请求会被 400 拒绝。需确保客户端配置 type: "http"。本项目选用：主流客户端（Claude Desktop、Claude Code、Cursor）已全面支持此协议，相比 SSE 更简洁（单端点）、无需维护长连接、更适合负载均衡。

④ WebSocket（全双工双向，暂不适用）

基于 RFC 6455，握手升级后客户端和服务端均可主动推送，天然支持双向实时通信。部分 MCP SDK（如 Python mcp 库）提供 WebSocket transport 支持。

Solon AI MCP 3.10.4-M1 当前版本尚未提供开箱即用的 WebSocket transport，接入需自行实现适配层。本项目不适用：审核工具全为请求-响应模型，无服务端主动推送需求，引入 WebSocket 增加复杂度而无收益。

3.4 落地方式

In-process 嵌入式 + Streamable HTTP（本项目实际架构）MCP Server 与宿主服务运行在同一 JVM 进程内，通过 Solon 内嵌容器托管，不占用额外端口，不产生网络 IO。

Spring Boot Tomcat（8085）
  └─ SolonServletFilter → /mcp/*
       └─ Solon 内嵌容器（同一 JVM，非独立进程）
            └─ McpServerEndpointProvider（Streamable HTTP 传输）

这是架构层面的部署模式，而非独立传输协议——它对外暴露 Streamable HTTP 端点（③ 方案，单 POST），区别在于 Solon 容器复用了 Spring Boot 的 Tomcat 线程池，随主服务同生命周期启停。

嵌入式的核心收益：不引入新端口、不增加运维复杂度；代价：Solon 与 Spring 共享同一 JVM，需要通过双重过滤器链（McpAuthFilter → SolonServletFilter → Solon 兜底 filter）做好隔离，详见第四节。

-----
主流客户端兼容✅（本地）✅✅...✅
多客户端接入❌✅✅✅
独立端口无复用 8085复用 8085通常需要
JDK 8 + Spring Boot 2 落地难度低中中高
是否选用❌⚠️ 已弃用✅ In-process部署模式❌

四、核心组件详解

4.1 @McpTool — 工具注册注解

只需在已有 Controller 方法上加一行注解，无需编写任何额外代码：

@McpTool(value = "search_machine_audit_logs", description = "分页查询机审日志。")
@GetMapping("list")
public WebResponse<PagedResult<MachineLogVO>> getLogList(
        @ApiIgnore ConsoleContext ctx,   // ← 必须存在
        @Valid MachineLogDTO logDTO,
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "20") Integer limit) { ... }

命名规范：&lt;动词&gt;_&lt;名词&gt;，全小写 snake_case。

4.2 McpSpringToolProvider — 自动 Schema 生成 + 动态调用

职责：启动时扫描所有 @RestController Bean，找到 @McpTool 方法，自动构建工具描述和 JSON Schema。

注解 → Schema 映射示例

4.3 McpContextBuilder — 上下文生命周期管理

McpAuthFilter 写入 CALLER ThreadLocal
      ↓
McpContextBuilder.runTool()
      ↓
build(appGroupId, appId, caller) → ConsoleContext(role=superAdmin)
      ↓ ThreadLocalUtil 写入
callable.call()  ← 调用 Controller 方法
      ↓
audit log 写入
      ↓
ConsoleContext.clear() + CALLER.clear()

createBy = "mcp:&lt;caller&gt;" 写入操作日志，可追溯每次 AI 调用的发起方。

4.4 McpAuthFilter — Bearer Token 鉴权

Nacos 配置（DynamicConfig，支持热刷新，无需重启）：

mcp.auth.key.mcp_key_claude_ops=claude-ops-team
mcp.auth.key.mcp_key_ai_bot=ai-assistant-bot
mcp.service.mi-account=12345678

请求链路：

请求到达 /mcp/*
  ↓
McpAuthFilter（Order=0）
  ├─ 命中 Nacos key → 写 mcpCaller + skipAuth attr → 放行
  └─ 未命中 → 401 {"jsonrpc":"2.0","error":{"code":-32001,"message":"Unauthorized"}}
  ↓
LoginFilter（检测 skipAuth=true → 跳过 SSO）
  ↓
SolonServletFilter → Solon 兜底二次校验 → 工具执行

七、常见问题

Q：客户端连接返回 400？A：检查客户端配置。本项目使用 Streamable HTTP 协议，客户端必须配置 type: "http"，不能用 type: "sse"。旧版 SSE 客户端会发 GET 建连请求，而 Streamable HTTP 端点只接受 POST，因此返回 400。

Q：工具调用返回空数据？ A：检查 Controller 方法是否有 ConsoleContext 参数。缺少该参数时 appGroupId=-1 导致查询空结果，启动日志会有对应 ERROR。

Q：新加的 Key 不生效？ A：McpAuthFilter 监听 DynamicConfig，Nacos 推送后自动热刷新，无需重启。查看日志 [MCP] auth keys reloaded, count=N 确认。

Q：工具注册数量不对？ A：查看启动日志 [MCP] tools registered, count=N，注册失败的 tool 会有 [MCP] failed to register tool: xxx 的 ERROR。

*Q：Solon 启动失败后 /mcp/ 请求怎么处理？** A：solonStarted=false 时 SolonServletFilter 被禁用，/mcp/* 走 Spring Security 报 403，不会出现服务假响应。
