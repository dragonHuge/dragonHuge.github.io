Agent 真正缺的，不是更长的 Context，而是一个能持续存在、可追溯、可纠正的 外部大脑。

最近这两年做 Agent，我越来越确定一件事：模型的智商已经不是瓶颈了。

Claude、GPT、Gemini、DeepSeek，一个比一个能推理，Agent 也从简单问答变成了会查资料、会写代码、会调用工具、会跑任务的角色。但只要你连续用上几天，一个特别尴尬的问题就会冒出来——它压根不记事。

举个我自己天天遇到的场景。你和 Claude Code 聊了一下午，告诉它这个项目数据库用 MySQL，所有 SQL 修改先做只读检查，测试环境和生产环境不能混，技术方案统一写成 Markdown。这一整轮对话里它都记得清清楚楚。可第二天你重新开一个 Session，问它“昨天那个项目我们最后定了什么”，它大概率会告诉你：“抱歉，我无法访问之前的对话。”

很多人第一反应是上下文不够长，于是想办法扩大 Context Window，或者干脆把历史聊天记录整段塞进去。但我越想越觉得，这根本不是上下文问题。Agent 真正缺的是一个长期存在、独立于对话之外的“外部大脑”：它昨天学到的东西今天还应该在，它知道一个事实的同时也该知道这个事实是从哪来的，事实变了旧知识要能被纠正，如果两个来源互相打架，它最好告诉你“这里有冲突”而不是随便挑一个糊弄过去。

这也是我最近花时间研究 GBrain的原因。它想解决的不是“怎么让模型多看几篇文档”，而是另一个更底层的问题：能不能给 Agent 建一个持续存在、可检索、可更新、可追溯的知识大脑？这件事不适合只停留在概念层面讨论，所以下面我直接动手搭一遍，把整个过程和踩过的坑都记下来。

01

CLARIFY

GBrain 到底不是什么

先破除一个误区：GBrain 不是简单的 Markdown 笔记库，也不是又一个 Vector Database，更不能简单理解成“把企业文档丢进去，然后让 LLM 做 RAG”。

传统 RAG 的思路很直接：用户提问 → Embedding → 进 Vector DB 检索 → 找到 Top-K 相关文档 → 拼进 Context → LLM 生成回答。这套流程解决的其实是一个很单纯的问题——从大量文档里找到和问题相关的内容。

但 Agent 的长期记忆问题比这复杂得多。“张三负责哪个项目”是关系问题，“这个项目现在谁负责”是当前状态问题，“为什么换成李四负责”是事件和因果问题，“去年这个项目负责人是谁”是时间问题，“销售说能打八折，财务说只能八五折，到底哪个是真的”则是知识冲突问题。真正的 Agent Memory 早就不是单纯的“搜索相似文本”了，它至少要处理 Knowledge、Entity、Fact、Relationship、Time、Source、State这些维度。GBrain 有意思的地方，就在于它试图把这些东西组织成一套可以持续使用的知识体系。

02

COMPILED

编译式知识：不是现查，而是提前“编译”好

这是理解 GBrain 最关键的一个概念。如果把普通 RAG 比作一座图书馆，你进去问“有没有关于 AI Agent 的资料”，系统现场搜索，甩给你十篇文档，剩下的还得自己读。而 GBrain 更像是先把图书馆里的资料整理、分类、建好索引，把人物关系和事件关系也梳理出来，再交给 Agent 使用——原始资料经过解析后套上 Schema，提炼出 Entity 和 Fact，做 Embedding，构建 Graph，最终变成一份“编译好”的知识，Agent 直接拿来用。

「它的核心不是每次提问时再临时现找，而是把知识提前加工成 Agent 能理解和使用的结构。」

GBrain 官方设计文档把自己描述为一种 compiled intelligence system，核心思路之一就是把当前理解的知识和持续的时间线结合起来。传统 RAG 更接近 Query → Retrieve → Generate三步走，而这种编译式知识系统走的是 Import → Structure → Link → Compile → Retrieve → Reason这条更长的链路。两者要解决的问题，其实已经不完全一样了。

03

INIT

动手：先建一个自己的 Brain

理论讲到这就够了，下面开始实操。GBrain 目前比较适合本地快速体验的方式，是用 PGLite 建一个本地 Brain：

．．．bash

gbrain init --pglite

！踩坑提示 🕳

如果你在网上搜 GBrain 教程，会看到不少旧版本的安装方式，不要照抄——GBrain 迭代很快，官方文档已经把本地初始化、PGLite、MCP 这几条路径重新整理过了。

初始化完成后，你可以先把它理解成一个空壳：你的电脑上多了一个 GBrain，里面预留了 Knowledge、Entity、Fact、Graph、Timeline这几类容器，但暂时什么都不知道，接下来就是喂数据的过程。

04

SCHEMA

Brain 里到底该存什么

很多知识库项目最大的误区，是觉得“知识库不就是一堆 Markdown”。从 Agent 的角度看，Markdown 只是知识的载体，真正有价值的是里面的关系。

假设有这样一个目录结构：projects 下面放项目资料，people 下面放人员档案，companies 放公司信息，meetings 放会议记录。真正值钱的不是这四个文件夹本身，而是“张三负责 AI Agent 项目，项目使用 Claude Code，Claude Code 接入了 GBrain”这样一条关系链，或者“某次会议产生了一个决策，决策影响了项目状态，状态变化由张三执行”这样的因果链。

一个成熟的 Knowledge Brain，至少要考虑几类基本对象：

Page

知识的具体载体，比如 projects/ai-agent．md 这个文件本身。

Entity

现实世界中的对象，比如张三、AI Agent 项目、Claude Code、ABC 公司。

Fact

关于某个 Entity 的具体事实，比如“张三负责 AI Agent 项目”。

Timeline

记录事实发生和变化的时间点，比如“2026-09-10 张三负责项目，09-12 负责人变更为李四”。

Graph

把这些对象串起来的关系网。有了这五层，一堆孤立的文档才真正变成一个知识网络。

这也是 GBrain 当前 schema 设计值得留意的地方——新建的 Brain 默认已经采用 gbrain-base-v2，对应一套更规范的 canonical taxonomy。所以不要把“导入文档”和“建立知识”当成同一件事，前者只是把数据搬进来，后者才是真正在构建 Brain。

05

IMPORT

导入第一批知识

有了目录之后就可以导入了：

．．．bash

gbrain import knowledge

如果资料会持续变化，可以用 gbrain sync --watch让知识源变动后自动同步——官方安装文档里也提供了目录导入、watch 同步以及 autopilot 这几种玩法。

💡 建议第一次不要贪多，塞几万份企业文档进去意义不大，先准备十几篇、甚至五篇都行。

因为这一步真正要验证的不是“数据库能存多少东西”，而是“Agent 能不能从这些知识里建立关系，并且未来还能继续用上”——这是完全不同的两套验收标准。

06

THINK

Search 只是找到知识，Think 才是在用知识

知识进 Brain 之后，最先打交道的通常是 Search，比如“找一下所有和 AI Agent 项目有关的资料”，这种查询→检索→返回相关页面的活它干得很利落。但如果问题变成“综合最近几次会议记录、项目资料和人员信息，告诉我这个项目现在由谁负责，最近有哪些重要决策，还有哪些信息存在缺口”，事情就完全不一样了——这时候需要的链路是先 Search 再定位 Entity，顺着 Graph 关联多个来源，最后做 Synthesis给出答案。

这也是 GBrain 里 think 类能力的价值所在。它不是简单告诉你“这里有 A 文档、B 文档、C 文档”，而是尝试把这些信息真正综合起来。知识库到这一步才算从单纯的 Storage，变成了 Agent 推理时可以依赖的一层 Reasoning Substrate。

07

GOVERNANCE

好的知识库要知道自己不知道什么

企业 AI 最危险的场景，其实不是 AI 说“我不知道”，而是它不知道却编了一个看起来很合理的答案糊弄过去。所以测试 GBrain 的时候，不能只测“能不能找到答案”，还得故意问一些它答不上来的问题。

如果 Brain 里有明确资料，问“这个项目负责人是谁”，它应该给出“负责人：张三，来源：projects/ai-agent．md”这样带出处的回答，这算过关。如果问“这个项目明年的预算是多少”而库里根本没有相关数据，正确答案应该是“当前知识库没有足够信息”，而不是随便编一个数字出来。

第三种情况更考验系统——知识冲突。假设销售说这个客户可以打八折，财务说最低只能八五折，业务规则又说只有特定客户等级才允许八折，一个靠谱的知识系统不该简单甩出一个数字，而应该把冲突摆出来：三个来源分别给出了不同结论，当前状态标记为“存在冲突”。这就是 Knowledge Governance。企业知识系统真正难的地方，往往不是搜得快不快，而是知识到底还能不能信。

08

MCP

把 Brain 接进 Claude Code

到这一步 Brain 还是个独立工具，真正有意思的是把它交给 Agent 用。GBrain 可以通过 MCP 暴露能力，以 Claude Code 为例，注册命令是：

．．．bash

claude mcp add --scope user gbrain -- gbrain serve

claude mcp list

跑一下 claude mcp list，确认列表里出现 gbrain：gbrain serve - Connected就算接上了。官方文档也提供了通过 MCP 把 GBrain 接进 Claude Code、Codex 等 coding agent 的具体方式。

！踩坑提示 🕳

如果不指定 scope，MCP 很可能只注册到当前项目，导致你在目录 A 里能看到 gbrain，切到目录 B 就看不到了。跨 Session 实验经常需要切换工作目录，所以这类实验场景里一定要明确加上 --scope user，把它注册成用户级 MCP。

09

PITFALL

MCP 接上了，Agent 还是可能“失忆”

这是整篇文章我最想强调的一点。很多人以为 MCP 有了 Memory 工具，Agent 就自动拥有长期记忆了——实际不是这样。就算你给 Agent 提供了 search、remember、entity、synthesize、forget、context_pack、delta 这一整套工具，Agent 完全可能在用户提问后直接凭自己的理解回答，根本没调用 Brain。于是你会发现：“奇怪，我明明接了 Memory，怎么还是失忆？”

「工具提供的是能力，行为决定的是 Agent 是否真的会用这个能力。」

这也是整个实验过程里最容易被忽略的一层，很多“支持跨会话记忆”的宣传，其实都卡在这一步。

10

PROTOCOL

真正的 Memory 开关是行为契约，不是 MCP

我习惯把解决这个问题的方法叫 Brain-First Protocol，核心就三条。

1

Search-First：回答之前先查 Brain，尤其涉及项目历史、用户偏好、业务规则、已经做出的决策、过去发生的事实这些内容时，不能完全依赖当前 Context，要先问一下 Brain“过去有没有相关信息”。

2

Write-Back：产生新的长期有效事实之后，要写回 Brain。比如用户说“以后这个项目所有数据库修改都要先走只读检查”，这不是一次性的闲聊内容，而是长期有效的项目规则，理应写进去，否则今天 Session 知道，明天 Session 又是一张白纸。

3

Cite：使用 Brain 中的知识时要标明来源，比如注明这条信息来自 facts/brain-first-protocol-adopted-2026-06，这样以后出问题可以追溯——这条信息是谁写的、来自哪个页面、什么时候产生的、现在还有效吗。

这三条不是孤立的规则，而是一个闭环：Search-First 解决“读得到”，Write-Back 解决“存得下”，Cite 解决“信得过”。Search 完之后要能 Recall、Reason、给出 Answer，Answer 之后又要 Write-Back 进 Memory，Memory 再靠 Cite 保证可信——少一环，整个长期记忆链条都会出问题。

11

EXPERIMENT

别信“支持跨会话记忆”，自己做个实验

这部分我建议所有想上 Agent Memory 的人都亲手跑一遍，因为这是最容易被营销话术带过去的地方。实验目标很简单：Session A 写入一个事实，彻底关闭，重新打开一个零历史的 Session B，看它能不能把这个事实找回来。能，才算真正完成了跨会话记忆。

Step 1 · Session A 写入事实

在 Session A 里让 Agent 写下这样一条事实——slug 是 facts/brain-first-protocol-adopted-2026-06，内容记录 Brain-First Protocol 已经采用、状态为 ACTIVE、生效时间 2026-06，以及前面提到的三条规则。关键是不能让 Agent 只在聊天框里复述一遍，必须让它真正调用 GBrain 的写入能力，也就是走 Claude Code → MCP → GBrain → put_page这条链路写进 Brain，写完之后再读一次验证成功。

Step 2 · 彻底关掉 Session A

然后是最关键也最容易被人跳过的一步：彻底关掉 Session A。不要继续在 Session A 里问“你还记得刚才的内容吗”，这什么都证明不了，因为内容还在当前 Context 里。正确做法是写入 Brain 后完全退出，重新开一个没有任何 Session A 对话历史的 Session B。

Step 3 · Session B 主动检索

这时候在 Session B 里问：“我们之前采用的 Brain-First Protocol 是什么？现在状态如何？三条契约分别是什么？”正常情况下 Session B 应该主动调用 GBrain，从 Brain 里找到那条事实，再完整地把状态和三条规则复述出来。真正关键的不是它答对了，而是Session B 压根没有 Session A 的聊天历史——它之所以知道，完全是因为知识经由 Brain 从 A 传到了 B。

「记忆到这一步，才算从 Conversation Context 真正迁移成了 External Persistent State。」

我用来验证 GBrain 的实验材料里，A→B 这个环节也正是整套长记忆验证的核心：Session A 写入事实、完全关闭，再由零历史的 Session B 主动检索并引用来源。

12

TIMELINE

事实会变，记忆要能跟着改

只会“记住”还不够，真正的 Memory 系统还要解决事实变化的问题。比如测试数据库最初是 test-db-01，后来改成了 test-db-02，这时候问“现在测试数据库是什么”，答案当然该是 test-db-02，但更好的系统还应该能说清楚旧事实是什么、新事实是什么、变化发生在什么时候、当前状态是什么。

这说明 Memory 不是一个简单的 KV 缓存，它更接近“当前真相加持续时间线”的组合——这也是 GBrain 设计里很重要的一条思路：当前知识作为 compiled truth，同时保留完整的时间线证据。对企业系统来说这一点尤其重要，因为很多时候你问的不是“过去发生过什么”，而是“现在到底什么是真的”。

13

DECAY

Memory 也会“生病”

如果真让一个 Brain 跑上几个月，就会遇到另一个问题——它也会腐化。常见的几种情况包括：

Knowledge Drift

业务规则改了但旧文档还留着。

Duplicate

同一条知识被不同来源反复写入。

Contradiction

不同部门说法互相打架。

Stale Knowledge

曾经正确、现在已经过期。

Self-Poisoning

最危险的一种：Agent 自己写进去一条错误事实，后来另一个 Agent 把它当成真相继续引用。

一旦形成“错误写入→再次检索→当成事实→产生新结论→继续写入”的循环，就会自我强化下去，比传统数据库里的脏数据危险得多，因为人至少知道自己改过数据库。

所以 Memory 系统必须有自己的运维机制。GBrain 提供的 lint、doctor、dream这几个工具就是在解决这一层问题，其中 dream 更偏向发现知识漂移和潜在问题，而不是默认替你自动改知识——这个设计思路其实很重要，发现问题和修改事实最好分开处理，尤其在企业环境里。

14

TEAM

从个人 Brain 到团队 Brain

走到这一步，GBrain 已经不只是“个人第二大脑”了，下一步很自然会走向团队共享。想象一个研发团队里，Claude Code、Codex 和其他 Agent 都通过 MCP 接到同一个 Team Brain，共享 Knowledge、Entity、Fact、Timeline、Graph。问题也随之从“能不能记住”变成了谁能看、谁能写、谁能改、谁能删，哪些知识属于个人、哪些属于团队、哪些涉及敏感业务。企业级 Memory 最终一定会碰到 Permission、Isolation、Audit、Governance、Lifecycle这几个绕不开的词——说到底，Agent Memory 走到最后一定会变成一套 Knowledge Infrastructure。

真正成熟的架构，也不会要求员工每天手动把会议记录导入 Brain，那套系统大概率活不过一个月。更合理的方式是让 Slack、Email、Calendar、Git、CRM、会议记录、企业知识库这些数据源都接上 Connector，自动完成导入、编译，交给 Brain，最后给 Agent 用，出现冲突再进入治理流程。GBrain 目前已经提供 sync --watch、autopilot 这类自动化能力，官方安装文档也在持续补充不同数据源的接入方式。到这一步，Brain 才真正有了“生命力”——它不是一个静态知识库，而是一个持续更新的知识系统。

15

COMPARE

GBrain 和 Mem0、Zep、Letta 的边界在哪

这里要把边界讲清楚，GBrain 不是万能的。如果需求只是“记住用户喜欢什么”，不一定需要 GBrain，Mem0 这类 Memory Layer 可能更合适；如果需要对对话中的时间关系、实体和事件做持续建模，Zep 这样的 Temporal Knowledge Graph 路线更值得关注；如果需要让一个 Agent 自己长期运行、管理自己的状态和上下文，Letta 的 Stateful Agent 路线更贴近这个问题。而 GBrain 更擅长的，是把大量相对稳定或半稳定的知识、多来源资料、Entity、Fact、Graph 编译成一个 Agent 可以长期使用的 Knowledge Brain。

方案强项
Mem0用户事实、偏好、轻量 Memory
Zep时间关系、对话历史、知识图谱
LettaStateful Agent、长期自主运行
GBrain多来源知识、实体关系、Compiled Brain

所以别再问“谁的 Memory 最强”，这个问题本身就有点问题，真正该问的是——你的 Agent 到底缺哪一种记忆？

16

HYBRID

更现实的方案：混合架构

企业里一个很常见的场景是，产品手册、技术规范、售后政策、培训资料这类东西非常稳定，很适合做 Compiled Knowledge；但与此同时，客户工单、聊天记录、CRM 数据、实时库存、订单状态这些东西变化极快。硬把所有东西都塞进 GBrain 并不是最优解，更合理的架构是让 Agent 同时接入 Compiled Brain 处理稳定知识和关系、RAG 处理实时文档、Enterprise API 拿实时业务状态、Memory Layer 记用户偏好。这才比较接近真实企业 Agent 该有的样子。

以后再碰到 Agent Memory 的选型问题，不妨先问自己三个问题。

1

要记的是“用户”还是“知识”？如果主要是用户偏好、用户事实、用户历史，优先看 Memory Layer；如果主要是企业知识、项目资料、人员关系、会议决策、业务规则，就该考虑 Knowledge Brain。

2

知识变化快不快？稳定或半稳定的适合做 Compiled Knowledge，变化快的交给 RAG、API 或事件流，两者都有就做 Hybrid。

3

是不是多个 Agent、多个用户共同使用？个人用 Local Brain 就够了，团队需要 Team Brain 加权限和审计，到了企业级，就已经不是一个“记忆组件”能解决的问题了，而是要考虑 Knowledge Governance、Access Control、Data Lifecycle 和 Observability 这一整套基础设施。

∞

THE END

写在最后

回到最开始的问题：我们为什么会觉得 Agent“失忆”这件事很讨厌？因为我们默认它应该像一个同事。一个真正合作了几个月的同事，不会每天早上见到你都说“不好意思，昨天的事情我不记得了”，他该知道项目是什么、谁负责什么、过去做过什么决定、哪些事情已经改过、哪些规则不能碰、哪些信息来自哪里——更重要的是，他应该知道自己为什么知道。

这其实是企业 Agent 下一阶段很重要的功课：模型 + Context + Tools + Memory + Knowledge + State + Governance，缺一不可。过去我们一直在琢磨怎么让模型“更聪明”，现在冒出来的是另一个问题——怎么让 Agent 拥有一个持续存在的世界，这个世界里有人、有项目、有公司、有知识、有事实、有关系、有事件、有时间、有规则、有决策。

Agent 每次打开新 Session，都不该是从零开始，它进入的应该是同一个世界。

昨天发生的事情还在那里，新的知识可以继续写进去，旧的知识可以被纠正，有争议的知识会被标记出来。最终形成的，不再只是一个“会回答问题的聊天机器人”，而是一个有记忆、有状态、有知识、能持续工作的 Agent。这可能才是 RAG 之后更值得关注的一条路线：从“给 Agent 找资料”，走向“给 Agent 建一个可以长期存在的知识世界”。
