AI 出来后，很多人想过让 AI 帮我们"翻译"搜索意图。

但大多数方案的问题是：它们要么生成一段长篇大论的回答（还经常编），要么干脆就是套了层皮的传统搜索。

我们真正想要的其实很朴素——用自然语言提要求，搜索引擎帮我们找到真正相关的链接，而且按相关性排好序。

今天要聊的这个项目，就是冲着这件事来的。它叫 jev-search，来自 Search1API 团队，是 Jev 模型发布后最早一批跟进的开源项目之一。

演示站点 jev.s1.dev 上线后很快在开发者圈子里传开了。

更有意思的是，这个项目是一个完全独立的开源实现——不是 TypeSafe 官方出的 Demo，而是第三方团队看到 Jev 的能力后，马不停蹄搭出来的"杀手级应用"。

项目 README 里也特别注明了：这是一个独立项目，不是 TypeSafe 官方产品。

01

PART

项目简介

一句话：jev-search 是一个用自然语言搜索全网的 AI 搜索引擎前端，由 TypeSafe 的 Jev 模型驱动。

和你用过的大多数"AI 搜索"不一样，jev-search 不生成答案。

它返回的就是链接列表 + 摘要，和 Google 搜索结果页长得差不多。但区别在于：你可以用大白话提问，引擎自己帮你理解意图、选来源、限定时间、写搜索词，最后用 Jev 给每条结果打分排序。

举几个 README 里给的例子：

"Rust async runtimes on Hacker News this month"

"What do Reddit users think of the Framework laptop?"

"New papers on speculative decoding"

第一条你指定了来源（Hacker News）和时间（this month），第二条问了一个具体社区的看法，第三条连来源和时间都没说——让 Jev 自己选。

这些输入如果直接扔给 Google，结果会怎么样？你自己试试就知道了。但 jev-search 会把它们变成精确的搜索查询，同时跑多个引擎，最后合并、排名、流式展示。

02

PART

核心亮点

亮点一：不生成答案，只找结果

这可能是 jev-search 最"反 AI 潮流"的选择。现在市面上 AI 搜索的主流是：你问一句话，它给你写几段总结，来源链接放在下面。

jev-search 偏不。它就是帮你搜——搜完把链接和摘要摆出来，不做任何生成。

为什么？因为 AI 生成的总结有两个老毛病：一是会编（哪怕准确率再高），二是会漏（模型觉得不重要的信息直接跳过）。而开发者、研究者、重度信息获取者真正需要的是：所有相关来源的完整列表，我自己判断看哪个。

这个定位让它在 AI 搜索赛道里显得独树一帜——它不是你的 AI 助理，它是你的AI 搜索员。

亮点二：Jev 做"搜索裁判"，而不是搜索员

Jev 在这里扮演的角色很有意思。它不负责搜——搜索是 Search1API 对接的 Google、DuckDuckGo、Yandex、Reddit、Hacker News、GitHub、X、arXiv、YouTube、Wikipedia、IMDb、微信公众号等 12+ 个引擎同时并行跑的。

Jev 负责两件事：

第一，理解你的意图。 你输入一段大白话，Jev 会回答几个关键问题：

你想搜什么？（提炼成精确查询词）

你想看哪个来源的？（如果没说，Jev 帮你选）

你要什么时间段的？（这个月？这周？还是不限？）

这些问题的答案就是搜索的"路线图"。

第二，给结果打分。 所有引擎返回的结果会汇总到一起，Jev 对每条结果独立打分——这个链接和你的意图有多相关？分数 0-100，直接显示在每条结果旁边。

这比传统搜索引擎的内部排序透明多了。你能清楚地看到 Jev 觉得这条结果有多值得看，低分结果还会被单独归为"相关度较低"分组。

亮点三：多路并行，流式显示，不卡壳

搜索引擎最怕的是什么？等。Google 搜一次通常 0.5 秒以内，但如果你同时跑 12 个引擎呢？总不能等到最慢的那个回来才一起展示。

jev-search 采用了一个很聪明的设计：多路并行 + 流式输出。

个引擎同时发起请求，每个引擎有 15 秒的 individual deadline，整体 30 秒超时

哪个引擎先返回，它的结果就立刻出现在页面上

一个引擎挂了不影响其他引擎，页面上只会显示一个小 warning，而不是一个刺眼的"0 结果"

甚至 Google 还能在 Jev 还在理解你问题的时候就预启动搜索——Jev 和搜索是流水线跑的

你输入完一个复杂查询，先看到 Google 结果跑出来，然后 Reddit 的补充进来，接着 Hacker News、GitHub……像流水一样在页面上往上冒。

亮点四：完全透明的配置和可覆盖性

Jev 虽然会帮你选来源和时间，但它给你的"默认建议"不是死命令。每个 Jev 选择的来源和时间范围都会显示成可点击的标签（chip），你随时可以点掉它、加新的来源、改时间范围。

搜索词也是一样——Jev 生成的查询词会在页面上显示，你可以手动改。

这个设计很值得称道：AI 帮你做决定，但决定权始终在你手里。

03

PART

技术架构

jev-search 的技术栈选得很有想法，完全是为了"快"和"轻"设计的。

前端：TanStack Start + React

前端用的是 TanStack Start，一个基于 Vite 和 React 的全栈框架。

为什么不选 Next.js 或者 Nuxt？因为 TanStack Start 更轻量，而且原生支持 Cloudflare Workers 作为运行时——这直接让整个应用可以跑在边缘节点上，全球用户的访问延迟都很低。

后端：Cloudflare Workers

整个应用没有传统后端服务器。它部署在 Cloudflare Workers 上，这意味着：

全球 CDN 分发，响应速度快

按调用量付费，没有闲置成本

自带 KV 存储，用来缓存搜索结果（10 分钟到 6 小时不等）

自带 rate limiting，防止滥用

API 只有一个：POST /api/ask。它返回的是 Newline-Delimited JSON（NDJSON）——一种非常适合流式传输的格式。客户端拿到后逐行解析，每收到一个事件就更新页面。事件类型有四种：

intent Jev 理解完你的意图，告诉你它打算搜什么

found 进度计数，告诉你目前已经搜到多少条

lane 某一路引擎返回了排名后的结果

done 全部完成

三路 Jev Provider，自动 fallback

这部分设计得特别工程化。jev-search 支持接入 Jev 模型的三种方式：

Provider调用方式需要什么
TypeSafe 官方api.typesafe.ai/v1/systemoneTYPESAFE_API_KEY
Vercel AI Gatewayvercel.com/ai-gatewayAI_GATEWAY_API_KEY
Cloudflare Workers AIWorkers 内置绑定无（从 Cloudflare AI Gateway 额度扣）

三个 Provider 可以按优先级排列，主 Provider 失败了（402 没钱、429 限流、5xx 错误）自动切下一个。

本地开发时甚至可以完全用 Cloudflare Workers AI——连 API Key 都不需要配，直接通过 wrangler login 的会话就能调用。

搜索引擎大盘

Search1API 在背后对接了十几个引擎，分三种：

通用搜索 Google、DuckDuckGo、Yandex

社区聚合 Hacker News（专用 news endpoint）、Reddit、GitHub

垂直引擎 X（Twitter）、arXiv、YouTube、Wikipedia、IMDb、微信公众号

每个引擎有独立的适配器，Google 甚至同时在两个场景下被调用——通用搜索 + 社区的 site: 限定搜索。

从 jev-search 看 Jev 的真正玩法

我觉得 jev-search 最有意思的不是它做了个搜索引擎，而是它展示了 Jev 在实际产品里的正确用法。

很多人刚接触 Jev 时会想："哦，一个更快更便宜的 LLM，那我把项目里所有 GPT-4 调用都换成 Jev 不就好了？"

这完全想错了。Jev 不会写作、不会写代码、不会解释概念。它就是一个结构化决策引擎——给它一堆选项和上下文，它返回你该选哪个、有多确定。

jev-search 的做法是把 Jev 放在了两个恰到好处的位置：

理解层 把模糊的自然语言请求"翻译"成精确的搜索参数（查询词 + 来源 + 时间）

判断层 把搜索结果从"可能相关的一堆链接"变成"按相关度排好序的列表"

这两件事传统 LLM 也能做，但成本和延迟都不对。

搜索引擎这种高频场景，每一个查询都要花你几秒钟和几毛钱？那干脆别做了。但 Jev 把这两件事的成本压到了几乎可以忽略不计——每次调用几毫秒，成本不到一分钱。

这就是 TypeSafe 说的那句话："We're building prod, not God."（我们做的是生产工具，不是上帝）。Jev 不是用来让 AI "变聪明"的，是用来让已经很聪明的 AI 变得能用、敢用、天天用的。

写在最后

jev-search 还在很早期，代码里能看到一些打磨的痕迹——比如它在 Cloudflare Workers AI 上的调用还依赖 wrangler login 会话而不是独立 API Key，比如它的缓存策略还是比较粗粒度的固定时间窗口。

但这都不重要，重要的是它把一个一直被"AI 生成答案"的大方向盖过去的小需求挖了出来：

有时候我们不需要 AI 告诉我们答案是什么，我们需要 AI 帮我们更快、更准地找到答案在哪。

而在这件事上，Jev 确实比传统 LLM 好用太多了。
