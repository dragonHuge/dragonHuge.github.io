我：deepseek 新开源了个项目叫 DeepInfer，是他们的推理框架。拉下来看下有哪些亮眼之处。https://github.com/deepseek-ai/DeepInfer

dsh：先给两个底数：仓库 10-16 建的，到今天是四天、1.28 万 star、124 个 open issue，但只有 3 个 commit——初始提交加两次文档更新。这个比例本身就有信息量，先记着，后面聊。 读完我的结论是：这不是"又一个 vLLM 复刻"，它的稀缺性不在 kernel 快，而在于把推理系统里那些通常靠人肉调参和经验拍板的决策，变成了可计算、可在线修正的优化问题。 四处落点。 第一处，调度器。csrc/engine/flops_estimator.hpp 用 330 行把整个模型的 FLOPs 写成了解析式：每层按 KV 压缩比（0/1/2）、稀疏 indexer 的 top-k、SWA 窗口、YoCo 截断、mHC、Engram、LM head 分别建模，用闭式前缀和算 query-key 对数。它连"FP4 存权重不等于 FP4 算"这种口径都写进注释了。这个模型是开源的，但用它的那层没开源——Q&A 说 prefill 每步有 compute_quota_limit 时间预算，用拟合的二次代价反解 chunk size，但我在代码里 grep 不到 compute_quota。正好卡在"开源引擎 / 闭源负载均衡"那条缝上。 第二处，投机解码的验证长度。csrc/engine/mtp_varlen.hpp 是全仓最漂亮的一段：把 confidence head 预测的每个 draft token 接受率排序，逐个往上加，目标函数是"期望接受 token 数 / 单步耗时"。先定全局最优 total_q，再按接受率降序给每个请求分配验证长度。这一步的输入是启动时自测的 (batch→ms) 曲线、在线学出来的上下文斜率、再加快样器的耗时中位数。 第三处，KV 重算。YoCo 加 SWA bounded replay：cache miss 时只重算最近 128 个 token，把注意力窗口截断在重放段内，于是重算成本与上下文长度、层数都无关。命中策略是"命中长度由 block KV 决定，末尾那块要不要重算由 SWA KV 决定，缺了就退一个 block"，上限 L−134。 第四处，这两个东西的组合。异步调度本身不新（SGLang 有），难点在组合处：跑 schedule(N+1) 时第 N−1 步的接受率还没回来，CPU 根本算不出 per-request 的验证长度。他们的解法是 CPU 只定总预算，per-request 长度交给 GPU 侧的 TileLang kernel 算完写回 pinned buffer，再由 metadata remap 读回修正。这套"第一步乐观调度、第二步在设备端修正"，目前我没在别的开源框架里看到完整实现。 另外两条工程规范值得单独提。一是批不变性被 CI 钉住：test_batch_invariant.py 用 golden_token_ids 强制单条跑出和 batch 完全一致的 token，再逐位比对 50 步的 logprobs 和 top-5——比"比 argmax 是否相同"严格一个量级。二是双芯片的数值一致性：近 30 个 kernel 每个都有 CUDA 和 Ascend 两份实现，asc/rstd_1ulp.py 为了让昇腾上的 RMSNorm 和 NVIDIA 数值一致，用 compensated arithmetic 重写了整个归一化。跨厂商要复刻的是 1 ULP。 但也有明确的门槛。硬件只有两条路：SM100 + CUDA 13，或者昇腾 950 + CANN 9.2；社区在提 SM90 移植的 RFC 时提到 FlashMLA 已经在 9 月底删掉了 Hopper 分支，两个独立 issue 的说法一致，我没有回到 FlashMLA 仓库逐 commit 核实。最小高效部署单元是 64 卡 prefill 加 64 卡 decode。而且开源的是 engine，不是 service：没有 HTTP server、没有 KV 存储、没有 P-D 分离、没有跨 DP 路由——这些恰好是"做一个服务"最脏的那层。

我：我有一个地方没看懂。投机解码的验证长度做成在线动态的，这一点我不太理解——理论上模型和解码头在 serving 时都是固定的，那最优点为什么会不断迁移？这是在假设用户问题的分布会不断变化吗，还是说它是一个逐 batch 的动态变化？

dsh：你的直觉对了一半——模型固定 → 接受率分布固定，这个前提没错。错的是那个函数的目标：他们优化的不是"接受率"，是"每毫秒换多少已接受 token"。这个比值里，分母不是常数。 先说分子为什么会漂，有三层。请求之间差异巨大，同一步 batch 里，代码补全的接受率可能到 0.9，数理推理可能只有 0.4。draft 深度上单调衰减，第 1 个 draft token 的接受率远高于第 5 个，这是所有投机解码的共性。第三层最容易被忽略：同一个请求在自己生命周期的不同阶段会跳变——思考段低、正文段高、遇到结构化的收尾符号高、遇到开放决策点低。所以哪怕只有一个请求、batch 恒为 1，最优验证长度也不是常数。同一个请求在 10K 上下文和 100K 上下文时，长的不是同一个请求。 但真正的主因在分母。验证更多 draft token 的代价不是线性的，而是阶梯状、并且带上下文依赖。CUDA graph 按 batch size 分桶，total_q 落在哪个桶决定这一步耗时；启动时测的曲线不含上下文长度影响，所以他们在线学一个斜率项——(forward_ms − baseline) / graph_size，每个 batch size 用两层中位数估。这个斜率存在的唯一理由就是：同样是多验证一行，10K 上下文的一行和 100K 上下文的一行价格不一样。再加快样器耗时随行数涨（每个请求一行 logits 要做基数选阈值），也进分母。 于是"多验证一个 token 值不值"变成：边际收益 = 该位置被接受的预期概率；边际成本 = f(当前 batch 落在哪个 graph 桶, 该 batch 的总 KV 长度, 当前快样器开销)。成本项每步都在变，因为 batch 组成在变、请求进出不可预测。这就是为什么它必须是逐 step 的全局预算分配，而不是每请求一个常数：验证预算是这一步所有请求共享的一个池子，多给 A 一行就少给 B 一行。 代码里就是把这件事写成一个贪心背包：按接受率降序排所有请求的所有 draft 位，逐个往上加、每加一个就重算期望收益除以耗时，取全局最优的 total_q。而且这个贪心只在桶边界上评估，说明他们明确承认了阶梯性。 顺带回答一个隐含问题：为什么不用实测接受率、而要用 confidence head 预测？因为实测率是上一轮的——在异步调度下，本轮调度时上一步的接受结果还没回来，而新请求根本没有历史。head 在同一次 forward 里就给出本轮、每个请求、每个深度的预测，代价是一个融合 kernel。所以它是"预测 + 用上一轮校正"的混合。 有意思的是数据能反过来验证这套解释。Q&A 那张表：16 并发是 −1.5%，60 并发 +5.4%，96 并发 +11.0%。这跟接受率没关系，跟当前步是不是算力受限完全对应。低并发是 launch-bound，bs=16 时 q=3 和 q=16 的墙钟时间几乎一样，这时候砍掉 30% 的验证行不省任何时间、只是白丢已接受 token，所以净负；高并发是 compute 和 KV 带宽受限，total_q 从 480 降到 311，省的是实打实的 30%，所以 +11%。所以更准确的一句话是：动态验证长度的收益不是"接受率相关"的，是"这一步的验证行是否真的贵"相关的。 这个量只有 batch 组起来之后才知道。

我：这个解释我接受。而且我觉得整套框架确实体现出一种趋势——凡是需要决策的环节，都尽量做成在线自动决策。这个理念本身是好的。顺着想一个问题：假设硬件资源充足，真的要跑起来这套东西，需要多大的工作量？考虑 AI 协作的前提下。

dsh：先把"硬件充足"定义清楚：离线跑通，单机八张 B200（192GB）够，FP4 权重约 499GB 加上 KV；但要接近它宣称的性能，decode 侧推荐 EP64 到 EP128 在一个 scale-up 域内，也就是至少一个机柜级配置。这两个目标差一个数量级。 在报工作量之前，我核了两件事，都显著改变了估算。 第一件：开源版没有前缀缓存。 csrc/engine/block_manager.hpp 是一个纯 free-list 加引用计数加 pin 的分配器，没有任何 hash 化的前缀匹配。调度器里那个 prefix_caching_hit 变量只表示"这个 seq 进来时已经带好 block table 了"，是 fork 出来的分支或者闭源 entrypoint 帮你填好的。也就是说每个请求都要从头 prefill。对 chat 短对话还能忍，对 agent 负载是灾难级——不是少个优化，是成本模型完全不成立。这一条 README 没说是缺失项，只说"KV cache 系统未包含"，我觉得是最容易被低估的坑。 第二件：HTTP 层基本是给的。 deepseek-recipe 可以直接 pip 装，而且仓库里带 server-rs（Axum）和 server-py（FastAPI）两个 mock inference 的 API 服务示例。三套协议的转换、prompt 渲染、流式解析、tool call、response_format 到结构化输出的映射，全是现成的，你只需要把 mock 那一行换成引擎的 step。这一条把原本"服务化三周"砍到一到两周。 分阶段：环境与构建（六个子模块、CUDA 13、gcc 13、固定版本的 torch 与 flash-attn、500GB 权重下载）两到五天；离线跑通加数值对齐三到五天，他们自带 golden PPL 和 eval harness，验证极便宜；单副本服务化七到十二天；前缀缓存十到二十天，这是 C++ 调度器里的活，最危险；多副本路由加失败切换十到十五天；调参五到十天。合起来：可用单副本约 25 人日，完整多副本约 45 到 65 人日。 AI 的乘数只有 1.3 到 1.8 倍，不是很多人预期的 5 倍。它在"读 47k 行代码、200 个环境变量、写样板代码、翻译成熟设计"上赢，在"NCCL hang 定位、显存预算、数值不一致、profiling 驱动的调参"上不赢——后面这几项的成本由机器回路决定，不由打字速度决定。AI 最大的优势是廉价地大量迭代，而这个场景每次迭代都要八张卡跑一遍，优势被压掉了。 但最关键的一句是：跑起来和能用是两件事。 即使 64 卡到位，还差三样——没有 P-D 分离，TTFT 和 TPOT 互相绑架；没有 3FS KV 存储，跨副本零共享；没有跨 DP 负载均衡，多副本只能盲路由；而且因为没有前缀缓存，连"按前缀粘性路由"这个经典技巧都用不上。对照他们自己的数据，EP8 和 EP64 的 decode 曲线差出数量级的一部分。所以真实画像是：两三个月拿到一个正确、可服务、但吞吐只有人家零头的系统。 所以我的建议很直接：如果你的目标是部署 V4.1-Flash 这个模型，不该选 DeepInfer。 模型是 MIT、HF 上近两千 like，SGLang 和 vLLM 跟进是必然——V4 的结构里 MLA、压缩 KV、稀疏 indexer、MoE 全是它们已有的积木。等两三个月拿一个有人帮你修 bug 的版本，性价比高一个量级。DeepInfer 值得投入的只有三种情况：你就是要 B200 上这个模型族的极致性能且愿意养 serving 团队；你要走昇腾路线（这是目前唯一给出双后端对等实现的公开代码）；或者你要建 serving 团队拿它当参考设计——而这种情况读就够了，不需要跑。

我：deepseek 的 infra 团队在世界上也能算顶尖水平，你觉得他开源这个东西的主要目的是什么？

价格仍然保持一个稳定价差，那护城河在规模与反馈回路，设计知识不是护城河；如果设计和价格一起收敛，那这个领域已经商品化，没有护城河只有节奏；如果设计收敛而价格分化加剧，说明真正的变量是我们都还没命名的东西。 最后收到个人层面。护城河的定义可以收缩：你不可能有机队，但"规模耦合的反馈回路"有个人版——你手上有别人没有的、某个具体场景的生产失败分布。这次 DeepInfer 总结

一、DeepInfer 的技术密度集中在"省"上，不在"快"上。 能推导的不存（稀疏 indexer 的 K 从主压缩 KV 的 pre-RoPE latent 派生，所以那套专门给 indexer 用的压缩累加器在 V4.1 里干脆是空的）、能借用的不算（后 20 层压缩 KV 由 encoder 最后一层的 shared hidden 投影出来，不逐层重算）、能截断的不重算（128 token 的 bounded replay）、能省的带宽不用 copy engine（GDR 而非 cudaMemcpy）。按配置与 Q&A 交叉推断，V4.1 是 20 层纯 SWA 加 20 层压缩 KV 的结构，这也是"1M 上下文却能压到单会话 1.4MB 持久化状态"的来源。四个方向一致，而且每一步都把省下来的收益折算成了明确数字：单会话持久化状态 1.4MB、prefill 计算近乎减半、生产点吞吐 +4% 到 7%。

二、动态验证长度是"分母优化"而不是"分子优化"。 模型固定意味着接受率分布固定，但目标函数是"每毫秒换多少已接受 token"，而分母取决于这一步 batch 落在哪个 CUDA graph 桶、这批请求的总 KV 有多长、快样器要处理多少行。同一份数据里 16 并发是负收益、96 并发是 +11%，说明这个优化的收益与接受率无关、与"这一步是不是算力受限"强相关。它必须在 step 级重算，因为验证预算是这一步所有请求共享的一个池子。

三、这份开源的真实产出不是代码，是"问题排序"。 代码对直接竞争对手价值有限（没有机队和 3FS 复现不了成本结构），但它免费给出了"该往哪里投研发"的答案，而问题排序是基础设施研发里最贵的输入。开源切口的精确度本身就是实力展示：能切在"单集群可复现"与"必须有机队"之间，说明团队对自身优势的位置有非常清晰的认知。

四、infra 的护城河不是设计知识，是"负担得起做实验"。 动态验证长度这条设计需要 60 以上并发才划算，也需要同等规模的流量才能验证该不该做——你需要规模才值得优化，也需要规模才验证得出该不该优化。设计知识会随公开而折旧，这条反馈回路不会。由此推论：看不清护城河，可能是因为这个市场在按"速率"而不是"存量"计分，而速率没有位置可占。

一个可证伪的预测

关注设计收敛之后，价格是否跟着收敛。 三个分支互斥、可观测、有半年到一年的时滞：

  1. 十二个月内，非 DeepSeek 的团队把 wide-EP、动态验证长度、类 YoCo 的 KV 重放都做出来了，但同等级模型质量的每百万 token 价格仍保持稳定价差 → 护城河在规模与反馈回路，设计知识不是护城河

设计与价格一起收敛 → 这个领域已商品化，没有护城河，只有节奏

设计收敛、价格分化加剧 → 真正的变量是我们还没命名的东西（候选：单位算力的有效 token 产量，一个跨模型、跨硬件的系统级指标）

配套的两条更窄的：DeepInfer 仓库本身在未来半年基本静止（commit 数 <20、无 roadmap、KV 存储与跨 DP LB 缺口不补），而 deepseek-recipe 反而持续维护（跟进新模型版本与协议变更）——若成立，说明前者的目的是宣示、后者的目的是标准化。反面证据是：他们开始认真 triage issue、合并社区 PR、补 KV 存储、甚至支持 Hopper，那"证明题而非交付物"的判断就不成立。
