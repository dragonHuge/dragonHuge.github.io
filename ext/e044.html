先认识一下 Seata

做微服务的人，差不多都碰到过同一种事故：订单写进去了，库存没扣掉，钱倒是先收了。三个库各自的本地事务都没问题，合在一起就不是同一件事。

Seata 补的就是这一截。它是 Apache 孵化中的分布式事务方案，最早在阿里内部扛过多年大促，2019 年开源。你可以把它想成交易现场的协调员。业务服务负责说「这单要一起成，或者一起撤」，Seata 负责把这句话带到每一个参与方，并盯着还没做完的那一部分。

角色就三个，名字有点古板，记场景就够了。

  • TM 是发起人。下单接口上标一个全局事务，由它来开口和收尾。
  • RM 是各个资源的管家。订单库、库存库、账户库，各自向协调器登记自己的分支。
  • TC 是协调器，也就是 Seata Server。全局事务记在这里，提交或回滚由它来推。

模式也不止一种。想少改代码，用 AT，它记下数据改之前和改之后的样子，出问题再补回去。想自己把每一步写清楚，用 TCC。流程长、步骤多，用 Saga。数据库本身支持 XA，就走 XA。日常业务里，AT 出现得最多。

一段很常见的下单写法是这样：

- - - - - - - - -

/**
 * 创建订单。订单、库存、账户要么一起成功，要么一起撤回。
 */
@GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
public void createOrder(Order order) {
    orderService.save(order);
    storageService.deduct(order.getSkuId(), order.getCount());
    accountService.debit(order.getUserId(), order.getAmount());
}

方法顺利跑完，TC 推动各分支提交。中途抛了异常，已经做过的分支会被拉回去。这套机制这些年没变，AI 也没有接手「这单要不要提交」。

控制台里多了一个会听话的助手

新的部分在 Console。2.6.0 把 NamingServer 和 Console 升到了 JDK 25、Spring Boot 3.5，并引入了 Spring AI 的 MCP 模块。MCP 可以理解成大模型的通用插口：模型不直接连你的库，而是通过一组事先声明好的工具去问 Seata。

这项能力默认开着。传输用 Streamable HTTP，端点是 /mcp，也可以改成 SSE。Console 管登录和权限，MCP Server 把模型的工具调用翻译成对 TC 的请求，NamingServer 告诉它该找哪一台 TC。

模型能分担的，主要是值班时那些重复动作：

  • 按 XID、应用名、状态、时间范围查全局事务，需要的话把分支一并带上。
  • 把提交失败、回滚失败、超时回滚失败这类异常事务捞出来。
  • 查全局锁，看有没有一把锁占得太久。
  • 看服务端日志。AT 模式下，还可以把 undo log 读成能看懂的样子。
  • 暂停重试、重发提交或回滚、删除会话、释放锁。凡是会改数据的，都要人先点头。

社区也聊过更远的事，比如用模型做异常检测，或者让 Saga 去接 Agent 工作流。那些还在探索。眼下能直接用的，就是「用嘴问控制台」。

一句话是怎么走到事务协调器的

你在 Cursor 或 Claude Desktop 里说「帮我看看 order-service 最近有没有提交失败的事务」，后面大致是这么走的。

查哪一台机器，不是模型猜的。它会先拿到一份 NamingSpaceDetail，里面有 namespace、cluster 和 vGroup。后面的查询都带着这份地址走。

写操作更谨慎。模型不能自己说「我确认了」。它得先把影响讲清楚，等你输入带有「确认」或 confirm 的句子，再去换一把修改令牌。令牌只活 120 秒，过期就要重新要。

接到 Cursor 上

Console 和 NamingServer 部署在一起时，不用再单独填 NamingServer 地址。MCP 的默认配置写在命名服务那份配置里：

- - - - - - - - - - - - -

spring:
  ai:
    mcp:
      server:
        protocol: streamable          # 传输方式，默认即可
        streamable-http:
          mcp-endpoint: /mcp           # 客户端要连的路径
        name: mcp-server
        version: 1.0.0
console:
  user:
    username: 你的用户名
    password: 你的密码

Console 如果是单独拆出去的，把 NamingServer 地址补上，不然 MCP 找不到 TC。

客户端还要带登录令牌。先用控制台账号登录，取出返回数据里的 token，放进请求头。Cursor 里可以这样接：

- - - - - - - - - -

{
  "mcpServers": {
    "seata": {
      "url": "http://127.0.0.1:8081/mcp",
      "headers": {
        "Authorization": "Bearer 这里换成控制台登录返回的 token"
      }
    }
  }
}

端口按你的实际部署改。官方示例里请求头前缀写成了 Bear，接到客户端时用标准的 Bearer。Cursor 调用工具没有问题，不过开了自动选模型时，偶尔会漏掉「先查清楚，再请人确认」。真要删数据，看一眼它准备提交的参数。

接到 Claude Desktop 上

Seata 官方更推荐 Claude Desktop。它把工具调用走全，也比较听「先查再改」这句话。接法和 Cursor 不一样：配置文件只认本机启动的程序，直接写一个 url 不但连不上，新版本还可能把整段 mcpServers 清掉。

Seata 暴露的是 HTTP 端点，所以中间要垫一层 mcp-remote。它由本机的 Node.js 拉起来，一边用标准输入输出跟 Claude Desktop 说话，一边去请求 Console 的 /mcp。电脑上先有 Node.js，再完全退出 Claude Desktop，然后改配置文件。

Windows 上文件在 %APPDATA%Claudeclaude_desktop_config.json，也就是 C:Users&lt;用户名&gt;AppDataRoamingClaudeclaude_desktop_config.json。macOS 在 ~/Library/Application Support/Claude/claude_desktop_config.json。文件已经有别的服务时，只往 mcpServers 里加 seata 这一段，别把原来的覆盖掉。

- - - - - - - - - - - - - - - - - -

{
  "mcpServers": {
    "seata": {
      "command": "npx",
      "args": [
        "-y",
        "mcp-remote",
        "http://127.0.0.1:8081/mcp",
        "--allow-http",
        "--header",
        "Authorization:${AUTH_HEADER}"
      ],
      "env": {
        "AUTH_HEADER": "Bearer 这里换成控制台登录返回的 token"
      }
    }
  }
}

--allow-http 是给本地的 http:// 地址用的。令牌放在 env 里，请求头写成 Authorization:${AUTH_HEADER}，冒号两边不要加空格。Windows 会把参数里的空格拆开，写成 Authorization: Bearer xxx 经常一启动就认证失败。

保存之后重新打开 Claude Desktop。输入框旁边出现锤子或工具图标，里面能看到 seata，就说明桥接成功了。第一次启动会通过 npx 拉包，多等几秒是正常的。

对话可以新建一个项目，把下面这几句放进自定义指令。官方文档里有一份更长的系统提示，日常用这几条就够：

- - - - -

你是 Seata 值班助手。
先查清当前状态，再谈修改。
删除、改状态、暂停重试、释放全局锁，都必须等我自己输入带有「确认」的句子。
不要替我生成确认句，也不要自动调用 confirmAndGetKey。
时间用 yyyy-MM-dd HH:mm:ss。

然后可以这样开场：

先列出现在能连上的 TC 节点。连上 default 之后，看 order-service 今天有没有 CommitFailed 的全局事务，分支一起带上。先别改任何东西。

Claude 会先调 getTCNameSpaces 拿节点，再去查异常事务。确认它真的停得住，再进入改状态。一轮正常的对话长这样：

- - - - - - - - - -

你：暂停这笔事务的提交重试，XID 是 192.168.1.20:8091:28419331。

Claude：这笔事务当前是 CommitFailed，下面有 3 个分支，库存那个二阶段提交失败。
暂停之后，TC 不会再自动重试提交。
请输入：确认停止事务 192.168.1.20:8091:28419331

你：确认停止事务 192.168.1.20:8091:28419331

Claude：已拿到修改令牌，这笔事务的提交重试已暂停。
令牌 120 秒内有效，这次已经用掉了。

它要是没等你这句话就准备调用修改工具，把那次调用拒掉。查询可以放手，改状态不要放手。

两个可以照着问的例子

先把异常事务捞出来。 不用背状态码，直接说：

查一下 default 命名空间里，order-service 从今天零点到现在的异常事务，分支也带上。

模型会去调异常事务查询。它重点看的是提交失败、回滚失败、超时回滚失败，以及两边的重试超时。你希望它收回来的是一段人话，而不是一坨 JSON：

- - - - - - - - - - - - -

发现 1 笔需要处理的事务

XID：192.168.1.20:8091:28419331
应用：order-service
事务名：create-order
状态：CommitFailed（提交失败）
开始时间：2026-11-07 01:18:06
分支：3 个
  - order_db.t_order        一阶段已完成
  - storage_db.t_stock      二阶段提交失败，还可以重试
  - account_db.t_account    一阶段已完成

库存这次没提交上去。可以先看服务端日志，确认库存服务当时是不是不可达。

它要是没把分支展开，补一句「把 withBranch 打开」就行。时间用 yyyy-MM-dd HH:mm:ss，比如 2026-11-07 00:00:00。分页别开太大，一页 20 到 100 条够用。

再看一把不肯松手的锁。 业务上通常是：同一行库存改不动，新事务一直在等。可以这么问：

t_stock 上有没有拿了超过 10 分钟的全局锁？有的话告诉我是哪笔事务拿着，先别删。

这一步只查询。模型应该回报表名、主键、XID 和分支号。你核对过业务数据，确实要放锁，再单独说删除，并且自己输入确认句，例如：确认删除事务 192.168.1.20:8091:28419331 的全局锁。这句话不要让模型替你打。
