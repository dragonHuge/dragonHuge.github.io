我：今天想聊 Cloudflare 昨天发的那篇事故报告——GLM-5.3 在 Workers AI 上跨请求泄露了用户的 KV cache。你先把这个机制讲清楚，我关心的是它为什么会跑出"一切正常"的样子。

dsh：先把机制摊开，因为它比"又出安全漏洞了"精细得多。 Cloudflare 在 Workers AI 上用 SGLang 跑 GLM-5.3，disaggregated 部署：一组 prefill GPU 处理 prompt、产出这块 prompt 的 KV cache，通过 RDMA（Mooncake）交给 decode GPU 去逐 token 生成。KV cache 在显存里是个共享的定长页池，请求结束归还页，但页不清零——下一个拿到该页的请求直接覆盖。这是所有推理引擎的通行做法，也是性能的必要条件，代价是"页的归属和生命周期"变成引擎自己的责任。 事故由两个条件咬合而成。 第一，池子比上下文小。他们配了 1,048,576 token 的上下文窗口，但 prefill 的 KV 池只装得下 681,280 token。而且这个池子不是配置项——SGLang 启动时按"模型权重加载完剩下多少显存"自己算出来的，模型公布的 context length 是另一个独立配置值。没有任何机制强制两者一致。 第二，超长请求的拒绝路径在 disaggregated 模式下是坏的。请求塞不进池子时，SGLang 调度器会拒绝它：错误记下来、prompt 换成一个 token 的占位符，让它走完批处理机制。单机部署下这没问题——占位符跑完，客户端收到 error。但 P/D 分离之后，prefill 和 decode 的 admission 队列查的是 req.finished()，不是"是否被拒绝"。而被拒的请求把错误存在 to_finish 字段、不是 finished_reason，所以 finished() 仍然返回 False——它看起来还活着。 于是：router 告诉 decode"这是 8 页 prompt"，decode 预留 8 页；prefill 只发出去 1 页占位符的 KV，然后发了个"transfer complete"；decode 认为前 8 页都被本次请求写过了，开始 attention，读了全部 8 页——P1 到 P7 还是上一个用户的 prompt 和半截生成。客户端收到 HTTP 200。 然后是这次事故最值钱的部分：所有信号都是绿的。prompt_tokens 对得上，状态码 200，回复连贯——因为那确实是真模型生成的连贯文本。甚至比正常的 8 页 prefill 还快，因为只 prefill 了 1 个 token。Cloudflare 自己在复盘里写得很不客气：他们 pre-launch 只验证了 HTTP 状态码和长上下文下的引擎性能，没有验证模型输出本身和连贯性。 还有一个日期得指出来：这个 bug 7 月 6 日就有人报给 SGLang 了（issue #30233）。Cloudflare 是在查自己的事故时才发现这条已存在的报告。这个洞在公开的 issue tracker 里躺了两个月，而所有跑 P/D 分离 SGLang 的人当时都在同一条船上。 现在把第二篇叠上来，因为它是同一枚硬币的另一面。做 agentic coding 时，cache read 占总 token 支出的 96%–99%，cache 命中率 90%–100%。因为每一轮对话的整个历史都在 cache 里，你每一轮都在重读它。所以 Fable 5.1 那把 cache 读价砍 75%，等价于整体成本砍 70%–75%——"cache 费用只是账单脚注"完全是错觉。Anthropic 说 Opus 5.5 "requires less compute to serve than Opus 5, and its pricing reflects that"，降的也是这个。DeepSeek V4 Flash 的 cache 读价定在 input 的 2%，OpenAI 和 Anthropic 是 5%–10%——那 80% 的降价基本就是在这上面打的。 所以两篇拼起来是一句话：KV cache 既是你 96%–99% 的钱，也是你能把别人数据串进你回复的那块内存。而且降本的全部杠杆都压在"让 cache 更便宜、复用更狠"上，也就是说这个 tradeoff 没有任何松动的趋势。 然后是修复的代价，这里跟直觉正好相反。SGLang 测了 21 组 2×H100 的跑，吞吐差异全在 ±2% 以内，95% 置信区间个个跨零；H200 上把特性默认打开的代价是 −0.38%，置信区间 −2.12 到 +1.36，不显著。Cloudflare 那个"给每个物理页打 tag、decode 读之前校验"的原型，性能代价不到 1%。 也就是说"安全和性能要 tradeoff"在这件事上根本不成立——隔离不是被性能挤掉的。那它为什么还是会漏？我的答案是代价全部转移到了状态复杂度上：修复不是"加一行判断"，而是给跨节点的共享可变页所有权做延迟释放、要处理 ack 快慢路径、要保证 prefill 和 decode 的 ack 格式不版本错配（一方新一方旧就直接退化到超时兜底）。这部分没有 benchmark 能给你打分，也不会在压测里暴露。 所以我最想问的是：如果你自己搭这套东西，或者选型一个 serving 引擎，"池子装不装得下上下文"这种不变量，你打算靠什么把它钉死？靠部署时的人工 checklist，还是靠引擎把它变成启动就 fail 的硬断言——而后者意味着引擎要替你决定"宁可起不来也不要带病跑"，这跟推理引擎追求吞吐、弹性、不停机的整个设计哲学是冲突的。你觉得这个责任该落在引擎上，还是落在地上那个部署的人身上？

我：这类工程上的取舍似乎也不算一个新的问题。虽然我们常说 "no error should pass silently"，但是线上系统很多非致命模块实际都被 try-catch 放行。这个错误其实也是在系统有迹可循，只是被放过了。从责任上讲我觉得还是引擎的责任，至少这类问题应该让使用引擎的人知道，落地层主动排查出这个问题还是要求有点高，可能对部分应用是永远不会碰到的场景。

dsh：你那个 try-catch 的类比，对了一半——但恰恰是"不对"的那一半，决定了这次事故该归到哪一类问题里。 先说同意的部分：工程系统里"非致命模块被静默放行"确实满地都是，这也不是新问题。而且你说"这个错误在系统里有迹可循，只是被放过了"，从结果看完全对。 但它不是"放行"。try-catch 放过的前提是有人先抛了东西出来，你看见了、判断了、决定不处理。这里从头到尾没有任何一层抛出、吞掉或降级——错误被正确地记录进了 to_finish，本来就准备返回给客户端；出问题的是之后那句"这个请求现在还能不能进解码器"的判断，它去读了 finished()，而 finished() 回答的是另一个问题。 这不是异常被吞，是两个状态被压进了一个布尔值：rejected 和 live 合并成了 not finished。这个区别不是抠字眼，因为两类问题的修法正好相反：

  • 静默放行是纪律问题，修法是"别吞异常"、加告警、加 fail-fast 的文化。
  • 状态合并是契约问题，修法是把谓词换对（SGLang 的正式修复 #38935 就是提前在 admission 阶段按 rejected 拒掉，根本不让它进 handoff）、以及让"我预留了 8 页"和"你实际传了 8 页"对得上（他们后来加的 decode 侧校验传输 token 数）。

对着这次事故喊 "no error should pass silently" 是打空的，因为没有任何 error 被放行过。这就是它难抓的原因，也是为什么它值得单独写一篇——它把"可观测性"这个词的边界暴露出来了：你能观测的只有你想到要观测的东西，而这个 bug 是在你没定义的字段上说谎。 还有一个词我得顶回你，就是"取舍"这个词本身——我认为这次事故真正的教训，是它把"取舍"这个说法也否掉了。 Cloudflare 自己写了："We were aware of this mismatch before launch." 他们知道上下文 1,048,576、池子 681,280，知道这两者不一致。他们以为自己在做什么？以为自己接受了一个可用性上的降级：超长的请求可能会失败、可能会慢，但引擎会优雅处理。他们的测试甚至"支持"了这个判断——长上下文压测返回了成功的 HTTP 状态码和正常的流式响应。 所以他们以为自己在舍的是 A 类代价（长 prompt 可能报错），实际舍掉的是 B 类代价（多租户隔离）。这两个的代价不在一个量级上，而且方向相反。 当事人以为自己舍的是 A、实际舍的是 B，这不能叫取舍——那叫误判了在不舍什么。而一旦这么看，"责任在引擎还是在地上的人"这个问法就变了，因为这次地上那个人信息是全的：池子大小在启动日志里打印、还作为 metric 暴露出来，他清楚地知道自己踩在不一致上。 所以我不认为这是可见性问题。这是证伪能力的问题——他们的测试手段，在结构上就不可能否掉"长上下文是好的"这个假设。状态码 200 加流式 body 正常，在这类 bug 面前天生全绿，因为 bug 的输出也是一段合法、连贯、由真模型生成的文本。 至于你说的"引擎应该让人知道"，我原则上同意，但你说的方向恰恰不支持"加启动断言"这个做法，反而指向另一个东西。你举的理由是"对部分应用是永远不会碰到的场景"——那如果引擎在启动时硬断言"池子小于上下文就起不来"，那些小显存、根本不会发 70 万 token prompt 的部署会怎样？直接被引擎替他们做了决定、连服务都起不来。这恰恰是你说的"要求有点高"的另一种形态，只不过这次的施害者变成了引擎。 真正该补的通道，是这次唯一一个从头到尾缺席的东西：这个 bug 7 月 6 日就在公开 issue tracker 里了。信息完全公开、两个月、没藏。但没有一条路径把它推到"正在跑 P/D 分离 SGLang 的算子"面前。开源推理引擎没有 advisory 通道、没有 CVE、没有"你当前版本在 P/D 模式下有已知隔离缺陷"的推送——大家 pip install -U 靠的是博客和感觉。 那我把问题递回给你，而且是真的顶你一下：如果"引擎应该让人知道"成立，那运营商"知道了还发"算谁的？Cloudflare 是知情的。如果引擎把 warning 打得更响、把版本黑名单列得更清楚，Cloudflare 依然可能发——因为发版有它自己的理由，而 bug 只在 681K 以上的 prompt 上触发。你觉得这种情况下，责任该怎么切？是"知情就是算子自己的事"，还是说"引擎必须把这条路堵死、不给算子知情后仍犯错的机会"？

我：我觉得部署者知情的话，可以算引擎侧做到了自己该做的，长期来看，每个版本都有自己的问题和局限，但不代表不能用。不过如果只是躺在 issue 里，而影响面有比较大，那算是引擎侧有一些责任。他们意识到这个问题后最好公开说明一下。不过这里确实界限很模糊，如果这个问题他应该澄清，可能还有类似的问题也该澄清，但他也无法知道现存的所有问题。所以总的来说这类事可能很难完全避免，从部署侧只能想办法提升自己做切换或打补丁的能力。

总结

一、共享必须是你要求的，不能是你不小心得到的。

这次事故真正的分界线不是"引擎负责还是部署负责"，而是共享的来源。Cloudflare 那个 bug 是无意的：decode 读了一页它从没写过的内存，没有任何设计打算让两个请求共享状态，这是一次内存安全缺陷，引擎的账。而 vLLM 的 prefix cache 是文档化、可关、有旋钮的行为，多模态 uuid 撞键甚至在文档里明写"谁先到谁的数据给两边都用"、责任归客户端——那是你要求到的共享，部署的账。

同一条原则能同时解释两个案子，而"责任归属"不能：头部引擎已经公开声明租户隔离不是它的事，所以把责任一律往引擎推，会撞上一条已被明确拒绝的承重前提。

二、隔离不是被性能挤掉的，是被状态复杂度挤掉的。

修复的实测代价：±2% 以内、置信区间跨零、页级 tag 原型不到 1%。所以"安全要拿性能换"这个默认借口在这里根本不成立。真正的代价转移到了跨节点的共享可变页所有权上——延迟释放、ack 快慢路径、prefill 与 decode 的版本错配。这部分没有 benchmark 打分，也不会在压测里暴露，它是隔离真正昂贵的地方。

三、这类事故的所有信号都会是绿的，所以"部署侧提升检测/切换能力"是一场空。

13 天、155 条泄露、零告警。状态码 200、prompt_tokens 真实、回复连贯、延迟甚至更好。发现它的是一个外部研究员。切换和补丁流程靠告警触发，而这里没有告警可触发——检测能力在引擎里，不在部署侧。因此对租用方，能做的全在事前：问清池子与上下文是否一致、把极端长上下文做成独立可关的路径、以及算清"我的请求和谁共享同一块显存"。

四、越像数据泄露的缺陷，越被记成可用性问题。

同一个 CVE 库里，仅"时序推断"的那条定 Low 2.6 且版本范围清楚；"直接拿到他人缓存媒体"的那条 CVSS 向量是 VC:N / VA:H，机密性判 None、可用性判 High，EPSS 0.275%，advisory 里 package、affected、patched 全部留空，Dependabot 不支持。

用"影响面"当披露尺子会系统性失灵，因为隔离类缺陷的影响面与严重度反相关：触发概率越低，单次泄露的信息越完整。这里连计分体系都用了同一把错尺子。

五、披露不是终点，能被自动消费的披露才是。

问题的症结不是没人写文档——#30233 就躺在公开仓库里——而是写下的东西没有任何路径能主动到达算子面前。而即使后来补了 advisory，缺 package 和版本范围就进不了 Dependabot，你就永远不会被强制升级。这条链断在最后一米，于是同一个洞可以既被修好、又被下一个租户重新踩中。

六、而这一切背后有一个只朝一个方向用力的经济结构。

cache read 占 agentic coding token 支出的 96%–99%，官方缓解手段 cache_salt 的代价明写为"降低 cache 效率"。隔离旋钮直接对赌那 96%，而池子留宽就是浪费成本。价格战打的每一分钱里，有一部分是从隔离余量里出的——所以这不是某个团队不留神，是结构在持续往下压。

一个可证伪的预测

到 2027-10-27，AI 推理 / serving 基础设施（vLLM、SGLang、TensorRT-LLM 及同类开源引擎）领域会再出现至少一起这样的案例——缺陷的具体形态不设限（不必是 cache 撞键或租户数据泄露，也可能是引擎崩溃、错误输出、可被利用的配置路径等），但必须同时满足三个可核观测：

  1. 该缺陷在公开 issue tracker / 邮件列表首次被报告；
  2. 从首次报告日起超过 60 天，既没有安全公告（CVE / GHSA / 官方 security advisory），也没有面向算子可见的通报、修复版本或默认值变更；
  3. 在该窗口期内，有独立于报告者的下游算子被确认受影响。

三观测缺一不算命中。若到 2027-10-27 一起都没有，本条证伪——意味着这个领域的通报时滞被治好了。
