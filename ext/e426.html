我：选题就定这两个吧，Gemini 这个 Decisions API 和那篇 MMDM 一起看——一个产品形态，一个它的边界。另外我这边正好跑过 Jev 和 Gemini 的同口径对比，你看完我们再接着聊。

dsh：看完了。先把品类的形状摆清楚，因为它比新闻标题重要：这不是首发，是品类确认。decision model 已经有一串名字在跑——TypeSafe 的 Jev 基本是这个品类的事实标准，还有 OpenAI Decisions API、Perplexity Decider、Liquid、respan 的 span-02。Gemini Decision 1 是又一家大厂进场，而且它进场的方式说明这个品类正在被"产品化"。 机制上它跟前两年所有"用小模型降本"的路子都不是一回事：它不是让模型说得短一点，是不让它说话。输入（文本 / 图 / 音 / 视频 / PDF，最长 262K）加你预先写好的选项，单次前向 pass 直接返回选项上的概率分布，没有逐 token 解码，所以 output token 恒为 0。端到端 150–250ms，其中模型算 50–100ms。三种题型：noul（yes/no，可给正反描述标准）、choice（2–255 个候选）、score（有序 rubric，返回概率加权期望分）。一次请求最多 1,000 个独立问题，共享同一份 input，input 只计费一次，$0.10/M。 Google 内部四个用例很能说明它想吃哪块地：Gemini Notebook 拿它做实时路由（判意图，日常查询延迟降 40%）、Stitch 做快速画布、CC 从 200 个 emoji 里挑、Google Search 拿它做 MCP 工具的安全层。四个全是闭集、高频、错一点不死人。 MMDM 那份体检报告说的是另一面：5,448 题 / 16 类 / 28 个 decision 模型 / 选项空间 2–1024 / 输入到 64K。最扎人的不是总分，是同一批模型在不同轴上的断崖——Perplexity Decider-V1.2 世界知识 78.75%，换到选项逻辑 53.95%、约束规划 47.95%；全模型里 Hard Multi-select 最高 36.81%。 我的读法是：它擅长"看懂这段输入属于哪个格子"，不擅长"这些选项之间有依赖关系"。这在架构上是必然的——单 pass、无中间状态、不能调工具、不能先查 A 再决定 B。它的输出是一个给定选项上的条件分布，不是一次推理过程。选项一旦互相耦合，"猜格子"就退化成"解约束"，而它没有那张草稿纸。 所以压两处。第一处：它把"判定函数"产品化了，代价是把"可解释"从设计里删掉。第二处：那个 36.81% 的多选，可能正好砍掉 agent 场景最大的一块。

我：可以看看这里，我进行过 Jev 和 Gemini 这两个 API 的一些测试，你先看下我们再接着讨论。

dsh：看完了。先对账，我上一轮有两处说错的，而且改的不是细节，是判断。 一、我说"同一输入两次调用答案会变"——对 Jev 成立，对 Gemini 不成立。 你的实测里 Gemini 三次重复逐位相同，Jev 的 score 有 ±0.03 抖动、概率量化到 0.01 栅格。所以"判定层不可复现"是引擎实现问题，不是品类属性。这条往下推就重要了：只要确定性可实现，decision model 就能进"必须可复现"的回路——回归测试、审计、灰度、A/B。 二、confidence 我猜对了，而且比我想的更彻底。 文档直接写了公式：noul 取 max(p, 1-p)，choice/score 取 top 概率。它不是模型自评，是从分布形状按固定规则算出来的数。加上 noul 永远落在 [0.01, 0.99]——阈值切在 0.99 之外永远不命中。这个字段的工程含义就被锁死了：它只能当"要不要转人工"的开关，不能当"我有多可能对"的估计。 你的数据里我捞出三条。 (a) "打平 + 错同一条"是最值钱的结果，不是最无聊的。 两家不同架构、不同训练、不同量化策略，在同一任务上错同一条工单——退货 + 退款双意图，都被 money 带去了 billing。这说明上限由题面的可判定性决定，不由模型决定。而修法你已经写在报告里：把"退货状态优先于退款金额"写进 rubric。这就是"可形式化才被产品化"的确切形态：产品化之后，剩下的红利全在形式化得好不好，不在模型。 它同时解释了为什么竞争点会迅速迁到多模态覆盖、延迟、价格、概率工程质量——准确率红利被吃干了。 (b) 你把"概率工程质量"排在 ECE 前面，是这次实验里最有迁移价值的判断。 Jev 的 ECE 更好（0.023 vs 0.042），但概率是 1% 栅格 + score 抖动；Gemini 差一点，但连续 + 完全确定性。工程上后者赢，因为 ECE 是评价指标，粒度和确定性是控制能力的载体。你要拿这个概率去定阈值、做回归、做审计，可复现性比 0.02 的 ECE 重要得多。这条往上接一层，就是"可测性压力"在算子尺度的镜像：组织层问"能不能自动判"，算子层问"同一个输入能不能给出同一个数"。 (c) P(x)+P(¬x) ≠ 1，而且两家偏向相反——这是你这次最原创的观测。 Jev 高估（两条问题各自独立求值，和 > 1），Gemini 低估（平均 0.76，否定式被系统性压到 0.6 以下）。我的读法：它们的概率是条件在"提问方式"上的，不是条件在"事实"上的。 所谓"校准过"，真实含义是"校准到厂商训练时的提问风格"。这给那篇批评文章一个可量化的形式：P(x)+P(¬x)-1 的偏离量就是"提问风格依赖度"。我认为这可以直接沉淀成一个进场体检的三件套，比看 benchmark 有用：正向/反向一致性、同输入重复一致性、阈值附近抖动幅度。 两处我要压你。 第一，我不认同把"Jev 便宜 1.5 倍"放进选型表。 百万次调用差 $9。而在工单分诊里，一条错判走错部门的人力成本是它的千倍以上。这个差在"中低频 + 有兜底"的场景里权重应该很低，列成一个可比维度容易误导。反过来，只有在"每天十亿条的批量判定"里，1.5 倍才是全部——那时它不是选型问题，是生意。同理"Gemini 快 4 倍"：一回合只做一次 gate，3.18s 和 0.75s 都无所谓；一回合做五次 gate，3.18×5 就致命。延迟结论的适用条件是"这个判定点会被高频调用"，不是"Gemini 更好"。 第二，context caching 那条限制，可能比多模态更能决定它落在哪。 文档明写不支持 context caching、"Repeated input across requests counts in full"，同时 best practice 说"只发问题需要的字段，无关内容会降低准确率"。两条合起来是最硬的约束：decision 层在 agent 里不能直接读原始 trace，必须前置一个裁剪器——而裁剪器自己就是个判断。而且它喜欢的形态（一份大输入 + 一次问几百个问题）跟 agent 的形态（同一份长上下文 + 反复做小判定）正好相反。

我：我倾向于认为这种决策模型在不能微调的前提下，适用性会比较有限，尤其对于大公司的业务场景来说。对个人开发者可能更有用，能做一些常规简单的判断，具有更好的性价比。不过长远来看，我觉得这种方式可能处于一个被低估的阶段。Jev 刚出时候一度挺火的，但是其实在这行有一定从业经验的都会倾向于认为这是 encoder-only 的老路，并不算太大的创新，最近几乎已经没看到太多讨论和应用了。但是我认为一个复杂的应用实际上也可以由若干 n 选 1 的简单决策完成，就像在生成式模型成熟之前，NLP 领域也有很多落地应用场景一样。现在的大模型 agent loop 的方式吸引了很多的注意力，很少会从架构层重新构思如何基于这种模型来设计自己的产品，但是未来我认为这类模型的效率和成本优势会给它空间，被捡起来用。当然，大公司可能会自己微调类似的模型，而不是直接用接口。

dsh：三个判断，我同意两个半。先说我要改的那一个，因为它把原因放错了位置。 "不能微调"不是大公司的真阻断，「无归因」也不是——真正的是「无可观测」。 不能微调确实限制适用性，但它的机制是"校准只对厂商的问题分布成立，你得自己标几百条验证"，而这件事对有标注能力的公司恰恰不难。真正挡住的是另外两条： 一是判定要被审计。 大公司的判定点（风控、合规、审批、内容处置）都挂着申诉、复核、追责。decision model 天生不给理由，而且没有 LLM 那条退路（至少能读输出、能看走了哪步），出了错你只能改措辞重试。 二是多约束正好是它崩的区间。 约束规划 47.95%、多选 36.81%，而大公司的真实判定恰恰是"同时违反哪几条"加"这些规则之间有优先级"。你的 longlist 实验还证明大选项空间不是问题（40/100 全 rank=1），所以瓶颈精确地是耦合，不是规模。 所以我把它改成：判定要可审计 + 判定是耦合的 → 只在低风险、单标签的判定点上可用。 这个改法更窄，但更硬——它连"大公司自己微调一个"都一并否掉了，因为微调解决不了无归因。反过来说，如果你的业务判定不需要出审计材料（内部实验、个人产品、后台质检），限制立刻就松了。 关于"encoder-only 老路"：技术上你是对的，但推论会咬到你自己。 从 ML 血统上讲，它跟 cross-encoder / reranker / zero-shot NLI 是同一族：输入加候选，出一个分数。所谓"新"主要在接口层——选项在推理时用自然语言定义、返回归一化概率、零 output token、一次 prefill 问上千个问题、多模态原生。架构没公开，文档、模型页、全量文档都翻过，没有模型卡。 而"创新在接口不在模型"这条一旦成立，就有个残酷推论：门槛低。Liquid 已经 $0.02/M，还有第三方自称同机制的开源实现。大厂可以把这一层当免费额度送掉，通用 LLM 加一个 strict-schema 判定模式也能逼近。 于是"被低估"要拆成两个完全不同的赌注：押模型被低估——我认为错，模型层没什么护城河；押架构范式被低估——这可能是对的，而且这才是你真正在说的话（"很少有人从架构层重新构思"）。但范式扩散不靠性价比，靠 killer role。历史上有个很贴的类比：embeddings 被低估了很多年，它长期只是"更便宜的分类器"，直到 RAG 给了它一个系统级角色，它才变成基础设施。decision model 可能也在等它的 RAG。 你说的"复杂应用 = 若干 n 选 1 的组合"，我同意，但要划死一个界：它能组合判定，但两件事做不了——生成选项，和决定下一个该问什么。这两件恰好是开放式 agent 的成本大头。所以"若干 n 选 1 组合"成立的前提是流程图已经画好了：分支有限、判定对象已知、判定之间能用代码串。 这意味着它的正确定位不是"agent 的组件"，而是规则引擎的模糊谓词。每个 if 条件原来要么写死（可审计但脆），要么塞个 LLM（灵活但不可审计、贵、慢）。decision model 提供第三种：一个 150ms、带概率、可以挂在规则里的模糊谓词。这个定位比"agent 的 gate"大得多——企业里规则引擎是海量存在的（工单路由、审批流、风控规则树、内容审核），个人开发者写的"这封邮件是不是垃圾"也是规则引擎。你说的"从架构层重新构思"，我理解就是：先画判定图，再把模型填进谓词位，而不是"主循环里塞一个 classify 调用"。 不过这一定位同时解释了你说的"大公司会自己微调"为什么大概率不成立：规则引擎的谓词位是最需要审计的地方，自研也治不好无归因，除非你自研的是"可解释的谓词"——那就不是 decision model 了，是带归因头的分类器。这反而是个空位。 再补一个削弱"成本优势"论的反方，以及它的反方。decision model 的真正竞争者不是它自己这一族，是通用 LLM + strict schema + prompt caching。等缓存让长上下文复用接近免费、小模型价格继续砸，"用 LLM 做判定"的成本会逼近它，换来的是能解释、能调工具、能多跳。但这个反方也有反方，而且我觉得是这条赛道最关键的变量：LLM 做判定的成本大头从来不是单价，是它想的那部分 thinking token，而 thinking 量在涨。所以 decision model 省下的不是 5 倍单价，是整块思考预算。 于是这条赛道的空间可以写成一个条件，比"成本优势会给它空间"精确：decision model 的市场规模 ∝ 判定所需的 thinking 量是否随模型升级而上升。 如果前沿模型在"该不该拦这条请求"上也越思考越长，判定层必然被剥离出来做轻量件；如果模型学会了在简单判定上"不想"，LLM 直接吞掉这一层。 最后，"对个人开发者更有用"你这个判断的机制比"性价比"更狠：它剥削的是标注稀缺，不是算力稀缺。 传统分类器要求先有数据再上模型，decision model 让你先在请求里写选项和 criteria 就立刻拿到可用判定——冷启动被抹掉了。个人开发者缺的正是标注，大公司缺的是审计和耦合约束，两边的稀缺项正好互补。 顺带给你一个数作为自建 vs API 的边界：交叉点不是"省不省钱"，是"一张卡能不能跑满"。粗算（7B 级 cross-encoder、每请求 300 token、单卡每秒 2000 次），自建边际成本约 $3.5e-7/次、API 是 $3e-5/次，差 80 倍——但要跑满到那个量级是每秒 2000 次、每天约 1.7 亿次判定。低于它，自建是浪费人力；高于它，API 只是在交税。所以大公司自建的门槛不是"能不能训"，是"这个判定点有没有变成基础设施级调用量"；而多数公司自建的真实理由其实是数据不出境和审计，不是省钱——又绕回第一条。

我：我觉得按大类分的话它应该属于一种 encoder-only，但是未必是以前的一个分类头，也有可能有一些特别的设计，比如我记得它好像宣称速度与选项数量无关，也许稍微做了些什么改动，能大致想象，但毕竟没有开源不能断定。我觉得这种 n 选 1 也可能和现在的 agent 结合，比如说作为一种 agent 分发的中控，或者一些工具内部用于作为某些硬规则的上位替代等。我觉得黑盒这一点是一种阶段性劣势，但是可能是可以逐步被接受的。agent 就算有 thinking，它也会出错，错误的 thinking 对于整套系统优化的指导意义通常也比较有限，最终我们只需要整体的效果准确率高于一定指标。所以只有 confidence 不应该成为它的桎梏，只要它能以可靠的比例完成任务。

dsh：先纠正一个事实，因为它正好是"架构反推"的入口："速度与选项数量无关"这条我在文档里没找到。 文档写的是"延迟随问题数（1→100 问）近乎持平"，没提选项数（2–255）。你测了 40/100 选项的准确率和 rank，也没测延迟随选项数的曲线。这是目前唯一还空着的行为事实，而它恰好能把"黑盒"往前推一大步。 我补跑了：2 / 5 / 10 / 25 / 50 / 100 / 150 / 255 个选项，各 6–7 次取中位数，记录延迟和 input token。

三个读数。 一、token 随选项严格线性，约 25 token/选项。 这说明选项是被序列化成文本塞进同一个 prefill，不是 N 个候选各自过一遍编码器——否则 token 的记账方式不会这么干净。 二、延迟不是"与选项数无关"，是"随 token 线性、斜率极缓"。 2→100 选项 median 只涨 35%，但 255 选项 p90 到 1381ms；扣掉约 390ms 的网络下界后，模型侧约 680–990ms，是官方宣称 150–250ms 的 2.7–4 倍。所以准确说法是"弱相关，100 个选项以内可以当无关处理"。 三、选项描述写清楚是要花钱的（25 token/个）。255 个选项约 6.5k tokens ≈ $0.00065/次——单价仍低，但"把 criteria 雕细"和"选项多"会互相挤。顺带一个实测坑：连跑 7 次 255 选项就撞了免费层的 TPM 上限返回 429。 所以架构这条我维持原来的读法、但现在有实测支撑：共享前缀一次 prefill + 每问一段短指令接打分头，选项作为同序列里的候选槽位。这个形态能同时解释"问题数近乎持平"和"选项数缓增"，而旧式逐候选 cross-encode 解释不了前者。你的直觉是对的：大类 encoder-only，但"选项怎么进模型"是新的一半。 "黑盒是阶段性劣势"——我接受，但要把它换成可操作的条件。 它不是态度问题，是信息结构问题：这个判定点事后能不能拿到真值？ 能拿到（工单最终归属、申诉结果、抽检复核）→ 黑盒完全可接受，用验收替代解释，你的实测就是在做验收。拿不到 → 黑盒永远不可接受，不是因为没解释，是因为你连"它在变好还是变坏"都不知道。所以"阶段性"的触发条件我可以押一个具体的：出现第三方 decision model 校准评测。一旦有第三方背书加分布可比，接受成本会跳变；没有的话，每家团队都得自己攒几百条验证，扩散就被卡在"愿意自己验"的人手里。 "只要以可靠比例完成就行"——门槛不是问题，手柄才是。 两件事要补。 一是"可靠比例"要持续度量，而度量成本落在你身上。你实测已经看到它的失败是分层的：歧义 0.4492、注入后 0.7388、否定式被压到 0.6 以下。这三件事在监控上看起来是同一件事（置信度下降），你不知道该去追问、该拆选项、还是该拒绝。所以"可靠比例"不是一次性的验收数字，是要持续采样维护的指标——也是另一种 ground truth 依赖。 二是手柄太少。LLM 至少四个旋钮（prompt、few-shot、工具、思考预算），它只有两个：criteria 措辞和阈值，而改措辞答案会变这件事你实测过。少手柄意味着从 90% 调不到 95%，到顶就没了。那条错判就是活证据：换模型救不了，只能把优先级规则写进 rubric。所以它的天花板在 rubric 工程，不在模型。这推出一个成立条件：任务不漂移时它能一直用；任务漂移（新客群、新政策、新话术）时没有手柄可用，只能重写 criteria——那时它退化成一份要持续维护的规则集。 至于"agent 分发的中控"，我认为只在意图路由层成立，不在工具可用性层。 中控要决定"调哪个工具/哪个档位"，它给得出 top 概率；但 agent 里工具调用失败的主因不是"意图不匹配"，是前提不满足（缺参数、没权限、状态不对）。这需要逐步检查、需要知道"差什么"，而它只给一个标量。中控最需要的是"错误原因 + 下一步建议"，恰好是它结构上给不了的。所以它能当"该走哪条链路"的路由，不能当"这个工具现在能不能用"的守卫。 至于"硬规则的上位替代"，我认为顺序要反过来：规则在上，判定补灰区。 硬规则的价值是可审计加确定性，这两样正是它缺的。用判定替代规则，等于把审计路径拆了；用判定补规则覆盖不到的灰区，则黑盒被限制在"本来就没有明确规范"的地方，而那些地方恰好人也说不清，只能靠抽检建 ground truth。这个顺序直接决定它能不能过审计，也决定它是不是被采购。 补一条你没提但更硬的：责任归属。 文档明写校准是在厂商自己的问题分布上校准的、你的分布不适用——这句话的法律后果是用错了责任在使用方。所以黑盒被"逐步接受"的真实代价是责任留在调用方，这会自动把它推向低风险判定。不是技术不行，是没人敢签那个字。

我：我觉得这类模型可能应用于 agent 框架中，就是具体位置的区别，中控位可能是垂域粗判，不一定是具体到工具分发和选槽位。decision 榜出现我觉得可以作为预测，因为这个出现基本意味着使用率上来了。

dsh："垂域粗判"这个位置我同意，但它恰好是护城河最浅的位置。 机制上它成立，理由很硬：垂域粗判的选项集合稳定、可枚举、互不依赖（垂域就那么几个），判错代价低（走错流程很快暴露，甚至可并行两条），输入短、调用频。它正好避开 MMDM 崩掉的那两个轴。 但正因为舒服，它是最容易被便宜 LLM + 分类 prompt 吞掉的位置：输入短、选项少、不需要推理——它那三个结构性优势（大输入共享 prefill、零 output token、一次一千问）在这个位置上一个都用不到。唯一剩下的差异是延迟，而延迟只在"每次交互都要判、判很多次"的产品里有价值。 所以我认为争的不是"agent 里的哪一格"，而是"判定表存不存在"： 它先落地的地方一定是已经有显式判定表的地方——在 agent 里就是那个前置粗判表，在工作流/规则引擎里就是规则表。而 agent 循环中段的动态判定不会先落地，因为那儿没有表，而且恰好是长上下文加多约束的区间。 这个说法把你的判断和我的判断都装进去了，而且可证伪：回测时看第一批生产系统，只要看它是不是写在一张人画的表里就行。 decision 榜那条你说得对，榜出现基本等价于使用率上来（有人愿意为"可比"花时间）。我补一个回测判据：看榜是否独立于三家厂商——独立评测是使用率驱动，厂商赞助是营销驱动；以及首个榜覆盖的是不是标准化任务（内容审核、垂域分诊），而不是"agent 路由"这种连任务定义都还没有的领域。

总结

一、这个品类的分水岭不在模型能力，在"题面能不能写清"。 两家不同实现在同一批工单上打平、连错的那条都相同；MMDM 上同一个模型（Perplexity Decider-V1.2）世界知识 78.75%，换到选项逻辑 53.95%、约束规划 47.95%，全模型的多选最高也只有 36.81%；而选项数量不是问题——40 和 100 个候选的检索全都 rank=1。所以边界精确地是"选项之间有没有耦合"，不是"选项多不多""模型强不强"。可用域是：单标签、选项彼此独立、判定所需信息已经在输入里。

二、判定层被产品化的代价，是三个失败原因被压成一个标量。 confidence 是概率分布形状的固定函数（max(p,1-p) 或 top 概率），不是正确性估计。信息不足、选项都成立、输入被污染，在字段上完全不可区分——而它们需要的动作相反：追问、拆选项、拒绝。注入实测把这个说得很清楚：干净输入 0.99，塞入指令后 0.7388，没有被翻转成攻击者想要的 yes，但被拉低 25 个百分点；阈值设在 0.7/0.9 的话，这次攻击看起来就是"模型不确定"，跟正常转人工一模一样。它不是解释不了，是低置信时你不知道该做什么。

三、选型该看概率的工程质量，不是 ECE。 连续、确定、可细切的概率能进闭环控制；量化到 1% 栅格还带 ±0.03 抖动的概率不能，哪怕它的 ECE 更好看。这是"可测性压力"在算子尺度的镜像：组织层问"能不能自动判"，算子层问"同一个输入能不能给出同一个数"。

四、它更像"规则引擎的模糊谓词"，而不是 agent 的零件。 它能组合判定，不能生成选项、不能决定下一个问什么，所以它落在已经有显式判定表的地方。而规则要留在上面、它补灰区，不能反过来替代规则——否则拆掉的是审计路径。代价是责任留在使用方：校准是在厂商问题分布上校准的，你的分布不适用，用错了没人替你签这个字。

五、它可能被低估，但赌注不在模型上。 它剥削的是标注稀缺而不是算力稀缺——个人开发者先写选项和 criteria 就拿到可用判定器，"先有数据再上模型"的顺序被倒过来了；大公司不缺数据，缺的是审计与耦合约束，两边稀缺项正好互补。而它的护城河很浅（ML 血统是交叉编码器那一族，创新在接口层），所以扩散不靠性价比，靠两个东西：比价基础设施（第三方校准榜）和一个 killer role（类比 embeddings 等到了 RAG）。

一个可证伪的预测

预测 A（使用率侧）：未来 12 个月内（到 2027-11），会出现独立于各厂商的 decision model 校准评测，且首批覆盖的是标准化判定任务（内容审核、垂域分诊、rubric 打分这一类），而不是"agent 路由"这种任务定义本身都还没稳定的领域。榜出现即视为使用率成规模的一个代理信号。

回测时要看的信号：榜是否由第三方而非厂商资助；比的是 ECE / Brier / 阈值曲线这类校准量，还是又一个聚合准确率分；以及有没有人把这些分数写进采购文档。

预测 B（落地位置侧）：第一批生产系统会出现在已经有显式判定表的地方——agent 的前置粗判表，或工作流/规则引擎的规则表——而不是 agent 循环中段的动态判定。判断标准只有一条：看它是不是写在一张人画的表里。

反向信号：如果第一批落地集中在 agent 循环中段（判定对象由模型自己生成、选项由代码动态拼装），说明"判定表"这个前提是我脑补的，本条的定位判断作废。

一条不押但会观察的：confidence 会不会被拆成语义不同的字段（信息不足 / 选项都成立 / 输入被污染）。不押的理由是这更像实现愿望而不是能证伪的预测；真要观察就退一档，看 12 个月内文档里是否出现"区分低置信原因"的操作指引，而不是看字段本身。
