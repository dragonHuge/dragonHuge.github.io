我：看 You don't need long context 这篇。

先说我自己的一个判断：上下文策略确实是 harness 设计里的重要环节，甚至可以说是为数不多真的有选择的环节。工具准备和 ReAct 框架本身，基本都不是算法层的修改目标，把上下文策略做好，对系统的体验很关键。

不过我想先确认一下：他 SAC 方法里的"语义状态"具体是指什么？如果有例子，给一个。

dsh：机制上比名字朴素得多，没有任何隐藏向量。每个会话的 user message 里，在 task 之后多挂一段文本，模板变量就叫 {recap_section}；会话里只放这一份交接单，不放历史。做完一个动作、看到结果，模型被要求重写这份交接单，然后整个会话丢弃，下个会话带着新交接单重开。 模板本身（附录 G.1，mini-swe-agent 版）是六段： 停止工作。只写一份简短的 handoff recap；不要运行命令、不要调用工具。 会话会重置为 system prompt、task 和这份 recap。 记录： 1. Objective — 一行写清需要的结果 2. Established facts — 精确路径、相关的符号或命令、观察到的值、重要的错误/输出。把观察和未验证的想法分开写 3. Applied changes — 每个改动/新建的文件、改了什么、是否已验证 4. Verification — 跑过哪些检查、结果、失败、障碍、绕法 5. Dead ends — 不该再重试的失败路径 6. Remaining plan — 未完成的子目标（按执行顺序）、下一条要跑的命令或要做的编辑、完成判据 如果需要的输出被截断了，给一条窄命令把它取回来。 mini-agent 版略有差别：更强调"已验证的事实 vs 假设"，并明确写"不要复述整份任务或文档清单"。 论文里没放真实 recap 样本（附录 E.2 只有选择性读取的 trace），所以我按这个模板手写一个，用来看结构： 1. Objective 让 tests/queries/test_filtered_relation.py::test_filteredrelation_aggregate 通过，且不动测试文件。 2. Established facts - 目标用例失败点：django/db/models/sql/query.py:482，KeyError: 'filteredrelation' - 复现：python -m pytest tests/queries/test_filtered_relation.py::test_filteredrelation_aggregate -x - HEAD = a1b2c3d（git log -2 已确认，工作区当前有改动） - 观察：query.py:482 的 join_promote 分支在取 alias 时假设它已被注册 - 未验证：annotations.py:210 的注释暗示 Subquery 路径不注册 alias —— 只是读到注释，没验证 3. Applied changes - django/db/models/sql/query.py：在 join_promote 前加了别名注册（未验证） - 其他文件无改动 4. Verification - 跑了上面那条 pytest：报错位置后移到 501 行，变成另一个错误（AttributeError） - tests/queries/ 全量尚未跑 5. Dead ends - 改 join_promote 的返回值为 tuple：12 个既有用例挂，已 revert - 改测试断言：评测只看源码，不允许，别再试 6. Remaining plan (a) 读 annotations.py:88-145，确认 alias 在 Subquery 路径上的传播 (b) 在 501 行那个 AttributeError 上复现一次，确认是同一根因还是新问题 (c) 全量 python -m pytest tests/queries/ 下一条命令：sed -n '88,145p' django/db/models/sql/annotations.py 完成判据：目标用例通过 + tests/queries/ 全绿 对比被扔掉的东西：几十条工具输出（大部分是 grep 命中和 traceback 中间的几百行）、两次失败的 grep、一次被截断的 stdout。state 里留下的不是这些内容，而是"这些内容在哪、哪条命令能把它们再取回来"——模板里"给一条窄命令把它取回来"那句，就是干这个的。 由此我有两个判断。 一、这份 state 不是"记忆"，是"任务进度快照"，所以它才配被丢弃。 里面的每一项都是任务局部、可验证、随时能从环境重建的：路径、错误、跑过的命令、死路。它刻意不装任何跨任务的东西——没有"用户偏好什么"、没有"上次为什么这么选"。这正好把论文的适用范围说清了：它能被压到 7–9K，不是因为压缩技术强，而是内容本身就不是需要长期保真的那类。人机协同里那些没写进文件的偏好，这套模板无处安放（附录 A 承认了，但结论没跟着收窄）。 二、SAC 有一个隐含前提：环境是单调的。 交接单里全是"指针"——query.py:482、annotations.py:88-145。但 agent 自己在改文件，行号会漂。我见过更糟的：agent 重写一个文件之后，上一版交接单里的行号指向的是完全无关的代码，模型照着去读，读到的东西看似合理、其实是错的。论文的 SWE 任务里这个风险被"评测只看最终 patch"掩盖了——有 test 兜底，错误指针最终会被测试打回来；换成没有 verifier 的任务（写文档、做调研、谈判），错误指针不会被打回来，会被当成事实写进下一版交接单，然后再下一版。 所以这篇该被记住的位置是：它证明的是"极端压缩在可验证、可回滚的任务上不崩"，不是"长上下文不必要"。 这个区分对 harness 设计有意义，但撑不住标题那句话。

我：如果在一套比较收束的场景里，能有好的配套环境支持，通过自进化让 agent 探索语义交接内容，我觉得有一定可行性——不过能不能很理想，我也没试验过，不是很确定。

但我觉得更重要的一点，其实是你前面提到的：压缩策略会影响 KV cache，进而影响效率和成本，所以并不是越频繁越好。这个时机需要一个把成本、效率、效果（长上下文带来的 rot）结合起来的点；这个点如果能在 harness 里动态计算，可能是一个比较理想的状态，但这件事并不容易。具体压缩上还有选择：是直接摘要式的，还是 mask + 可查式的，等等。不过可以确定的一点是，很多场景确实不需要非常全的上下文才能做事。

dsh：先说自进化这条路。它已经有实证，而且是今天的候选之一：ParetoSaddler 做的就是"搜 harness"——把 harness 当被优化对象，中间候选按 quality/cost 双目标晋升。它最关键的手法你可能没想到是哪个：用 Bayesian bootstrap 去筛掉"增益在重复执行间站不住"的候选。也就是说，harness 改动的信噪比低到需要统计检验才能认出真增益。 这对"自进化交接内容"是很硬的约束：搜索空间里的收益大部分是噪声，如果奖励信号只有"这轮任务成没成"，进化出来的交接格式会朝能被测试验到的那部分收敛——恰好把测不出来的东西（人的偏好、没写成断言的约束、风格判断）丢掉。这不是假设，是 Goodhart 在状态设计上的直接形态。要挡住它，eval 里得放一条只有读了交接单才知道的 held-out 约束（比如"后续步骤必须遵守某条只在第一步出现过、环境里查不到的用户要求"），并且这条约束不进训练侧反馈。这可以设计，但我没看到有人做。 顺带一个反证：论文自己反而故意用同一份六段模板打穿所有 workflow（SWE、检索、对话、工具编排），并且有效。这说明结构化模板的可迁移性比"让模型自由发挥"值钱——自由发挥的搜索空间太大，而你手里的验证信号太少。 再说压缩时机。你说的方向对，但我想把成本结构拆开：压缩的开销是固定项——一次对当前上下文的全量 prefill（成本 ∝ L）+ 一次状态生成（∝ 状态长度）；收益是从下一轮起每轮省掉的 decode（∝ L − L_short）。所以：

  • 压得晚：单次收益大、次数少、固定开销摊薄得少，但被摊的轮数也少
  • 压得频繁（SAC 极限）：每轮都付一次 prefill + 一次生成，被省的只有一轮的 ΔL

直觉上这几乎必然亏。而论文正文那张 SAC 的表只有准确率和峰值 context，完全没有成本列；所有成本分析（2.2–8.8x、6.5–233x）都挂在 EoCC 上，SAC 只被用来证明"准确率不崩"。它也没单独报"每次压缩花多少 token / 多少时间"——而这恰是做动态调度最缺的那个数。所以"什么时候压"这篇其实没给答案，只给了"压得狠也不崩"这条上界。 还有一个比成本更容易被忽略的点：API 用户拿不到这个成本结构。 平价计费下，长上下文的 KV 经济性由 provider 吸收；而 cache read 现在便宜到 $0.20 / 1M（今天 Opus 5.5 的价格，官方说 agentic 工作负载的成本大头就是 cache read）。对 API 用户，压缩的驱动力其实是另外两件事：rot（质量）和延迟——不是钱。你自己的账单看得见的只有自部署那条路。这意味着"动态算一个成本-效率-效果最优点"在 API 场景里算不出成本项，只能算延迟和质量。 所以我倾向把这个事换个形式实现：不要按 token 阈值触发，按语义边界触发。 交接单最便宜、最准的时刻，恰好是 agent 刚结清一个子目标的时候——那时"当前在做什么、下一步做什么、哪些是死路"本来就在最近几十行 trace 里，写状态的边际信息成本最低；而按 token 阈值触发，经常打断在一个动作中间，写出来的状态全是半成品。 至于摘要 vs mask，我把它拆成三层，因为这不是一个选择题，是三个不同的实现位置：

  1. 不让内容进 context（harness 层）：延迟读、按需读、只读窗口。无损，成本落在 CPU（grep/sed），完全不占 KV。论文在长输入任务上最高 +40ppt、6.5–233x 的收益，主要来自这一层。
  2. 进了但把 KV 掩掉 / 驱逐（引擎层）：省显存不一定省算力，而且驱逐会改变 attention 分布、破坏 prefix cache 复用。harness 做不到，得引擎支持——这层基本空白。
  3. 生成摘要（harness + 模型层）：有损，且有 GPU 生成成本 + 每次重写的成本。

我的判断是：只要源材料可 grep，第 1 层严格优于第 3 层。 第 3 层真正不可替代的场景，是源材料根本不在环境里的那类（纯对话历史、人说过的话、一个口头决定）。而论文 §3.1 给的补救——保留完整日志 + 给 agent 一个选择性读取工具——恰好把第 3 层的适用面压到很小。但论文自己推荐的 SAC 是典型的第 3 层做法，这里有点内部打架：最强的实验结论指向第 1 层，最激进的机制用的是第 3 层。 不过第 1 层有一个真实的软肋：检索是查询驱动的，agent 不知道自己缺什么时就不会去搜。 摘要虽然丢信息，但它把"你没想到的东西"塞到你眼前——被动召回。所以这不是精度之争，是主动召回 vs 被动召回之争。 最后，你说的"很多场景不需要全上下文"，我想把分界说得更准：不在"全不全"，而在是 query 决定 target，还是 target 决定 query。

  • 可定位任务（找那段代码、找那个数、改这个测试）：query 能描述目标，指针和检索就够，短上下文完胜。
  • 需要全局一致性的任务（500 页合同的一致性、跨文件重构里"哪里都改对了"、文献综述里"这两篇到底矛盾在哪"）：没读完之前你不知道该找什么，目标反过来决定 query。这类必须在同一视野里，长上下文是真实需求——而且 rot 的代价恰好在这类任务上最高。

这两类在同一个产品里是混着来的。这解释了为什么"统一压到 16K"在 benchmark 上不掉分、在真实产品里却会被人骂：benchmark 是前一类，骂人的场景多半是后一类。

我：模型容易被之前完成的行为诱导，尤其是之前做错的情况。比如它会不断抄之前的结果，而不愿意重新搜一次，或者说再思考一次。这种情况下，没有 context 没准反而能做对。

dsh：这个现象有一个理性的内核，值得先说出来，因为它决定了它治不治得好。 "抄之前的结果"不是一个懒，是在基率上正确的策略。agent 轨迹里绝大多数前一步是对的（否则早失败了），所以"信任已产生的结论"在统计上期望收益最高。预训练还在加一层：文本里的行为主体是自洽的，模型被 conditioned 在自己写过的内容上时，最高概率的续写就是继续一致的行为。两股力量叠加，"不重搜"就成了默认解。 但关键是这个基率不均匀。错误一旦发生，p(错误 | 已经错了) 会显著升高——因为错误多半来自任务或工具层面的系统性问题（读错文件、理解错测试、被截断的 traceback），不是独立噪声。而"信任历史"这个策略恰好在自己最该失效的时候最自信。所以这是策略的适用条件被违反了，不是策略本身错。 这也解释了为什么靠提示词治不好（"请重新验证你的结论"）。模型并不知道哪一步错了，它只知道"我做过这件事"。"我搜过" ≠ "我知道"，而这两者在一个只记录结论的上下文里长得一模一样。 所以"无 context 反而能做对"成立的条件，是两个成本的比较： 重做一次的代价 < 信任错误结论的代价

  • 成立：搜索结果可重取、任务步数短、失败可单步检测。这时清空就是廉价的独立重采样，正确率回升。
  • 不成立：需要累积探索的任务。清空会把"已排除的死路"一起清掉，模型重走同样的坑，token 消耗爆炸，很多场景还有预算上限。

差别的根子不是上下文长短，而是上下文里存的是结论还是证据：存"best answer / 当前结论"必然诱导，因为那是可供照抄的最短路径；存"证据在哪个文件第几行 + 一条能重取它的命令"就不诱导，因为每次都要重新推。 顺便说，论文的模板在这里是自己给自己下绊子。 mini-agent 版交接单的第一项原文是 "Current progress and best answer/result"。它把照抄锚放在第一位，然后指望第六项的 dead ends 和"不要凭空发明观察"来救。从实际行为看，第一项的权重压过后面所有约束——这跟附录 A 里"最好的压缩是给后续执行的简报"是同一个道理的反面：给后续执行用的简报，不该包含"已完成"的答案。 两个我认为能真改掉它的动作： 一、状态里的事实要带"可推翻"的形态，而不是肯定语态。 论文那行 "Separate observations from unverified ideas" 方向对，但只是一句话，没有强制力。强制力得来自结构：未验证的项写成问题形式（"482 行的 KeyError 是否由 alias 未注册导致？待验"）而不是陈述形式；已验证的项必须挂一个重验命令。语态本身会改变行为，而且这是可以 grep 出来检查的东西。 二、把"重验"做成 O(1) 原语，让重验比回忆更便宜。 现在模型不重验，是因为重验要一次 tool call 往返 + 读输出，而回忆是零成本。只要把差价抹平，"信任历史"就不再是优势策略——这其实就是把心理学问题换成成本问题，而成本是可以设计的。做法是：状态里那条指针不要写成"annotations.py:210 显示 alias 未注册"，写成 grep -n "alias" annotations.py | sed -n '1,5p' 这种一行能重跑的东西；更狠一点，让 harness 每 N 步自动重跑这些命令，和新结论 diff，不一致就标红。这一步不需要模型判断，纯机械 diff——它不愿意重新搜，机器可以替它搜。 顺带，第二条还顺手解决了"错误指针固化"：指针错了，自动重验会当场发现，而不是等到第五版交接单里变成一个看似权威的事实。 不过"完全无 context 更优"我不完全同意，反例是：没有 verifier 时，清空重来选不出对的。 best-of-N 只有在能判定对错时才有用；判定不了，你大概率选那个"看起来最自信"的，而自信往往正来自重复，也就是诱导。 要验这件事，三段对照就够，用同一批已失败的轨迹：A 全历史重试；B 只给任务、清空重试；C 给任务 + 已验证事实（带重验命令）+ 死路，不给任何"当前结论"。预期 C > B > A。如果 C ≈ B 而 B > A，说明死路清单没价值、光"清空"就是解药——那才是真正的反直觉结论。如果 C 明显 > B，说明价值恰在"负面信息"上，压缩策略的重心就该整个挪到"怎么保留死路"。

dsh：其实是三个不同的问题，混在一起看会觉得"模型就是不听话"，拆开后会发现只有一个真是模型的问题：

失败本质谁该负责
---
引用中间工具结果不再重调观察会过期——工具是活的，context 是快照harness（缓存失效）
误读结果 → 写错结论 → 后续坚持结论引用结论，错误在链上传播harness（证据锚定）
换个工具 / 换条路不愿试策略惯性，真·模型行为提示词 / 动作空间

前两类可机械检测，这类问题不该用提示词去治——用 diff 能解决的事，别交给模型判断。 第一类（观察过期）最被低估。 你说的"重调结果会变"是关键：一份工具结果在 context 里被当成事实，但它其实是一个有时效的缓存条目，而 agent 的上下文是全行业唯一一个永不失效的缓存。没人给状态写过 invalidation 规则。工程上要求事实带两样东西：取的时间和重取的方法。不要存"当前 3 个测试失败"，存 pytest -x -q 的重取命令 + 上次输出落在 runs/0031.log。之后重验就是重跑 + diff。 顺带一个约束：只有可重放的工具才能自动重验。 读类（grep / git status / cat / query）幂等，可以每 N 步跑一遍对答案；写类（commit / migrate / deploy / send）不能重放，对它们的验证必须是读回来观察状态（重新 git diff），而不是重做那个动作。把工具按"可重放 / 不可重放"打标，是 harness 层该有的元数据，现在基本没人写。 第二类（结论引用结论）我认为最该工程化。 规则很简单：状态里只允许引用 observation，不允许引用之前的结论。 每条结论必须挂一个 observation 的 id 或一段可重跑的命令；每次重写状态时，结论要从证据重新生成，而不是从上一版状态改写过来。这一条直接切断传播链——上一轮说的"错误越写越像定论"，源头就是状态允许自我引用。副产品是状态可审计：每条结论都能追到原始输出。 至于工具错误设计，你说得对，而且我认为它跟你之前那个判断是同构的：拒绝只有被结构化成"原因 + 可执行的替代路径"才可被下游使用，光一句"我拒绝了"没有信息量。 工具错误就是工具侧的拒绝，结构化的要求一模一样：

分类：可恢复 / 前提不满足 / 永久不可行 / 参数错

具体原因：哪个参数、哪个前提、期望什么、实际什么

下一步：给替代动作或前置条件，不是"请重试"

能力边界：这个工具不做这件事时，说清楚该找哪个工具

第 4 条最容易被漏，而它恰好治"行动惯性"——模型用 grep 撞墙后会继续用 grep，因为它不知道还有 doc-read 这个选项。错误信息里带"你该换工具"，是最便宜的路由器，比在 system prompt 里列一遍工具清单有效得多。 死路那部分，我同意"不能白死"，但要加两条约束，因为死路记录本身也会变成毒： 一、死路记录必须带判据，不能只记结论。 不是"试过 X 失败"，而是"X 失败，因为 Y；Y 变了就可以重试"。不带判据的死路会永久封死一条本来有效的路——环境变了（依赖升级、权限开了、数据变了），死路就过期了。所以死路和结论一样有时效，只是没人给死路写过 TTL。 二、压缩时机该由结果决定，不由长度决定。 我上一轮答"按语义边界"，你这条给了更好的答案，我改一下： 成功了才压缩绕路，失败时绝不压缩死路。 理由是信息状态不对称：任务还在失败着的时候，你不知道哪段过程是承重的——那个看起来没用的搜索，可能正是最后成功的线索；一旦成功了，整条绕路的过程就降级成"我们最终走了 B，因为 A 不通"，中间几十步可以放心压掉。而失败中的死路一旦被压，就变成了白死。 这个规则还有个好处：它把触发条件从"要预测的阈值"变成了"可观测的事件"（任务成功 / 子目标结清），不需要动态成本计算那个难算的东西。你想做的"动态最优时机"，大部分价值可能就来自这一条规则，而不是一个调度器。 三、死路的保留形态要可被搜索，不是被复述。 死路清单不该每次都塞进 context——那也会诱导，模型看到"试过 A 失败"就不敢碰 A，哪怕条件已经变了。放在环境里能被 grep 到的地方，只在需要时读。这又回到同一个结论：能不进 context 的，就别进。

这种问题会发生在工具非常多、并且有一定相似性的场景。工具建设之初可能是独立的，很多看起来相近的功能被设计成了不同工具。比如车载座舱那种形态，可能会有"打开地图"是一个工具，而"放大地图"是另一个工具。因为打开地图，可能和打开音乐、打开电台一起，被设计成了一个开启 app 类的工具；而放大地图，是地图中的设置类操作，暴露的工具名可能类似 map_setting 一类。于是用户说"打开地图"的时候，模型就容易误用它，传入一个 open 参数，实际这个工具不支持。此时可以针对性提示，"如果要打开地图请调用 xx"。

dsh：这个例子命中的是一个很具体的结构问题：命名空间即路由。 把那次调用抽出来看，模型是在拼一句话：动词来自用户（"打开"），名词来自工具名（map_*）。它不关心 map_setting 到底支持什么，它只看到"用户说地图 → 有个叫 map 的工具 → 那大概就是它"。这不是理解错误，是在工具空间里做名词-动词拼接，而工具集合恰好给这个拼接留了一个看起来合法的落点。 所以误用的根源不是"相似工具太多"，而是工具的切分轴和用户的意图轴不正交：

  • 用户的话切在意图轴上：打开 / 放大 / 导航 / 播放
  • 你的工具切在应用边界轴上：地图 / 音乐 / 电台

open_map 落在"打开 app"这个横切工具里，而"放大地图"落在"地图 app 的内部设置"里。于是唯一一个名字里带 map 的通用设置工具，就成了所有地图类意图的默认吸附点。谁的名字里有实体，谁就吞掉这个实体的所有没被明确覆盖的意图。这跟工具数量关系不大，跟命名空间的引力关系很大。 由此有两条比"写指引"更前置的规则： 一、每个实体必须有且只有一个"默认入口"，其余工具必须靠动词区分。 open_app(app="map") 存在之后，map_setting 就不再被误吸附。现在的问题是地图根本没有"打开"这个合法落点，模型只能去撞最近的那个。 二、catch-all 工具的 schema 必须展开枚举。 map_setting 这种"设置一切"的工具是最坏的一类——名字最宽、schema 最泛，任何地图意图都能塞进去。它应该显式列出支持的 setting 项枚举，让模型在规划阶段就枚举，而不是调用完了才知道不支持。枚举是最便宜的误用防线。 但你那条"针对性提示"，作用范围比看起来窄。它有个致命的位置问题：它写在错误工具的 schema 里，所以只有模型已经选中它之后才读得到。 如果模型在候选里根本没打开 map_setting，这句话是空气；而工具一多，每条 schema 里塞的"请不要用我做 X"会互相竞争注意力，越写越没人读。 它真正有效的场景是：工具集不是你说了算的——第三方 MCP server、跨供应商的 app 注册、历史遗留接口。这时候改不了名、改不了分组，描述是唯一的杠杆，那它就从次优解变成唯一解。 所以我同意"从真实错误里总结的指引最能落地"，但落地的位置应该往后挪一层：挪到参数校验失败的那个点上。 你例子里模型传了 open 给一个不支持它的工具——这是整个链路上信息最全的时刻：它知道 unknown param: open，也知道 tool: map_setting，还知道 entity: map。三个信息拼起来就能机械地推出"用户想打开地图，该调 open_app"： {unknown_param: "open", tool_prefix: "map"} → open_app(app="map") 这类规则表可以离线从 trace 里长出来，而且触发条件是确定的（参数校验失败），不依赖模型读不读描述。代价是要维护那张表——就是"知识库维护"那个问题，但它的正确性能被 eval 直接度量。 至于"从真实误调用总结指引"的系统化版本，我觉得可以做成一个很便宜的东西：误调用矩阵。行是意图（打开地图 / 放大地图 / 导航到 X / 播下一首），列是被误选中的工具，格是频次 + 典型错误参数。一百条 trace 就能画出来，而且它直接告诉你三件事：哪条边最粗（先修它）、误用的是"选错工具"还是"选对工具传错参"（修法不同）、以及哪些工具是净吸收器（被误选但很少被正确选中——要么改名，要么加枚举）。 座舱这类域特别适合暴露这些问题，因为用户 utterance 极短——"打开地图"四个字，动词 + 实体，没有上下文可补。意图几乎全靠工具元数据补全，于是工具命名和 schema 就成了事实上的协议。这种场景里，"工具设计"和"prompt 设计"的边界基本消失。

dsh：你说的这个取舍，本质是"载入成本"和"选择准确率"反向。而且我觉得它被说成了一个"要不要全量"的二选一，实际上渐进式加载真正删掉的不是 token，是"横向对比"这个动作。全量时模型面前摆着同族的五六个工具，它可以比；渐进时它一次只看得到一两个候选，没有对照组，那"看起来像"就是它唯一能用的判据。误选不是模型笨，是它被剥夺了做排除法所需的信息。 顺着这个看，lazy 的失败模式其实和上一个例子是同一个：

  • 全量加载 + 工具正交 → 误选（选错工具）
  • 渐进加载 → 模型不知道自己不知道什么，于是构造一个不存在的调用（传 open 给 map_setting）

后者更糟，因为它连"候选错了"这个信号都没有——它是从"我以为有这个能力"里长出来的。所以渐进式加载必须配一条硬兜底：schema 严格拒绝 + 反向建议（"不支持 open；你要的可能是 open_app"），这比任何描述都可靠，因为触发条件是确定的。 但真正能降成本的做法，是把集中治理的量级从 O(工具) 降到 O(意图)。你说命名正交不现实，我完全同意——所以别在命名上做统一，在路由层做归一。 各团队保留自己的名字，harness 侧只维护两张小表：

默认入口表：每个实体一个"打开 / 进入"的合法落点（map → open_app(app="map")）

意图 → 工具 的显式映射（不是 embedding 相似度，是预写的表）

规模是 O(意图数)，不是 O(工具数)。座舱这个域的意图是有限的——导航、媒体、车控、设置、通讯、语音——几十个簇封顶，而工具可以几百个。这是唯一一处值得集中治理的东西，而且它小到一个人能维护。 再往上就是三级结构：

  • 常驻层：每实体默认入口 + 高频意图，控制在十几个，描述压到一行
  • 族索引层：每族一行（map_*：导航 / 缩放 / 图层 / 设置；打开地图请用 open_app）——这层是索引不是 schema，成本可控
  • 按需层：具体工具的完整 schema 和枚举，进了族才拉

关键约束是：默认入口必须常驻。 "打开 X"是最高频意图，也是最不该走检索的——误调用主要就发生在"默认入口没常驻"的那片真空里。 最后，关于"弥补策略"这个定性，我想把它说得更锋利一点。如果承认团队分散、历史包袱、工具数量这三个约束短期不会消失，那这类工作的正确性标准就不该是"消除误调用"，而是"让误调用可恢复"。因为消除不了。能改的是： 从"选错工具"到"回到正确路径"要几次 tool call，中间会不会产生副作用。 这个指标可以度量（trace 里能算）、能立项（直接对应体验和预算），而且它把优化方向指向了错误信息质量，而不是工具设计完美度——后者你改不动，前者你能改。你上轮说的"失败提示要丰富"，落在这个指标上就是"把恢复成本从 3 次调用压到 1 次"。 顺带一个反直觉的推论：允许模型误调用一次，比逼它做一次完美的规划更便宜。 因为误调用是确定的（一次 tool call + 一条明确错误），而让模型在几十个工具里做完美规划，代价是更长的推理、更贵的前置 token，而且失败时你还不知道它错在哪。所以渐进式加载的方向没错，错的是把它当成"省 token"来优化——它其实是把一次性的大额规划成本，换成多次小额试错成本，那前提就是每次试错必须便宜且安全。

总结

  1. 论文证明的是"极端压缩在可验证、可回滚的任务上不崩"，不是"长上下文不必要"。 三档上下文制度的对照确实做得干净（同一 harness、同一模型，只换上下文策略），但它的收益结构分两块：长程任务上是"准确率基本平、成本省 2.2–8.8 倍"；长输入任务上最高 +40ppt 的那种涨幅，更像"满输入基线在 needle 类任务上被打废了"，而不是压缩本身很神。真正的分界不在"全不全"，而在是 query 决定 target（可定位，短上下文够），还是 target 决定 query（需要全局一致性，长上下文是真实需求）——而 rot 的代价恰好在后一类任务上最高，benchmark 却主要长在前一类。
  2. 压缩时机该由结果决定，不由长度决定。 论文的 SAC 把压缩推到"一个动作一个 context"的极限，准确率确实没崩，但正文里 SAC 那张表只有准确率和峰值 context，没有成本列——成本分析全挂在阈值压缩上，也没单独报每次压缩的开销。而压缩的成本结构是固定的（一次全量 prefill + 一次状态生成），收益是逐轮的，所以"越频繁越好"在成本上几乎必然亏。真正可实现的规则是：成功了才压缩绕路，失败时绝不压死路——因为失败中你不知道哪段过程是承重的，而成功后整条绕路就降级成一句"走 B 因为 A 不通"。加上"死路要带判据和 TTL"，这套规则的触发条件是可观测事件，不需要预测器。
  3. 上下文该给"可推翻的过去"，而不是"可依赖的过去"。 "模型抄自己之前的结果"不是懒，是基率意义上的理性策略；而错误发生后 p(错误 | 已错) 会显著升高，策略恰在自己最该失效时最自信。所以提示词治不好，能改的只有成本和结构：状态里存证据和指针而不是结论，结论只允许引用 observation、每次从证据重新生成，未验证的事实写成疑问句而不是陈述句，重验命令自动重跑并与结论 diff。"我搜过"和"我知道"在一个只记录结论的上下文里长得一模一样，而这句话的工程含义就是：能不进 context 的就别进，进了的必须能被机械推翻。
  4. 工具空间是同一个问题的另一个投影：命名空间即路由。 模型误调 map_setting 的那一次，动词来自用户、名词来自工具名，它在工具空间里拼了一个看起来合法的调用。这个错误的根源是工具切在应用边界轴上、用户意图切在动作轴上，而"名字里带这个实体"的工具会吸掉该实体所有没被显式覆盖的意图。在工具数量大、团队分散、命名正交不现实的约束下，能在工程上改的不是命名，而是路由层：把集中治理的量级压到 O(意图)，默认入口常驻，参数校验失败处做反向建议，并把考核指标从"误调用率"改成"误调用恢复成本"——前者你消除不了，后者能压到一次调用。

一个可证伪的预测

未来 12 个月内（至 2027-11）：

  1. 主流 agent harness 的压缩机制会从"纯 token 阈值"演化出以事件为触发的默认形态，并且会出现"成功后压缩 / 失败时保留死路"的显式语义。可观测信号：主流开源 agent 框架（LangGraph / LlamaIndex / OpenAI Agents SDK / Anthropic SDK 这一层）的 compaction 配置或文档里，出现"按子目标完成 / 任务成功"触发、或按 observation 有效期触发的选项，而不是只有 max_tokens 类阈值。反向信号：12 个月内所有主流框架的压缩触发仍然只有长度阈值这一类参数，且没有出现"死路保留"的独立机制——那说明这个方向在工程上没有需求，本判断证伪。（这条的基线我没有逐一核过所有框架，只核到"当前主流形态是按长度/百分比触发的自动压缩"；如果你知道的某家已经有事件触发的实现，这条要改窄或撤掉。）
  2. 工具错误会从自由文本走向机器可读的结构字段。当前基线（已现查）：MCP spec 2026-07-28 已经有两级错误机制——JSON-RPC 协议错误（模型基本改不动）与 isError: true 的工具执行错误（要求内容带"模型能用来自纠、调整参数重试"的反馈），另有 InputRequiredResult 这条"服务端需要更多输入"的多轮往返。也就是说"怎么分类、怎么说人话"的要求已经有了，缺的是"机器可解析"这一层。所以我押的是在 isError + 自由文本之上，再长出结构字段：错误类别枚举（参数错 / 前提不满足 / 永久不可行 / 需要更多输入）+ 建议的下一个工具或参数。可观测信号：spec 或主流 SDK 的 tool result 里出现 suggested_tool / next_action / error_category 一类的字段，且有至少一家大厂文档明确要求工具作者填写。反向信号：工具错误仍然普遍以非结构化字符串返回，且主流 SDK 明确把"工具该给什么错误信息"留给实现者自由决定。
