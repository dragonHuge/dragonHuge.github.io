原文沉淀

我替大家先试了一把 Jev：一个不写代码、不聊天，只负责“做决定”的奇葩模型

来源：https://mp.weixin.qq.com/s/P1nQ9FwFypiYkMThJVftgw 平台：weixin｜作者：智能体AI

做决定，可能是企业 AI 最缺的那一步。Jev 不写文章、不写代码、也不陪聊，它只干一件事——给软件一个可以直接执行的决定。

最近在关注一个挺有意思的新模型，叫 Jev。

它不是又一个“更强的聊天模型”，也没打算跟 GPT、Claude 这类通用大模型正面竞争。恰恰相反，它做的事情很窄——窄到有点反常。不写文章，不写代码，也不负责陪聊。它就干一件事：做决定。

比如：这是不是一个退款请求？这个工单该交给哪个团队？这条消息紧不紧急？客户到底有多不满？RAG 检索出来的文档相不相关？Agent 该调用哪个工具？

这些问题看着简单，却是企业软件里每天都在处理的判断。过去我们习惯把这类判断也扔给 LLM，让它先生成一段话，再想办法从文字里解析出程序能用的结果。TypeSafe 的思路反过来了：既然软件真正要的只是一个“决定”，为什么还要让模型先绕一圈写作文？

我专门跑了一次测试，结果值得聊聊。

01

REAL CASE

一个真实的客服场景

不讲概念，先看一个很普通的例子。用户说：

我上周三买的那笔订单已经扣款两次了，一共 398 块，到现在货还没发出。客服机器人让我等 48 小时，可我这周五就要出差，赶不上就别发了，直接把多扣的钱退给我，不然我就去投诉。

这一句话，传统客服系统其实要拆成好几个判断：客户是不是在要退款？他急不急？这个工单该转给财务、客服、物流还是技术？他现在的不满程度有多高？

如果交给普通 LLM，链路通常是这样的：

普通 LLM 的链路

Prompt → LLM → “我认为客户主要是因为重复扣款和物流问题产生不满……” → JSON Parser → Schema Validation → Business Logic

问题在于，软件真正想要的从来不是那段解释，而是：

. . . output

wants_refund = true

is_urgent = true

route_to = billing

frustration = 1.21

我把同样的问题交给 Jev，定义很简单：

. . . json

{

"wants_refund": {

"type": "noul",

"instructions": "这条消息是在要求退款吗"

},

"is_urgent": {

"type": "noul",

"instructions": "这条消息表达了明确的时间压力或紧急感吗"

},

"route_to": {

"type": "choice",

"instructions": "这条工单应该交给哪个团队",

"criteria": {

"billing": "付款、发票、重复扣款、退款",

"logistics": "发货、物流、配送进度",

"technical": "Bug、宕机、接口报错",

"other": "以上都不属于"

}

},

"frustration": {

"type": "score",

"instructions": "这位客户的不满程度有多高",

"criteria": ["平静陈述", "不满但克制", "非常愤怒，用词激烈"]

}

}

返回结果：

. . . json

{

"wants_refund": { "noul": 0.96 },

"is_urgent": { "noul": 0.97 },

"route_to": { "choice": "billing", "confidence": 1 },

"frustration": { "score": 1.21, "confidence": 0.69,

"probabilities": { "0": 0, "1": 0.79, "2": 0.21 } }

}

用的是 jev-1.13.0：

这展示的不是“AI 能不能回答客服问题”，而是“AI 能不能直接给软件一个可以执行的决定”。

02

DIFFERENCE

和过去用 LLM 有什么本质区别

这是理解 Jev 的关键。过去我们用 LLM 的方式很自然：Prompt 进去，Text 出来。同样问“这条客服消息该交给哪个团队”，LLM 可能回答：

根据客户描述，问题主要涉及重复扣款和退款，因此建议转交财务或账务团队，同时考虑到客户存在明确的时间压力，也应该优先处理。

人看没问题，软件看就麻烦了——它需要的是 billing，不是一整段有理有据的分析。于是我们又得加一层 Text → JSON → Parser → Validation → Enum。本来只是想问“该交给谁”，结果变成了先让生成模型写一篇小作文，再想办法把作文翻译成程序能理解的数据。这正是传统 LLM 应用里一个很普遍、也很别扭的模式。

软件世界和人类世界的偏好其实很不一样：人喜欢自然语言，软件喜欢类型——boolean、enum、number、probability。“是否退款”，软件要的是 true/false；“交给哪个团队”，软件要的是 billing 这个词，而不是一段综合分析；“客户多不满”，软件要的是 1.21，不是一段感受描述。

两种模式画出来很直观：

这就是 TypeSafe 想做的事。

03

CONCEPT

Jev 是什么

Jev 是 TypeSafe 推出的第一个 System One Model。真正值得关注的不是“Jev”这个名字，而是“System One”这个定位——如果把传统 LLM 理解成一种生成系统，System One 更接近一种决策系统。逻辑很简单：告诉它现在发生了什么，告诉它你希望它判断什么，它返回结构化的答案。这和聊天模型的交互方式完全是两回事。

三个核心能力：Noul、Choice、Score

Noul · 是不是处理的是二元判断。“这是不是退款请求”给出 0.96，“这个请求急不急”给出 0.97。软件可以直接拿这个数字做控制流：

. . . python

if is_urgent > 0.9:

priority = "high"

if wants_refund > 0.9:

route_to_refund_workflow()

到这一步，AI 已经不只是在回答问题，而是直接参与了程序的控制流。

Choice · 该选哪个本质是一个路由器。工单可能属于 billing、logistics、technical、other，Jev 直接给出概率分布和最终选择。过去我们常让 LLM 做“理解意图 → 选工具”这一整套推理；如果一个企业 Agent 挂了 30 个工具，不一定每次都要让大模型从头想一遍该调哪个，完全可以先让 Decision Model 做第一层路由，大模型专心处理更复杂的推理。

Score · 有多确定不只是是或否。比如刚才那个“客户不满程度”的例子，分数是 1.21，看着像是“1 和 2 之间”，但概率分布才是关键——79% 落在“不满但克制”，21% 落在“非常愤怒”。这意味着模型的真实判断更接近“主要是克制中带着不满，同时存在一定激烈情绪”，而不是简单粗暴地说“这个客户很生气”。

企业系统很多时候真正关心的不是 AI 说了什么，而是 AI 有多确定。

04

CONFIDENCE

Confidence，可能是最值得研究的设计

传统 LLM 给你一个建议——“建议转交财务部门”——但它到底有多确定？你可以追问“你有多大把握”，它可能回你“我有 90% 的把握”，可这个 90% 本身还是生成出来的文字，没法直接被程序信任。

Jev 把 probability 和 confidence 做成结构化结果的一部分，Agent 的控制逻辑因此可以变成：

控制逻辑

AI → Decision + Confidence → Policy → Action

比如设一道简单的策略：confidence 高于 0.95 就自动执行，0.80～0.95 做二次确认，低于 0.80 转人工审核。这件事之所以重要，是因为——

企业 AI 最大的问题从来不是“AI 能不能做”，而是“AI 什么时候可以自己做主，什么时候不能”。

Confidence 恰好是这中间最关键的控制信号。

05

ARCHITECTURE

Agent 架构里可能多出一个 Decision Layer

传统 Agent 架构基本是这样一条线：

问题是一个模型承担了太多事：理解用户、推理、选工具、判断风险、决定是否执行、生成最终回复，全挤在一起。Jev 提出的是另一种分工：

LLM

负责生成和复杂推理

Jev

负责结构化判断

Policy

决定什么时候允许执行

Tools

真正改变外部世界的动作

这比“一个大模型包打天下”更接近软件工程的思路——早期软件也是把所有逻辑塞进一个巨大程序里，后来才逐渐拆成数据库、缓存、队列、服务、网关这些独立的部分。AI 可能正在走同样的路。

06

ENTERPRISE

为什么这对企业 Agent 特别重要

企业系统里大量的工作，本质上都是判断：这个客户是不是 VIP？这个订单是不是异常？这份发票是不是重复了？这份合同是不是少了条款？这个请求风险高不高？这次代码改动是否违反架构规范？测试结果够不够可信？Agent 该继续跑还是该停下？

这些任务有个共同特点——输出空间是有限的。它们不是“写一篇关于这个客户的文章”，而是 Yes/No、A/B/C/D、0/1/2/3、Pass/Fail/Review。这正是 Decision Model 最擅长介入的地方。

07

POSITIONING

Jev 不是来替代 LLM 的

如果把 Jev 理解成“一个比 GPT 更厉害的新模型”，反而理解错了方向。它和 LLM 的关系更像是分工合作：LLM 负责生成，Jev 负责判断，Embedding 负责检索，Reranker 负责排序，Guard Model 负责安全检查。

未来一个完整的 Agent，可能根本不是“一个模型加一堆工具”，而是 多个专业模型 + Agent Runtime + Context + Harness + Tools 的组合。模型开始出现专业分工，这和软件工程的演化路径其实很像。

08

SCENARIOS

两个具体场景：RAG 和 AI Coding

Jev + RAG

传统 RAG 的链路是：

传统 RAG

Embedding → Vector Search → Top K → LLM → 回答

问题在于 Top K 不等于真正有用——检索出来的内容可能相关性不够、已经过时、彼此矛盾，甚至藏着 Prompt Injection。加一层 Decision Layer 之后，流程变成：

RAG + Decision Layer

Retriever → Top K → Jev 判断（相关性、有用性、冲突、注入风险）→ 筛出真正可用的证据 → LLM 生成

Jev 并没有替代 RAG，它做的是给 RAG 加一层把关。

Jev + AI Coding

现在 AI 写代码的最大问题，已经不是“会不会写”，而是“该不该这么改”。比如一个需求是“业扩预受理增加一个校验”，Agent 很快找到文件、写出代码、能编译、测试也能跑，结果架构师一看——改错地方了，因为系统里可能有页面入口、前端服务、领域服务、共享服务、省级规则、全国规则、数据库这么一长串层级，AI 写代码不难，难的是判断这个需求到底该落在哪一层。

这时候可以让 Jev 在改代码前后分别把关：这是哪类变更？是否涉及核心领域？是否违反架构规则？是否需要人工确认？测试通过后风险等级如何？是否需要 Review？Jev 不是在写代码，它是在帮 Coding Agent 判断“能不能做、该不该做、做完是否可信”。

09

CONTEXT

这其实也是 Context Engineering 的问题

很多团队做 Agent 时把大量精力花在 Prompt、RAG、MCP、Memory、Tool 上，却容易忽略一个问题：Agent 做决定时，依据的到底是什么？Decision Model 同样需要 Context，而且可能比普通 LLM 更敏感——判断“这个订单是不是异常”，给它订单金额、支付状态、退款记录、发货状态，它可能判断得很准；但如果一股脑塞进客户历史订单、营销活动、聊天记录、物流日志、全部 CRM 字段、二十份产品文档，效果不一定更好，因为真正有用的信息反而可能被淹没。

Context Engineering 的目标从来不是“给 AI 越多信息越好”，而是给它做这一次判断所需要的信息。

10

BOUNDARY

边界也很明显，不该神化

Jev 很有意思，但不是万能模型——这一点反而是 TypeSafe 文档里比较让人放心的地方：官方公开列出了 Jev 1.13 的已知局限。这很好理解，“123456×987654 等于多少”最合理的方案是调用计算器，不是让 AI 去想；而“这个请求是否需要人工审核”这种问题，才是 Decision Model 的主场。

！已知局限 🕳

Jev 1.13 不适合复杂数学计算、不该承担精确日期计算，也不能当成通用的多步推理模型来用。

合理的架构应该是分工明确：能算的交给代码，要检索的交给 Search/RAG，要生成的交给 LLM，要复杂推理的交给 Reasoning Model，要结构化判断的交给 Decision Model，要真正执行动作的交给 Tools。模型开始各司其职之后，AI 系统才会真正长成一套软件系统该有的样子。

11

EVOLUTION

一个更大的变化

回顾这几年 AI 的演进路径，会看到一条很清晰的脉络：

更大的模型

先是研究“怎么让模型回答得更好”。

RAG、Knowledge Graph、Memory

然后研究“怎么让模型看到企业知识”。

Function Calling、MCP、Agent

接着研究“怎么让模型调用工具”。

Harness、Guardrail、Human-in-the-loop、Audit

再往后是“怎么让 Agent 可靠执行”。

Decision Layer

现在冒出来的问题是——“Agent 到底应该什么时候做决定？”

未来的 Agent，可能不再是一个模型，而是一整套系统：Agent Runtime 之下，Generation（LLM）、Decision（Jev）、Context（企业知识图谱）三条线并行，最后统一交给 Harness 控制执行，再通过 MCP、Tools、Workflow 真正连接到企业系统。LLM 负责怎么生成，Jev 负责怎么判断，Context 负责依据什么判断，Harness 负责怎么控制执行——这时候 AI Agent 才算真正从“聊天机器人”过渡成“软件系统”。

12

REVISIT

回到最开始那个客服案例

再看一次那条客户消息，Jev 的完整判断是：要求退款 0.96，紧急 0.97，路由到 billing（置信度 1.00），不满程度 1.21（79% 属于“不满但克制”，21% 属于“非常愤怒”，整体 confidence 0.69）。

如果只是一个普通分类器，我们大概率只会拿到一个干巴巴的 frustration = 1。但现在系统清楚地知道：这位客户主要是克制的不满，但有约两成的概率其实已经很激烈了。企业可以据此定出更细的策略——退款意图超过 0.9 就进退款流程，紧急度超过 0.9 就提优先级，billing 路由直接转账务团队，普通不满程度走常规人工处理，一旦 confidence 偏低就转人工复核。这时候 AI 已经不只是在回答用户，而是实实在在地参与到了业务流程里。

13

WHAT THEY WANT

企业 AI 真正想要的东西

企业最终不会因为“这个模型很会聊天”就把核心业务交给它。企业真正在意的是能不能——

判断控制追踪解释回退人工接管审计

所以企业 AI 需要的可能从来不是一个超级大脑，而是一整套可控的智能系统——LLM、Decision Model、RAG、Context、Memory、MCP、Tool、Workflow、Policy、Harness、Human Review、Audit，各就各位。

Jev 的价值就在这里：它提醒我们，AI 模型不一定非要“什么都会”。有时候，一个模型只把一件事做到位，反而更有用。

∞

THE END

结语：从“会说”到“会决定”

这几年我们一直在追一个问题——谁的模型更聪明？参数越堆越大，Context 越拉越长，Reasoning 越练越强，Agent 越搭越复杂。但当 AI 真正走进企业之后，另一个问题变得更重要：AI 到底什么时候可以自己拍板？

这其实是完全不同维度的问题。模型可以很聪明，但一个企业系统还需要知道什么时候该执行、什么时候不该执行、什么时候继续、什么时候停下、什么时候该交给人。所以 Jev 最值得关注的，不是它能不能替代 GPT，也不是它是不是下一个超级模型，而是它把一个很朴素也很关键的方向摆到了台面上——

把“生成”和“决策”拆开来看。

未来的 Agent 或许不再是“一个 LLM 加一堆 Tools”，而更接近“LLM + Decision Model + Context + Harness + MCP + 企业系统”这样一套组合。LLM 负责把话说清楚，Decision Model 负责把事情判断明白，Context 告诉它为什么这么判断，Harness 决定它能不能动手，MCP 让它真正接得上企业系统。走到这一步，AI 才算从一个“会回答问题的模型”，慢慢变成一个真正能嵌进业务流程里的软件系统。

而这，可能才是 Jev 这个模型真正值得被记住的地方——

AI 的下一步，也许不是让一个模型什么都会，而是让不同的模型，各自把自己最擅长的事情做好。

END
