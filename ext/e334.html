Codex 从小白到实战高手：大厂工程化实战手册

先读这一页：你真正需要知道的 12 件事

  1. Codex 不是普通聊天机器人。它能在授权范围内读项目、改文件、运行命令、跑测试、生成差异（diff）和审查建议。
  2. 它不是“自动写完就上线”的替代品。专业用法是：先理解 → 先计划 → 小范围改动 → 自动验证 → 人工审查 → 再提交。
  3. 第一次用，不要让它直接改代码。先让它只读项目、生成导读、找入口和测试命令。
  4. 最重要的不是“提示词写得花”，而是把任务说清楚。至少要有：背景、目标、范围、约束、验收标准、验证方式。
  5. 永远要求它运行检查。例如 lint、类型检查、单元测试、构建、关键功能手测。没有验证的“完成”，不叫完成。
  6. 不要随意开 Full Access，也不要用 --yolo。对本地项目，优先使用 workspace-write + on-request，让 Codex 遇到高风险操作先问你。
  7. 不要在主分支上让它大改。真实团队应在独立分支或 Git worktree 中改，改完走 diff / PR 审查。
  8. 项目根目录应该有 AGENTS.md。它相当于“给 AI 的项目说明书”，能减少你反复解释规则。
  9. 大任务先开 Plan mode。任务模糊、文件多、要跨模块时，先让它出计划，不要直接执行。
  10. 对科研代码，必须明确写“不要改算法逻辑、不要改随机种子、不要碰原始数据”。
  11. 对外网、密钥、数据库、生产环境，默认拒绝或严格限制。Codex 能执行命令，因此它的权限就是你的风险边界。
  12. 高手不是用 Codex 写得最快，而是让 Codex 产出的改动可解释、可复现、可验证、可回滚。

很多人把 Codex 称为“AI 编辑器助手”，这个说法不算错，但不够准确。

更准确的理解是：

Codex 是一个 AI coding agent（编程代理）。它可以在你指定的项目目录或云端环境中，读取代码、改代码、运行命令、查看输出、继续调整，直到任务完成或需要你决定。

普通聊天机器人通常是这样工作：

你提问 → AI 给一段建议或代码 → 你复制粘贴 → 你自己运行 → 你自己排错

Codex 的目标工作方式是：

你交任务 → Codex 读取项目 → 制定计划 → 修改文件 → 运行检查 → 汇报 diff 和验证结果 → 你审核

Codex CLI 官方定义为：在本地终端运行的编程代理，可在所选目录中读取、修改和运行代码。(S1) IDE 扩展则能在 VS Code、Cursor、Windsurf、JetBrains 等编辑器中与代码并排工作，也可把较长任务委托给 Codex Cloud。(S2)

1.2 把 Codex 当成什么角色，最容易用对？

最危险的定位是：

“反正它会写，直接全交给它。”

因为 Codex 不知道你脑子里未写出来的业务规则、历史包袱、线上约束、数据合规要求和团队约定。

1.3 最适合与不适合直接放手的任务

适合交给 Codex

  • 阅读陌生项目，生成项目导读。
  • 解释某个函数、模块、接口调用链。
  • 定位明确报错。
  • 在明确范围内新增一个小功能。
  • 为已有逻辑补单元测试。
  • 把重复脚本自动化。
  • 重命名、迁移、格式统一等机械性改动。
  • 做 PR 风格代码审查。
  • 检查类型、lint、构建或测试失败原因。
  • 针对设计图或截图修改前端页面。

不适合“直接放手”

  • 修改生产数据库结构。
  • 执行不可逆删除命令。
  • 自动部署到正式环境。
  • 处理未脱敏的隐私数据。
  • 读取、复制或提交密钥。
  • 在不了解算法的情况下修改科研模型核心逻辑。
  • 在没有测试的情况下重构整个项目。
  • 自动合并 Pull Request。

经验法则：

越容易回滚、越容易自动验证、影响范围越小的任务，越适合交给 Codex。

越不可逆、越高权限、越依赖业务判断的任务，越应该由人主导。

大厂工程化工作流：从需求到提交的标准闭环

真正成熟的使用方式，不是“问一句、改一堆”，而是下面这个闭环。

R：Read（阅读与建立上下文）

P：Plan（规划与拆解）

I：Implement（小范围实现）

V：Verify（自动验证）

R：Review（人工审查与 AI 自审）

D：Deliver（提交、PR、文档、回滚信息）

可以简称为：

R-P-I-V-R-D 工作流

5.1 R：Read——先阅读，不要抢着改

Codex 先应该做：

  • 找入口；
  • 找相关模块；
  • 找配置；
  • 找测试；
  • 找调用链；
  • 找已有实现方式；
  • 找历史改动和风险点。

在修改前，请先完成阅读阶段：

  1. 列出与任务最相关的 5~10 个文件；
  2. 解释它们之间的调用关系；
  3. 找到已有相似功能；
  4. 找到对应测试；
  5. 说明你准备改哪里、为什么。

先不要修改。

大厂经验：一个任务如果 Codex 在第一轮就开始写代码，往往是因为你没有要求它先建立上下文。

5.2 P：Plan——复杂任务必须先计划

任务满足以下任一条件，就应该先 Plan：

  • 要改 3 个以上文件；
  • 涉及前后端联动；
  • 需要数据库或接口变更；
  • 需求描述不清；
  • 影响登录、支付、权限、训练算法等关键流程；
  • 你自己也说不清该怎么实现。

官方建议：复杂、模糊或难描述的任务，先让 Codex 计划；Plan mode 可通过 /plan 或 Shift + Tab 使用。(S4)

高质量计划应包含什么

  1. 目标与不做什么；
  2. 涉及文件；
  3. 每个文件的改动理由；
  4. 主要风险；
  5. 验证方案；
  6. 回滚方案；
  7. 需要你确认的决策点。

目标：

【写清楚最终目标】

请输出：

  1. 需求拆分；
  2. 现有实现分析；

  4. 每个文件的修改内容；
  5. 不确定点与风险；
  6. 测试与验证方案；
  7. 回滚方案；
  8. 你需要我确认的地方。

只有在我明确回复“按计划执行”后，才开始修改。

5.3 I：Implement——小步提交，而不是一把梭

错误做法：

把整个登录模块、用户模块、权限模块全重构了。

正确做法：

第一轮：先补齐错误处理；

第二轮：只改登录表单；

第三轮：再补测试；

第四轮：再做结构整理。

每一步都让 Codex 输出：

  • 改了哪些文件；
  • 哪些地方没改；
  • 为什么不改；
  • 有无新增依赖；
  • 是否存在兼容性风险。

5.4 V：Verify——验证不是“它说没问题”

验证至少分四层：

请验证刚才的修改，不要只说“已完成”。

按以下顺序执行：

  1. 运行格式检查；
  2. 运行 lint；
  3. 运行类型检查；
  4. 运行与本次改动直接相关的测试；
  5. 如可行，运行完整测试；
  6. 说明每项通过、失败或未执行的原因；
  7. 如果某项没有验证，请明确写“未验证”，不能省略。

5.5 R：Review——必须看 diff

无论 Codex 多厉害，都要看 diff。

你最该检查：

  1. 是否改了无关文件？
  2. 是否删掉了原有逻辑？
  3. 是否新增了不必要依赖？
  4. 是否硬编码了密钥、地址、账号、测试数据？
  5. 是否绕过异常处理？
  6. 是否把问题“藏起来”而不是解决？
  7. 是否改变了接口返回格式？
  8. 是否影响兼容性？

官方建议，在完成改动后让 Codex 运行检查并审查 diff；Codex 的 /review 可用于基于分支、未提交改动、提交或自定义规则进行审查。(S5)

测试、验收与代码审查：防止“看似完成，实际埋雷”

10.1 代码能运行，不等于任务完成

很多 AI 产出的问题是：

  • 页面能打开，但异常路径没处理；
  • 测试能过，但测的是错误内容；
  • 重构后代码更“漂亮”，但性能变差；
  • 逻辑修了，但接口兼容性破坏；
  • 训练能跑，但实验结果已经不可比。

所以你必须定义“完成”。

10.2 一个合格的 Definition of Done

本任务完成的标准：

  1. 功能满足需求描述；
  2. 修改范围不超过约定文件；
  3. 不引入无关依赖；
  4. 相关单元测试通过；
  5. lint、类型检查和构建通过，或明确说明未通过原因；
  6. 关键用户流程已经手动验证；
  7. diff 已审查；
  8. 风险、兼容性和回滚方式已说明。

10.3 让 Codex 做“自审”而不是只做“实现”

请不要继续实现功能。

请把自己刚才的改动当作别人的 PR 来审查。

重点检查：

  1. 是否存在逻辑错误；
  2. 是否覆盖了失败路径；
  3. 是否有空值、并发、超时、权限、类型边界问题；
  4. 是否改动了不该改的文件；
  5. 是否存在安全或隐私风险；
  6. 是否有可以更小、更稳的改法。

请按“阻塞问题 / 高风险 / 建议优化 / 测试缺口”四类输出。

10.4 手工验收的最小清单

前端页面

  • 页面是否能打开；
  • 桌面与移动尺寸是否正常；
  • loading、空状态、失败状态是否可用；
  • 表单校验是否清晰；
  • 提交后状态是否正确；
  • 是否影响其他页面。

后端接口

  • 正常输入是否正确；
  • 空输入、非法输入、超长输入是否安全；
  • 错误码和错误信息是否符合约定；
  • 是否有权限检查；
  • 是否有超时、重复请求、幂等性问题；
  • 是否影响旧客户端。

科研训练

  • 数据量、样本数是否正确；
  • 随机种子和配置是否记录；
  • 小样本 smoke test 是否通过；
  • 指标计算是否一致；
  • 输出路径是否正确；
  • 是否意外覆盖旧结果。

  • 原有测试必须通过；
  • 新增测试至少覆盖被拆分的关键分支；
  • 接口签名不变；
  • 性能不明显下降；
  • diff 不出现大量无意义格式变化；
  • 一个 PR 只做一类重构。

实战 7：PR / 代码审查

请审查当前分支相对 main 的改动。

审查重点：

  1. 正确性；
  2. 异常和边界；
  3. 安全与权限；
  4. 性能；
  5. 兼容性；
  6. 可维护性；
  7. 测试充分性。

输出格式：

  • 阻塞问题：必须修复，给出文件和行级依据；
  • 高风险问题：建议本次修复；
  • 建议优化：可后续处理；
  • 缺失测试：建议补哪些；
  • 总结：是否建议合并。

让 Codex 审自己刚改的代码：

请把你刚才的改动当作一个独立 PR 再审一次。

不要修改代码，只输出审查意见。

特别检查是否因为实现本次需求而破坏了旧逻辑。

Git、分支和 Worktree：让 Codex 的改动可控可回滚

12.1 一个基本原则

不要让 Codex 在你的主分支、未提交工作区、唯一副本上做大改。

最稳妥流程：

main / master

↓

新建 feature 分支

↓

让 Codex 在该分支工作

↓

看 diff + 跑测试

↓

提交 commit

↓

发 PR

↓

审查与合并

12.2 每次任务前的 Git 检查

git status

git branch --show-current

git diff

如果工作区不干净：

  • 先提交；
  • 或 stash；
  • 或单独建立分支；
  • 不要混着让 Codex 改。

12.3 Worktree 是什么，为什么适合 Codex

Git worktree 可以理解为：

同一个仓库同时开出多个独立工作目录，每个目录可以在不同分支上工作，但共用 Git 历史。

Codex App 的 worktree 功能基于 Git worktrees，可以让多个任务在不同目录、不同分支并行进行。(S11)

适合场景：

worktree A：修 bug

worktree B：做新功能

worktree C：实验重构方案

这样不同任务不会互相污染。

12.4 专业建议：一个任务一个分支

分支名示例：

fix/login-redirect

feat/export-csv

refactor/order-service

test/auth-boundaries

chore/update-lint-rules

告诉 Codex：

请只在当前分支内工作。

不要切换分支、不要改 main、不要执行 merge、rebase、reset --hard。

完成后只输出 diff 和建议 commit 信息。

12.5 Commit 信息让 Codex 帮你写，但别让它乱提交

请根据当前 diff 生成：

  1. 建议的 commit message；
  2. PR 标题；
  3. PR 描述；
  4. 测试说明；
  5. 风险说明。

不要执行 git commit 或 git push。

权限、安全、联网与敏感数据：必须看懂的边界

这是整份文档里最值得反复看的部分。

Codex 的价值来自“它能行动”，风险也来自“它能行动”。

13.1 三种常见沙箱级别

官方 CLI 文档列出以下 sandbox 策略：(S7)

新手推荐

默认：read-only

确认任务后：workspace-write + on-request

不要轻易使用：danger-full-access

13.2 什么是 approval policy

简单说，就是：

Codex 什么时候必须停下来问你“能不能做”。

常见值包括：untrusted、on-request、never。(S7)

13.3 为什么不建议 --yolo

CLI 中 --dangerously-bypass-approvals-and-sandbox / --yolo 会绕过审批和沙箱。官方明确说明：只应在外部已经强化隔离的环境中使用。(S7)

人话：

它等于对 Codex 说：“不用问我，想干什么都行。”

对个人电脑、科研目录、公司代码库、含有凭证的环境，这是高风险操作。

13.4 网络访问：不是越开放越好

官方说明：对于 App、CLI、IDE 的 workspace-write 模式，网络默认关闭，除非你显式开启；Cloud 的 agent phase 默认也离线，setup 阶段可用于安装指定依赖。(S6)

为什么默认关网络？

  • 提示注入；
  • 恶意依赖；
  • 不可信网页命令；
  • 源码或密钥泄露；
  • 许可证风险；
  • 无法追踪的外部数据来源。

正确做法

  1. 默认关闭网络；
  2. 只有确实要下载依赖、查官方文档时才开；
  3. 能白名单域名就不要全开放；
  4. 不直接执行网页、issue、README 中的命令；
  5. 不让 Codex 把密钥粘贴到命令行或日志。

13.5 敏感信息红线

以下内容不要直接放进提示词，也不要让 Codex 接触：

  • API Key；
  • 数据库密码；
  • SSH 私钥；
  • .env 真实生产凭证；
  • 身份证、手机号、病历、支付数据；
  • 未脱敏客户数据；
  • 内部商业策略；
  • 生产环境直接访问 token。

更安全的做法

  • 用假的示例值替代；
  • 用环境变量名代替真实值；
  • 只给脱敏样本；
  • 让 Codex 写“读取环境变量”的代码，不要把值写入代码；
  • 生产配置与开发配置分开。

13.6 Cloud 的额外安全理解

Codex Cloud 在 OpenAI 管理的隔离容器中运行。官方说明：云端使用两阶段运行模型——setup 阶段可联网安装依赖；agent 阶段默认离线；云端环境配置的 secrets 只在 setup 阶段可用，进入 agent 阶段前会被移除。(S6)

这并不意味着你可以把所有敏感信息都放心交出去。正确理解是：

云端有隔离与权限机制，但你仍应遵守最小权限、最少数据、最少联网的原则。

Local 与 Cloud：什么时候让它在本机做，什么时候丢到云端

14.1 用本地 Local 的情况

适合：

  • 项目只在你电脑上；
  • 需要本地数据库、硬件、GPU、私有文件；
  • 需要看实时日志；
  • 需要频繁手工调试；
  • 你想严格控制网络和文件范围。

优点：

快、上下文近、能用本地环境、适合调试。

风险：

如果权限过大，可能影响你的本机文件和环境。

14.2 用 Cloud 的情况

适合：

  • GitHub 仓库中的明确任务；
  • 后台较长任务；
  • 想让它独立开 PR；
  • 并行处理 issue；
  • 不想占用本机；
  • 希望隔离环境做实验。

官方文档说明，Cloud 任务会创建容器、检出指定仓库分支或提交、运行 setup script、应用网络规则，然后在隔离环境中执行任务并输出变更 diff。(S12)

优点：

隔离、可并行、适合后台任务、适合 PR 工作流。

局限：

看不到你本机未上传的文件；

不适合依赖本地硬件、GUI 或私有环境的调试；

环境准备不充分时，容易“跑不起来”。

14.3 Local / Cloud 决策表

进阶能力：Plan、Goal、Subagents、MCP、Skills、Automations

这一章不是让你一次全开。正确顺序是：

先掌握：Plan + AGENTS.md + 测试 + Diff

再使用：Goal + Worktree + Review

最后再碰：Subagents + MCP + Skills + Automations

15.1 Plan mode：复杂任务先规划

适合：

  • 新功能；
  • 大重构；
  • 跨前后端；
  • 需求模糊；
  • 你想先看方案。

计划不是“列几个步骤”。

好的计划必须能回答：

  • 为什么改这里？
  • 改哪些文件？
  • 不改哪些文件？
  • 风险是什么？
  • 如何验证？
  • 如何回滚？

15.2 Goal mode：给长任务一个可检查的终点

Goal mode 的作用是让 Codex 持续围绕一个明确目标工作，并以目标文本作为完成标准。官方建议目标应具有明确结果、可衡量指标或测试标准。(S8)

坏目标：

把项目改好。

好目标：

将本项目从 JavaScript 迁移为 TypeScript。

验收标准：

  1. strict mode 编译通过；
  2. 不出现显式 any；
  3. 全部测试通过；
  4. 不改变现有接口行为。

15.3 Subagents：并行不是“越多越好”

Subagents 是子代理。它适合把可以并行的工作拆开，例如：

代理 A：梳理前端调用链

代理 B：梳理后端接口

代理 C：梳理数据库模型

代理 D：梳理测试缺口

主代理：汇总方案

官方说明：Codex 不会自动无限制地生成子代理；应由你明确请求，而且子代理会消耗更多资源。(S13)

正确提示词

请使用 3 个并行子任务完成只读分析：

任务 A：检查前端页面到 API 调用链；

任务 B：检查后端接口、参数校验和错误处理；

任务 C：检查测试覆盖和现有测试缺口。

每个子任务必须输出：

  1. 涉及文件；
  2. 关键发现；
  3. 证据；
  4. 风险；
  5. 建议。

最后由主任务汇总为一个修复计划。

先不要修改代码。

不适合用子代理的场景

  • 一个小函数解释；
  • 单文件小修改；
  • 没有明确边界的任务；
  • 任务间高度相互依赖；
  • 你还没有稳定的验收方式。

15.4 MCP：让 Codex 连接外部工具

MCP（Model Context Protocol）可以理解为：

让 Codex 不只看本地代码，也能安全、结构化地访问外部工具和上下文的协议。

适合连接：

  • GitHub；
  • 文档库；
  • issue 系统；
  • 数据库查询工具；
  • 内部知识库；
  • 监控 / 日志系统；
  • 设计系统；
  • 云资源查询。

官方建议：不要一开始把所有工具都接上，只接一两个真正能消除手工循环的工具。(S5)

好的使用方式

我经常需要：

  • 从 GitHub 读 issue；
  • 从内部文档读接口规范；
  • 根据规范修改代码。

先接 GitHub 和文档两个 MCP。

不要接数据库写入和生产部署工具。

MCP 的危险点

外部工具意味着：

  • 更大权限；
  • 更复杂数据来源；
  • 可能有副作用；
  • 可能遭遇提示注入。

所以 MCP 接入顺序应该是：

只读工具 → 低风险写入工具 → 高风险工具（尽量不接）

15.5 Skills：把成熟流程封装成“组织能力”

当你发现自己反复说同一套提示词，就该用 Skill。

Skill 可以包含：

  • 固定说明；
  • 输入输出格式；
  • 辅助脚本；
  • 参考文件；
  • 触发语句；
  • 验证步骤。

官方将 Skills 定义为可复用工作流的编写格式，可在 CLI、IDE extension 和 Codex app 中使用。(S14)

适合先做成 Skill 的流程

  • Python 科研实验检查
  • PR 审查
  • 前端页面验收
  • 数据清洗报告
  • 发布前检查
  • 接口变更影响分析
  • 测试覆盖补齐

原则：

一个 Skill 只解决一类问题。

不要做“万能 Skill”。

输入和输出必须清晰。

先把一个流程跑稳，再封装。

15.6 Automations：让重复任务自动跑

当某个流程稳定、可重复、可验收时，可以考虑 Automations。

官方举例包括：汇总最近提交、扫描潜在 bug、生成 release notes、检查 CI 失败、生成站会摘要、按计划执行重复分析。(S15)

好的自动化任务

每周一：

检查上周新增代码中测试覆盖不足的模块，

生成 Markdown 报告，不修改代码。

每天：

读取最近 24 小时失败的 CI，

按失败类型归类，

列出最可能原因和推荐负责人。

不好的自动化任务

每天自动修改所有 lint 问题并直接提交到 main。

自动化适合“发现问题、生成报告、提交候选改动”，不适合跳过人工审核直接影响正式系统。

典型翻车现场与修复方法

16.1 Codex 改了一堆无关文件

原因

  • 你没有限定范围；
  • 它发现了相似问题就顺手改；
  • 项目没有 AGENTS.md；
  • 任务描述包含“顺便优化”。

立即处理

git status

git diff --stat

git diff

然后对 Codex 说：

停止扩大修改范围。

请列出你改动的全部文件，并按“任务直接相关 / 间接相关 / 无关”分类。

除任务直接相关文件外，先不要继续修改。

预防

范围必须写：

只允许修改：

  • 文件 A
  • 文件 B

允许新增：

  • tests/xxx.test.ts

禁止修改：

  • 配置
  • API
  • 数据库
  • 无关目录

16.2 Codex 说“测试通过”，但你发现根本没跑

改法

请不要使用“测试通过”这种笼统表述。

请以表格输出：

检查项执行命令结果证据 / 失败原因
----

未执行的项目必须明确写“未执行”。

16.3 Codex 编造了不存在的 API / 函数

在写代码前，请先搜索项目中是否已有相关 API、组件、工具函数或类型。

如果不存在，请明确写“项目中未找到”，不要假设它存在。

所有调用必须给出实际文件路径或官方文档依据。

16.4 Codex 为了通过测试修改了测试

本次任务中，测试是验收标准，不是可以随意调整的目标。

只有当测试本身与已确认需求矛盾时，才允许修改测试；

修改测试前必须先说明原因并等待确认。

16.5 会话越来越长，Codex 忘了早期约束

长会话会触发上下文压缩，旧细节可能被摘要化。官方也说明 Codex 会在长任务中压缩上下文。(S3)

解决：

  • 每个大任务一个新线程；
  • 关键规则写进 AGENTS.md；
  • 复杂需求写入 PLAN.md 或任务说明文件；
  • 阶段完成后让 Codex 输出“当前事实摘要”；
  • 使用 /compact 整理上下文；
  • 用 /fork 比较不同方案，避免主线程混乱。

16.6 Codex 想联网、下载依赖、执行陌生命令

你该问：

  1. 为什么必须联网？
  2. 要访问哪个域名？
  3. 要下载什么依赖？
  4. 这个依赖是否已有替代？
  5. 是否会读取或上传项目文件？
  6. 能否只给我命令和说明，我自己执行？

默认原则：

不清楚，就不批准。

最后一段：把 Codex 用好的本质

Codex 不是“替你写代码的魔法棒”。

它更像一位速度很快、执行力很强、但必须被清楚管理的工程师：

你负责：

需求、边界、决策、风险、验收。

Codex 负责：

阅读、分析、实现、测试、整理、提出候选方案。

当你能做到：

需求清楚

→ 范围清楚

→ 权限收紧

→ 先计划

→ 小步改动

→ 自动验证

→ 人工审查

→ 可回滚交付

Codex 才会从“偶尔帮你写代码的聊天工具”，变成真正能提高交付效率的工程协作者。
