benchmark 不是被人刷坏的，是被可测性拽歪的

参考资料

  • Random Is Almost Enough? Stable and Low-Cost Benchmark Compression via BestRand — arXiv 2611.00883，Bosch Research + CMU，2026-10 · link — 本次对谈的起点，把"用小子集估全量分"当成统计问题来解
  • Artificial Analysis v5 and the benchmarker's dilemma — Nathan Lambert / Interconnects，2026-10-28 · link — 行业侧对聚合指数与"benchmaxxing"的复盘
  • Introducing Claude Opus 5.5 — Anthropic，2026-11-09 · link — 厂商侧自认"benchmark 差距已不是可靠指引"，本篇引用的原话出处
  • TinyBenchmarks / ZipBench / Anchor Points / SparseEval — 2024–2026 的 benchmark 压缩方法，BestRand 的对标基线（构造代表性题目子集，或用历史分数训练预测器）
  • 对谈中提到的另一类资产：企业自建的契约层断言与轨迹评审，不指向具体公开产品

我：看下这篇，第三篇那个 BestRand。

dsh：读完了 arXiv HTML 全文，含 70 个 benchmark 的主表和消融。作者是 Bosch Research + CMU。它要解的问题比标题那句"随机就够了"具体得多。 设定很干脆：一个 N 题 × M 模型 的打分矩阵 X，每道题的难度 g_s 定义为该题上所有模型得分的均值。你想只跑 k 题（k ≪ N）就估计出全量分数，误差 E_m = 子集均分 − 全量均分。它量化的是"这个估计有多准、以及为什么不准"。 它的巧思是把误差拆成两部分：共模位移（子集整体比全量偏难还是偏易，对所有模型是同一个数）和个体偏差。关键假设是 Cov(E) = c(k)²·C，其中 C 的相关系数 ρ 就是"模型之间误差的相关性"。基础模型同源同料甚至同蒸馏，所以它们在同一批题上一起对一起错，ρ 很高——这意味着误差几乎不会随着模型数平均掉。于是整个评估问题退化成"有没有抽到难度对的那批题"，一个一维问题。 三条结论：第一，误差近似零均值多元正态，Pr(MAE &gt; t) ≥ 2Φ(−t/s)，长尾是结构性的；第二，s = c(k)·σ·√(ρ + (1−ρ)/M)，M→∞ 时 s → c(k)σ√ρ &gt; 0，多跑几个模型消不掉这个不稳定性；第三，随机采样本身已经接近最优，MAE 分布的众数贴着下端点——所以"挑代表性题目"的收益天生有限。 方法叫 BestRand：抽一个池（n·k 题），用 5 个便宜的探针模型跑一遍，算出池的探针均分作参照，再从池里抽 128 个候选子集（这步只是缓存向量求平均，不花模型调用），选探针均分与参照 L2 距离最小的那个，目标模型只跑这一个子集。理论依据是 Cauchy–Schwarz：共模位移被探针解释掉的那部分可以对齐掉。 44 个文本 benchmark 的 MAE（%）：保留 2% 时随机是 7.37、BestRand 6.27；10% 时 3.17 对 2.67；20% 时 2.11 对 1.73；50% 时 1.05 对 0.85。总体 MAE 降 16.4%、高误差风险降 50.2%、构造成本只有数据类 baseline 的 51.3%。有个反直觉结果：学习类方法（SparseEval）在 OOD 下比随机还差，拟合历史分数记录反而有害。

我：这个可能主要作为一种快速校验模型训练的 checkpoint 有没有崩掉的方法吧。全跑比较慢，采取抽样跑的方式。有点倾向于 benchmaxxing 的技巧。

dsh：这个定位比论文自己给的定位更合理，但边界要先划出来——用论文自己的数字划。 按 44 个文本 benchmark 的 MAE，保留 2% 是 7.37 分、10% 是 3.17、20% 是 2.11、50% 是 1.05。取 N=1000 的规模，这分别是 20 题、100 题、200 题、500 题。 再反推一下：s = c(k)·σ·√(ρ+(1−ρ)/M)，取题目难度标准差 σ=20 分、ρ=0.9、M=5、k=100，c(k)=0.095，s≈1.8。一次抽样自己就带 1.8 分的 1σ 抖动，而 20 题时 s≈4.3。所以检测 1 分级的退化不可能，5 分级勉强，10 分级才稳。 于是这个用途要分两半，结论完全不同：抓灾难性崩塌（模型直接失效、大批题从对变错），20 题就够，甚至比 2% 还少，因为信号远大于噪声；抓早期退化（慢慢变坏、掉 1–2 分），抽样没戏，不管用什么选题方法都没戏，这时候 400 题往上或者换指标。 还有一个容易被忽略的点："代表性"和"检出力"是两个目标，选题准则相反。BestRand 要的是子集难度分布匹配全量，那是为"报准全量分"服务的；哨兵集要的是"能暴露崩法"。整体垮塌型（格式崩、循环、截断）会让大批题直接变 0，均值极其敏感，根本不需要代表性；局部遗忘型（某个能力面掉 30 分、其他面不动）均值最不敏感——你抽 20 题，如果没踩在那个面上，你会看到一个完全正常的分数。而"崩"在真实训练里，更常见的恰恰是第二种。 至于"benchmaxxing"，这篇本身不算——它是评测压缩，是让评测变便宜，不是让评测看起来更好。但你担心的事情是真的，而且有个更准确的名字：一旦压缩子集进入决策回路，它就从"估计器"变成了"优化目标"。用 20 题的子集挑 checkpoint，连挑 50 个，你挑中的大概率是噪声峰，不是真实最优。更麻烦的是反复训练场景：子集被当成选择信号用上几百次之后，模型会开始适配那 20 题的分布。 另外，如果目标只是"崩没崩"，抽样 benchmark 其实偏贵——每道题都要跑完整 rollout 才能判分。而崩溃最早的表现基本都不需要判分：固定 continuation 上的 held-out ppl、输出长度分布、JSON / tool-call schema 解析成功率、重复 n-gram 比例、拒绝率。这些跑 20 条样本就有信号，比 20 题 benchmark 灵敏一个量级，还不用付 judge 和环境成本。 最后追问一句，这个决定所有参数：你说的"崩掉"，具体形态是什么？loss 发散那种一眼可见的，还是"工具调用参数开始错、但总分的掉幅在两个点以内"那种？

我：loss 发散不需要靠这个集合来发现。可能是那种 SFT 中发生的灾难性遗忘，是比较适合用这种方式发现的。因为这种场景，一般会有另一个目标看起来是正常提升的。

dsh：那这个用途我认为是对的，而且它恰好用到了这篇论文提供的、但没用上的那个否定性结论。 SFT 里的灾难性遗忘，真正发生的不是"能力均匀下滑"，而是你优化的那批数据把输出分布整体拽过去了，于是那些离训练数据分布最远的协议性能力先塌：工具调用参数 schema、多轮状态、长上下文、拒绝边界、格式。它是轴级的，不是均分级。 这决定了这个场景和论文的框架不匹配。某个轴的 schema 合法率从 98% 掉到 71%，20 题就能抓住（10/10 变 7/10 这种量级）；但同一件事在总均分上可能只动 1–2 分，完全淹没在 s≈1.8 的噪声里。所以按 benchmark 的分布去抽（BestRand 正是这么做的），被遗忘的那个轴在子集里可能只占两三个点，它整个人塌了你也看不见。选题准则必须从"按分布抽"换成"按轴抽"，而按轴抽的时候，每轴题量由"你希望在这个轴上检出多大的跌幅"决定，不由它在全量里的占比决定。 统计形态也跟着变了：遗忘是局部的、系统性的、近乎二值的（要么还对，要么整片错），不是小幅均匀下滑。这意味着哨兵集的样本效率比论文的 MAE 框架暗示的高一个量级——但那是拿"探雷器"换"刻度尺"换来的。它能告诉你哪条轴塌了，不能告诉你塌了几分。 两个设计我认为必须先定死。 一，不要做加权总分。你说那个场景——"另一个目标看起来正常提升"——本身就是一个统计陷阱：如果哨兵集给的是一个总分，改进轴会把退化轴的下降抵消掉，总分看着是平的，你会以为没事。必须每轴独立报率，独立设绝对阈值（比如工具调用合法率 <90% 报警），而不是"比上个 checkpoint 低了多少"。绝对阈值对噪声不敏感，差分对噪声敏感。 二，频率的价值大于题量。SFT 的遗忘曲线早期是比较陡的，相当一部分遗忘在前几百步就发生了。30 题每 200 步跑一次，比 200 题每 1000 步跑一次有用得多。这里的理由其实不是算力，是反馈延迟：全量 benchmark 最贵的不是那点 GPU 时，是它只能让你在训练结束后知道。 还有一件事必须承认：哨兵集会失效。模型在变，数据配比在调，某个轴可能悄悄从"有判别力"变成"没判别力"。唯一的手段是每隔几个训练 run 用一次全量评测校验"哨兵集的变化方向 == 全量的变化方向"。这篇论文在这里正好有用——它的 OOD 结论说明时间漂移下所有压缩方法都会退化，学习类方法甚至比随机还差。 选轴的原则是按"离 SFT 数据分布的差异"选，不按 benchmark 覆盖率选。协议类（工具调用 schema、多轮、长上下文、格式、拒绝边界、跨语言）优先级高于知识类。传统学术遗忘指标（MMLU 那类）测起来最方便，但对这类场景也最没用：客户不会因为 MMLU 掉 2 分换供应商，工具调用参数错会让产品直接不可用。 所以问你一个会决定设计的问题：你预期或者见过的遗忘，主要落在协议类轴还是知识类轴？如果是协议类，这个哨兵集甚至可以不用生成式打分，大部分能靠"解析成功率 / schema 合法率 / 多轮状态正确率"这类确定性指标判，成本再降一个量级。如果是知识类，那才需要真的跑题、真的判分。

我：benchmark 可以准备多个，来印证不同协议。其实跟固定 prompt 集也没太大区别。我过去训的时候观察到的主要是协议类的失效，有些模型拿去训输出特定 function call 的 code 之后，就不再具备原有的问答能力了。但是理解 query 时一定的语义泛化性还存在。

dsh：你这条观察其实比"灾难性遗忘"这个说法精确得多：失效发生在解码协议层，不在理解层。模型仍然能解析 query 的语义并泛化，但输出先验被拽过去了，"响应该请求"这个映射被"产出 function call 形状的东西"覆盖了。 这更像策略坍缩 / 格式先验偏移，而不是知识擦除。区分这两者不是术语洁癖，是可逆性差了一个量级：知识擦除只能靠回滚或混数据救，格式先验偏移在推理时就有可能救回来。 这直接改变测法。你现在用一个分数，其实把三件事混在一起了：知不知道答案、能不能按要求说出来、说出来的东西合不合协议。后者是产品级信号（确实崩了），但它作为诊断信号是错的——你会误判成知识丢失，然后去混知识数据，而这是不对症的药。 该测的是四格：

协议合规协议不合规
---
内容正确正常"知道但说不出来" → 格式先验问题
内容错误能说但说错真遗忘，或本来就 0

只有第二格和第四格的区别能把"能力丢了"跟"说不出来"分开。这两格的处置完全相反：前者混知识数据 / 降 LR，后者混格式多样的数据（同一任务换多种输出协议去训），或者干脆上约束解码。 你当年那种"只会吐 function call 的 code"的模型，正好是第二格的极端样本——理解还在，"能吐出去"这条路被堵了。 至于"多个 benchmark 印证不同协议"，可以再往前一步：同一批题 × 多个协议，做成矩阵，而不是几套互不相同的题集。理由和论文直接相关——它证明误差的大头是共模位移（子集难度整体偏了，所有模型一起偏）。那么正交的解法就是在实验设计里把共模消掉：同一道题，分别要求自由文本 / JSON / function call / 纯代码四种输出，题目难度这一项在对比里自动抵消，你量到的是纯粹的"协议效应"。这是 within-item 配对设计，20–30 题就有分辨率。而"几个独立 benchmark 各 200 题"是 between-item 设计，题目难度、题源偏置全混在里面，你还得花力气证明它们可比。同一个 60 分和另一个 60 分，可能压根不是同一件事。 还有一件：哨兵集的题源要换。不要把公开 benchmark 当题库直接用。更靠谱的是用基座模型跑一批候选 prompt，只保留基座能稳定通过的——这才叫"训前能过、训后不该崩"。公开 benchmark 里有大量题基座本来就是 0，训前训后都是 0，对遗忘监控是零信息，它们只会把均分稀释掉。所以 benchmark 的角色是候选池，不是分数来源。 下次再遇到这种模型，不用重训，测两件事就够了：一是前缀翻转，同一道 QA 题，一边直接问，一边强制以 Answer: 或纯文本开头（约束解码 / 强制前缀），如果强制前缀后大部分题恢复了，就是先验问题；二是 few-shot 格式提示，给两条"正确协议"的示例再问同样的问题。这两个能拉回大半的话，"遗忘"这个说法就得改——它是可逆的协议坍缩。 那我想在稿子里立一句可证伪的：SFT 导致的退化里，协议层失效的占比远高于知识层失效，而前者在推理时部分可逆、在数据侧可通过格式多样性预防。验证只要两格表加一个前缀翻转实验，不需要大规模评测。

我：形状就变了。不过确实像你说的差不多也是一回事，可以说整体的指令遵循能力丢了。抛开这篇文章来讲，围绕 benchmark 或者就是各类自建的测试集去衡量训练质量这件事，总会让人感觉会走入过拟合的老路。所有 benchmark 只要允许反复测试，都会在一定时间被刷的不成样。我认为这其实是这个领域一直以来存在的问题。所有的 benchmark 最有效的永远是它刚诞生那一刻，之后一旦成为一个努力目标，意义就没那么大了。

dsh：我同意大半，但需要拆开——"会被刷坏"混了四种完全不同的机制，解药不一样，混着说就没法行动。

机制是什么免疫方式
---
饱和题不够难了，分都挤在顶部换题（自然耗尽，不算坏）
污染训练语料里含了题数据卫生 / 私有集
耦合优化训练环境与数据分布朝评测靠无解，只能换参照系
选择偏差用它做过多轮决策纪律（冻结、预注册）

"一旦成为努力目标意义就没那么大"严格讲只对第三、第四种成立。第三种是这四条里最硬的：Nathan Lambert 10 月 28 日那篇点得很准——今天相当一部分能力增长来自"RL 环境的分布贴近评测分布"。这不是作弊，这是正常优化的必然路径，信号在哪你往哪走，而信号就是评测。 第四种我认为最值得写，因为它和 benchmark 公不公开完全无关：你自己的私有测试集，在同一套题上做了 200 次决策之后，同样失效，而且没有任何人会觉得这是个问题。每个团队都踩，没人修。 还有一句要改："最有效的永远是刚诞生那一刻"——那一刻最有效的是判别力，不是效度。新 benchmark 通常标签是错的、题目有歧义、难度分布未知——Lambert 那篇就顺手提了一句，社区找 bug 并推动 benchmark 自我修正"happens a lot"。所以： 新鲜：判别力强，校准度差。陈旧：校准度好，区分度没了。 这两件事对应两个用途，而且要求相反：排名前沿要新鲜，能把只差 2 分的两个模型分开；回归护栏要陈旧，要的是期望值稳定、判据明确、答案已知。 第二条里那个"过拟合"不是缺陷，是设计目标。单元测试的期望值是写死的，它就该被过拟合；你不会因为"测试被过拟合"删掉测试。所以这个领域真正的病不是"benchmark 会坏"，是同一份资产兼任两个用途：拿排行榜挑 checkpoint（选到噪声峰），又拿冻结的护栏去排名（没有区分度）。这两个动作常常就在同一条流水线上，却要求相反的资产属性。 再往下有一条可以立成分界线的：可刷的是"能力代理分"，不可刷的是"约束满足率"。schema 合法率、注入成功率、延迟 P99、单任务成本、确定性——这类指标和现实是同构的，你没法"改善测量而不改善现实"。而"MMLU 78 还是 80"这种，中间的空隙能塞进一整个营销部门。 还有两个补充。一，排行榜失去意义的第一个信号不是被刷坏，是强者不再看它。Lambert 那篇有个很尖的观察：Anthropic 和 OpenAI 早就"不 care 这些指数了"，他们的优化目标是内部使用和花大钱的客户；而对中小实验室来说，指数是生存问题，因为品牌就建立在"追上前沿"上。公开榜的真实功能已经变成品牌资产和融资材料。 二，私有测试集不是免费解。Artificial Analysis v5 转向私有 benchmark，动机是防止别人照着形状造训练数据，代价是失去社区帮你找题目错误——Lambert 说这是他最不满意的那个 trade-off。所以私有集的寿命问题从"被刷"换成了"没人校准"。 落到操作面：评测的独立性是消耗品，每用它做一次决策就消耗一点。所以三条纪律——预注册阈值（先定判据再看结果）、冻结集不进选择回路、决策点设上限（看够几次就作废重采样）。这不是洁癖，是让一个资产能撑两年而不是两个月的唯一办法。

我：感觉上大部分公开 benchmark 没有太高的约束满足率方面的考虑，为了尽量通用，一般没有设置特别的格式要求。企业内部自己的场景更容易出现非常不通用的格式要求。

dsh：你这条观察修正了我上一轮划的那条线：约束满足率免疫 Goodhart，原因不是"同构"，是不可迁移。 你的约束集（tool schema、输出语法、字段语义、业务校验）是你自己的，没有外人会朝它优化，所以没人能把它刷坏；但也正因为它不可迁移——没有外人比对它的分数。由此得到一个替换： 通用性越强 → 约束越松 → 越可比、越容易被刷；约束越紧 → 越可比对你自己的部署、越不可迁移、越不可审计。 这两样是同一个 trade-off 的两端。公开 benchmark 为了可比性放弃约束；企业评测为了保真度放弃可比性。这不是先进和落后的区别，是选了两端。 但代价转到了另一个地方：不可迁移意味着不可审计。企业约束集的危险不是被刷，是琐碎化——一个能通过 schema 校验的模型看起来"很会"，但那可能什么都不是。约束有三层，越往下越接近真正的质量，也越容易失效：

  • 语法层：schema 合法、JSON 可解析、tool call 结构对。几乎不能刷，也几乎不能说明问题——模型可以吐出一个完全合法但毫无意义的 JSON。
  • 语义层：字段值正确、参数指向对、多轮状态一致。开始有信号，判分要写代码。
  • 业务层：端到端结果对，用户视角没问题。这才是真正在乎的，也是最贵、最容易被优化坏的。

企业最常见的错误是把语法层当成质量指标来汇报，因为它便宜、稳定、不吵架。"schema 合法率 99.2%"听起来比"任务成功率 71%"安全得多，但它跟产品好不好几乎无关。 另外要改一个说法：公开 benchmark 不是"没有格式约束"，而是把约束外包给了 harness，且不报告。同一道 agent 题，换一个 harness 分数就会变——Anthropic 自己发 Opus 5.5 的时候就在脚注里标了：公开榜用 Claude Code harness 跑出 51.8%，他们自己的配置复现是 52.3%，"在噪声内"。差异确实不大，但它是真实存在的一个自由度，而且 AA v5 那个 index 里的 FrontierCode、Terminal-Bench，本来就是要靠一个 agent harness 才能跑出来的量。这带来两件事：一是榜单上的分是 模型 + harness 的联合产物，不是一个可以跨榜单比较的标量；二是想提升分数，改 harness 比改模型便宜得多，而且没人会把它记为作弊。这才是 benchmaxxing 最便宜的入口。所谓"通用"，本质是把约束搬到了没人统计的地方。 于是衰减的分类要多一条，而且是对称的：

资产主要死法可见性
---
公开 benchmarkGoodhart（被优化）静默：分数只涨不跌，没人知道
企业约束集spec drift（产品迭代把测试放废）可见：你改了 schema，你知道

企业自建评测的优势不在"更准"，而在"死法更便宜"：它不会悄悄失效，它随你的产品变更一起失效，而且失效时你人在现场。反过来说，公开榜最危险的不是"被刷"，而是"被刷了你还以为它是真的"——它的失效没有告警。 落地就是双层结构。契约层（可枚举、语法 + 语义约束、判分确定）：高频、便宜、免疫 Goodhart，但随产品变更就要刷新，它回答"还在不在"。能力层（开放、需要 judge 或人工）：低频、贵、会被优化，但反映真实能力，它回答"变没变好"。这跟前面聊的 SFT 协议失效正好闭环：协议类失效就是契约层崩塌，是最容易被测出来的那一类；能力层的退化才需要大样本认真测。 最后一个风险：评测即 spec。你设的约束在教模型怎么输出，这是产品决策，不是测量决策，只是没人把它当决策。一个要求严格 JSON 的评测集，会把 agent 往"结构化优先"的方向拉，而真实用户可能根本不需要 JSON，只需要一句人能读的话。所以"企业内部场景更容易出现非常不通用的格式要求"这句话，反过来也在塑造你的产品行为。约束设错了不会让你测错，会让你优化错方向——而且全程绿灯，因为它测的东西确实在变好。 问一个实操层面的：你那边能把这个"契约层"枚举出来吗？能列出"模型必须满足的格式 / 协议约束清单"的话，这一层几乎是免费的哨兵；如果列不出来，说明产品契约本身还没被写清楚，那是比评测更上游的问题。

我：如果从工具和格式的角度可以定义，但是从轨迹的角度有的时候不完全能定义。这也是实操评测中一个较为复杂的点：若干条路径可能结果都是有效的，好坏不是那么容易区分。有时就是产品策略问题，还会随时间变化。

dsh：那就得把"轨迹"这个词拆开，它混了三样东西，其中只有两样可判：

可形式化？该进什么
---
违规（越权动作、循环、重复、跳过验证、读不该读的）能，负面约束枚举门禁
代价（token、步数、工具调用、延迟）完全能，客观量预算，而非分数
优雅（这条路径是不是"对的那条"）不能，是策略问题，还随时间变评审

关键是这个转换："路径好不好"里面，"违规"和"代价"是可判的，"优雅"是不可判的。而"优雅"本来就不该进门禁——它是复盘的对象，不是判据。硬把路径质量塞进一个分数，得到的指标既不可靠（策略一变就失效），又会被刷（审轨迹的那个 judge 会成为新的目标）。 先修正我上一轮的一个说法。我说企业自建集"不会悄悄失效、失效时你人在现场"——这只在语法层成立。格式改了你 diff 得出来；但策略变了没有告警：你改的是"什么算好"，改的是标注口径，改的是产品想要的行为。这时候测试集一个字节都没变，但它的标签全都不对了。所以那张表的正确版本是：企业集的失效在语法层可见、在语义和策略层依然静默。这反而让轨迹层成了最危险的一块——它恰好是最需要人判、又最不可能被自动化监控的。 多路径都有效的时候，有三个可操作的替换，本质都是把连续判定改回离散判定，因为离散的东西抗漂移。 一，存在性判定优于质量判定。同一任务采 N 条轨迹，只问"有没有一条可接受"，不问"每条多好"。判定从 per-trajectory 降到 per-task，成本降一个量级，跨策略变化的稳定性也高得多。 二，失败模式打标签优于打质量分。循环、无效工具、越权、多余澄清、错误重试、跳过验证——这些是离散、可枚举、可统计的。"失败模式分布"比"平均质量分"可靠得多，而且直接可诊断：哪个模式涨了，就知道该修哪。 三，成对比较优于绝对分。问"A 和 B 哪个好"，不问"打几分"。成对比较噪声小、跨时间一致性高，代价是要多做几次对比。 还有一个必须避开的陷阱：轨迹上最容易算的指标，恰好是最容易被刷的指标——步数、token 数、工具调用数。因为"少走几步"不等于"更好"，而这三样都是能单独优化的。所以轨迹层只报两种东西：作为预算的代价（超了报警，不是越少越好），和违规。绝不报"效率分"，那是最典型的"改善测量而非改善现实"。 把前面几轮串起来看，结构是同一个：公开榜被刷，因为只有分数可测，而分数就是品牌和融资；企业内部 eval 琐碎化成 schema 合法率，因为只有格式可自动判，而业务正确性判不了；协议失效被误诊成"能力遗忘"，因为只有总分可测，而"知道"和"说出来"分不开。 三件事的共同起点不是恶意作弊，是度量不对称。企业内部的"刷分"通常也不是坏心，是"我只能测这个"。所以我想立的论点是：benchmaxxing 的主因是可测性压力，不是作弊。当组织唯一能自动化的指标是格式合规率，整个组织就会朝格式合规率优化，而这背后没有任何人的私心。 这条论点还自带一条推论：能抵抗它的不是更严的评测纪律，而是把更多的判断转成离散的、结构性的、可诊断的量——违规、失败模式、存在性——而不是转成一个分数。分数一旦成为唯一的对外接口，就必然被压向可测的那一端。

总结

一，benchmark 的失效不是一种，是四种。饱和是自然耗尽，污染是数据卫生，这两类可以管；耦合优化（训练分布朝评测靠）无解，只能换参照系；选择偏差（同一套题反复用于决策）是最少被谈、最多人踩的一种，而且跟 benchmark 公不公开无关——私有集一样会坏。工程上唯一真正能施力的是后两种，而它们共同的解药是纪律，不是更好的题。

二，"新鲜"和"好用"是两件事，被混成了一件。新 benchmark 强在判别力，弱在校准度；老 benchmark 强在校准度，弱在区分度。排名工具必须不断换，回归护栏必须永远不换，而回归护栏"被过拟合"本来就是它的功能——单元测试的期望值就该写死。所以这个领域真正的病灶是同一份资产兼任两个用途：拿排行榜挑 checkpoint，又拿冻结的护栏排名。这两件事要求相反的资产属性，却常常跑在同一条流水线上。

三，能免疫 Goodhart 的指标有个共同结构：离散、局部、与现实同构。约束满足率之所以不可刷，根子不在"同构"，在不可迁移——没有外人会朝你的契约优化。代价是不可审计、不可比。而更上层的问题是评测即 spec：你设的约束在教模型怎么输出，这是产品决策而不是测量决策，设错了不会让你测错，会让你优化错方向，而且全程绿灯。

四，轨迹层没有"质量分"这种对象，只有三样东西：违规、代价、优雅。前两个可形式化，后一个是产品策略、随时间变、且必然被误判。多路径都有效的时候，解法是把连续判定换成离散判定——存在性判定、失败模式标签、成对比较。这三个都比质量分便宜、稳定、可诊断。

五，可测性压力才是 benchmaxxing 的主因。公开榜被刷、企业 eval 琐碎化、协议失效被误诊成能力遗忘，三件事的起点都不是恶意，是度量不对称：能自动测的只有那么多，组织就只能朝那些方向优化。所以压制它的办法不是更严的评测规范，而是把判断改造成离散可诊断的量，把"分数"从唯一的对外接口上撤下来。

一个可证伪的预测

未来 12 个月（到 2027-11），主流 agent 评测平台会把"硬约束断言 + 失败模式标签"做成一等公民：平均分从默认视图降级为可选项之一，轨迹级统计以"违规率 / 失败模式分布 / 代价预算"为默认呈现。

可被证伪的点很具体：如果到那时主流平台（LangSmith、Braintrust、各家的 eval SDK）的默认产物仍然是"一个聚合分数 + 一个雷达图"，没有原生的失败模式标签体系，这条判断就算错——说明可测性压力还不足以倒逼工具形态变化。

配套还有一条更弱的：公开聚合指数（Artificial Analysis / Epoch 一类）会在一年内被要求附带刷新日期与不确定区间，否则在 agent 场景的权威性会被企业自建集进一步侵蚀。
