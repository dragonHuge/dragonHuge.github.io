架构师（JiaGouX）

我们都是架构师！ 架构未来，你来不来？

一家公司的客服系统里，放了十来个专家子 Agent。用户等回复的时间变长了，不同专家回答的口吻也难以统一。

这是 Anthropic 在 10 月 22 日文章中提到的企业案例。它的 Applied AI 团队在多个企业部署中发现，一些原来交给子 Agent 的工作，改由一个配备 Skills 的主 Agent 完成后，回答质量提高了，单次任务的成本和延迟也常有下降。

按业务拆分，本来是为了让每个 Agent 专心处理一类问题。为什么拆完以后，反而要花更多时间，才能把一件事做完？

Anthropic 给出的做法，是把部分子 Agent 并回主循环，原来的业务步骤和规则改由 Skills 承载，数据查询和操作交给工具。这样省下了交接，但专家原来做的工作，主 Agent 还得接着做。

交接的代价

不同团队各自维护一项业务，各做一个 Agent，再由平台团队加一层编排，接到同一个用户入口。这是 Anthropic 在企业里见到的一种做法。

每个团队都能维护自己的提示词和工具。但一个用户请求进来以后，可能要经过好几个团队的 Agent。

主 Agent 先读用户的问题，再把任务交给专家。专家有另一份上下文，并不自动知道前面聊过什么：用户加了哪些条件，已经查到哪些数据，哪些办法试过但没用，都需要主 Agent 在委派时说明。

专家做完后，把结果整理成摘要交回来。接下来如果还要找另一个专家，主 Agent 又要决定哪些内容值得传过去。摘要没保留的细节，后面的 Agent 就看不到；需要用到时，只能补传或重查。

重述背景、生成摘要、等待结果，都算在用户等回复的时间里。

当两个专家查同一份数据，几乎总是前后调用时，这种开销就更难省掉。后一个必须拿到前一个的结果才能开工，业务名称虽然不同，工作却很难分开。

这与我们 4 月讨论的多 Agent 信息流问题相通：团队可以分别维护业务知识，执行时却可能需要共享上下文。比如用户在前文补充了一个条件，后续查订单、判断配送都要用到；拆成两个 Agent 后，这个条件就得跟着任务传过去。维护工作分开，并不意味着每次执行也要分开。

Anthropic 建议从调用记录里找这样的组合，把它们合并为一个 Agent。配套开源的 single-agent-loop-kit 把这一步称为 merge。业务规则继续保留，但前一步查到的内容可以直接供后一步使用，省去这两个 Agent 之间重新说明背景和传递摘要的过程。

交接也消耗 token。今年 1 月，Anthropic 讨论多 Agent 选型时提到，在它的测试中，同等任务下，多 Agent 的 token 使用量通常是单 Agent 的 3～10 倍，其中就包括重复传递背景、协调任务和生成摘要的开销。

1 月和 10 月的文章都没有公开完整的测试集，这些结果还不足以说明单 Agent 普遍更好。不过，按任务需要的上下文来拆分，是 Anthropic 年初就已提出的主张。10 月的文章进一步讨论了现有系统怎么改：模型已经能自行规划和调用工具，部分拆开的步骤便有了合并的余地。

按职责拆分与按上下文拆分的区别

图 1｜上半图把写功能、写测试、审查分给三个 Agent；下半图让同一个 Agent 写功能和测试，再交给验证器运行测试。写测试需要理解实现，运行测试可以只返回结果。来源：Anthropic 原文。

主循环接手

两个专家可以合成一个。如果继续把专家并回主 Agent，它原来掌握的业务流程又该放在哪里？

Anthropic 的做法是，把原来写在专家提示词里的步骤、规则和判断方法整理成 Skill，把查询数据、调用 API、执行操作的部分交给工具。工具包把这一步叫作 fold。

原来是主 Agent 找专家，专家读自己的提示词、调用工具，再交回答案。改完以后，主 Agent 读取对应 Skill，按其中的业务步骤调用工具。业务团队继续维护这些步骤和规则，无须为每一项业务再运行一个模型循环。

工具返回的原始结果放进主 Agent 的上下文。模型读到结果后，决定下一步：信息不够就继续查，缺用户条件就提问，已经能回答就结束。假如查询结果推翻了先前的判断，它也能就地修改计划，不必再把新情况交给另一个负责规划的 Agent。

但如果所有业务都放进来，提示词会不会越来越长？

Claude Code 团队的做法是按需读取。Anthropic 内部使用了数百个 Skills，会话开始时，Claude Code 只拿到它们的名称和简短描述。模型判断某个 Skill 与当前任务有关，才读取完整的 SKILL.md；其中引用的脚本和参考文件，也可以等用到时再打开。

这种按需展开的方式叫作渐进式披露。模型先知道有哪些业务可处理，接到具体任务后再读相应手册。

之前，我们拆解 Pi 的动态发现时，我们看到的 Skill 读取过程也是这样：先提供名称、描述和路径，匹配任务后再读正文。系统里有多少能力，与当前上下文里放了多少内容，是两回事。放到客服系统里，主 Agent 处理配送问题时，可以只读配送规则，等用户问到退款，再加载退款流程。

工具也有类似安排。Claude Code 团队介绍工具设计时提到，当时产品大约有 20 个工具。工具多了，模型每次决定下一步时，就要辨别更多选项。Tool Search 可以先搜索当前任务需要的工具，再加载调用说明；订单、库存这类会变化的数据，则等调用时再查询。

权限检查则留在工具内部。这是 Anthropic 建议保留的一层程序约束。以查询订单为例，模型选中查询工具后，工具核对当前用户能否访问这笔订单；没有权限就返回拒绝说明。同一个 Agent 因而可以服务权限不同的用户。

包括之前的 Graph 、Harness 讨论，讨论过另一层分工：稳定的流程依赖可以写进 Graph，模型在 Loop 中根据查询结果决定下一步，Harness 负责执行工具、记录结果，并控制预算和写操作。

即便客服业务只用一个 Agent，也可以由程序规定：授权通过后才查询订单，查询超时后重试，超过次数就返回失败。减少 Agent，不等于取消业务流程和程序检查。

独立上下文

按需读取解决了会话开始时加载多少的问题。任务开始以后，仍然可能读进来一大批资料。

用户询问 Claude Code 的配置或功能时，Claude Code Guide 子 Agent 会搜索相关文档，再把答案交给主 Agent。Guide 翻过的页面、检索中的中间结果，留在自己的上下文里。主 Agent 拿到答案后继续对话，无须在后续每一轮都带上整批文档。

Anthropic 把这种调用方式称为 as-tool。主 Agent 交代任务，子 Agent 用自己的上下文完成工作，再返回结果；与用户持续对话、判断下一步和组织最终答复的，仍然是主 Agent。

合并子 Agent、作为工具调用，以及改为 Skills 与工具

图 2｜从左到右：把共享上下文的专家合并；保留子 Agent，由主 Agent 调用并接回结果；把专家的提示词改为 Skills，API 调用改为工具。三种改法改变了不同的交接关系。来源：Anthropic 原文。

Simon Willison 在子 Agent 指南里也提到了这些用途：探索代码库、处理冗长的测试输出、独立调试。把这些工作放到新的上下文里，可以减少它们对主任务的干扰。

不过，主 Agent 拿到的依然是一份整理后的结果。如果子 Agent 没有说明结论的依据和未确认的部分，主 Agent 就可能把尚未确认的判断当成事实。委派时有没有交代输入、完成条件和返回内容，也会影响结果。

把同一份 Skill 交给主 Agent 或子 Agent，效果会有什么不同？微软研究院的《Subagents vs Agent Skills》做过比较：研究者从 SkillsBench 的 87 个任务中，整理出 64 个程序型 Skill，分别交给两者执行。

当 Skill 本身缺少完整步骤，输入输出也没有说清时，直接加载到主 Agent 的表现持平或更好。补足这些内容以后，子 Agent 取得了更好的结果。强模型在超过 80% 的任务中减少了峰值上下文占用，不过主、子 Agent 之间多了通信，总 token 消耗也更高。

同一份专业知识写成 Skill 后，既能由主 Agent 读取，也能交给子 Agent。频繁依赖当前对话，会增加交接的负担；任务能单独说清，又需要读取大量资料，独立上下文就有了用处。

还有些子 Agent 必须直接向用户提问，并根据回答继续处理。Anthropic 在这种情况下建议完整交接，也就是 handoff，由子 Agent 接管这一段对话。OpenAI Agents SDK 也区分了两种方式：作为工具调用时，结果交回主 Agent；完整交接后，接下来的对话由接手的 Agent 处理。

工具包将必须自行与用户多轮对话，以及由外部机构控制、团队无法改造的子 Agent 列为 keep，继续保留。

并行与协调

保留子 Agent 还有一个理由：把几项工作分出去，同时做，能不能让用户少等一会儿？

Anthropic 的 Research 系统就是这样工作。主 Agent 拆解研究问题，多个子 Agent 沿不同方向搜索，最后汇总。在它公布的评测中，多 Agent 系统的研究任务表现相对单 Agent 提升了 90.2%，衡量的是完成研究的质量，速度收益还要另外看。

Anthropic 还报告，多 Agent 系统的 token 使用量约为普通聊天的 15 倍。这里的消耗以普通聊天为基准，与前面的单 Agent 质量对比口径不同。

几条搜索路径可以各自推进，最后再比较结果。代码修改却可能遇到另一类问题：几个 Agent 同时改同一个文件，或共用同一份运行环境。一个 Agent 修改了代码，另一个还可能按修改前的状态继续工作。

一项针对 Codex、Claude Code 和 Kimi Code 的动态并发研究，比较了 354 个任务、2,124 次执行。并发模式的 token 消耗是顺序模式的 1.41～3.31 倍，整体成功率没有稳定提高。

研究者还单独比较了两种模式都成功的 366 个案例。并发更快的占 27.9%，至少快 20% 的占 12.6%。在他们标注的失败实例中，共享状态、结果合并和并发写入都是突出问题。

同时开工省下的时间，可能又花在了等待、合并冲突和重新验证上。

Cognition 在软件工程 Agent 上采用较多的一种做法，是让一个主 Agent 修改代码，其他 Agent 审查并提供建议。审查用的 Agent 在新的上下文里找问题，修改则由主 Agent 完成，减少多个 Agent 同时写入造成的冲突。

搜索结果可以最后汇总，互相影响的代码修改却需要边做边协调。并行能省多少时间，也取决于后续要花多少时间处理这些相互影响。

合并后的遗漏

除了企业中的观察，Anthropic 还用一个客服示例测试了合并的效果。把一个子 Agent 并入另一个之后，回复变快了，一个原本能通过的流程却失败了。

主 Agent 拿着订单查询工具，自己给出了答复，没有再向配送专家确认送达日期。用户需要知道何时送达，系统却跳过了查日期这一步。

这个问题在两次运行中只出现了一次。只跑一遍，或者只看平均延迟，都可能看不到它。

配套工具包的验证也还有限。截至 10 月 28 日，仓库只记录了两次真实模型运行，都来自同一个客服示例和同一个模型：一次是 12 个任务上的 fold，另一次是 17 个任务上的 as-tool。merge 步骤、最终单循环版本和其他真实业务系统，还没有完整的实跑记录。

Anthropic 的迁移方法因此把每次改动前后的任务结果放在一起比较。现有系统先跑一组真实请求，逐个调整子 Agent 后，再跑同一组任务，比较完成情况、延迟、模型调用、token 和成本。这样既能看到总分的变化，也能找到原本成功、改完却失败的请求。

假如继续把配送专家改成 Skill 和工具，执行记录里的对应步骤就变了：过去是主 Agent 找到配送专家，之后是主 Agent 读取配送规则、调用工具，拿到送达日期。最终都可能生成一句答复，执行记录能进一步说明，中间有没有完成这些工作。

这也解释了 Anthropic 为什么建议分开维护两类评测。业务团队维护各自的 Skills、工具和测试，一个小团队负责系统提示词和端到端评测。订单工具查得到数据，配送工具也能返回日期，只能说明各自能工作。端到端评测覆盖从接到请求到给出答复的过程，能查出工具各自正常、整条调用却漏了一步的情况。

对那个客服请求来说，合并前后都需要一个经过确认的送达日期。交接可以少一次，查日期这一步还得完成。
